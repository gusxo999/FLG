# 제0부 — 조사 결과

## 0.1 계산 시작 시점 — "버튼 클릭"이 아니라 **6단계 렌더**다

사용자 전제("6.검토 및 실행 버튼을 클릭할 경우 시작")는 **거의** 맞지만, 정확한 트리거는
버튼이 아니라 `AutoLayoutContainerPanel` 의 **마운트 이펙트**다
([AutoLayoutContainerPanel.tsx:99-106](../src/UI/components/AutoLayoutContainerPanel.tsx#L99-L106)).

```tsx
const autoStartedRef = useRef(false);
useEffect(() => {
  if (!autoStartedRef.current && props.targetRecipe && props.selectedMachines.size > 0) {
    autoStartedRef.current = true;
    handleRun();
  }
}, []);
```

패널은 `step === 'review'` 일 때만 렌더된다([AutoLayoutModal.tsx:420-445](../src/UI/components/AutoLayoutModal.tsx#L420-L445)).
따라서 **6단계에 도달하는 모든 경로가 곧 계산 시작**이다:

| # | 진입 경로 | 계산 시작 | 근거 |
|---|---|---|---|
| 1 | 5단계에서 "다음" 버튼 | ✅ | 의도된 경로 |
| 2 | 스테퍼의 "6." 칩 **직접 클릭** | ✅ | 칩은 skip 단계도 클릭 가능([:315](../src/UI/components/AutoLayoutModal.tsx#L315)) — 1~5단계를 건너뛰어도 돈다 |
| 3 | **앱 재시작 / 사이드바 재오픈** | ✅ | `wizardStore` 가 `step` 을 persist([wizardStore.ts:80-83](../src/UI/store/wizardStore.ts#L80-L83)) — 마지막이 6단계였으면 켜자마자 돈다 |
| 4 | 6단계 → 다른 단계 → 6단계 복귀 | ✅ **매번 재계산** | 조건부 렌더라 언마운트 → `autoStartedRef` 가 초기화된다 |

추가로 확인된 것:

- 가드는 `targetRecipe` 존재 + `selectedMachines.size > 0` 둘뿐이다. **게임데이터 `loaded` 는 안 본다** — 경로 3에서 데이터 로딩 전 실행될 여지가 있다.
- **재실행 버튼이 없다.** 실행 중 "중단"만 있고([:339-345](../src/UI/components/AutoLayoutContainerPanel.tsx#L339-L345)), 한 번 끝난 뒤 같은 설정으로 다시 돌리려면 **단계를 왕복**해야 한다(경로 4).
- 결과는 컴포넌트 로컬 `useState` 다([:74-76](../src/UI/components/AutoLayoutContainerPanel.tsx#L74-L76)). **단계를 벗어나면 결과가 소멸**한다 — 이게 경로 4의 강제 재계산과 한 쌍이다.

## 0.2 후보는 **언제나 0개 아니면 1개**다

`runLayeredWizard` 는 후보 트리를 만드는 척하지만 실제로는 leaf 하나를 감싸기만 한다:

| 경로 | candidates | stats | 코드 |
|---|---|---|---|

| `flg.candidates()` / `flg.apply()` | [debugApi.ts](../src/debug/debugApi.ts) | 배열이지만 원소 1개 |

## 0.3 실패는 **전부 아니면 전무**다 — 그래서 "성공한 부분"이 화면에 없다

`runModulePipeline` 은 **첫 거절에서 즉시 `return`** 한다. 8가지 `RejectReason` 은 실패 시점으로
두 무리로 갈리고, **그 시점에 무엇이 이미 만들어져 있느냐가 완전히 다르다.**

| 무리 | kind | 코드 | 실패 단위 | 그 시점에 존재하는 것 |
|---|---|---|---|---|
| **A**<br>배치 전 | `stale-gamedata`<br>`non-square`<br>`no-pipe-entity`<br>`no-rotation`<br>`fluid-face-crowded` | [moduleWizard.ts:173-218](../src/autoLayout/planner/moduleWizard.ts#L173-L218) | 레시피 노드 1개 | 레시피 트리 + 머신 선정뿐.<br>**셀 0개** |
| **B**<br>배치 후 | `unrouted-lines` | [:366-374](../src/autoLayout/planner/moduleWizard.ts#L366-L374) | 모듈(placement) 1개 | `pack.placements` **전부** —<br>머신·트렁크·인서터 절대좌표 |
| | `pipe-merge-conflict` | [:421-431](../src/autoLayout/planner/moduleWizard.ts#L421-L431) | 모듈 + **좌표 1칸** | 위와 같음 |
| | `hop-failures`<br>`fluid-unplannable` | [:448-461](../src/autoLayout/planner/moduleWizard.ts#L448-L461) | 홉 1개 | 위 + **성공한 홉 셀 전부**(`hopRes.cells`) |

> **핵심 발견:** B무리는 **성공한 배치가 이미 메모리에 완성돼 있는데 통째로 버린다.**
> `hopRes.routes` 는 홉마다 `ok`/`reason` 을 이미 들고 있다([moduleHop.ts:81-89](../src/autoLayout/planner/moduleHop.ts#L81-L89))
> — 어느 연결이 왜 실패했는지 **엔진은 이미 안다.** UI 에 도달하지 못할 뿐이다.

A무리는 셀이 물리적으로 없으므로 부분 배치가 불가능하다. 대신 **어느 레시피 노드가 왜 막혔는지**는
정확히 안다 → 그리드 표현이 달라야 한다(제1부 축 3).

# 제1부 — 무엇을 바꾸나 (축 3개)

## 축 1 — 계산 시점: **명시적 실행**으로

| 옵션 | 동작 | 평가 |
|---|---|---|
| A | 현행 유지(진입 시 자동) + 재실행 버튼 추가 | 경로 3(앱 켜자마자 실행)·경로 4(왕복 재계산)가 남는다 |
| **B ★추천** | 6단계 진입 시 **아무것도 안 함**. "레이아웃 생성" 버튼으로만 시작 | 아래 |
| C | 5단계 "다음" 시점에 백그라운드 선계산 | 실질 시점이 현행과 같고, 취소·진행 표시가 두 화면에 걸친다 |

**B 를 추천하는 이유:**

1. 6단계가 "후보 고르는 화면"에서 **"결과·진단 화면"**으로 바뀐다. 결과 화면의 정상 초기 상태는 "아직 결과 없음"이다.
2. 경로 3(persist 복원 자동 실행)이 사라진다 — `loaded` 를 안 보는 문제도 같이 사라진다.
3. **결과를 store 로 올린다**(축 1의 필수 동반 작업). 지금 결과가 로컬 state 라 단계를 벗어나면 사라지고, 그래서 재진입 = 재계산이 강제된다. store 로 올리면 설정 조정 → 6단계 복귀 시 **직전 결과가 그대로** 보이고, 사용자가 원할 때만 다시 돌린다.
4. 입력이 바뀌었는지 store 가 안다 → **"설정이 바뀌었습니다 — 다시 생성"** 배지를 정직하게 띄울 수 있다.

## 축 2 — 엔진: reject 를 **부분 결과 + 문제 목록**으로

> **부분 성공의 존재 이유** (2026-08-04, 사용자 정정 — 이 문서의 다른 서술보다 우선한다):
> **어느 부분(머신들의 모듈)이 실패했는지 알아내기 위한 것**이지, 부분적으로 성공한
> 배치를 **갖다 쓰기 위한 것이 아니다.**
>
> 따라서 부분 결과는 **진단 장치**다. 화면에 그리는 것은 "여기까지는 섰고 이 모듈이
> 막혔다" 를 보이기 위해서이고, 그 배치를 블루프린트로 내보내거나 이어서 편집하는 용도가
> 아니다. 이 전제가 제4부 결정 3(export 정책)을 자명하게 만든다 — **차단**이다.
> 부분 결과를 "쓸 수 있게" 만드는 방향(끊긴 홉을 수동으로 잇게 한다든지)은 **범위 밖**이다.

새 타입 하나를 도입한다(신규 파일 `src/autoLayout/layoutIssue.ts`, 순수 타입):

```ts
export interface LayoutIssue {
  kind: RejectReason['kind'] | 'hop-failed' | 'no-machine-match';
  /** blocking = 배치 자체가 없다 / partial = 배치는 있고 이 부분만 빠졌다 */
  severity: 'blocking' | 'partial';
  detail: string;
  /** 어느 레시피 노드에서 — 노드 상태 표의 행 키 */
  nodeId?: string;
  recipeName?: string;
  /** 어느 품목 줄이 안 이어졌나 */
  item?: string;
  role?: 'input' | 'output';
  /** 그리드에 찍을 지점(합류 충돌 칸 · 실패 홉의 양끝 anchor) */
  cells?: { x: number; y: number }[];
  /** "고치려면 몇 단계로 가라" — 화면이 그 단계로 점프시킨다 */
  fixStep?: 'recipe' | 'machine' | 'inserter' | 'belt' | 'pipe';
}
```

`ModulePipelineResult` 를 확장한다:

```ts
| { ok: true;  leaf: CandidateLeaf; issues: LayoutIssue[] }  // issues 비면 완전 성공
| { ok: false; issues: LayoutIssue[] }                       // 배치 없음 — blocking 하나 이상
```

### B무리 → `partial` 강등 (배치를 끝까지 만든다)

| kind | 바꾸는 것 | 부분 결과가 화면에서 뜻하는 것 |
|---|---|---|
| `hop-failures`<br>`fluid-unplannable` | 즉시 `return` 제거. `hopRes.routes` 를 순회해 실패 홉마다 issue 1개 | 실패 홉은 `cells` 가 비어 있어 **자연히 안 깔린다.** 두 모듈이 각자 무한상자로 끝난 채 남아 "여기가 안 이어졌다"로 **그림이 정확히 읽힌다** |
| `unrouted-lines` | 즉시 `return` 제거 → issue | 그 모듈은 서 있고 그 줄만 탭이 없다 |
| `pipe-merge-conflict` | **blocking 으로 남긴다** (아래) | — |

> ⚠ **`pipe-merge-conflict` 만 blocking 을 유지하는 이유.**
> 다른 B무리는 *"덜 그려진 배치"* 지만 유체 합류 오염은 *"틀리게 이어진 배치"* 다 —
> 화면상 멀쩡하고 라우팅도 "성공"이라 보고하는데 물류가 거짓이다
> ([moduleWizard.ts:376-385](../src/autoLayout/planner/moduleWizard.ts#L376-L385) 의 주석이 정확히 이 얘기).
> 부분 결과로 내보내면 이 저장소가 가장 싫어하는 결과가 된다.
> 대신 `hit.cell` 좌표를 issue 에 실어 **어느 칸이 문제인지**를 그리드에 찍는다.

### A무리 → **모아서** 낸다 (지금은 첫 개만 본다)

현재 A무리 루프는 첫 노드에서 즉시 `return` 하고, 상위 [layeredWizard.ts:127](../src/autoLayout/layeredWizard.ts#L127) 의
머신 선정 실패도 `failure ??=` 로 **첫 개만 남기고 나머지를 버린다.**
사용자는 "고쳤더니 다음 노드가 또 실패"를 N번 반복하게 된다.

→ 루프를 **끝까지 돌려** issue 를 전부 모으고, blocking 이 하나라도 있으면 배치를 시도하지 않고 반환한다.
`non-square` / `no-rotation` 은 `fixStep: 'machine'`, `no-pipe-entity` 는 `fixStep: 'pipe'` 를 달아
화면에서 해당 단계로 바로 점프시킨다.

## 축 3 — 6단계 화면: 후보 목록 → **진단 그리드**

영역 셋으로 재구성한다.

```
┌─ ① 상태 헤더 ─────────────────────────────┐
│ [레이아웃 생성] [중단]   ● 부분 성공 · 문제 3건 │
│ (설정이 바뀌었습니다 — 다시 생성하세요)         │
├─ ② 모듈 배치 그리드 (SVG 미니맵) ───────────┤
│  ┌────┐   ┌────┐                          │
│  │철판 │───│기어 │  ← 회색 실선 = 이어진 홉    │
│  └────┘ ✗ └────┘                          │
│  ┌────┐╌╌╌┘         ← 빨강 점선 = 실패한 홉   │
│  │구리판│(주황=부분)                          │
│  └────┘                                    │
├─ ③ 문제 목록 ──────────────────────────────┤
│ ✗ 홉  구리판 → 회로  경로 없음      [2단계로] │
│ ⚠ 줄  철판 input     탭 자리 부족            │
└────────────────────────────────────────────┘
```

### ② 모듈 배치 그리드 — 이 계획의 핵심

| 항목 | 내용 |
|---|---|
| 좌표계 | `pack.bbox` 를 사이드바 폭에 맞춰 스케일(타일 1개 = 1~4px) |
| 모듈 사각형 | `pack.placements[].module.bbox`(절대좌표). 채움색 = 초록(성공) / 주황(부분) / 빨강(blocking) |
| 라벨 | 레시피 이름 + `×머신수`. 좁으면 툴팁 |
| 홉 선 | `hop.from.anchor → hop.to.anchor`. 회색 실선(성공) / 빨강 점선 + ✗(실패) |
| 문제 지점 | `issue.cells` 를 빨강 점으로 |
| 연동 | 그리드 hover ↔ ③ 문제 목록 행 하이라이트(양방향) |

> **왜 Pixi 캔버스가 아니라 SVG/DOM 인가.** 이 그리드가 보여주는 것은 **좌표가 아니라 관계**다
> (어느 모듈이 어느 모듈과 이어졌나 / 어디가 끊겼나). 진짜 좌표는 메인 캔버스가 이미 그린다.
> 사이드바 안에 줌·팬 없이 **한 화면에 전부** 들어가는 것이 이 표현의 요건이다.

### 배치가 **없을 때**(A무리 blocking) — 같은 자리에 **노드 상태 표**

`pack` 이 없으므로 모듈 그리드를 못 그린다. 대신 1단계의 `TreeView` 와 같은 트리 모양에
노드마다 상태 뱃지를 붙인 표를 그린다. 재료는 이미 있다 — `previewTree`
([AutoLayoutModal.tsx:136-154](../src/UI/components/AutoLayoutModal.tsx#L136-L154)).

```
▸ 회로              OK   조립기-2 ×2
  ▸ 구리선          OK   조립기-2 ×3
  ▸ 철판           ✗ 막힘  화학공장 4×3 — 정사각형이 아니라 유체 회전 불가  [2단계로]
```

이 표는 **배치가 있을 때도 함께** 보여 준다(모듈 그리드 아래). 한쪽은 "어디에 놓였나",

### ④ 메인 캔버스 연동

# 부록 A — 이 조사에서 발견한 **기존 결함 2건**

## A-1. 홉 인덱스 어긋남 — 유체와 아이템이 섞이면 라우팅 선이 엉뚱한 홉에 붙는다

`routeModuleHops` 는 **유체 홉을 먼저 깔려고 정렬한 순서**(`ordered`)로 `routes` 를 쌓는다
([moduleHop.ts:250-253](../src/autoLayout/planner/moduleHop.ts#L250-L253)):

```ts
const ordered = [...pack.hops].sort((a, b) => Number(isFluidHop(b)) - Number(isFluidHop(a)));
for (const hop of ordered) { ... routes.push(route); }
```

그런데 `moduleWizard` 는 **`pack.hops` 의 인덱스**로 그 배열을 읽는다
([moduleWizard.ts:540-542](../src/autoLayout/planner/moduleWizard.ts#L540-L542)):

```ts
pack.hops.forEach((hop, i) => {
  const placed = [...hop.from.cells, ...(hopRes.routes[i]?.cells ?? []), ...hop.to.cells];
```

`sort` 가 안정 정렬이라 **전부 아이템이거나 전부 유체이면 순서가 같아** 지금까지 드러나지 않았다.
**섞이는 순간** `routes[i]` 가 다른 홉의 셀을 가리킨다 → `Routing.placed` 가 틀린 선을 그리고,
드래그 재라우팅·`corridors` 사본도 함께 어긋난다.

→ 이 계획과 **독립적인 버그**지만, 축 2가 `routes` 를 홉별 issue 로 읽어야 하므로 **Phase 3 에서 함께 고친다**:
`HopRoute` 에 `hopKey`(`hopMapKey(hop)`)를 실어 인덱스 대신 map 으로 조회.

## A-2. A무리 실패는 첫 개만 보고된다

[moduleWizard.ts:178-206](../src/autoLayout/planner/moduleWizard.ts#L178-L206) 은 첫 거절에서 즉시 반환하고,
