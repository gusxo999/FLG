# 커스텀 레시피 — 계획서

> 작성 2026-09-07 · 상태 **승인 대기**
> 대상: `src/factorio/` (합성기 신규) · `src/UI/store/` (원천 스토어 신규) ·
> `src/UI/components/` (편집기 신규) · `src/debug/` (`flg.custom` 신규)

## 0. 한 줄 요약

**사용자가 말하는 어휘로 레시피와 머신을 받아, 게임데이터 어휘로 옮겨 스토어에 합류시킨다.**
새 개념은 하나뿐이다 — **원천(spec)과 산출(게임데이터)을 갈라 놓는 것**. 나머지는 전부
이미 있는 규약(유체 상자 네 필드 · 면 규약 · 파생 인덱스)을 **어기지 않게** 채우는 일이다.

---

## 1. 푸는 문제

지금 앱에 레시피가 들어오는 길은 **하나**다 — 게임에서 뽑은 `factorio-data.json` 파일 업로드
(`Toolbar.handleGameDataFile` → `parseGameData` → `setGameData`). 그래서:

| 지금 | |
|---|---|
| 게임에 없는 레시피를 **못 시험한다** | 모드를 만들거나, 아직 안 만든 조합을 배치해 보려면 게임을 켜서 데이터를 다시 뽑아야 한다 |
| AI 가 **입력을 못 만든다** | `docs/debug/ai-console.md` §4: *"게임데이터·블루프린트 파일 \| OS 파일 다이얼로그 \| … 다이얼로그는 사람 손이 필요하다"*. 그래서 유체 2줄짜리 · 큰 머신 같은 **경계 사례를 콘솔에서 못 만든다** — 실데이터에 그 모양이 있어야만 시험된다 |
| 유체 상자의 **모양을 못 바꿔 본다** | 트렁크 파이프·좌석 예산은 전부 유체 상자 배치의 함수인데, 실데이터에 있는 모양만 시험된다 |

## 2. 안 푸는 것 — 그리고 누구 몫인가

| 안 푼다 | 누구 몫 |
|---|---|
| **게임에서 실제로 돌아가는 블루프린트** | 커스텀 이름은 그대로 블루프린트에 실리고(`Toolbar` 가 `cell.entityName` 을 그냥 쓴다) 게임이 거부한다. 이 계획은 **경고만** 띄운다 → §10 |
| **아이템 존재 검증** | 게임데이터에 아이템 목록이 없다(`GameData` = recipes·entities·modules·technologies). 오타 난 아이템 이름은 그냥 **외부 공급 leaf** 가 된다 — 그게 지금 동작이고, 커스텀도 같다 |
| **연구 트리 반영** | 커스텀은 항상 `enabled: true`. 기술 그래프는 안 건드린다 |
| **모듈 효과·표면 조건** | v1 파이프라인이 안 본다(`makeMachineParamsLookup` 은 base `crafting_speed` 와 `productivityMultiplier = 1`) |
| **편집기의 아이콘·그림** | 앱 전체가 아이콘을 안 그린다 |

## 3. 끝나면 열리는 문

```
① AI 가 레시피를 만들 수 있다          flg.custom.add({...}) → flg.run()
   → 유체 2줄 · 큰 머신 · 재료 6개 같은 **경계 사례를 실데이터 없이** 시험한다.
     지금은 "그 모양의 머신이 실데이터에 없다" 가 곧 "못 시험한다" 였다

② 유체 상자 모양이 **변수**가 된다      같은 레시피를 3×3 과 5×5 에서, 상자 1개와 3개에서
   → trunk-pipe · 좌석 예산 · 지하파이프 사거리의 경계를 **골라서** 친다

③ 사용자가 모드 레시피를 손으로 넣는다   게임을 안 켜고
```

**①이 이 계획을 지금 하는 이유다.** 나머지 계획들(유체 여러 줄·좌석 경쟁)이 전부
*"실트리에 그 경우가 몇 건이냐"* 에서 막히는데, 그 질문에 답하려면 **경우를 만들 수 있어야**
한다.

## 4. 조사 — 코드가 커스텀 머신에 요구하는 것

편집기가 무엇을 물어야 하는지는 취향이 아니라 **아래 여섯이 정한다.**

### 4.1 유체 상자 좌표는 합성할 수 있다 — 그리고 정답지가 저장소 안에 있다

사용자는 *"입력은 W 면 1행"* 이라고 말한다. 게임데이터는 `{ direction, positions[4] }` 를
요구한다. 둘 사이의 변환은 **정확히 정의된다.**

`resolveFluidConnection` 의 역함수를 풀면 된다 — 그쪽은 좌표에서 `offset` 을 이렇게 낸다:

```ts
offset = face === "N" || face === "S"
  ? clamp(Math.floor(w / 2 + pos.x), 0, w - 1)
  : clamp(Math.floor(h / 2 + pos.y), 0, h - 1);
```

그러니 `N×N` 머신에서 면 `F`·행 `k` 의 **회전 0 좌표**는:

| 면 | `direction` | 좌표 (회전 0) |
|---|---|---|
| N | `0` | `( k − N/2 + 0.5 ,  − N/2 + 0.5 )` |
| E | `4` | `( + N/2 − 0.5 ,  k − N/2 + 0.5 )` |
| S | `8` | `( k − N/2 + 0.5 ,  + N/2 − 0.5 )` |
| W | `12` | `( − N/2 + 0.5 ,  k − N/2 + 0.5 )` |

그리고 `positions` 네 개는 그 좌표를 `(x, y) → (−y, x)` 로 **세 번 더 돌린** 것이다
(전제 ②).

**이 식은 지어낸 게 아니라 맞춰 볼 정답지가 있다.** `fluidPorts.test.ts` 의 두 fixture 는
실게임 덤프이고, 그 주석이 못 박는다: *"이 fixture 를 좌표만으로 지어내면 실제 데이터와
다른 걸 시험하게 된다."*

```
화학공장 3×3 · 입력 · N 면 · 행 0
  식:  x = 0 − 1.5 + 0.5 = −1 ,  y = −1.5 + 0.5 = −1 ,  direction 0
  rot4: (−1,−1) (1,−1) (1,1) (−1,1)
  실측: { direction: 0, positions: [{-1,-1},{1,-1},{1,1},{-1,1}] }          ✓ 일치

화학공장 3×3 · 출력 · S 면 · 행 0
  식:  (−1, +1) · direction 8  →  rot4: (−1,1) (−1,−1) (1,−1) (1,1)
  실측: { direction: 8, positions: [{-1,1},{-1,-1},{1,-1},{1,1}] }          ✓ 일치

SE 랩 9×9 · 입력 · W 면 · 행 6
  식:  x = −4.5 + 0.5 = −4 ,  y = 6 − 4.5 + 0.5 = 2 ,  direction 12
  실측: labBox("input", 12, −4, 2)                                          ✓ 일치
```

> **짝수 크기가 함정이다.** 4×4 면 칸 중심이 `±0.5 · ±1.5` 라 좌표에 **반정수**가 나온다.
> `Math.floor` 가 그걸 받아 주므로 식은 그대로 맞지만, 편집기가 정수를 고집하면 어긋난다.

### 4.2 입력 면과 출력 면은 **마주봐야 한다** — 이게 가장 센 제약

`chooseFluidTrunkPlan` 은 네 회전을 다 시험해 *"모든 줄이 자기 역할 면(출력 W · 입력 E)에
오는 첫 방향"* 을 고른다. 회전은 상대 각도를 보존하므로:

```
입력이 N · 출력이 S  →  90° 돌리면 입력 E · 출력 W        ✓ 성립
입력이 W · 출력 E   →  180°                              ✓ 성립  (SE 랩이 이 모양)
입력이 N · 출력 E   →  네 회전 어디에도 안 앉는다          ✗ 거절
입력이 N · 출력 N   →  같은 면                            ✗ 거절
```

**거절은 조용하지 않다** — `no-rotation` 사유가 나온다. 하지만 그때는 이미 배치를 돌린
뒤다. 편집기는 **저장 시점에** 이걸 막아야 한다. 그래야 사용자가 *"만들었는데 왜 안 돌지"*
를 겪지 않는다.

> 유체가 **한 쪽에만** 있는 머신(입력 유체만, 출력은 아이템)은 반대 면이 비어도 된다 —
> 규칙은 *"쓰는 줄이 자기 면에 앉을 수 있나"* 이지 *"양쪽이 다 차 있나"* 가 아니다.

### 4.3 좌석 예산 — 유체 상자가 면을 다 먹으면 벨트가 못 앉는다

`fluidJumpBlocker` 의 거절 문장이 그대로 편집기의 경고문이다:

```
면 좌석 ${seatRows}행에서 유체 ${n}행을 빼면 ${seatRows - n}행 — 벨트 ${beltDepths}줄이 안 들어간다
```

`seatRows` = 머신 높이. 즉 **한 면의 유체 줄 수가 머신 크기에 가까울수록 아이템 벨트가
설 자리가 없다.** 3×3 에 입력 유체 상자 3개를 다 채우면 아이템 재료를 하나도 못 넣는다.
편집기는 이걸 **막지 않고 경고한다** — 유체만 쓰는 레시피(경유 분해)는 정당하기 때문이다.

### 4.4 레시피가 보이려면 — `enabled: true`

`buildDerived.isRecipeSelectable` 이 `enabled === true` 이거나 어떤 기술이 언록하는 레시피만
`itemToRecipe` · `recipesByProduct` 에 넣는다. 커스텀은 기술이 없으므로 **`enabled: true` 가
강제**다(전제 ④). 사용자에게 묻지 않는다 — 선택지가 아니다.

### 4.5 머신이 후보가 되려면 — `crafting_categories ∋ recipe.category`

`makeMachinePicker` · `machineCandidates` 둘 다 이 한 줄로 고른다. 그래서 커스텀 레시피는
**자기 머신이 선언한 카테고리**를 써야 한다. 기본값으로 레시피 전용 카테고리를 만들면
그 머신만 후보가 되어 2단계(머신 선택)가 자동 스킵된다(`machineCandidates.length <= 1`).

### 4.6 저장 자리 — 이미 되어 있다

`gameDataStore` 는 `persist` 로 `recipes`·`entities`·`modules`·`technologies` 를 키
`factorio-game-data` 에 저장한다(전제 ⑤). **즉 배열에 넣기만 하면 세션을 넘는다** — 사용자가
요구한 "다른 세션에도 보이게" 는 새로 만들 것이 없다. 만들 것은 **재임포트에서 살아남는
길**뿐이다(§5).

## 5. 자료 모델 — 원천은 spec, 산출은 게임데이터

### 5.1 어디에 두나 — 세 안

| 안 | 장점 | 문제 |
|---|---|---|
| ① `gameDataStore.recipes/entities` 에 **그냥 append** | 소비처 변경 0. 영속화도 공짜 | 파일 재임포트(`setGameData`)·`reset()` 이 **통째로 지운다.** 그리고 무엇이 커스텀인지 셀 수 없어 **편집·삭제가 불가능**하다 |
| ② 별도 스토어만 두고 **읽는 쪽에서 병합** | 원본이 안 더러워진다 | 병합 지점이 `recipeMap`·`entityMap`·`machines`·`itemToRecipe`·`recipesByProduct`·`recipeToTech` … 전부다. **하나만 빠져도 조용히 다르다** |
| ③ **원천은 별도 스토어 · 파생은 gameDataStore 에 합류** ← 채택 | 소비처 변경 0 + 살아남는다 + 셀 수 있다 | 합류 지점을 놓치면 어긋난다 → 그래서 **합류를 한 함수로 못 박는다** |

**②를 기각하는 근거는 이미 코드에 있다.** `infinity-pipe` 는 프로토타입 없이 이름만 쓰는
엔티티인데, 그 때문에 `portInference` 에 `synthesizeCardinalFluidPorts` 라는 **특례**가
생겼다 — *"게임데이터에 prototype 자체가 export 되지 않을 수 있어 `entity.fluid_boxes` 에
의존할 수 없다"*. 프로토타입 없는 이름은 **소비처마다 특례를 낳는다.** 커스텀 머신은
`entityMap` 에 **진짜로 들어가야** 한다.

### 5.2 타입 — `src/factorio/customRecipe.ts` (순수, 스토어를 안 본다)

```ts
/** 사용자가 말하는 어휘. 게임데이터 어휘가 아니다 — 그래서 camelCase 다. */
export interface CustomFluidBoxSpec {
  role: 'input' | 'output' | 'input-output';
  face: 'N' | 'E' | 'S' | 'W';   // **회전 0 기준**
  offset: number;                // 면 위 행/열, 0 … size−1
  filter?: string;               // 이 상자가 특정 유체만 받으면
  volume?: number;
}

export interface CustomMachineSpec {
  name: string;                  // 엔티티 이름. 기본값 없음 — 이름과 저울은 함께 온다
  size: number;                  // N×N (정사각)
  craftingSpeed: number;
  craftingCategories: string[];  // 최소 1
  moduleSlots?: number;
  fluidBoxes: CustomFluidBoxSpec[];
}

export interface CustomRecipeSpec {
  name: string;
  category: string;              // 어떤 머신의 craftingCategories 에 있어야 한다
  energyRequired: number;        // 초
  ingredients: CustomStackSpec[];
  products: CustomStackSpec[];
}

export interface CustomStackSpec {
  name: string;
  amount: number;
  type: 'item' | 'fluid';
  /** 유체만. **미지정이 정상**(전제 ⑥) — 편집기는 0 을 절대 안 채운다. */
  fluidboxIndex?: number;
  probability?: number;          // 산출만
}

/** 한 벌 = 이 앱이 아는 커스텀 전부. 스토어가 이것 하나를 들고 있는다. */
export interface CustomDataSpec {
  machines: CustomMachineSpec[];
  recipes: CustomRecipeSpec[];
}
```

**머신과 레시피를 갈라 놓은 이유:** 커스텀 머신 하나가 커스텀 레시피 여럿을 돌릴 수 있어야
한다(재료의 레시피도 같은 머신을 쓰는 게 보통이다). 화면은 *"이 레시피 전용 머신"* 을
기본으로 만들되, 자료형은 그 결합을 강요하지 않는다.

### 5.3 합성 — `compileCustomData(spec)` → `{ recipes, entities }`

`parseGameData` 의 **형제**다. 원천만 다르고 도착지가 같다. 그래서 같은 규칙을 지킨다 —
*"여기서 고른 필드만 앱 안으로 들어온다 — exporter 가 뽑아도 여기 없으면 죽는다."*

```
CustomFluidBoxSpec  →  FluidBoxInfo {
    index: i + 1,                       parseGameData 와 같은 규칙 (fb.index ?? i + 1)
    production_type: role,
    filter, volume,
    connections: [{ direction: 면→0/4/8/12,
                    positions: rot4(§4.1 좌표) }]   ← flow_direction 은 **안 쓴다**
}
```

> **`flow_direction` 을 왜 비우나.** 그 필드는 *"파이프가 물리적으로 어느 쪽으로 흐르나"* 라
> `production_type`(레시피에서의 용도)과 **다른 것을 잰다**. 우리 편집기는 용도만 물으므로
> 흐름에 대해 할 말이 없다. 소비처는 전부 `flow_direction ?? production_type` 으로 읽으니
> 비워 두면 용도가 그대로 답이 된다. **모르는 칸을 지어내지 않는다.**

```
CustomMachineSpec  →  Entity {
    type: 'assembling-machine',      → 사이드바 assembler 탭 · EntityType.Assembler
    tile_width = tile_height = size,
    crafting_speed, crafting_categories, module_slots,
    fluid_boxes, id: <충돌 안 나는 번호>
}
CustomRecipeSpec   →  Recipe { enabled: true, ... }      ← 강제 (§4.4)
```

`collision_box` · `items_to_place_this` · `icon` 은 **안 채운다** — 저장소 전체에서 소비처가
0곳이다(`collision_box` 는 타입 정의와 `parseGameData` 밖에 참조가 없고,
`items_to_place_this` 는 `getTechForMachine` 안에서만 쓰이는데 커스텀은 기술이 없다).

### 5.4 합류는 **한 함수**다 — `syncCustomData()`

```
customDataStore(원천)  ──compile──▶  gameDataStore.recipes / .entities  ──persist──▶ localStorage
        ▲                                          │
        └── 편집기·flg.custom 이 여기만 고친다        └── 소비처 전부가 여기만 읽는다 (변경 0)
```

`syncCustomData()` 가 하는 일은 **딱 둘**: ① 기존 커스텀 항목을 걷어내고 ② 컴파일 결과를
다시 넣어 `setGameData` 를 부른다(파생 인덱스가 통째로 다시 선다).

부르는 자리도 **셋뿐**이고, 셋 다 "게임데이터가 바뀐 직후"다:

```
① 커스텀이 바뀐 뒤            편집기 저장 · flg.custom.add/remove
② 파일을 새로 올린 뒤          Toolbar.handleGameDataFile — 재임포트에서 살아남는 지점
③ 앱 부팅 시 rehydrate 뒤     원천과 산출이 어긋난 채로 저장돼 있을 수 있다
```

**커스텀 항목을 어떻게 알아보나.** `Recipe`/`Entity` 에 `custom?: true` 한 필드를 더한다.
이름 규칙(`custom-` 접두사)으로 알아보는 대안은 기각한다 — 이름은 사용자가 정하고, 규칙을
어긴 이름은 **영영 못 지운다.**

## 6. 검증 — 규칙을 다시 적지 않고 **그 함수를 부른다**

편집기가 §4 의 규칙을 자기 말로 다시 구현하면, 파이프라인이 바뀌는 날 **한쪽만 고쳐진다.**
그건 이미 `resolveFluidConnection` 주석이 경계하는 것이다 — *"유체 상자의 면을 읽는 규칙이
두 벌 있으면 한쪽만 고쳐지고 다른 쪽이 조용히 틀린다."*

그래서 §4.2 검증은 규칙을 재현하지 않고 **`chooseFluidTrunkPlan(compiled, size, lines)` 을
실제로 부른다.** 레시피의 유체 재료·산출이 곧 그 `lines` 다.

| # | 규칙 | 판정 방법 | 등급 | 처방 |
|---|---|---|---|---|
| 1 | 이름 중복 (게임데이터 전체) | `recipeMap`/`entityMap` 조회 | **거절** | Map 은 나중 것이 조용히 이긴다 — 다른 이름을 쓴다 |
| 2 | 유체 줄이 자기 면에 다 앉나 | `chooseFluidTrunkPlan` 이 `ok:true` | **거절** | 입력 면과 출력 면을 **마주보게** 한다 (§4.2) |
| 3 | 같은 면에 `offset` 중복 | spec 훑기 | **거절** | 두 상자가 같은 행이면 한쪽이 못 앉는다 |
| 4 | `offset` 이 `0 … size−1` 밖 | spec 훑기 | **거절** | `clamp` 가 조용히 끌어당긴다 — 안 보이게 틀린다 |
| 5 | 레시피 `category` 를 아무 머신도 안 맡는다 | `getMachinesForCategory` | **거절** | 2단계 후보가 0이라 배치가 안 선다 |
| 6 | `amount ≤ 0` · 비수치 | spec 훑기 | **거절** | `productYield` 가 NaN 을 내면 **인서터가 조용히 0개**가 된다 |
| 7 | 한 면의 유체 줄 수 vs 머신 크기 | `fluidJumpBlocker` 문장 | **경고** | 유체만 쓰는 레시피는 정당하다 — 막지 않는다 (§4.3) |
| 8 | `fluidboxIndex` 가 그 역할 상자 수를 넘는다 | `roleOrdinalOf` 와 대조 | **경고** | 못박은 서수가 없으면 배정이 다른 칸으로 간다 |

**사유는 문장이 아니라 필드로 낸다.** `LayoutIssue` 가 `RejectReason` 을 흡수할 때 배운
것과 같다 — *어디가* 막혔는지와 *무엇을 고쳐야* 하는지가 갈려 있어야 한다.

```ts
export type CustomDataIssue = {
  kind: 'name-taken' | 'fluid-no-rotation' | 'offset-clash' | 'offset-range'
      | 'category-orphan' | 'bad-amount' | 'seats-tight' | 'fluidbox-index';
  where: string;      // 'machine:my-plant' · 'recipe:my-recipe.ingredients[2]'
  detail: string;     // 무엇이 어긋났나
  fix: string;        // **다음에 할 일** — registry 의 available 과 같은 규약
};
```

## 7. 콘솔 — `flg.custom`

### 7.1 세 방식 판정 (ai-console.md §2)

저장 버튼의 로직이 **컴포넌트 안에 있으면 B**(등록), **스토어 액션 하나면 A**(직행)다.
이 계획은 **A 가 정직해지도록 설계를 고른다** — 검증·합성·합류가 전부
`customRecipe.ts` 와 `customDataStore` 에 있고, 모달은 그 위의 얇은 폼이다. 그러면 버튼과
명령이 **같은 일**을 하고, 화면 없이도 레시피가 만들어진다.

> 이건 **설계 제약**이지 관찰이 아니다. 모달 안에 검증을 짜 넣으면 그 순간 A 가 거짓말이
> 되고 B 로 내려가야 한다 — 그러면 **패널이 열려 있어야만** 레시피를 만들 수 있다.

### 7.2 명령

목록의 단일 출처는 `flg.help()` 다(ai-console §3). 여기 적는 것은 **왜 이 모양인가**뿐이다.

```
flg.custom.template(size)     채워 넣을 spec 뼈대. AI 가 형식을 안 틀리게 — 이게 첫 명령이다
flg.custom.add(spec)          검증 → 합성 → 합류. 실패면 CustomDataIssue[] 를 **던진다**
flg.custom.check(spec|name)   저장 안 하고 판정만. 고른 회전 · 줄별 면/행 · 안 쓰는 칸까지
flg.custom.map(name)          발자국 ASCII — 어느 면 어느 행에 무엇이 앉나 (flg.face 와 같은 장르)
flg.custom.list() / get(name) / remove(name) / clear()
flg.custom.export() / import(json)    파일이 아니라 **문자열** — §4 정직한 괴리의 그 이유
```

`check` 와 `map` 이 이 그룹의 핵심이다. **AI 는 화면을 못 보므로, 유체 상자를 "봤다" 고 말할
수 있는 유일한 길이 이 둘이다.** `map` 의 산출은 이런 모양이다(구현이 다듬는다):

```
my-plant 5×5    회전 0에서:
           0 1 2 3 4
         ┌───────────┐
  W:out1 │ · · · · · │ 0
         │ · · · · · │ 1
  W:out2 │ · · · · · │ 2  E:in1
         │ · · · · · │ 3
         │ · · · · · │ 4  E:in2
         └───────────┘
  파이프라인이 고를 회전: 0   (입력 E · 출력 W 가 이미 맞다)
  안 쓰는 상자: 없음
```

### 7.3 문서에 남길 것

`docs/debug/ai-console.md` §4 정직한 괴리표의 *"게임데이터·블루프린트 파일"* 줄과 루트
`CLAUDE.md` 의 *"게임데이터는 콘솔로 못 넣는다 — 파일 업로드뿐"* 이 **둘 다 반만 참이 된다.**
새 경계는 이렇다: *"게임 프로토타입은 여전히 파일뿐. **커스텀 레시피·머신은 콘솔로 넣는다**."*
고치는 것은 Step 4.

## 8. 편집기 화면

한 모달(`CustomRecipeModal.tsx`), 위아래 두 구획.

```
┌ 머신 ─────────────────────────────────────────────┐
│ 이름 [            ]  크기 [3]×[3]   제작속도 [1.0] │  ← 이름과 저울은 **함께** 온다
│ 카테고리 [custom-my-recipe]                        │
│                                                    │
│  유체 상자          ┌───────┐                      │
│   + 입력  + 출력    │ · · · │  ← 칸을 눌러 면·행을  │
│   #1 in   W 0  [x]  │ · · · │     고른다            │
│   #2 out  E 2  [x]  │ · · · │                      │
│                     └───────┘                      │
│  ⚠ 입력 W · 출력 E — 180° 로 성립                  │
└────────────────────────────────────────────────────┘
┌ 레시피 ────────────────────────────────────────────┐
│ 이름 [         ]   제작시간 [0.5]s                  │
│ 재료   + 추가                                       │
│   [iron-plate] [2]  (아이템)         [레시피 만들기] │
│   [water     ] [50] (유체)  상자 [자동▾]       [x]  │
│ 산출   + 추가                                       │
│   [my-thing  ] [1]  (아이템)                   [x]  │
└────────────────────────────────────────────────────┘
        [취소]                               [저장]
```

**격자 미리보기가 이 화면의 요점이다.** 유체 상자를 좌표로 입력받으면 §4.1 의 반정수를
사용자에게 떠넘기게 된다. 칸을 누르면 **면과 행이 정해지고**, 좌표는 합성기가 만든다.

| 요구 | 화면에서 |
|---|---|
| 가짓수를 원하는 만큼 | 재료·산출·유체 상자 모두 `+ 추가` / `[x]` 행 |
| 재료의 레시피도 커스텀 | 아이템 재료 행의 **[레시피 만들기]** — 그 아이템을 산출로 놓은 새 초안을 **위에 쌓는다**(빵부스러기). 자식을 저장하면 부모로 돌아온다. 저장은 **초안마다 독립** — 각각이 진짜 레시피가 된다 |
| 유체 상자 서수 | 상자마다 **역할별 1-based 서수**를 보여 준다. 재료의 `상자` 칸이 그 번호를 고르고, 기본은 `자동`(미지정 = 그 역할 상자 전부, 전제 ⑥) |
| 검증 | 저장 전 상시. **거절**은 버튼을 막고, **경고**는 문장만 띄운다 |

진입점은 둘:

| 자리 | 무엇 |
|---|---|
| 자동배치 1단계, 레시피 콤보박스 옆 | `+ 새 레시피` — 필요가 생기는 자리다 |
| 툴바 | 목록·삭제·내보내기. **만드는 자리와 관리하는 자리를 나눈다** |

## 9. 단계

### Step 1 — 합성기 (`src/factorio/customRecipe.ts`) · 순수 · 테스트

spec 타입과 `compileCustomData`. 스토어도 화면도 안 건드린다.

```
전제  ① positions 는 네 방향 배열이다 — fluidPorts.ts 머리말: "회전 = 배열 인덱스 하나다"
      ② 면은 direction 에만 있다 — 같은 곳: "추정 없음"
      ③ 두 fixture 는 실게임 덤프다 — fluidPorts.test.ts: "이 fixture 를 좌표만으로
         지어내면 실제 데이터와 다른 걸 시험하게 된다"

불변  화학공장 3×3 과 SE 랩 9×9 를 spec 으로 적어 컴파일하면 **fixture 와 같은 객체**가 나온다.
      기전: 두 fixture 는 손으로 지은 게 아니라 실측이라, 합성식이 틀리면 반드시 어긋난다.
      (합성식은 resolveFluidConnection 의 역함수이고, 그 함수는 이 계획이 안 건드린다)

관문  유체 상자를 **"면 + 행"으로 말할 수 있게 된다.** 좌표를 손으로 짜는 일이 사라진다
```

### Step 2 — 검증기 + 원천 스토어 + `flg.custom` (여기서 AI 가 쓸 수 있게 된다)

`validateCustomData`(§6) · `customDataStore` · `syncCustomData`(§5.4) · 콘솔 그룹(§7).

```
전제  ④ 파이프라인은 입력 E · 출력 W 회전을 찾는다 — wantFaceOf 주석: "역할이 정하는 면 …
         납품 경로·채널 장부가 이 규약에 기댄다"
      ⑤ enabled: true 라야 후보가 된다 — gameDataStore: "둘 다 아니면 … 자동완성 후보에서
         제외한다"
      ⑥ partialize 가 recipes·entities 를 저장한다 → 합류만 하면 세션을 넘는다

불변  검증을 통과한 spec 은 chooseFluidTrunkPlan 이 ok:true 를 낸다.
      기전: 검증기가 그 규칙을 **다시 적는 게 아니라 그 함수를 부른다** — 두 벌이 될 수 없다.

관문  **AI 가 게임데이터를 만들 수 있게 된다.** flg.custom.add → flg.run() 한 왕복으로
      경계 사례를 시험한다. 지금은 "그 모양이 실데이터에 없다" 가 곧 "못 시험한다" 였다
```

## 10. 결정 — 기본값이 있어 결정이 아닌 것, 그리고 진짜 결정

| | 어떻게 | 왜 |
|---|---|---|
| 카테고리 | **레시피 전용 카테고리를 자동 생성**(사용자가 바꿀 수 있음) | 그 머신만 후보가 되어 2단계가 자동 스킵된다. 기존 카테고리를 고르면 바닐라 조립기로도 돌릴 수 있다 |
| `fluidbox_index` | **기본 미지정** | 실데이터에서 이 필드를 가진 레시피가 **전체에 둘뿐**이다(fluid-box-semantics) |
| `flow_direction` | **안 쓴다** | 우리 편집기는 용도만 묻는다 — 흐름에 대해 할 말이 없다(§5.3) |
| 머신 타입 | `assembling-machine` 고정 | 사이드바 assembler 탭 · `EntityType.Assembler` 로 간다. 화로·광산은 파이프라인 취급이 다르다 |
| 커스텀 표시 | `Recipe`/`Entity` 에 `custom?: true` | 이름 규칙으로 알아보면 규칙 어긴 이름을 **영영 못 지운다**(§5.4) |
| **블루프린트** | **막지 않고 경고한다** | 커스텀 이름은 블루프린트에 그대로 실리고(`Toolbar` 가 `cell.entityName` 을 그냥 쓴다) 게임이 거부한다. 그래도 막지 않는 이유: 이 앱의 산출이 블루프린트만은 아니고, **거부는 게임에서 즉시 드러난다**(조용하지 않다). 내보낼 때 *"커스텀 N개 포함 — 게임이 거부합니다"* 를 띄운다 |

### 확인이 필요한 하나

**커스텀 머신을 손으로 그리드에 놓을 수 있게 둘 것인가.** `type: 'assembling-machine'` 으로
넣으면 사이드바 assembler 탭에 **자동으로 뜬다** — 아무것도 안 해도 놓인다. 막으려면 따로
걸러야 한다. 이 계획은 **막지 않는 쪽**을 기본으로 잡았다(자동배치 결과와 손 배치가 같은
엔티티를 쓰는 게 일관된다). 다르게 원하면 그때 §5.3 에 필터를 단다.
