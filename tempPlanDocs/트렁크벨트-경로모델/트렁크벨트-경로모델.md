# 트렁크 벨트 — 경로 모델

> **작성일:** 2026-08-13 · **상태:** **모델 확정**(§9 결정 다섯). 코드 변경 0 — 착수는 세부 폴더에서.
> **직전 시도는 전부 롤백했다**(병합기·레인 슬롯·`supplyMode`·A/B 계측). 사유는 §10.
> **현황·결함 목록은** [현황점검.md](현황점검.md), **끝난 판단의 기록은** [judgements.md](judgements.md)

## 0. 목표 — 한 문장

> **트렁크 벨트는 다이렉트 벨트 여럿을 한 줄로 합친 결과다. 그 "합치기"를 모델로 만든다.**

`trunk-redesign` 이 이 문장을 목표로 적어 두었고, 오늘 코드는 그렇게 **안** 돼 있다 —
탭은 별도 배분기·별도 방출기로 트렁크를 **따로 만든다.** 이 계획은 그 문장을 실제로 성립시킨다.

## 0.1 이 문서의 R·D 는 **분기문이 아니다** — 읽기 전에

> **여기 적힌 것을 하드코딩하면 매우 잘못된 설계다**(2026-08-15 사용자).
> **목적은 하나 — 모든 머신이 100% 가동한다.** 형태는 전부 그 목적을 이루려다 유도된 것이다.

```
목적    머신 m 의 줄 j 가 per_j 를 받는다/내보낸다.  전부, 항상
물리    팔은 좌석 타일에 앉는다.  reach 는 **고정 거리**라 집는 칸이 하나로 정해진다.
        팔 하나의 처리량은 **게임데이터가 준다**(가정하지 않는다)
자원    타일.  겹칠 수 없다
────────────────────────────────────────────────────────────────
유도    나머지 **전부**
```

| 형태 이름 | 실체 |
|---|---|
| 트렁크 · 부분 병합 · 다이렉트 | **벨트 구간 길이의 별명.** 배분기는 이 이름을 몰라야 한다 |
| **깊이(`d2`·`d3`)** | **축이 아니다 — 결과다**(§16). 축은 `(인서터, 그 팔이 집는 타일)` 쌍이다 |
| gap · N/S 면 | **좌석 타일이 모자랄 때 타일을 만드는 유일한 수단** |
| 모듈 크기 | 쓴 타일의 외접 사각형 |
| 팔 개수 `a` | `per ÷ (그 좌석에 실제로 앉는 팔의 처리량)` |

**구현이 답해야 하는 것은 하나다:**

```
"이 타일 배치에서 모든 머신이 100% 도는가.  아니면 타일을 어디서 더 만드나."
```

> `if (트렁크) … else if (fan-out) …` 같은 분기가 생기면 그 순간 이 모델을 배신한 것이다.
> **§13 의 R1~R13 은 규칙이 아니라 그 유도의 결과로 관측된 성질**이고,
> §14 의 여섯 단계는 분기 트리가 아니라 **유도 순서**다.
> 2026-08-13 롤백의 ★("구현의 *어떻게* 를 의도로 착각하지 않는다")를 **내 문서에도 적용한다.**

## 1. 무대 — 격자 위의 네 가지

| 것 | 차지 | 규칙 |
|---|---|---|
| **머신** | `W×H` | 자기 타일 밖으로 아무것도 안 한다. 아이템은 **인서터를 통해서만** 드나든다 |
| **인서터** | 타일 **1** | 한쪽에서 집어 반대쪽에 놓는다. `reach r` = `r` 칸 건너 |
| **벨트** | 타일 1 | **방향이 하나**. 아이템이 그 방향으로 흐른다 |
| **포트** | 타일 1 | 모듈 경계. 밖과 주고받는 유일한 창구 |

머신 면에서 바깥으로 센 거리 `d`:

```
d0   머신 자신의 가장자리
d1   머신에 붙은 첫 칸        ← 인서터 좌석
d2   reach 1 이 닿는 곳
d3   reach 2(긴팔)가 닿는 곳
```

**물리 하나:** 좌석 `d` 의 인서터는 `d + r` 을 집는다. 그래서 **벨트가 깊을수록 긴 팔이
필요**하고, 팔 종류가 유한하므로 **한 면에 겹쳐 놓을 수 있는 벨트 줄 수도 유한**하다.

## 2. 다이렉트 / 트렁크 — 정확히 무엇인가

### 다이렉트 — 머신 하나, 품목 하나

```
        ┌───────┐
   ▣ ←i │  M1   │    ▣ 포트  i 인서터(d1)  ║ 벨트(d2)
   ║    │       │
   ║ ←i │       │
        └───────┘
```

벨트가 **머신 하나만** 상대하므로 남의 행을 안 지난다 → **다른 품목이 같은 깊이를 행으로
나눠 쓸 수 있다.** 대가는 포트가 `머신 수 × 품목 수`.

### 트렁크 — 여러 머신의 인서터가 같은 벨트를 쓴다

```
        ┌───────┐
   ▣ ←i │  M1   │     인서터 넷이 벨트 하나를 공유
   ║ ←i │       │     → 포트 1개 (다이렉트였다면 3개)
   ║    └───────┘
   ║    ┌───────┐
   ║ ←i │  M2   │
   ║    └───────┘
   ║    ┌───────┐
   ╚ ←i │  M3   │
        └───────┘
```

> **"합친다"의 정확한 뜻:** 다이렉트 벨트 `N` 개(각자 포트 하나)를 **벨트 하나 + 포트 하나**로
> 바꾼다. **인서터 개수는 그대로다** — 머신이 필요로 하는 처리량은 안 변하니까.
> 병합은 처리량을 바꾸는 게 아니라 **배선을 바꾸는 것**이다.

## 3. 합치기가 성립할 조건 — 여섯

| # | 조건 | 어긋나면 |
|---|---|---|
| **①** | **같은 품목** | 두 품목이 한 벨트에 섞인다 |
| **②** | **같은 방향** — 전부 공급이거나 전부 수거 | 벨트 방향이 하나뿐이라 불가 |
| **③** | **부하 ≤ 벨트 용량** | 포화 → 뒤쪽 머신이 굶는다 |
| **④** | **도달가능** — 머신마다, 그 머신에 닿으면서 벨트에도 닿는 **좌석 타일**이 존재 | 그 머신은 이 트렁크에서 못 먹는다 |
| **⑤** | **연속** — 포트에서 모든 집는 지점까지 끊김 없이 | 구멍 너머는 아이템이 안 간다. **겹침도 미배치도 아니라 아무도 못 잡는다** |
| **⑥** | **비충돌** — 벨트·좌석·포트가 머신·남의 벨트·남의 좌석·파이프와 안 겹친다 | 배치 실패 |

**④가 기하의 전부다.** 형식으로:

> 머신 `M`, 벨트 `B` 에 대해 타일 `s` 가 존재해 — `s` 는 `M` 에 인접하고,
> `B` 의 어떤 타일 `b` 에 대해 `dist(s, b) = r` 인 인서터가 있다.

## 4. 맞바꿈 — **문제의 심장**

| | 다이렉트 | 트렁크 |
|---|---|---|
| **포트 수** | 머신 × 품목 | **품목당 1** ← 얻는 것 |
| 벨트가 지나는 타일 | 머신 하나 주변 | **여러 머신을 잇는 길 전체** ← 치르는 것 |
| 같은 깊이를 남과 나눠 쓰기 | **된다**(행 구간 서로소) | **안 된다**(길을 통째로 차지) |

> 트렁크는 포트를 줄이는 대신 **자리를 더 먹는다.** 그리고 **얼마나 더 먹느냐가 길의
> 모양에 달려 있다.** 이 한 줄이 §5~§7 전부의 근원이다.

## 5. 직선은 **특수해**다

지금 트렁크는 한 면을 따라 달리는 직선이다. **그 형태에서만** 나오는 제약이 셋:

```
직선이면 →  ① 머신들이 그 선 위에 나란히 있어야 한다      → 기둥 형태 강제
            ② 그 면의 그 깊이를 선 길이만큼 통째로 먹는다  → 다른 품목이 그 면을 못 씀
            ③ 겹쳐 놓으려면 더 깊이 → 더 긴 팔 → 팔 종류 수가 상한
```

**셋 다 "직선"에서 나온 것이지 "트렁크"에서 나온 것이 아니다.**

> **2026-08-13 실패의 정체가 이것이다** — 이 셋을 트렁크의 성질로 착각하고
> 새 코드에 그대로 옮겨 심었다(§10).

## 6. 그래서 모델의 핵심 객체는 **경로**다

```
   ┌────┐
   │ M1 │──┐          · 머신이 나란할 필요가 없다
   └────┘  │          · 지나가는 타일만 먹는다
   ┌────┐  ├──▶ ▣     · 두 트렁크가 안 만나면 깊이를 다툴 일이 없다
   │ M2 │──┤
   └────┘  │
      ┌────┴─┐
      │  M3  │
      └──────┘
```

> **트렁크 = (경로 `P`, 좌석 집합 `S`, 끝점)**
> `P` = 연결된 벨트 타일 열 · `S` = {(머신, 좌석)} 로 각 좌석이 자기 머신과 `P` 에 동시에 닿음
> **직선 트렁크는 `P` 가 직선인 특수해다.**

"면"과 "깊이"는 모델의 **축이 아니다.** 직선일 때 나오는 **좌표의 별명**일 뿐이다.

### 경로는 **두 종류의 조각**으로 갈린다

머신 하나가 팔 `k` 개를 쓰면 좌석도 `k` 개고, 좌석마다 닿는 벨트 타일이 있어야 한다.
**머신의 탭 자리는 점이 아니라 길이 `k` 의 지상 주행이다.**

```
▣ ──연결──▶ ═══ ──연결──▶ ═══ ──연결──▶ ═══
             M1탭          M2탭          M3탭
   ↑ 탐색한다   ↑ 구성한다(계산)
```

| 조각 | 누가 정하나 | 성질 |
|---|---|---|
| **탭 주행** | **구성**한다 — 좌석 수·면에서 바로 나온다 | **정의상 지상**. 여기가 일하는 자리다 |
| **연결 구간** | **열거**한다 — 후보가 손으로 셀 만큼이다(§14-2) | 여기서만 꺾이고, 여기서만 지하로 간다 |

> **이 갈래의 기하가 §14 에서 확정됐다**(2026-08-14): 탭 주행은 **세로만**,
> 연결은 **가로만**, 그리고 가로 행의 개수가 코너 후보의 개수다.

이 갈래가 하나를 공짜로 준다: **연결 구간이 지하로 가도 탭에 지장이 없다**
(지하 위에서는 인서터가 못 먹인다는 제약이 저절로 지켜진다 — [1-지하벨트](1-지하벨트/1-지하벨트.md) §4-4).

## 7. 좌표 문제 — 고리를 어디서 끊나

```
경로를 짜려면   →  머신이 어디 있는지 알아야 한다
머신을 놓으려면 →  벨트·좌석이 자리를 얼마나 먹는지 알아야 한다
```

지금 코드는 **직선이라서** 고리를 끊는다 — 직선이 먹는 폭은 좌표 없이 계산된다
(`gap 폭 = 깊이 수`). **경로가 되면 그 계산이 불가능하다.**

**그래서 반대쪽에서 끊는다: 머신을 먼저 놓고, 그 위에서 경로를 예약한다.**

이것은 예약 철학에 **어긋나지 않는다.** 철학은 *"좌표를 모르라"* 가 아니라
*"큰 그림을 보는 **주체 하나**가 자리를 먼저 잡고, 방출은 탐색 없이 놓기만 한다"* 이다.
그리고 **이 저장소에 이미 그 패턴이 있다** — `channelGeometryPlanner`·`deliveryRoute` 는
모듈이 놓인 뒤 좌표 위에서 경로를 **예약**하고 `emitPath` 는 덧셈만 한다.

> **진짜 남는 문제는 하나:** 경로를 짜다 자리가 없으면 무엇을 되돌리나(§9-마).
> 지금은 gap 폭이 그 되먹임을 암묵적으로 한다. 경로 모델은 그걸 **명시해야** 한다.

## 8. 끝점은 두 종류다 — 포트 | 머신집합

| | 트렁크의 양 끝 |
|---|---|
| **외부 줄**(원료·완제품) | 한쪽 **머신들**, 다른 쪽 **포트**(모듈 경계) |
| **내부 링크**(자식→부모) | **양쪽 다 머신들** — 이상적으로 포트가 **없다**(자식이 벨트에 놓고 부모가 그 벨트에서 집는다) |

외부만 보고 설계하면 타입에 *"끝은 포트"* 가 박히고, 내부 링크를 넣을 때 **핵심 타입을
고쳐야 한다.** 그리고 내부 링크는 **모듈 둘이 합의**해야 해서 `module/`(형제를 모른다)의
경계를 넘는다.

> **결정:** 끝점을 처음부터 **`포트 | 머신집합`** 둘 다 받게 정의하되,
> **구현은 외부 줄부터.** 타입이 열려 있으면 확장이 안 깨진다.

## 9. 결정 다섯 (2026-08-13)

| # | 질문 | 결정 |
|---|---|---|
| **가** | 머신 배치를 누가 정하나 | **다이렉트 전용 배치를 그대로 쓴다.** 새 배치 모델을 안 만든다 |
| **나** | 경로를 어떻게 찾나 | **구간 사슬** — `containerRouting` 재사용. 탭 주행은 구성, 연결만 탐색(§6) |
| **다** | 트렁크끼리 다툼 | **지하로 건넌다 / 바깥으로 돈다(모듈이 큰다) / 쪼갠다.** 셋 다 이미 모델 안 |
| **라** | 몇 대씩 묶나 | **최대로 시도하고 여유 마진이 정한다.** 마진이 사용자 손잡이 |
| **마** | 자리가 없으면 | **쪼갠다.** 극한이 다이렉트(`k = 1`) |

### 9.1 권한 — 트렁크가 **포트 위치와 모듈 크기를 정한다**

```
트렁크 계획이 정한다        받는다
  · 경로                    · 머신 좌표(다이렉트 기준 배치)
  · 좌석                    · 레시피 줄 · 팔 수
  · 포트 위치
  · 모듈 크기  ← 경로의 부산물
```

**모듈 크기가 경로의 부산물**인 것은 오늘 `gap 폭 = 배정의 부산물` 과 같은 구조다
(`layoutCluster(rowGaps)`). 새 패턴이 아니라 있는 패턴을 한 겹 넓히는 것이다.
모듈이 커져도 **다른 모듈은 평행이동만 한다** — 그 외 영향은 없어야 한다.

그래서 §7 의 고리가 풀린다:

```
다이렉트 기준 머신 배치 → 트렁크 경로 예약 → 모듈 크기 확정 → 모듈 배치
```

### 9.2 비용은 **전부 소프트**다 — 하드 금지를 두지 않는다

| 인자 | 성질 | 실패를 만드나 |
|---|---|---|
| `blocked` · `bounds` | 하드 | **만든다** |
| 타일 수 · `turnPenalty` · 점프 비용 | 소프트 | 안 만든다 |

**비용 때문에 트렁크가 연결이 안 되면 안 된다**(2026-08-13 사용자). 그래서
*"모듈 밖으로 나가는 것"* 은 `bounds` 가 아니라 **가산점**으로 넣는다.

```
bounds  = 탐색이 끝나게 하는 상한   ← 설계 의도가 아니다. 넉넉히
가산점   = 안쪽을 선호한다          ← 설계 의도
```

**`jumpCostModel` 은 `'length'` 로 고정한다**(막혔을 때만 지하). `'flat'` 은 막히지 않아도
지하로 가는데, 지하는 `(축, 티어)` 배타권이라는 **한정 자원**이라 공짜로 쓰면 나중 트렁크가
건널 자리를 잃는다.

### 9.3 손잡이는 **하나**다 — 여유 마진

*"모듈 크기"* 와 *"트렁크 연결 수준"* 은 같은 손잡이의 양면이다:

```
마진 크게 → 경로가 멀리 돈다 → 많이 묶인다 → 모듈이 크다
마진 작게 → 경로가 못 돈다   → 쪼개진다    → 모듈이 작다
```

마진이 모자라 경로가 없으면 §마(쪼개기)로 떨어지고 극한이 다이렉트다.
**손잡이 하나가 라와 마를 동시에 구현한다.** (D4·D5 — 모듈마다, 파라미터까지)

### 9.4 최적화는 나중이다

*"우선 구현되는 게 중요하다"*(2026-08-13 사용자). `turnPenalty`·모듈 밖 가산은
**켤 자리만 만들어 두고 값은 나중에** 정한다 — 교차가 실제로 관측되면 그때 켠다(D3).

### 9.5 기존 코드와의 상호작용 — **새로 만들 접점이 0 이다**

모듈 크기는 **이미 셀의 부산물**이다:

```ts
// moduleTransform.moduleExtent — 머신 ∪ **모든 셀**의 외접 사각형
for (const m of mod.machines) mk(...);
for (const c of mod.cells)    mk(c.x, c.y);   // ← 벨트 한 칸만 밖으로 나가도 반영된다
```

`linkPlanner` 주석이 이미 그렇게 적고 있다 — *"자리는 그냥 **바깥으로 자란다**: 모듈이
차지하는 범위는 `moduleExtent`(머신 ∪ 모든 셀)라 배치가 이 셀들을 이미 셈에 넣는다."*

**소비처 넷은 전부 `moduleExtent` 하나만 본다** — 모듈 내부를 아무도 안 들여다본다:

| 소비처 | 무엇에 | 모듈이 커지면 |
|---|---|---|
| `modulePacking` tidy-tree(`heightOf`) | 세로 배치 | **평행이동만** |
| `modulePacking` `colWidth[depth]` | 열 폭 = 그 열 모듈들의 **최대 w** | 그 열이 넓어진다 |
| `modulePacking` `absPortY` | 포트 절대 y = `anchor.y + topY − ext.y` | **포트 위치가 자동으로 따라온다** |
| `modulePerimeterPass` | 반출 시작점 | 자동 |

**포트 위치도 이미 모듈이 정한다** — `ModulePort.anchor` 는 방출기가 만들고
(`makeLinkPortChest`) 바깥은 **읽기만** 한다. *"트렁크가 포트 위치를 정한다"* 는
새 권한이 아니라 **이미 있는 권한**이다.

> **딱 하나 값을 무는 곳:** `colWidth` 는 **열 단위 최대치**라, 한 모듈이 커지면 같은
> depth 의 **열 전체**가 넓어진다. 트렁크 하나의 욕심이 이웃 모듈들의 배치까지 벌린다 —
> 그게 §9.3 손잡이가 실제로 무는 비용이다.

### 9.6 왜 (A′)인가 — 전용 탐색기(B)와의 대비

트렁크가 납품 경로와 다른 점 다섯:

| # | 트렁크 고유 | `containerRouting` 이 표현하나 |
|---|---|---|
| 1 | **N개 머신 곁을 지난다**(경유지) | ❌ 시작·끝 집합만 |
| 2 | **탭 주행이 지상 연속 `k`칸** | ❌ *"여기서 k칸 곧게"* 를 못 시킨다 |
| 3 | **자기 교차 금지**(벨트 한 줄) | ❌ 한 번 호출에선 자동, 여러 번이면 수동 |
| 4 | 흐름 방향 일관 | ✅ 경로가 곧 방향 |
| 5 | 지하 · corridor · 입구 방향 | ✅ 전부 있다 |

**(A′)는 1·2·3 을 탐색 밖으로 뺀다:**

```
1 경유지   →  구간으로 쪼갠다 (순서를 밖에서 정한다)
2 탭 주행  →  탐색 안 하고 **구성**한다 (좌석 수에서 바로 나온다)
3 자기교차 →  이전 구간 셀을 다음 구간의 `blocked` 에 넣는다
```

**(B)는 셋을 탐색 안으로 넣는다** — 상태에 *"몇 번째 머신을 지났나"* 를 더한 경유지
Dijkstra. 순서까지 탐색이 골라 **전역 최적**이 되지만, 상태 공간이 머신 수만큼 곱해지고
**지하·방향·corridor 를 다시 구현**해야 한다(R3 위반).

**(A′)가 지는 경우:** 구간1 이 최단으로 갔더니 구간2 가 크게 돌아야 하는 배치.
(B)라면 구간1 을 조금 돌려 전체를 줄인다. **기둥에서는 순서가 위→아래 하나뿐이라 이 손해가
거의 없고**, 격자([2-격자배치](2-격자배치/))에서 커진다.

> **결정: (A′)로 간다. 돌리는 것은 최적화 단계에서 본다**(2026-08-13 사용자).
> 착수 조건: 격자에서 이 손해가 **실제로 관측되면** (B)를 재검토한다.

## 10. 이번에 실패한 이유 — 2026-08-13 롤백

**한 문장:** **모델을 안 만들고 기존 트렁크의 기하를 옮겨 심었다.**

*"기존 코드의 **의도만** 파악하라"* 는 지시를 받고 "의도 셋"을 적었는데
(면당 깊이로 갈림 · 상한은 reach 종류 수 · 끝을 어긋냄), **그 셋은 의도가 아니라 탭의
구현 방식**이었다 — §5 의 "직선에서만 나오는 제약" 바로 그것이다. 그걸 `LinkLane` 으로
옮겨 심고 "의도만 취했다"고 이름 붙였다.

| 롤백한 것 | 왜 |
|---|---|
| `mergeBaseline`(연속 구간 접기) | "연속"은 직선 전제 |
| `LinkLane`(깊이 슬롯) | 탭의 깊이 레인 복제 |
| `spans`·`crossedGaps`·`gapPorts` 장부 | 면×깊이 축 — 경로 모델엔 없는 축 |
| `supplyMode` + `supplyCompare` | 모델 없이 만든 스위치와 계측 |
| `machineExt`·`portFace`·`FaceRefusal` | 위와 얽혀 있음. 새 모델에서 다시 판단 |

**남긴 것:** 사실 정정(`CLAUDE.md` 사유 타입 · 용어사전 낟알 · `code-folders` 축 판정 ·
`module-planning` §5)과 작업 방법(`tempPlanDocs/CLAUDE.md`). 모델과 무관하게 참인 것들이다.

**되찾는 법:** 롤백 직전 상태가 scratchpad 의 `rollback-backup/`(패치 + 새 파일 4개)에 있다.

### 다음이 같은 데를 안 밟게

1. **기존 구현의 "어떻게"를 의도로 착각하지 않는다.** 의도는 *"무엇을 이루려 했나"* 이고,
   깊이·레인·stagger 는 *"직선으로 하기로 했을 때 따라온 것"* 이다.
2. **모델 없이 검증을 늘리지 않는다.** 잴 것이 남의 모델뿐이면 계측이 아무 말도 안 한다.
3. **"산출물이 안 바뀐다"를 합격선으로 쓰지 않는다.** 기준선이 미완성이면 아무것도 증명하지 않는다.

## 14. 배정 모델 — 확정 (2026-08-14, 실물 배치 둘로 검산)

> **근거는 사용자가 준 실물 배치 둘이다**(`배치1` · `배치2`, electronic-circuit-wood ×4).
> 추측이 아니라 **읽어 낸 것**이고, §14-7 이 좌표로 검산한다.

### 14-1. 자원 — 면 하나가 가진 것

```
        d1        d2 .. d(1+R)         d(2+R)      d(3+R)
      좌석 열       벨트 레인          포트 인서터    포트 상자
      행으로 나눔    깊이 축. R = |reach 종류|
```

**레인에는 두 축이 있다.** 이것이 §14-5 의 전부다.

```
깊이 축   면당 R 개.   한 레인이 최대 N 대를 먹인다        ← 긴 팔이 있어야 쌓인다
행   축   연 gap 마다 가로 한 줄. 한 줄이 **정확히 2대**   ← 긴 팔 없이도 쌓인다
```

**인서터 물리** — 좌석 `s`, reach `r`, 벨트 `b = s + r`, 그리고 `s ≤ r`.
`ℛ={1,2}` 에서 동시 성립 조합은 `{(1,1),(1,2)}`(belts d2·d3) 또는 `{(1,2),(2,2)}`(belts d3·d4).
**개수는 `R` 로 유일하고 깊이 배열은 유일하지 않다**(유체가 d2 를 먹은 면에서 차이가 산다).

### 14-2. 수요 — 수 넷이면 끝이고 분기문이 없다

```
k_j = ⌊벨트처리량 / per_j⌋     한 벨트가 맡을 수 있는 머신 수
g_j = min(k_j, N)              묶음 크기 — **항상 최대로**            ← R1
c_j = ⌈N / g_j⌉                구간 수. 앞에서부터 g 대씩, 나머지는 뒤 ← 3+1 (균등 아님)
a_j(m)                          머신 m 에서 이 줄이 쓰는 팔 수
```

`c=1` 관통 · `c=N` 다이렉트 · 그 사이가 부분 병합 — **한 공식의 구간이지 다른 형태가 아니다.**

### 14-3. 배정 여섯 단계 — 전부 결정적, 탐색 0

```
① 면       밖(부모/자식 방향)이 준다. 트렁크는 못 고른다              ← R5
② 깊이     a(j,d) = ⌈per_j / tp(d)⌉ 로 후보를 거르고, 통과한 것 중 아무거나  ← R2
③ offset   ②의 순서대로 머신 안 행을 하나씩. 얕을수록 흐름 반대쪽 끝   ← R3
④ 구간     좌석 행에서 유도:  [min seat row .. max seat row]
⑤ 진출     구간 끝 행에서 d+1 .. maxLane 을 **한 칸씩**
⑥ 포트     maxLane+1 = 인서터,  maxLane+2 = 상자
```

**②(R2)의 근거 — 처리 가능성뿐이다:**

```
깊이가 팔 종류를 정하고(emitModule:48), 팔 종류가 처리량을 정한다.
        d2 = reach 1 = 가장 빠른 팔        d3 = reach 2 = 그보다 느린 팔
        실측 모드팩에서 fast 10/s vs long-handed 1.2/s — **8배**(moduleWizard:278)

a(j, d) = ⌈ per_j / tp(d) ⌉        그 깊이의 팔로 머신 하나를 먹이는 데 필요한 팔 수
후보     = Σ_j a(j, d_j) ≤ h 인 (줄 → 깊이) 조합
```

> **후보 중에는 우선순위가 없다.** 어느 줄이 얕고 깊은지는 **중요하지 않다**(2026-08-14 사용자).
> 옛 규칙(*"구간 적은 줄이 얕게"*)은 폐기 — §14-8 참조.

**⑤가 요구하는 것 — 진출 조건:**

> 레인 `d` 의 구간이 진출하는 행에서, `d+1 .. maxLane` 이 **그 행에 비어 있어야** 한다.

`c` 개로 쪼개진 레인은 구멍이 `c+1` 개(사이 + 양끝)라 대개 저절로 맞는다.
**막히면 수단은 둘뿐이다(R7)** — §14-8 이 실물로 보인다.

### 14-4. 상한

```
면 f 에 배정된 품목:   개수 ≤ R_f        (깊이 레인 수 — ①)
                       Σ_j a(j, d_j) ≤ h  (그 면의 좌석 행 — ③)

모듈 전체 좌석 예산 = 2h   (W면 h + E면 h).  **면은 선호이지 강제가 아니다**(R5·R8)
```

> **면마다 따로 세지 않는다.** 선호 면이 차면 반대 면으로 분산한다.
> (2026-08-13 에 같은 실수를 한 적이 있다 — *"입력은 E를 선호하니 E에만 앉는다"* 로 세다가
> 4줄 레시피에서 포트가 8개가 됐다. 예산을 모듈 전체로 바꾸니 4개가 됐다.)

> **`g`·`k` 는 상한에 안 들어간다.** 레인의 행 예산 `N×h` 를 구간 `g×h` 로 나누면 레인당
> `N/g` 구간이고, 품목 하나의 요구도 `N/g` 라 **`g` 가 약분된다.**
> `g` 가 정하는 것은 **포트 개수 `Σ⌈N/g_j⌉`** 뿐이다.

**넘으면 행 축으로 간다** — gap 을 연다(§14-5). *어느 품목을 내리나*는 미결(judgements **J2**).

### 14-5. 두 축 — 긴팔이 없으면 gap 으로 산다

`ℛ={1}` 이면 `R=1` → 면당 레인 1 → W+E 로 품목 2개가 한계. 품목 3개는 **밀착 기둥으로 불가능**하다.

```
 y=88  ███ M0 ███
 y=89   i   i   i   i     ← reach 1.  픽업 y=90, 드롭 y=88 (M0)
 y=90  ══ ══ ══ ══ ══     ← 가로 트렁크. 팔 개수는 길이만큼 무제한
 y=91   i   i   i   i     ← 픽업 y=90, 드롭 y=92 (M1)
 y=92  ███ M1 ███
```

**가로 벨트 하나가 위·아래 두 머신을 먹인다.** `clusterLayout.ts:17` 의 `ROW_GAP = 3` 이
정확히 이 폭(좌석/벨트/좌석)이다.

```
총 레인 = 2R  +  G          긴팔 있음 → 깊이에 쌓는다 → 모듈이 옆으로
          ↑깊이  ↑행         긴팔 없음 → gap 에 쌓는다  → 모듈이 아래로
```

4대·`R=1`·gap 3개 → 레인 `2+3=5`. 대가는 높이 12행 → 21행(**+75%**).

> **그래서 §14-1 의 *"탭 주행은 세로뿐"* 은 `gap = 0` 전제였다.** gap 이 열리면 무너진다.

### 14-6. 지하 — 건너지는 쪽이 들어간다

`y=t` 행에서 얕은 레인 A 가 깊은 레인 B 를 건너려 할 때, **A 는 점프를 시작할 수 없다**:

```
containerRouting.ts:351   if (di !== cur.arr) continue;   // entrance-straight
```

A 는 코너에 **남쪽으로** 도착하므로 남쪽으로만 점프할 수 있다. **B 가 잠수해야 한다:**

```
 y=t-1   ⊐   ║      ⊐ B 지하 입구 (남쪽 도착 → 남쪽 점프 ✓)
 y=t    ══╝  ·      ← A 가 지상으로 지나간다.  B 의 corridor 는 axis='v'
 y=t+1   ⊏   ║      ⊏ B 지하 출구
         B   A
```

**대가:** B 는 행 `t` 에서 탭을 못 한다(몸통이 땅속). 그 행에 B 의 좌석이 없어야 한다.
**언제 쓰나는 미결** — J3(모든 줄이 관통이면 구멍이 없다).


**근거였던 것:** 얕은 레인의 진출은 깊은 레인에 **지상 전달 타일**이 필요하니, 구간 많은 줄을
깊게 두면 구멍이 남아돈다.

**폐기 이유 셋**

```
① 진출 수단을 하나(지상 전달 타일)로 가정했다.  R7 이 둘을 주면 회피가 필요 없다
② c 가 같으면 완전 대칭이다 — 배치2 에서 나무↔구리를 offset 까지 바꾸면 타일 하나까지 같다
③ 처리량 논리와 정면 충돌한다:
     c 작다 ⟺ k 크다 ⟺ per 작다  →  옛 R2 는 **수요가 작은 줄에 가장 빠른 팔**을 준다
     그런데 a = ⌈per/tp⌉ 라 빠른 팔은 **수요가 큰 줄**에 필요하다
```

**그리고 이 폐기가 순환을 끊는다.** 옛 R2 는 `c` 를 깊이 배정의 입력으로 썼는데,
`c` 는 `그릇 = ⌊벨트/tp(d)⌋` 를 거쳐 깊이에 의존한다 — `c → 깊이 → tp → 그릇 → c`.
새 R2 는 `c` 를 안 보므로 고리가 없다:

```
① 면  →  ② 깊이(a 로 후보 거르기)  →  a·그릇·g·c 를 한 번 계산  →  ③④⑤⑥
```

### 14-10. 지하는 **아끼는 자원이 아니다** (2026-08-14 정정)

§9.2 는 지하를 *"`(축, 티어)` 배타권이라는 한정 자원"* 이라 적었다. **모듈 안쪽에서는 그렇지 않다.**

```
containerRouting.isJumpAllowed
   같은 blockGroup ∧ 같은 axis ∧ 같은 line  →  range 가 strict disjoint 여야 한다
   line 이 다르면  →  **검사 자체를 건너뛴다**
```

레인 하나(`axis='v'`, `line=x`)는 **그 트렁크가 이미 독점**하고 있다. 그러니 같은 line 위의
corridor 들은 서로만 안 겹치면 되고, 그건 자기 구간을 자기가 쪼개는 것이라 **다툴 상대가 없다.**

> **§9.2 의 "한정 자원"은 채널 층(모듈 사이)에서 여러 경로가 같은 line 을 다툴 때의 이야기다.**
> 모듈 안쪽 트렁크에는 적용되지 않는다.

**인접한 두 행을 건너야 하면 하나로 합친다.** 계단(§14-3 ③)에서 얕은 레인 둘이 `t`, `t+1` 에서
같은 깊은 레인을 건너야 할 때, corridor `[t−1, t+1]` 과 `[t, t+2]` 는 겹쳐 둘 다는 못 판다.
대신 **`[t−1, t+2]` 하나**로 판다 — 몸통이 `t`·`t+1` 둘이 되고 그 두 행의 탭만 잃는다.
필요 점프 길이 3 은 바닐라 `transport-belt`(`max_underground_distance = 4`) 안이다.

**(나) 끊기로 떨어지는 경우 — 규칙으로**

```
① 그 벨트에 지하 변종이 없다              maxJumpDistance = 0
② 필요한 점프 길이 > max_underground_distance   (합쳐야 할 인접 행이 너무 많다)
③ 잠수 구간의 몸통 칸이 그 트렁크의 탭 행이다   탭을 잃으면 그 머신이 굶는다
```

### 14-11. 좌석 예산이 넘치면 — **gap 을 열어 N/S 면을 쓴다** (R8)

밀착 기둥(`gap = 0`)에서 머신 한 대가 가진 좌석은 **W면 `h` + E면 `h` = `2h`** 뿐이다.
N/S 면은 **옆 머신의 몸통**이라 못 쓴다.

```
 y=88   ███████  ┐
 y=89   ███████  │ ← 이 경계가 M0 의 S면인데 바로 M1 이라 좌석이 없다
 y=90   ███████  ┘
```

**gap 을 열면 그 경계가 살아난다.**

```
gap = 3   (좌석 / 벨트 / 좌석)
 y=88   ███ M0 ███
 y=89    ·  [i]  ·      ← M0 의 S면 좌석.  남쪽(y=90)에서 집어 M0 에 넣는다
 y=90   ══ ══ ══ ══     ← 가로 벨트 **하나가 위·아래 두 대를 먹인다**
 y=91    ·  [i]  ·      ← M1 의 N면 좌석.  북쪽(y=90)에서 집어 M1 에 넣는다
 y=92   ███ M1 ███
```

```
좌석 예산    2h  →  2h + 2w      (w = 머신 폭.  3×3 이면 6 → 12)
```

**gap 은 전부 열지 않는다 — 머신 2대마다 하나면 충분하다**(R11). 가로 벨트 하나가 위·아래
두 대를 먹이기 때문이다.

```
M0 ┐
   ├ gap  ← 가로 벨트가 M0(S) 과 M1(N) 을 먹인다
M1 ┘
M2 ┐      ← M1·M2 는 **밀착**.  여기 gap 을 열면 아무도 안 쓴다
   ├ gap  ← M2(S) · M3(N)
M3 ┘

4대 · h=3 · gap=3    전부 열면 21행 · **2대마다 열면 18행** · 밀착이면 12행
N 대에 필요한 gap 수 = ⌈N/2⌉
```

`layoutCluster` 가 **이미 `rowGap: number | number[]` 를 받는다**(`clusterLayout.ts:51`) —
*"gap 은 자리마다 다를 수 있다. 그 gap 을 지나는 가로 벨트 수에서 유도되기 때문이다."*
**새 자료구조가 필요 없다.**

#### gap 폭은 가로 벨트 줄 수에서 유도된다 (2026-08-15 사용자 확인)

gap `g` 행: 맨 위가 위 머신의 S면 좌석, 맨 아래가 아래 머신의 N면 좌석, 가운데가 벨트.
좌석 `r` 은 `r + reach` 를, 좌석 `r+g−1` 은 `r+g−1−reach` 를 집는다. `ℛ = {1,2}` 로 세면:

```
g = 3   벨트 1줄  {r+1}                위 reach1 · 아래 reach1     → **양쪽 공유**
g = 4   벨트 2줄  {r+1, r+2}           위 reach1·2 · 아래 reach2·1 → **둘 다 양쪽 공유**
g = 5   벨트 3줄  {r+1, r+2, r+3}      가운데만 공유, 바깥 둘은 한쪽 전용
g = 6   벨트 4줄  {r+1..r+4}           **공유 0** — 가로 벨트의 이점(2대 동시)이 사라진다
```

> **`ℛ = {1,2}` 에서 "위·아래를 동시에 먹이는" 가로 레인은 최대 2줄이고 그때 `g = 4` 다.**
> 이게 면당 `R` 의 가로판이다 — 세로는 면당 `R` 줄, 가로는 gap 당 `R` 줄.
> `g` 를 더 벌리면 줄은 늘지만 **한쪽 전용**이 되어 좌석 예산이 안 는다.

**몇 줄이 지나가야 하는가는 요구에서 나온다** — 그 gap 이 맡은 두 대에게 N/S 로 공급해야 할
품목 수. 세로 레인 배정에서 밀려난 품목 수가 곧 그 수다.

> **이것이 *"한 자식 머신이 한 부모 머신에 여러 벨트로 전달하는 형태"* 의 실체다**(2026-08-15 사용자).
> 한 머신이 **W·E·N·S 네 방향**에서 벨트를 받는다.

**그리고 gap 행은 세로 트렁크가 공짜로 잠수하는 자리다.** 가로 벨트가 세로 레인을 건너야
하는데, 그 행에는 **어차피 탭이 없다**(머신이 없으니까) — R7 (가)의 대가가 0 이 된다.

**gap 은 두 가지 부족을 동시에 푼다:**

```
레인이 모자라다 (품목 수 > R)      →  가로 레인이 생긴다        (R4)
좌석이 모자라다 (Σa > 2h)          →  N/S 좌석이 생긴다         (R8)
```

#### 폐기 — *"fan-out = 같은 레인을 행으로 나눠 쓴다"*

2026-08-14 에 내가 적었던 해석이고 **기하가 성립하지 않는다**:

```
레인 x=159 에 구리(offset 0)와 나무(offset 2)를 올리면
   구리 M0 = 86,  나무 M0 = 88,  구리 M1 = 89
                              88 과 89 가 **붙어 있다** → 두 벨트가 이어져 아이템이 섞인다
offset 0/1 로 해도 86-87 이 붙는다
```

**밀착 기둥에서 `h = 3` 이면 한 레인에 두 품목을 못 올린다.** 그러니 그 해석으로는 팔이 줄지
않는다. 실제 답은 위의 **gap** 이다.

## 16. 축의 정정 — **깊이는 결과이지 입력이 아니다** (2026-08-15 사용자)

> *"깊이에 대해서 저는 잘 모릅니다. 제가 아는 건 사용자가 선택한 인서터들 중 reach-1·reach-2 가
> 존재한다는 것이고, 그것들을 **정확하게 작동시키려면** 벨트를 깊이-2·깊이-3 에 두어야 한다는
> 사실뿐입니다. … 여러 머신의 **규칙성을 파악하기만 한다면** 깊이 개념을 몰라도 괜찮습니다.
> **인서터를 제대로 배치할 수만 있으면 됩니다.**"*

### 16.1 무엇이 축인가

```
축이 아니다   깊이 d2 · d3        ← 기둥에서 규칙성이 만들어 낸 **이름**
축이다        (인서터 i, 그 팔이 집는 타일)   ← 물리.  reach 는 고정 거리다
```

```
줄 j 를 인서터 i 로 먹인다  →  팔 개수  a(j,i) = ⌈ per_j / tp_i ⌉
팔 i 하나를 앉히려면        →  타일 둘.  **좌석**(머신에 인접) + **벨트**(좌석에서 reach_i 칸)
```

**"깊이"는 그 벨트 타일이 머신 면에서 몇 칸인지의 별명**일 뿐이다. `reach 1` 을 고르면 벨트가
`d2` 에, `reach 2` 를 고르면 `d3` 에 가는 것이지, **`d3` 를 고르고 나서 긴팔이 딸려 오는 게 아니다.**

### 16.2 그래서 순서가 뒤집힌다

```
지금 코드   팔 개수를 센다(reach 1 고정) → 앉힌다 → **깊이/reach 를 재배정**한다
            (clusterPortPlanner.ts:402-427 — 수요 내림차순 ↔ throughput 내림차순 zip)
            ③이 ① 뒤에 있어 ①이 쓴 수가 무효가 된다

새 순서    **줄마다 인서터를 고른다** → 팔 개수가 그 인서터에서 나온다 → 타일을 예약한다
```

### 16.3 규칙성은 **결과**다

같은 레시피의 머신 `N` 대는 같은 줄 집합을 가지므로 **같은 인서터 배정이 반복**된다.
그래서 좌석이 같은 열에 늘어서고, 벨트가 같은 열에서 길어진다.

> **트렁크는 그 규칙성을 한 줄로 이어 붙인 것**이고, §14 의 "깊이 레인"은 그 규칙성의 이름이다.
> **격자로 가면 규칙성의 모양이 바뀌지만 축은 안 바뀐다** — 여전히 `(인서터, 집는 타일)` 이다.
> 그래서 §16 은 §14 를 폐기하지 않는다. §14 는 **기둥에서의 §16** 이다.

### 16.4 §14 를 읽을 때

```
§14 의 "깊이 d"      →  "reach = d−1 인 인서터를 골랐을 때 벨트가 놓이는 칸"
§14 의 "면당 R 레인"  →  "한 면에 동시에 세울 수 있는 서로 다른 (인서터, 벨트타일) 쌍의 수"
§14 의 tp(d)         →  tp_i  (그냥 그 인서터의 처리량)
```

**수는 전부 같다.** 바뀌는 것은 **무엇이 원인이고 무엇이 결과인지**뿐이고, 그것이
§0.1(하드코딩 금지)을 지키는 데 결정적이다 — 깊이를 입력으로 두면 `if (depth === 3)` 이 생긴다.

| `commitLinkFace` 가 머신 여럿을 **이미 순회한다** | `linkPlanner.ts:249-266` |
| 막는 것은 `arms.size !== 1` 과 **고정 `laneDepth`** 둘뿐 | `linkPlanner.ts:197,222` |
| 면당 레인 수를 아는 함수가 **이미 있다** | `clusterPortPlanner.laneSlots` · `clusterLayout.columnTapCapacity` |
| 머신당 수요·벨트 처리량이 **실경로에 온다** | `SupplyCapacity.lineRates` ÷ `machineCount` · `input.belts` |

### 19.6 불변 — 기전으로

```
불변 1   `g = N` 이면 그룹이 하나라 오늘의 "묶은 그룹"과 같다 → 계획이 다른 답을 낼 수 없다
불변 2   `emitTapInserting` 이 사라지면 트렁크 기하를 아는 코드가 **한 곳**이 된다
         → `rg "emitTapInserting"` = 0 (R3)
불변 3   `arms.size !== 1` 을 푼 뒤에도 **좌석 예산 검사는 그대로**다
         (`tryLinkFace` W/E 가지가 이미 머신마다 센다) → 없던 자리가 생기지 않는다
```

### 19.7 하지 않는 것

```
· gap 되먹임(좌석이 모자라면 gap 을 연다) — 별도 단계
· 격자 · 형태 분기(§0.1) — 여전히 0
```

### 19.8 예상되는 변화

```
· 오늘 트렁크가 나오던 모듈의 **포트가 축 방향 → 옆 방향**으로 바뀐다 (좌표가 바뀐다)
· 오늘 "한 줄이라도 안 되면 모듈 전체 다이렉트" 이던 것이 **줄마다** 갈린다
· 수요가 벨트를 넘는 줄이 **다이렉트가 아니라 부분 트렁크**가 된다 (포트가 N개 → c개)
```
