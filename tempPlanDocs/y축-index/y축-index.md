# y축-index — 세로 자리도 **번호로** 계획한다

**한 줄 요약:** 세로 채널이 x 에서 하는 일(**수요 → 폭 → 좌표**)을 행 채널이 y 에서도 하게
한다. 그러면 `STACK_GAP` 상수가 사라지고, 사이 띠도 자라고, 되먹임 A 가 열린다.

---

## 1. 푸는 문제 — **x 는 어디서도 좌표가 아닌데 y 는 어디서나 좌표다**

채널 둘은 90° 돌린 같은 기계다. 각자 한 축의 구간을 받아 **직교하는 축의 번호**를 낸다.

| | 세로 채널 | 행 채널(띠) |
|---|---|---|
| **입력**(겹침을 재는 축) | y 구간 `[startY, endY]` — **절대 행** | x 구간 `[x1, x2]` — **모듈-로컬 x** |
| **출력**(배정 결과) | x 번호 → 맨 마지막에 x | y 번호 → **그 자리에서 절대 행** |
| 그 번호가 정하는 것 | 채널 **폭** | 띠 **높이** |

대칭이 **두 군데서, 둘 다 y 쪽으로** 깨진다:

```
① 세로 채널의 입력이 좌표다   absPortY = anchorY + topY − ext.y   ← topY 를 먹는다
② 행 채널의 출력이 좌표다     row = band.top + t                  ← band.top 이 이미 절대 행
```

세로 채널은 y 를 **먹고**, 행 채널은 y 를 **뱉는다.** 방향은 반대인데 원인은 하나다 —
**y 가 경로를 보기 전에 굳어 있다.**

x 쪽은 양쪽 다 좌표가 아니다. 세로 채널의 출력은 `tx = channelStartX(depth) + 1 + t` 로
맨 뒤에 풀리고, 행 채널의 입력은 **일부러 모듈-로컬 x** 다(코드 주석: *"같은 깊이의 모듈은
전부 `colX[depth]` 에 왼쪽 정렬되므로 로컬 x 로 비교해도 겹침 판정이 같다"*).

### 그래서 지금 일어나는 일 셋

```
① 사이 띠가 못 자란다      fitRowChannel 이 between 을 **그대로 돌려준다**
                          → rowChannelShort 에 담기고 그 경로는 탐색으로 간다
② 되먹임 A 가 닫혀 있다    끝을 거리로 고르려면 y → 높이 → 모듈 → 끝(모듈의 입력)
③ 이름 없는 공간이 남는다  진입 다리 · 기둥 밖 세 행 — 어느 index 에도 없다
```

---

## 2. 오늘의 순서

```
1   gen                      모듈 로컬. 높이 확정
2   tidy-tree → topY         ★ y 확정 ── 경로를 아직 하나도 안 봤다   (STACK_GAP = 3)
2b  겹침 스윕                 같은 깊이에서 아래로 민다               (STACK_GAP = 3)
2c  띠 자리                   topY 들 **사이의 빈 칸**으로 정의
5   absPortY                 포트 절대 행
5c  띠 트랙 배정 → 높이        수요를 처음 본다. **이미 늦었다**
5d  트랙 수 → 채널 폭 → colX   ★ x 확정
```

**2c 와 5c 사이가 이 계획이 뒤집는 구간이다.** 띠의 *자리*(2c)가 그 띠의 *수요*(5c)보다
**앞**에 있다 — 세로 채널이었다면 있을 수 없는 순서다.

---

## 3. 핵심 발견 — **문서가 말하는 순환은 실재하지 않는다**

`rowChannelPlanner.ts` 머리말이 이렇게 적고 있다:

> ## 왜 위치 반영이 여기 없나 — **순환** (2026-08-18)
> ```
> topY → absPortY → 띠를 지나는 경로 → 띠 폭 → topY
> ```
> 세로 채널은 이 순환을 **축을 갈라서** 피한다 … 행 채널은 **같은 축**이라 그 수가 안 통한다.
> … 그 폭을 실제 배치에 먹이는 것은 … **두 패스**(임시 간격으로 배치 → 통과 경로 계산 →
> 폭 확정 → 재배치)로 순환을 끊는다.

**둘째 화살표가 거짓이다.** 띠 배정의 입력을 하나씩 세어 보면 **어느 것도 y 를 안 본다:**

```ts
// 수요에 들어가나 — 면이 정한다
if (port.face !== "N" && port.face !== "S") continue;

// 배정에 실제로 넘어가는 것 넷
{ id, x1: 0, x2: port.anchor.x - ownerExt.x, side: face === "N" ? "bottom" : "top" }
//     ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~   ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
//     모듈-로컬 x                            면
```

| 입력 | 어디서 오나 | y 가 필요한가 |
|---|---|---|
| 이 끝이 띠를 쓰나 | `port.face` 가 N/S 인가 | **아니다** |
| 가로 구간 `x1`·`x2` | 모듈-로컬 x | **아니다** |
| `side`(위/아래 진입) | `port.face` | **아니다** |
| 어느 띠인가 | `bandOf(nodeId, depth, face)` — **신원**으로 찾는다 | **아니다** |
| 같은 깊이의 세로 **순서** | 오늘은 `topY` 로 정렬하지만, 그 `topY` 자체가 **DFS 순서**다 | **아니다** |

`portY: absPortY(...)` 가 수요 레코드에 **담기긴 하는데 배정이 안 쓴다** — `RowCrossing` 은
`{ id, side, x1, x2 }` 뿐이다. 진단용이다.

마지막 줄이 요점이다: `layoutY` 는 자식을 **배열 순서대로 위→아래**로 놓고, 2b 스윕은
**아래로만** 민다(순서 보존). 그러니 같은 깊이의 세로 순서 = **트리 DFS 순서**이고,
그건 좌표 없이 나온다.

> **∴ 띠 배정은 `topY` 보다 앞에 설 수 있다. 두 패스가 필요 없다.**

세로 채널이 *"축을 갈라서"* 피했다는 그 수는 행 채널에도 그대로 통한다 — 행 채널의
겹침 축은 **x** 이기 때문이다. 머리말이 *"같은 축이라"* 고 적은 것이 사실과 다르다.

## 4. 단계

### Step 1 — 세로 **순서**를 좌표에서 떼어 낸다

같은 깊이의 모듈 순서를 `topY` 정렬이 아니라 **트리 순회**에서 직접 낸다.

- **전제:** `layoutY` 가 자식을 배열 순서로 놓고 2b 가 순서를 안 바꾼다. (확인: `layoutY:723-736`
  는 `kids.map(layoutY)` 를 배열 순서로 돌고, 2b 는 `t < prevBottom + GAP` 일 때만 **아래로** 민다)
- **불변:** 새 순서 함수와 옛 `topY` 정렬이 **모든 깊이에서 같은 배열**을 낸다 — 단언으로 건다.
  (*"배치가 안 바뀐다"* 가 아니라 **두 계산이 같은 답을 낸다**는 기전 단언이다.)
- **관문:** 띠의 **신원**(깊이·순번·above/below)이 좌표 없이 선다. Step 2 의 전제다.

### Step 2 — 띠 트랙 배정을 `topY` **앞으로** 옮긴다

`rowChannelNeeds` 수집을 둘로 가른다: 띠에 필요한 부분(면·로컬 x·신원)은 앞으로,
세로 채널에 필요한 부분(절대 구간)은 지금 자리에 남긴다.

- **전제:** §3 의 표 — 배정 입력 넷이 전부 좌표를 안 본다.
- **불변:** 옮긴 뒤의 `plan.tracks`·`trackCount` 가 옛 자리에서 계산한 것과 **같다**.
  옮기기 전에 두 자리에서 다 계산해 비교하는 단언을 임시로 건다.
- **관문:** 띠 **높이**가 `topY` 의 입력이 될 수 있게 된다. Step 3 이 그것을 쓴다.

### Step 3 — `STACK_GAP` 을 **띠 높이**로 바꾼다

```
2b 스윕:  if (t < prevBottom + STACK_GAP)     →   + bandHeight(depth, i)
```

- **전제:** 2b 는 **아래로만** 밀므로 간격을 키워도 순서·겹침 성질이 안 바뀐다.
- **불변:** 수요가 0인 띠는 `channelWidthFromTracks(0, 3) = 3` 이라 `STACK_GAP` 과 **같은 수**다
  — 통과 경로가 없는 트리는 한 칸도 안 움직인다(기전: 두 식이 같은 상수로 만난다).
- **관문:** **사이 띠가 자란다.** `fitRowChannel` 의 `between` 갈래가 존재 이유를 잃는다.

### Step 4 — 삭제

Step 3 이 서면 아래가 **근거를 잃는다.** 지운다.

```
STACK_GAP                       간격을 정하는 상수 (2b 자리)
RowChannelBand.wantHeight       "수요대로면 얼마여야 하나" — 이제 실제 높이가 그것이다
fitRowChannel 의 between 갈래    "모듈을 밀어야 한다" 던 미봉책. 이제 민다
rowChannelShort                 띠가 모자랄 이유가 없다
rowChannelPlanner 머리말 §순환   전제가 거짓이다(§3). 두 패스 계획도 함께
moduleWizard 의 「띠가 좁아…」 경고  사유가 사라진다
```

- **관문:** 계획 포기 사유 하나가 **화면에서 사라진다** — `flg.report()` 의 `띠 부족` 줄.

### Step 5 — (측정 가늠) **중앙 정렬도 뺄까**

> **사장님 지시(2026-09-06):** *"tidy-tree 가 y 를 결정하는 부분은 가차없이 삭제해 달라.
> 잘못된 설계였다."*

Step 1–4 가 지우는 것은 tidy-tree 의 **간격 결정**이다. 남는 것은 **중앙 정렬**
(부모를 자식들 중점에) 하나다. 그것까지 빼면 y 는 x 의 완전한 쌍둥이가 된다 —
`colX[d] = colX[d-1] + 열폭 + 채널폭` 의 세로 판인 **순수 누적합**.

**빼기 전에 값을 알아야 한다.** 중앙 정렬은 부모↔자식 세로 거리를 줄여 세로 채널의
트랙을 줄이고 있다. 빼면 그 값이 청구된다 — 얼마인지는 **재 보면 나온다.**

- **관문:** 이 단계는 *"뺀다"* 가 아니라 **"빼도 되나를 수로 답한다"** 다.
  세 사례(ec 10/s · ec 30/s · ac 5/s)의 셀·트랙·폴백을 켜고 끄며 잰다.
- **불변:** 없다 — 이 단계는 측정이다.

## 5. 이 계획이 **안 푸는** 것

- **`FaceTable` 의 행이 머신 틈을 모르는 것** — 같은 축의 문제지만 모듈 **안쪽**이라
  별개다(`벨트-레인` ㉥ 문단이 그 자리를 적어 둔다).
- **진입 다리에 자리를 배정하는 것** — 이 계획은 띠 **높이**만 수요에서 낸다. 포트에서
  띠 행까지 내려오는 세로선은 여전히 `side` 전순서로 **교차만** 피한다.
- **기둥 밖 띠(합류 포트가 튀어나오는 세 행)** — `벨트-레인` ㉣ 소관.
- **되먹임 A 를 실제로 여는 것** — 이 계획은 **열 수 있게** 만들 뿐, 끝 선호를 거리로
  다시 고르는 것은 별개 결정이다(형제 순번을 버릴지는 그때 잰다).

## 6. 이게 끝나면 열리는 문

- **계획 포기 사유 하나가 사라진다** — `rowChannelShort` 가 구조적으로 빈다.
- **되먹임 A 를 열 수 있다** — y 가 수요에서 나오면 *"높이를 알아야 끝을 고른다"* 의
  고리가 x 축처럼 끊긴다.
- **기둥 밖 공간에 이름을 붙일 자리가 생긴다** — 띠가 자랄 수 있게 되면 그 안에
  진입 다리·합류 도형을 넣는 이야기가 비로소 성립한다(㉣ 이 세 번 막힌 그 자리).
- **격자-클러스터가 `innerColumnChannel` 을 얹을 바닥이 선다** — 그 계획서 §4 가
  *"행 채널이 선행"* 이라고 적어 둔 그것이다.
