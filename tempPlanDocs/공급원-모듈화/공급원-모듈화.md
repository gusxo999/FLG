# 공급원 모듈화 — 같은 품목은 **한 곳에서** 받는다

## 0. 한 줄 요약

**목적은 입력 통합이다.** 같은 원료를 여러 모듈이 쓰면 오늘은 투입점이 여러 개인데,
그걸 **하나로 모은다.**

수단은 둘이고 **분리되지 않는다**:

```
① 외부상자를 **더미 모듈**로 승격 — 머신 역할을 하는 자식 모듈이 된다
② **한 자식이 여러 부모**를 먹인다 (트리 → DAG)

①만 하면 소비자마다 더미가 하나씩 생겨 통합이 안 되고 면적만 는다
②만 하면 raw 가 여전히 모듈이 아니라 묶을 대상이 없다
```

---

## 1. 문제 — 같은 품목을 여러 곳에 넣어야 한다

```
오늘   n0 이 iron-plate 필요 → raw 상자 A (외곽 어딘가)
       n1 도 iron-plate 필요 → raw 상자 B (외곽 다른 곳)
       사용자가 **두 곳에** 철판을 넣는다

목표   iron-plate 더미 모듈 하나가 n0·n1 을 함께 먹인다.  투입점이 **하나**
```

**이건 사용자가 체감하는 문제다.** 배치가 커지고 작아지는 것보다 직접적이다 —
블루프린트를 실제로 쓸 때 손이 가는 지점이다.

### 1.1 그 밑에 깔린 구조 문제 — 공급원이 두 종류다

한 모듈의 입력이 어디서 오느냐에 따라 **완전히 다른 기계**가 처리한다.

```
자식이 공급   포트끼리 짝 → 납품 경로(deliveryRoute) → 채널 예약 · 계단꼴 · 지하 횡단
외부에서 공급 짝 없음 → rawPorts → 반출 패스(rePathToPerimeter) → lane 예약 · elbow
```

그래서 **예약 주체가 둘**이고, 서로를 모른다. 2026-08-17 실측에서 둘이 서로를 망가뜨렸다 —
납품 폴백이 마진을 관통하자 반출 예약이 깨져 완제품 상자가 갇혔다.

> `planner/CLAUDE.md`: *"주체가 둘로 갈리면 **무관한 판정이 이미 끝난 예약을 삼키는** 버그가 난다"*

공급원을 한 종류로 만들면 이 부류가 **구조적으로** 사라진다. 그리고 그래야 묶을 수 있다.

### 1.2 그리고 트리가 실제 공장을 못 그린다

`NodeSpec.parentId` 는 **스칼라**다. 자식은 부모가 하나뿐이다. 같은 품목이 여러 부모에
필요하면 자식을 **복제**하거나 raw 로 떨어뜨린다 — 둘 다 낭비다.

---

## 2. 이 계획이 **안 푸는 것** — 먼저 못 박는다

**`planned = 0`(계획대로 깐 납품 경로 0개)은 이 계획으로 안 끝난다.**

```
실패 사유   chain-blocked: **모듈 몸통** (12,0) · (12,6)
                           ^^^^^^^^^^ base.has(k) — 부모 모듈 **자기 셀**.  예약 충돌이 아니다
```

납품 체인이 부모의 입력 포트 상자까지 가야 하는데 그 상자가 면 **속**에 있어 더 깊은
레인들을 가로질러야 한다. **공급하는 쪽이 자식이든 더미든 받는 쪽 기하가 같다.**

```
더미 모듈  → **예약 충돌**을 없앤다 (장부가 하나가 되므로)
포트 표면화 → **물리적 가로막힘**을 없앤다 (상자를 면 표면으로)
             서로 경쟁하지 않는다. **다른 층**이다
```

→ [judgements.md](judgements.md) `J-표면`. 다음 세션이 *"더미를 넣었는데 왜 planned 이
그대로지"* 로 헤매지 않도록 여기 적는다.

---

## 3. 이미 있는 것 — **무엇을 새로 만들 필요가 없나**

> 계획서는 *"무엇을 만든다"* 앞에 *"무엇이 이미 있나"* 를 센다
> (2026-08-16 함정표 ★★★★ — 이 절이 없어 있는 기능을 다시 만들 뻔했다).

| 있는 것 | 어디 | 그래서 |
|---|---|---|
| 노드 → 모듈 → 배치 파이프라인 | `packModuleTree` | 더미도 **같은 길**로 간다. 새 파이프라인 0 |
| 포트 짝짓기 | `pairDeliveryPorts` — 신원 있으면 조회, 없으면 위치-zip | 더미 포트가 어느 쪽인지만 정하면 된다 |
| 납품 경로 예약·방출 | `planChannelGeometry` · `buildPlannedChain` | 그대로 쓴다 |
| 무한상자 생성 | `makeLinkPortChest` · `makeContainerCell` | 더미의 본체가 이것이다 |
| 실패 진단 | `chainMisses` · `skips` · `flg.report()` | 통일 전후를 **같은 잣대로** 잰다 |
| 규칙 검사 | `flg.check()` | 새 불변식을 같은 자리에 붙인다 |

**새로 만드는 것은 셋이다: 더미 노드를 만드는 자리 · 더미의 배치 규칙 · `parentId` 를 복수로.**

## 4. 단계

### Step 1 — 더미 노드를 만든다 (1:1 유지, 최외곽 배치)

raw 입력·루트 출력마다 `NodeSpec` 을 하나 더 만들어 넣는다. **연결 구조는 아직 안 건드린다.**

**더미의 자리는 최외곽이다.** 이건 자의적 예외가 아니라 그 노드가 무엇인지의 표현이다 —
*원료는 밖에서 온다 → 공급원은 경계에 있다*. 반출 패스가 하던 일(*"공급점을 경계에 노출"*)이
**배치 규칙으로 흡수**된다.

```
전제:  generateModule 이 "머신 0대 · 줄 1개" 를 받아 상자 하나짜리 모듈을 낸다.
       확인 = count=0 으로 불러 본다.  안 되면 **상자 전용 모듈 종류**가 필요하다
전제:  더미 출력이 pairDeliveryPorts 에서 부모 입력과 짝지어진다.
       확인 = 신원(linkId)을 줄지 결정.  ext: 사고(2026-08-17)를 반복하지 않는다
불변:  rawPorts.length === 0
       (기전: 모든 입력이 더미 자식을 갖게 되므로 짝 못 지을 포트가 없다)
관문:  공급원을 **한 종류**로 만든다.  반출 패스는 아직 안 지운다
```

### Step 2 — 반출 패스를 지운다

```
전제:  Step 1 뒤 rawPorts 가 정말 0이다.  확인 = flg.report() 의 raw 수치
불변:  `rg "rePathToPerimeter"` = 0
       (기전: 짝 없는 포트가 없으면 이 함수가 처리할 입력이 없다)
관문:  예약 주체를 **하나**로 만든다 — 채널 장부만 남는다
```

### Step 3 — **도착점**: 한 자식이 여러 부모를 먹인다

> 여기가 이 계획의 목적이다. Step 1·2 는 그 앞의 정지 작업이다.
> **확정이 아니라 방향으로 적는다** — Step 2 를 끝낼 때 전제를 다시 확인한다.

같은 품목의 더미를 **하나로 합치고** 여러 부모에 잇는다. `parentId?: string` →
`parentIds: string[]`.

```
막고 있는 것 (modulePacking 의 parentId 사용처 7곳 — 읽어서 셌다)
  childIdsByParent   자식 → 부모 하나로 뒤집는다
  dfsVisit           트리 순회.  DAG 면 방문 표시가 필요하다
  layoutY            tidy-tree 세로 배치.  **부모가 여럿이면 y 를 누가 정하나** ← 가장 얇다
  edgeLinkGroups     간선당 한 번 캐시 — **자식 id 로** 캐시한다(간선이 유일하다는 전제)
  productOf          자식 출력이 하나라는 전제
  deliverySeeds      간선마다 하나 → 부모마다 하나로

정해야 할 것 (아직 안 골랐다 → judgements J-DAG)
  · 자식 산출을 부모들에게 **어떻게 나누나** (rate 배분)
  · 부모들의 깊이가 다르면 자식은 어느 깊이에 서나
  · 채널을 **여럿** 가로지르는 납품 경로를 계획이 그릴 수 있나
```

## 5. 불변 — 기전으로

```
불변 1   공급원이 한 종류다 → 예약 주체가 하나다
         → "남의 예약을 밟는다" 가 구조적으로 불가능해진다 (reservationOverrun = 0)

불변 2   rawPorts = 0 이면 반출 패스는 처리할 입력이 없다
         → 지워도 동작이 안 바뀐다.  "안 바뀐다" 가 아니라 **입력이 없다**가 근거다

불변 3   같은 품목의 투입점이 **하나**다
         → 이 계획의 목적 그 자체.  Step 3 의 성공 판정이기도 하다
```

> **"산출물이 안 바뀐다" 를 불변으로 쓰지 않는다.** 이 계획은 배치를 바꾼다 —
> 상자가 모듈이 되면 채널이 늘고 폭이 달라진다.

## 6. 검증 — 착수 전에 정한다

```
성공 기준   Step 1·2   rawPorts = 0 · rg "rePathToPerimeter" = 0 · reservationOverrun = 0
            Step 3     같은 품목의 외부 투입점이 **1개**  ← 이 계획의 목적

동반 지표   planned ↑ · dijkstra ↓
회귀 감시   flg.diff('before') — 셀 수·penalty.  **더미만큼 넓어지는 것은 예상된 대가**
            다만 Step 3 뒤에는 **줄어야 한다**(중복 더미가 합쳐지므로)
새 검사     flg.check() 위반 0 유지

도구        flg.run() → flg.report() → flg.check() → flg.face(모듈, 면)
금지        스크린샷 눈대중.  가설을 코드로 확인하기 전에 계획 세우기
```

## 7. 대가 — 받아들이는 것

**Step 1·2 에서 배치가 넓어진다.** 상자 하나가 모듈 하나가 되면 채널이 그만큼 는다.

**Step 3 에서 되돌아온다** — 같은 품목의 더미가 합쳐지므로 중복이 사라진다. 그래서
**Step 2 에서 재고 멈추면 손해만 보이는 지점**이다. 도착점까지 가야 값이 나온다.

그리고 그 값은 면적이 아니라 **사용성**이다 — 같은 원료를 한 곳에만 넣으면 된다.
