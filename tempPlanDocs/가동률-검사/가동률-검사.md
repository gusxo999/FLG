# 가동률-검사 — 배치를 정상상태로 풀어 100% 가 아닌 머신을 드러낸다

**한 줄 요약:** 그리드 전체를 한 번 풀어 머신마다 가동률 `u` 를 내고, `u < 1` 인 머신에
빨간 테두리를 친다. 벨트 흐름 검사는 그 해(解)의 **한 칸 조회**가 된다 — 지금의 `beltFlow` 는
이 기능의 첫 조각이었고, 여기서 완성된다.

---

## 0. 승인받을 것 — 기본값으로 적었다. 이의가 없으면 이대로 간다

| # | 결정 | 기본값 | 왜 |
|---|---|---|---|
| **D1** | 무엇을 "100%" 로 보나 | **엄격** — `u ≥ 1 − 1e-6`(부동소수 오차만 허용) | 여유를 두면(예: 99% 초록) 머신 수 올림(`ceil`)으로 생기는 **과잉 생산 머신이 안 보인다.** 그게 이 기능이 보여 줄 것 중 하나다 |
| **D2** | 어떻게 보이나 | 미달 = **빨간 테두리 + `73%`** · 판정 불가 = **주황 테두리 + `?`** · 100% = **안 그림**. 기본 켜짐, 캔버스 칩에서 끈다 | 요청이 *"안 돌면 빨간 테두리"* 다. 판정 불가를 빨강·무표시 어느 쪽에 넣어도 거짓말이 된다 — 경계를 화면에 드러낸다 |
| **D3** | 부족분을 **어느 머신이** 떠안나 | **게임의 우선순위** — 같은 레인은 상류가 먼저(넣기도 집기도), 합류 칸은 직진이 먼저 | **총 부족량은 우선순위와 무관하다.** 우선순위는 그 부족이 *누구의 빨간불*로 나타나나만 정한다. 게임과 같아야 사용자가 게임에서 같은 머신을 본다 |
| **D4** | 유체 | **Step 3** 에서 넣는다. 그 전엔 유체를 쓰는 머신은 **아이템 쪽이 이미 모자라면 미달, 아니면 판정 불가** | 아이템 쪽 부족은 유체와 무관하게 **확정**이다. 확정이 아닌 초록은 내지 않는다 |
| **D5** | 범위 | **그리드 전체** — 수동 배치 포함, 자동 배치 여부 무관 | `belt-flow-inspection` 결정 1(*"그리드 자체를 정적 분석 — 수동 배치/수정한 벨트도 동작"*)을 잇는다 |
| **D6** | 관련 UI 를 한 범주로 | §5 의 정리안 | 사용자 요청 |

## 1. 푸는 문제

### 1.1 목적은 적혀 있는데, 그리드에서 재는 곳이 없다

이 저장소의 배치 목적은 한 줄이다 — `layout-models` §5: *"§0.1(목적 하나 — **모든 머신 100% 가동**)"*.
그리고 이 저장소가 반복해서 적어 둔 실패는 전부 **같은 모양**이다:

> *"배치는 성공이라 말하는데 물류가 거짓인 실패"* — `arith/belt.ts` `determineBeltCount`
> *"총량이 맞는데 안 흐르는 실패가 있다"* — `belt-lane-semantics` §6
> *"파이프는 멀쩡히 이어져 있고, 그림도 정상이고, 라우팅도 '성공'으로 보고된다. 머신만 굶는다."* — `fluid-box-semantics`
> *"접기가 90/s 로 세 놓고 방출이 15/s 를 깔면 그 줄은 조용히 굶는다"* — 용어사전 §벨트 티어

계획기는 자기 셈(레인 상한·팔 수·굶주림 보상)으로 성공을 보고한다. **계획기의 셈을 계획기가
검사하면 같은 가정이 같은 답을 낸다** — 검사는 방출이 끝난 **그리드**를 봐야 한다. 그 장치가 없다.

### 1.2 벨트 흐름 검사는 그 장치의 첫 조각이었고, 거기서 멈췄다

`analysis/beltFlow.computeBeltFlowAt` 은 벨트 한 칸을 누르면 상류를 거슬러 모아 그 칸의
유입·유출을 낸다. 머신 판정으로 가려면 모자라는 것이 다섯이고, 넷은 **개념에 미달한 결함**이다
(문서를 고칠 일이 아니다 — 저장소 `CLAUDE.md` 의 판정):

| | 지금 | 개념 | 자리 |
|---|---|---|---|
| **㉠ 레인이 없다** | 용량을 **줄 전체**로 잰다 | 인서터가 한쪽에서 싣는 줄은 **절반**만 흐른다(`belt-lane-semantics` ①·§1). §6 함정 그대로 — *"벨트 검사가 줄 단위로 포화를 재면 그 상황을 정상이라고 말한다"* | `beltFlow.ts:406-409` · `:428` |
| **㉡ 다재료 머신의 재료를 첫 번째로 고정** | 벨트에서 집는 인서터의 소비율을 `ings[0]` 로 잡는다(산출은 `prods[0]`) | 벨트에 **실린 품목**의 재료율이어야 한다. 구리선+철판 머신이 철판 벨트에서 집으면 **구리선 소비율**로 계산된다 | `beltFlow.ts:221` · `:231` · 호출 `:301` · `:328`(`item = null`) |
| **㉢ 정체가 없다** | 상류를 **더하기만** 한다 | 하류가 안 가져가면 벨트가 차고 상류 투입이 **막힌다**. 소비 없는 막다른 줄에도 흐름이 흐르는 것으로 나온다 | `belt-flow-inspection` *"버퍼/기아/역압은 표현 안 함"* |
| **㉣ 굶주림이 안 번진다** | 머신이 굶어도 그 머신의 산출은 **정격**으로 잡힌다 | 굶은 머신은 덜 만들고, 그 아래가 또 굶는다 | `machineItemRate` 가 가동률을 모른다 |
| ㉤ 한 칸씩만 | 머신 판정이 없다. 누를 때마다 그리드 전체 인서터 색인을 다시 만든다 | 한 번 풀어 모든 칸·모든 머신이 같은 해를 읽는다 | `computeBeltFlowAt` 의 `buildTapIndex` |

### 1.3 손셈 한 건 — 이런 것을 잡으려는 것이다

> **착수 전 손셈이다(실측 아님).** Step 1 의 파이프라인 시험(⑫)이 이 예측을 그대로 검증한다.

합성 게임데이터로 `runLayeredWizard` 를 돌린 배치(2단 트리 · 인서터 `rotation 0.04` = 2.4/s ·
노랑 벨트 15/s)에서, 하위 머신(`sub-item`, 제작 0.5s)은 광석을 **4/s** 먹는다. 머신 옆 팔은 둘(4.8/s)이라
**굶주림 보상은 충족**됐다. 그런데 그 줄을 먹이는 **외부 공급 상자의 인서터가 하나**(2.4/s)다:

```
C(광석) → [인서터 2.4/s] → 벨트 → [팔 둘 4.8/s] → sub-item 머신 (필요 4/s)
                ↑ 여기가 병목 — 계획기는 이 팔을 세지 않는다
```

예측: sub-item 머신 둘 **60%** → 산출 2.4/s(필요 4/s) → 트렁크 하류의 상위 머신 넷 중
**상류 둘은 100%, 셋째 40%, 넷째 0%**(D3). **배치는 "성공" 으로 보고된다.**

## 4. 모델

### 4.1 머신 하나

```
정격 제작수/초   c = 제작속도(모듈 반영, applyEffectsToMachine) ÷ energy_required
재료 i 필요       need_i = c × amount_i
산출 j 생산       prod_j = c × productYield_j × 생산성배수
가동률 u         0 ≤ u ≤ 1. u 로 돌면 재료를 need × u 로 끌고, 산출을 prod × u 로 낸다
```

### 4.2 가동률 = **탐침의 비율**, 전체는 고정점

머신 `m` 의 `u` 를 정하는 질문은 둘이다 — *"100% 로 돌려고 하면 **받을 수 있는** 양은?"* 과
*"**내보낼 수 있는** 양은?"*. 그 머신 **하나만** 100% 로 올리고 흐름을 풀면 나온다(탐침).

> **Step 1 에서 바뀌었다 — 탐침은 둘이다.** 아래 원안(탐침 한 번, 나머지는 전부 현재 `u`)은 생산자·소비자가
> 서로를 0 에 가두는 가짜 고정점을 낸다. 지금은 공급 탐침(대 주는 쪽 = 공급 능력 `us`)과 배출 탐침(받아 가는
> 쪽 = 배출 능력 `ud`)을 따로 풀고 `u = min(us, ud)` 다. 코드의 단일 출처는 `analysis/flow/solve.ts` 머리말.

```
u_m ← min( 1,  min_i 받은_i ÷ need_i,  min_j 내보낸_j ÷ prod_j )     ← (원안) 탐침 한 번
```

모든 머신의 `u` 가 안 바뀔 때까지 되풀이한다(모두 1 에서 출발). 굶주림은 앞으로(㉣),
정체는 뒤로(㉢) 한 바퀴에 한 칸씩 번진다. 반복 상한을 두고, 못 닿으면 결과에 **`converged: false`** 를
싣고 화면에 *근사* 로 표시한다 — 조용히 넘기지 않는다.

> **왜 "현재 u 로 받은 양" 이 아니라 탐침인가.** 머신은 `need × u` 만큼만 끄므로 *받은 양 ÷ 필요량* 은
> 언제나 `≤ u` 다 — 한 번 내려간 `u` 가 다시 오를 길이 없다. 상류 소비자가 뒤늦게 출력 막힘으로 덜
> 먹게 돼도 하류 소비자가 영영 0% 로 남는다. 탐침은 그 머신의 **자기 수요를 빼고** 잰다.

### 4.3 `u` 가 주어졌을 때 흐름 — **집히는 만큼만 들어간다**

벨트는 **레인 노드의 숲**이다 — 칸마다 레인 둘, 레인마다 하류가 정확히 하나(없으면 막다른 끝).
투입(드랍)을 우선순위(4.5) 순서로 하나씩 하류로 밀어 넣는데, **하류의 집기(픽업)가 실제로 가져가는
만큼만** 받아들인다. 끝까지 안 집히는 물건은 벨트를 채워 그 투입을 막는다 — 그게 정상상태의
정체다(㉢). 지나가는 레인 노드마다 남은 용량을 깎는다(㉠).

머신·상자 사이의 **직결 인서터**(벨트 없이 머신→머신, 상자→머신, 머신→상자)는 같은 규칙의
길이 0 짜리 경우다.

### 4.4 레인 규칙 — `belt-lane-semantics` §2 를 그대로

```
레인 용량        벨트 처리량 ÷ 2
투입(드랍)       먼 레인(①). 벨트와 나란히 선 경우는 4.9 (b)
집기(픽업)       두 레인 다(②) — 받는 쪽이 받는 품목만
옆 유입          그 칸에 뒤 유입이 있거나 유입이 둘 이상이면 → 두 레인을 닿은 쪽 레인 하나로 접는다(③⑥)
                유입이 옆 하나뿐이면 → 곡선, 좌/우 보존(⑥)
뒤 유입          좌/우 보존(⑤) · 지하 입구→출구 보존(④)
```

### 4.5 우선순위 (D3)

```
같은 레인        상류의 투입이 먼저 자리를 얻고, 상류의 집기가 먼저 가져간다
합류 칸          뒤(직진) 유입 → 옆 유입 → 그 칸의 투입 순서로 자리를 얻는다(⑦)
한 머신의 팔들    같은 품목의 팔 여럿은 풀(need × u · prod × u) 하나를 나눠 쓴다
```

### 4.6 품목

투입마다 품목을 안다 — 머신 인서터는 그 머신의 산출물, 상자 인서터는 필터 품목. 집기는
**받는 쪽이 받는 품목만** 가져간다(머신 = 제 레시피의 아이템 재료, 상자 = 전부). 이게 ㉡ 을 닫는다 —
다재료 머신이 어느 재료를 받는지는 **벨트에 실린 것**이 정한다.

### 4.7 상자

| 상자 | 역할 |
|---|---|
| 무한상자 · `at-least` 필터 | 그 품목의 **무한 공급** |
| 무한상자 · `remove_unfiltered_items` 또는 `at-most` | **무한 회수** |
| 설정 없는 무한상자 · 보통 상자 | **중계** — 들어온 만큼만 나간다(채우기만 하면 결국 가득 → 막힘) |

> 설정 없는 무한상자를 회수로 치지 않는 것은 게임이 그렇기 때문이다. 수동으로 놓은 무한상자는
> 설정을 못 넣으므로(설정 UI 가 없다) **수동 배치의 회수 상자는 막힘으로 나온다** — 문서에 적는다.

### 4.8 판정 불가와 그 번짐

| 사유 | 조건 |
|---|---|
| `no-recipe` | 레시피가 없거나 게임데이터에 없다 |
| `yield` | 범위 산출물의 기대 수율을 모른다(`productYield === undefined`) |
| `scale` | 그 머신의 팔·벨트에 저울(`inserter_rotation_speed`·`belt_speed`)이 없는 프로토타입이 있다 |
| `fluid` | 유체 재료·산출이 있고 아이템 쪽은 충분하다(Step 3 전) |
| `kind` | 연구실·채굴기 |

판정 불가 머신은 흐름 계산에서 **정격(u = 1)으로 가정**하고, 그 머신과 벨트 트리나 직결을
공유하는 머신에 **`assumed`** 꼬리표를 단다 — 그 판정이 가정 위에 서 있다는 표시다.

### 4.9 게임에서 확인할 가정 둘 — **어느 머신이** 빨간지만 바꾼다

| | 가정 | 틀리면 |
|---|---|---|
| **(a)** | **정체된** 벨트에서도 상류 투입이 이긴다 — 소비로 생긴 빈자리가 줄 **꼬리**(가장 상류 투입 지점)에 나타나서 | 과잉 생산 줄에서 빨간 머신이 상류 쪽이 아니라 하류 쪽이 된다 |
| **(b)** | 벨트와 **나란히** 선 인서터(벨트가 멀어지거나 다가오는 방향)는 진행 방향 **오른쪽** 레인에 떨군다 | `belt-lane-semantics` ① 은 *"그래도 먼 레인"* 이라고만 적는다. 용량은 "레인 하나" 로 같으므로 그 줄에 **다른 투입이 같은 레인으로 합류할 때만** 달라진다 |

둘 다 **총 부족량은 안 바꾼다.** 확인되면 `belt-lane-semantics` 에 옮겨 적는다.

### 4.10 결과의 모양 (Step 1 이 확정한다 — 지금은 스케치)

```ts
interface MachineVerdict {
  entityId: string; x: number; y: number;           // origin 칸
  state: 'full' | 'short' | 'unknown';
  u: number;                                        // unknown 이면 가정값
  inputs:  { item: string; got: number;  need: number }[];
  outputs: { item: string; sent: number; made: number }[];
  /** 가장 모자란 한 줄 — 화면의 "왜" */
  limit?: { side: 'input' | 'output'; item: string; by: 'arms' | 'belt' };
  unknown?: 'no-recipe' | 'yield' | 'scale' | 'fluid' | 'kind';
  assumed?: boolean;
}
```

`by` 는 둘뿐이다 — **팔이 모자라나**(그 머신 인서터 처리량의 합 < 필요량) **벨트가 안 주나/안 받나**.
사용자가 고칠 자리가 그 둘로 갈린다.

>    (`us < ud` 면 굶주림) — 처음엔 까닭을 가르려고 입력만·출력만 푸는 풀이를 두 번 더 돌렸는데 그게 사라졌다.
