# 판단 — 포트 표면 규약 주변에서 아직 안 고른 것

> **미결 2** (2026-08-17 작성). 전제는 그날의 실측(concrete 트리 · 머신 8대)이다.

---

## J-폭 — 채널 트랙이 모자란다 (`no free lane track in channel`)

**사실:** 2026-08-17 에 관통 포트를 기둥 끝으로 옮기자 채널 트랙 수요가 늘어 반출 상자가
트랙을 못 받는 경우가 생겼다. 테스트 6건이 이걸 본다(공급 보장 3 · 예약 불변식 3).

```
옛 옆 포트    포트 y = 자기 좌석 행   → 세로 구간이 짧다
새 끝 포트    포트 y = 기둥 끝 **밖** → 세로 구간이 기둥 전체 + α → 겹침 급증 → 트랙 수요 ↑
```

**전제:** 채널 폭은 **폭 역전**으로 배정 결과에서 나온다
(`channelWidthFromTracks(trackCount, MODULE_CHANNEL_MIN)`). 그렇다면 수요가 늘면 폭도
따라 늘어야 하는데 **안 늘었다.**

**길 셋 (아직 안 골랐다)**

| | 무엇 | 확인해야 할 것 |
|---|---|---|
| 가 | `cap` 상한이 막고 있다 | `planChannelGeometry` 의 `cap = max(MIN_TRACK_CAP, 납품+반출 수)` 가 실제 수요보다 작은가 |
| 나 | ④ phantom 예약이 그 구간을 안 센다 | 부적격·fallback 경로의 폭 예약이 기둥 끝 포트의 긴 구간을 반영하나 |
| 다 | 폭은 맞는데 **배정이 못 찾는다** | ②의 백트래킹이 반출을 뒤로 미뤄 굶기나 (실패 비용 순: 유체 → 반출 → 아이템) |

**착수 조건:** [[포트-표면-규약]] Step 3 이 끝난 뒤. 그때 `flg.report()` 의 트랙 관련 수치를
다시 재고 셋 중 무엇인지 가른다 — **포트 표면화가 세로 구간을 다시 바꿀 수 있어** 지금
가르면 헛수고다.

**코드 역참조:** `channelPlanner.channelWidthFromTracks` 에 한 줄 주석을 남긴다.

## J-도달규칙 — `flg.check()` 의 R-도달이 기둥 끝 포트를 모른다

**사실:** 2026-08-17 기준 위반 5건이 뜨는데 **대부분은 규칙이 낡은 것**이다. 기둥 끝 포트는
머신에 안 붙는 것이 정상인데(상자가 기둥 밖이다) 규칙이 *"포트와 머신 사이"* 를 잰다.

```
n0-concrete 포트 (8,3) E 와 머신 사이가 비었다 — (7,3)          ← 기둥 끝 포트.  정상
n0-concrete 포트 (13,5) E 와 머신 사이가 비었다 — (9,5)…(12,5)  ← **네 칸.  진짜 결함일 수 있다**
```

**아직 안 가렸다.** 다섯 건 중 몇이 진짜인지 모른다.

**길 둘**

| | 무엇 | 성질 |
|---|---|---|
| 가 | 규칙을 고친다 — 기둥 끝 포트는 **벨트를 통해** 머신에 닿는지 본다 | 정확하다. `portEnd` 를 규칙이 알아야 한다 |
| 나 | 규칙을 둘로 나눈다 — `R-도달(옆)` · `R-도달(끝)` | 사유가 갈려 처방이 분명해진다 |

**착수 조건:** [[포트-표면-규약]] Step 3 에서 `R-표면` 을 넣을 때 **함께** 본다 — 같은 파일
(`src/debug/checkRules.ts`)이고, 표면화가 이 위반들의 절반을 없앨 수 있다.

**전제 부패 신호:** 표면화 뒤에도 `(13,5)` 류가 남으면 그건 규칙 문제가 아니라 **진짜 결함**이다.
