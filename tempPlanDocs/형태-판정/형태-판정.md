# 형태 판정 단일화 — 계획서

> **한 줄:** 형태는 조건에서 나온다. 그런데 **조건을 재는 자가 셋이고, 판정하는 기전이 둘**이다.
> 자를 하나로 만들고(Step 1), 셀 수 있게 하고(Step 2), 판정을 하나로 만든다(Step 3).

---

## §1 — 인과 (이 계획이 서 있는 자리)

```
①  붓기        edgeLinkGroups        내부 줄: 흐름을 벨트 줄에 붓는다
②  조립        externalLineGroups    외부 줄: 원료·완제품 줄을 그룹으로 만든다
        │  여기서 형태가 **정해진다** — 조건은 양(벨트 처리량)과 좌석
        ▼
③④ 면 배정    tryLinkFace           정해진 형태를 **조건으로 받아** 자리를 정한다
        │
        ▼
   방출        emitOutputLinks       배정을 격자에 놓기만 한다
```

**판단은 ①②에 있다.** ③④가 `arms.size` 를 보는 것은 판정이 아니라 **그 줄 자신의 자료를
읽는 것**이라 어긋날 수 없다 — 거기엔 고칠 결함이 없다. 이 계획은 ①②만 다룬다.

## §2 — 갈려 있는 것 둘

### (가) 자가 셋이다 — "한 면에 팔 몇 개 앉나"

```
붓기 ①    seatCap(h) = h × 팔처리량           rate 단위 · 유체 행 무시
배정 ③    seatRows   = h − 유체 행 수          팔 단위  · 유체 행 뺌
조립 ②    (없다)                              machine.h 가 인자로 **안 들어온다**
```

같은 물리(면의 칸 수)를 세 곳이 각자 센다. ①이 낙관이라 앉을 수 없는 그룹이 나면
③에서 `linkMismatches` 로 **통째로 사라진다**(2026-08-22 에 실제로 그랬고, `seatCap` 이
그때 들어왔다). ②는 아예 안 재서 그 실패가 **더 늦게**(면 배정 전부 실패 → `unrouted`) 난다.

### (나) 판정 기전이 둘이다 — 갈리는 축이 **출처**다

| 줄의 출처 | 공유(트렁크)냐 전용(다이렉트)냐를 **무엇이** 정하나 |
|---|---|
| **내부**(자식→부모) | 줄마다 **양** — `mergeFrom`/`mergeTo`(머신 최대 부하 ≤ 면 좌석) · `room`(줄 남은 용량) · `fitsInFreshLine`(억지 쪼갬 회피) |
| **외부**(원료·완제품) | `supply.mode !== "tap"` — **모듈 전체 비트 하나.** 줄 하나가 탭에 실패하면 그 모듈의 **모든** 외부 줄이 머신마다 쪼개진다 |

[용어사전 §D](../../docs/용어사전.md) 가 이미 폐기로 적은 모양이 여기 남아 있다:
*"예전엔 쪼갬 여부가 양이 아니라 **출처**로 갈렸다."* 쪼갬 축은 2026-08-22 에 양으로
옮겨졌지만 **트렁크/다이렉트 축은 아직 출처로 갈린다.**

## Step 1 — 자 하나로 ✅**완료**(2026-08-23)

**무엇** — `faceSeatArms(machineH, fluidRows)` 하나를 만들고 세 곳이 그것을 부른다.

```ts
붓기 ①   faceSeatArms(child.machine.h, 0) × 팔처리량   // 0 = "유체를 일부러 무시한다"
배정 ③   faceSeatArms(machine.h, pf?.rows.length ?? 0)
조립 ②   (Step 3 에서 부른다 — 여기서는 인자를 받을 자리만 연다)
```

**전제**
- 붓기는 **면을 모르고**(배정이 나중) **다른 줄이 먹은 좌석도 모른다**(간선 하나씩 돈다).
  → 자를 통일해도 그 두 낙관은 **남는다.** 이 Step 이 없애는 것은 *유도가 셋* 이라는 사실뿐이다.
- ③의 `h − 유체 행` 은 그 면의 유체 상자 행 수다(`pipeFaces` 가 면마다 따로 안다).

**불변 (기전으로)**
- 세 자리의 **값이 오늘과 같다** — ①은 `fluidRows = 0` 을, ③은 오늘 쓰던 그 수를 넘긴다.
  식이 같으므로 다른 답을 낼 입력이 없다. *산출물 비교가 근거가 아니다.*

**관문**
> 판정을 통일하려면(Step 3) **양쪽이 같은 자로 잰 수**를 비교할 수 있어야 한다.
> 지금은 한쪽이 rate, 한쪽이 팔 개수, 한쪽은 아예 없다.

**검증** — 타입 0 · 실패 **3건 그대로**(기존 그것). 테스트 592 → 595.

> **착수해 보니 편집이 셋이 아니라 둘이었다.** 원래 서술은 *"조립(`externalLineGroups`)은
> 인자를 받을 자리만 연다"* 였는데, **쓰지 않는 인자를 여는 것**이 된다. 이 저장소가
> 반복해 지운 것이 바로 그것(소비처 0인 코드)이라 **열지 않았다** — 조립은 Step 3 에서
> 실제로 부를 때 인자를 받는다. 대신 gap 면의 좌석 셈(`machine.w`)도 같은 자를 타게 해서
> **면 넷이 전부 한 함수**를 본다.

## Step 2 — 형태를 셀 수 있게 ✅**완료**(2026-08-23)

지금 형태는 **산출물 어디에도 안 남는다.** glass 54줄(필요 5줄)을 사후에 손으로 셌다.
Step 3 이 동작을 바꾸는데, **재는 눈이 없으면 좋아졌는지 모른다.**

- 판독(줄 하나에서): 이 줄이 만지는 머신 수 · 실은 흐름 수 · 기둥 관통 여부.
- 판독(그룹 집합에서): 그 머신이 쓰는 줄 수(fan-out) · 그 흐름이 쪼개진 줄 수(링크).
- 싱크는 [`debug/runStats`](../../src/debug/runStats.ts) — *"파이프라인은 관측만 당한다"* 는
  그 파일의 설계 그대로. `flg.report()` 에 한 줄:

```
형태   트렁크 3 · 다이렉트 12 · 관통 1 · 최대 fan-out 4 · 줄 이용률 중앙값 62%
```

**J1 은 (가)로 정해졌다** — 계획 함수가 싱크를 직접 부른다. `planner/moduleWizard.ts:45` 가
이미 같은 싱크를 import 하고 있어 새 층이 아니라 간선 하나다.

**착수해 보니 함정이 하나 있었다 — `packModuleTree` 는 모듈을 두 번 만든다.** 1차는 끝
선호를 재려고 만들고 버린다. 그대로 두면 외부 줄이 **두 번 세진다.** 2차 직전에
[`resetBeltFormStats`](../../src/debug/runStats.ts) 로 1차 몫을 버린다.

### 첫 측정 (2026-08-23, 브라우저 아님 — 픽스처 프로브)

```
realTree (advanced-circuit, count=1)   트렁크 0 · 다이렉트 9 · 관통 0 · 최대fan-out 3 · 이용률 12% (22/180)
glass 꼴 (자식 2×100/s, 부모 13×15/s,   트렁크 8 · 다이렉트 3 · 관통 0 · 최대fan-out 4 · 이용률 50% (495/990)
          벨트 90/s)                     linkMismatches 0
```

**읽히는 것 셋:**

1. **줄 수를 정하는 것은 벨트가 아니라 좌석이다.** glass 꼴에서 벨트 상한만 보면 195/s ÷ 90
   = 3줄이면 되는데 11줄이 났다. 자식 한 대가 100/s 를 내는데 **한 줄이 그 머신에서 받을 수
   있는 최대가 `좌석 3 × 팔 13.2 = 39.6/s`** 이기 때문이다. 이용률 50% 의 절반은 낭비가
   아니라 **물리**다.
2. **관통이 0이다.** `spansAllMachines` → 기둥 끝 포트 경로가 두 사례 모두에서 한 번도 안
   돌았다. 드문 형태일 수 있다 — 실물 트리에서 확인할 값.
3. **count=1 트리는 전부 다이렉트다**(트렁크 0). 합칠 대상이 없으니 정상이다.

> **이 숫자는 픽스처다.** 실물은 `flg.report()` 의 `형태` 줄이 답한다 — 게임데이터는 콘솔로
> 못 넣으므로 사용자 실행이 필요하다.

## Step 3 — **`createLinks` 하나로** (재설계 2026-08-23 · 개명 반영)

> **원래 서술은 *"판정 하나로 — `canShareLine` 을 둘이 부른다"* 였다. 실측이 그것으로는 부족함을
> 보였다.** 외부 줄의 결함은 *조건을 안 보는 것*이 아니라 **능력이 없는 것**이다 — 술어를
> 공유해도 안 고쳐진다. 아래 §3.1 이 그 증거다.

### 3.1 실측 — 같은 상황에서 한쪽만 할 줄 안다

```
내부 붓기   자식 1대 → 부모 1대, 20/s, 벨트 15/s, 좌석 3×4.6=13.8/s
            → 13.8/s + 6.2/s  두 줄.  **한 머신을 두 줄에 걸쳐 쪼갠다**

외부 조립   머신 1대, 수요 40/s, 벨트 15/s
            → 40/s  한 줄. 팔 9개.   **쪼갤 줄 모른다 → 벨트가 15/s 라 그 머신은 굶는다**
            (머신이 4대면 머신을 나눠 담아 4줄로 쪼갠다. 1대면 나눌 것이 없다)
```

외부 조립의 루프는 *"머신을 줄에 순서대로 담다가 넘치면 새 줄"* 이다. **머신이 낟알**이라
머신 하나보다 작게는 못 쪼갠다. 내부 붓기는 낟알이 **흐름의 조각**이라 쪼갠다.
술어(`canShareLine`)를 공유해도 낟알이 그대로면 이 차이는 남는다.

### 3.2 그래서 **만드는 곳을 하나로** 한다 — `createLinks` ✅**추출 완료**(2026-08-23)

`Link`(= 벨트 줄) 를 만드는 함수는 **하나**여야 한다. 그것이 곧 [[link table]] 의 행을 만드는 일이다.

```
createLinks(흐름 목록, 상한) → Link[]                 ← 두 곳이 **이것만** 부른다
  열기   티어를 골라 줄 하나를 연다             determineBeltCount
  얹기   이 흐름 조각을 이 줄에 실어도 되나      벨트 처리량 ∧ 양끝 좌석(faceSeatArms)
  읽기   그 줄이 무엇이 됐나                    beltLineForm · spansAllMachines  ← 이미 있다
```

> **"두 생산자가 함께 쌓는다"는 표현은 버렸다**(2026-08-23 사장님 지적). 합치고 나면
> **`Link` 를 만드는 곳은 하나**이고, 남는 차이는 *"흐름을 어디서 얻나"* 뿐이다.
> 그건 층이 달라서 생기는 정당한 차이다 — 안쪽 흐름은 자식·부모를 **둘 다** 봐야 나오고
> (`planner/link`), 바깥 흐름은 자기 모듈만 보면 나온다(`module/`).

**양쪽 끝이 `undefined` 일 수 있다는 것이 통합의 열쇠다.** [LinkCarry] 가 이미 그렇게 생겼다
(`from?`·`to?`, 빈 쪽 = 모듈 밖). 그래서 외부 줄은 *"한쪽 끝이 밖인 흐름"* 으로 그대로 표현된다
— 밖에는 좌석이 없으니 그 끝의 상한만 안 건다. **새 개념을 안 만든다.**

| 생산자 | 흐름을 어디서 얻나 | 양끝 |
|---|---|---|
| `edgeLinkGroups`(내부) | [allocateFlows] | 자식 머신 ↔ 부모 머신 |
| `externalLineGroups`(외부) | 머신마다 `총량 ÷ 대수` | 머신 ↔ **밖** |

### 3.3 자리

`createLinks` 는 **`module/link.ts`** 에 둔다 — 로컬 머신 index 와 상한만 보므로
폴더 축(*module 은 형제를 모른다*)을 통과하고, 벨트 줄의 타입·판독이 이미 그 파일에 있다.
`planner/link/edgeLinks` 는 흐름을 **계산해서**(두 클러스터를 봐야 하므로 planner) 넘긴다.
새 import 간선은 `edgeLinks → link` 하나이고 역방향이 없어 순환이 아니다.

### 3.3″ 착수 후 (2026-08-23 실측) — **주 합격선 달성**

| 시나리오 | 줄 수 | **과적재** | **못깐줄** |
|---|---|---|---|
| A 다이렉트 1.5/s | 3 → 3 | 0 → 0 | 0 → 0 |
| B 트렁크 6/s(부모 6대) | 3 → 3 | 0 → 0 | 0 → 0 |
| C 20/s | 4 → 7 | **2 → 0** | **2 → 1** |
| D 100/s · 부모 6대 | 19 → 39 | **7 → 0** | 14 → **21** |
| E realTree | 9 → 9 | 0 → 0 | 0 → 0 |
| 실현 가능 5종(머신당 8~12/s) | — | **0** | **0** |

**과적재는 전 시나리오 0이 됐다.** 이제 깔린 줄은 전부 실제로 나를 수 있다.

**D 의 못깐줄이 늘어난 것은 회귀가 아니라 정직해진 것이다.** D 는 자식 **한 대**가 원료
200/s 를 받아야 하는 입력인데, 그러려면 팔이 `200 ÷ 4.6 = 44개` 필요하고 3×3 머신의 면
칸은 최대 12개다 — **물리적으로 불가능**하다. 전에는 그걸 한 줄에 우겨넣고 *"깔았다"* 고
셌을 뿐이다(그 줄이 과적재 7에 있었다). **거짓 성공이 정직한 실패로 바뀌었다.**
머신당 몫이 물리 한계(면 3칸 × 4.6 = 13.8/s) 안에 드는 5종은 전부 `0 · 0` 이다.

C 는 **부모 모듈이 완전히 해결**됐다(못깐줄 1 → 0, 포트 4개). 남은 1건은 자식의 원료
40/s(팔 9개)로, 역시 물리 한계에 가깝다.

### 3.4 바뀌는 동작 — 예측과 합격선

| 바뀌는 것 | 왜 |
|---|---|
| 외부 줄이 **좌석 상한**을 본다 | 지금은 안 본다 |
| 외부 줄이 **머신 하나를 여러 줄에 걸쳐** 쪼갠다 | 지금은 머신이 낟알이라 못 쪼갠다 |
| 그래서 **줄이 늘 수 있다** | 늦은 실패(자리 못 찾음·굶음)를 **먼저 나누기**로 바꾼 결과 |

**합격선은 "산출물 불변"이 아니다.** 미완성 기준선을 재는 것이라 아무것도 증명 못 한다.
계측으로 잰다:

```
과적재 줄(실은양 > 그 줄의 벨트 처리량)     > 0  →  0      ← 이게 **주 합격선**
linkMismatches · unroutedLines               늘지 않는다
벨트 줄 수                                   늘 수 있다 — 이용률로 낭비가 아님을 확인
```

> **Step 3.0 — 계측 보강 ✅완료(2026-08-23).** 아래는 그 결정의 기록이다. 지금 계수기는 이용률을 **합계**로만 낸다
> (glass 꼴에서 133% 가 나왔지만 *어느 줄이* 넘쳤는지는 못 말한다). `overloaded`(과적재 줄 수)를
> 한 칸 더한다. **바꾸기 전의 값을 먼저 기록**해야 합격선이 의미를 갖는다.

### 3.5 하지 않는 것

- **표를 판정의 *기준*으로 삼지 않는다.** 표는 판정이 **쌓는 대상**이지 판정의 입력이 아니다.
  판정에 필요한 것 중 표에 **없는** 것이 있다(면·인접·이미 찬 좌석) — 그건 배정(③④)의 자원이고
  거기 남는다. 표의 열을 판정의 입력 목록으로 읽기 시작하면 배정이 붓기로 새어 든다.
- **`supply.mode` 는 안 건드린다**(Step 4, 관문 대기). `perMachine` 은 여전히 낟알을 고르고,
  다만 그 낟알이 이제 **같은 붓기**를 탄다.

## Step 4 — 모듈 전체 비트 제거 (관문 대기)

Step 3 이 서면 `supply.mode` 는 형태에 쓸 일이 없어진다(줄마다 조건이 있으므로).
다만 그 비트가 지금 막고 있는 실패는 **레인 부족**이라, 없애면 그 실패가 다른 얼굴로 나온다.
처방은 [트렁크벨트-경로모델](../트렁크벨트-경로모델/트렁크벨트-경로모델.md) 이 낸다 —
[배선-형태 Step 5](../배선-형태/CLAUDE.md) 그 자체다.
