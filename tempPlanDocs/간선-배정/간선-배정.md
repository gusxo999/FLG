# 간선 단위 배정 — 링크의 **양끝을 한 자리에서** 정한다

> 상태·읽을 것·범위는 같은 폴더의 `CLAUDE.md`.
> 배경 사실은 옆의 셋: `조사-되먹임.md` · `조사-짝.md` · `조사-순서.md`.

## §0 두 낱말의 정의

### 「간선」 = 자식 노드 → 부모 노드 하나

레시피 트리의 변 하나다. 간선 하나가 **품목 하나**를 나르고, 양이 벨트 한 줄을 넘으면
**그룹(= `Link` = 벨트 한 줄)이 여럿** 난다. 간선의 신원은 `linkId` 가 든다
(`자식id→부모id:품목#순번`).

### 「간선 단위 배정」 = **루프의 축을 모듈에서 간선으로 바꾼 배정**

```
지금 (모듈 단위)
  for 모듈 M:
      gen(M) 안에서 planModulePorts(M):
          allocateLinkFaces(M의 표, M의 출력링크, side="from", "W")
          allocateLinkFaces(M의 표, M의 입력링크, side="to",   "E")
  → 링크 L 하나가 **두 번, 서로 모르게** 배정된다
    (자식 C 가 gen 될 때 L.from 을, 부모 P 가 gen 될 때 L.to 를)

바꾼 뒤 (간선 단위)
  tables: Map<모듈id, Map<면, FaceTable>>          ← 표는 여전히 **모듈마다**
  for 간선 e(자식 C → 부모 P)  — 정해진 순서로:
      for 그룹 g in e:
          C의 표에 side="from",  P의 표에 side="to"  를 **함께 시도**
          둘 다 되면 확정 · 한쪽이라도 안 되면 그 자리에서 처방
  → 링크 L 의 **양끝이 한 번의 결정**으로 정해진다
```

**바뀌는 것은 루프의 축 하나다.** 좌석표는 그대로 모듈마다다 — 한 모듈의 면은 여러
간선이 나눠 쓰기 때문이다(부모는 자식 여럿에게서 받는다). `tryLinkFace`·`commitLinkFace`·
`FaceTable` 은 손대지 않는다.

### 이 배정이 갖는 성질 넷

```
① 원자성    한 링크는 양끝이 다 앉거나 둘 다 안 앉는다        (반쪽 배정이 없다)
② 국소성    처방(쪼갬·다른 면)을 **그 자리에서** 낸다          (밖에서 고쳐 다시 만들지 않는다)
③ 순서      간선·그룹 순회 순서가 **명시적 루프**가 된다        (지금은 붓기의 부산물)
④ 무좌표    양끝을 보므로 끝(N/S)을 **형제 순서**로 정할 수 있다 (좌표가 필요 없다)
```

## §1 왜 이 축인가 — **오늘의 문제 셋이 전부 같은 뿌리다**

`Link` 는 **두 모듈에 걸친 객체**인데, 자식은 `group.from` 만·부모는 `group.to` 만 본다.
같은 객체를 **두 모듈이 서로 모르게** 읽는다. 그래서 셋이 불가능해졌고, 지금 코드는
그 셋을 **밖에서 우회**하고 있다:

| 불가능한 것 | 지금의 우회로 | 대가 |
|---|---|---|
| **쪼갬** — 한쪽이 쪼개면 반대쪽이 모른다 | `modulePacking` 이 밖에서 `linkCache` 를 고치고 **전부 다시 만든다** | **되먹임 B** |
| **끝 맞추기** — 자식은 부모의 끝을 모른다 | `lineEnds` 를 tidy-tree **뒤에** 만들어 다시 넣는다 | **되먹임 A** |
| **순서** — 누가 먼저 앉나 | 붓기가 낸 배열 순서를 그대로 쓴다 | **못**(`span-blocked`) |

> **판단:** *"자기 모듈만 본다"* 는 **좌표**에 대한 규율이어야지 **링크**에 대한 규율이면
> 안 된다. 모듈을 위치 독립적인 단위로 두는 것은 지금도 옳다 — 좌표는 여전히 안 본다.

## §2 목표 상태

```
지금                                          목표
─────────────────────────────────────────────────────────────────────
P0   linkCache 조립                           P0   linkCache 조립
                                              P0b  **간선 단위 배정 (트리 전체)**
P1   gen ×N   ← 높이 재려고                          ├ 양끝 동시 확정
P1b  사다리 — linkCache 사후 변형                    ├ 못이 있으면 **여기서** 쪼갠다
P1′  gen ×N   ← 쪼갠 것으로 다시                     └ 끝(N/S)은 형제 순서로
P2   tidy-tree                                P1   **gen ×N — 한 번** (배정을 받아 방출만)
P3   lineEnds ← tidy-tree                     P2   tidy-tree
P4   gen ×N   ← 끝 선호 반영                   ─    (P3 · P4 없음)
P5~  채널 · 좌표 · 납품                        P5~  그대로

gen 3회 · 되먹임 2                             gen **1회** · 되먹임 **0**
```

## §3 단계 — 여섯. **각 단계가 무엇을 없애는지로 끊는다**

| | 단계 | 동작 | `gen` | 되먹임 |
|---|---|---|---|---|
| 1 | **배정을 `gen` 밖으로** 꺼낸다 | 무변경 | 3 | 2 |
| 2 | **루프 축을 간선으로** — 양끝 동시 확정 | 변경(순서) | 3 | 2 |
| 3 | **쪼갬을 배정 안에서** 한다 | 변경 | **2** | **1** |
| 4 | **끝을 배정 안에서** 정한다(교차 회피) | 변경 | 2 | 1 |
| 5 | **트렁크 끝**을 앞으로 → 2차 생성 제거 | 변경 | **1** | **0** |
| 6 | **배정 순서 규칙** — 못을 줄인다 | 변경 | 1 | 0 |

**1~2 는 구조, 3~5 는 되먹임 제거, 6 은 품질이다.** 되먹임을 지금 다루기로 했으므로
**5까지가 이 계획의 본체**이고, 6은 그 위에서 값을 더한다.

---

### Step 1 — 배정을 `gen` 밖으로 꺼낸다 (**동작 무변경**)

**목적:** 배정이 **독립 단계**가 되게 한다. 지금은 `gen` 안에 갇혀 있어서, 배정 결과를
보려면 방출까지 해야 하고 배정을 고치려면 밖에서 입력을 고쳐 다시 만들어야 한다.

`planModulePorts` 는 이미 순수 함수다(`clusterModule.ts:260`). ①(링크 면 배정)만
`modulePacking` 의 `P0b` 로 올리고, `planModulePorts` 는 그 결과를 **인자로 받는다.**

```
전제:  ① → ③ 의 전달이 좁다 — `seatRowsUsed`(면당 숫자 하나)뿐이다
       → 확인: planModulePorts.ts:287 · clusterPortPlanner.ts:220. 확인함(2026-08-29)
전제:  ①이 필요로 하는 입력이 P0 에 다 있다(machine · count · inserters · pipeFaces · links)
       → 확인: ModulePortPlannerInput 의 필드가 toModuleInput 에서 오는지
불변:  **산출이 같다** — 기전: 같은 함수를 같은 입력으로 **같은 순서로** 부른다.
       루프 축은 아직 모듈이다
관문:  배정이 `gen` 밖에서 산다
```

### Step 2 — 루프 축을 간선으로 (**양끝 동시 확정**)

**목적:** 링크의 두 끝을 **한 결정**으로 만든다. 3·4가 여기 기대고, 여기 없이는 둘 다 불가능하다.

```
tables: Map<모듈id, Map<PortFace, FaceTable>>     ← 트리 전체가 한 장부
for 간선 e(C → P):
    for 그룹 g in linkCache.get(C):
        candC = tryLinkFace(C의 ctx, g, "from", "W")
        candP = tryLinkFace(P의 ctx, g, "to",   "E")
        if (candC && candP) { commit 둘 다 }
        else                { 처방 — 지금은 정직 실패(3에서 쪼갬이 들어온다) }
```

```
전제:  한 모듈의 표를 여러 간선이 나눠 쓰는 것이 문제없다
       → 확인: 지금도 한 면에 여러 그룹이 앉는다(행이 안 겹치면 레인 공유)
전제:  넘침(spill)·유체 면 회피가 이 축에서도 성립한다
       → 확인: spill 은 `deferred` 만 보므로 축과 무관. 착수 시 재확인
불변:  **원자성이 생긴다** — 한쪽만 앉은 링크가 0이다
       → 기전: commit 을 둘 다 성공한 뒤에만 부른다. 계측으로 0을 확인
관문:  양끝을 함께 보는 배정
```

> **여기서 동작이 바뀐다**(순서가 달라진다). 그래서 1과 2를 갈랐다 — 1이 깨지면 전달 문제,
> 2가 깨지면 축 문제다.

### Step 3 — 쪼갬을 배정 안에서 (**되먹임 B 제거**)

**목적:** `linkCache` 를 **밖에서 고치고 다시 만드는** 구조를 없앤다.

양끝을 쥐고 있으므로 그 자리에서 `resolveSpanBlock` → `splitLinkAtRows` 를 부르고,
난 토막을 **같은 루프 안에서** 다시 앉힌다. `linkCache` 갱신은 여전히 필요하다
(`pairDeliveryPorts` 가 `linkId` 로 조회하므로) — 그러나 **`gen` 이 아직 한 번도 안 돌았으므로
재생성이 없다.** 그게 고리가 사라지는 지점이다.

```
전제:  resolveSpanBlock · splitLinkAtRows 를 **손대지 않는다** — 부르는 자리만 옮긴다
       → 확인: 두 함수가 표를 안 읽고 행 목록만 받는다. 확인함(2026-08-29)
전제:  쪼갠 토막을 다시 앉히는 것이 유한하다
       → 확인: 못은 레인 수만큼에서 멈춘다(machine-link.md — *왜 무한히 안 도나*)
불변:  `gen` 호출이 **3 → 2** 로 준다
       → 기전: `modulePacking.ts:482` 의 재생성 자리가 사라진다
관문:  **되먹임 B**
```

### Step 4 — 끝을 배정 안에서 (**교차 회피**)

**목적:** 관통 링크의 포트가 짝과 **교차하는** 끝에 서는 것을 막는다. 좌표 없이.

배정이 양끝을 보므로 형제 순서만으로 단조 배정한다 — **앞선 형제가 N, 뒤인 형제가 S.**
왜 거리가 아니라 교차인지는 `조사-짝.md` §2.

```
전제:  layoutY 가 kids 를 배열 순서대로 위 → 아래로 놓는다
       → 확인: modulePacking.ts:489-501. 확인함(2026-08-29)
전제:  가운데 자식은 트리로 판정 불가 → `undefined`(오늘처럼 선착순)
불변:  형제가 하나뿐이면 오늘과 같다 — 기전: 단조 규칙이 항등이 된다
관문:  **짝을 보는 끝**
```

### Step 5 — 트렁크 끝을 앞으로 → **2차 생성 제거** (**되먹임 A 제거**)

**목적:** `gen` 을 **한 번**으로 만든다. 4는 링크 절반만 연다 — `lineEnds` 는 유체 트렁크
줄에도 살아 있어(`조사-짝.md` §0 마지막) 그게 남으면 `gen` 이 두 번 돈다.

```
전제:  lineEnds 소비처가 emitTrunkPipe · emitTapInserting · meta 셋뿐이다
       → 확인: 착수 시 재검색
전제:  링크가 난 품목의 lineEnds 는 이미 죽어 있다(linkedKeys 로 restLines 에서 빠짐)
       → 확인: 실물 트리에서 그 항목이 소비되는지 계측
불변:  `gen` 호출이 **2 → 1**, 되먹임 **0**
       → 기전: `modulePacking.ts:597` 의 두 번째 호출이 사라진다
관문:  **되먹임 A**
```

### Step 6 — 배정 순서 규칙 (**못을 줄인다**)

**목적:** 못이 애초에 안 생기게 한다 → 3의 쪼갬이 거의 안 돈다.
자유도 낮은 줄(관통 → 긴 구간 → 팔 많은)을 먼저. 근거와 실측은 `조사-순서.md`.

```
전제:  관통 줄이 실물 트리에 실제로 있다 → 확인: 트리마다 spansAllMachines 인 그룹 수
불변:  정렬이 항등일 때(그룹 하나뿐인 면) 오늘과 같다 — 기전: order 가 [0] 이다
관문:  **못이 안 생기는 배정**
```

## §4 푸는 문제 · 안 푸는 것

### 푼다

| 문제 | 끝난 뒤 |
|---|---|
| **되먹임 A·B** | **0** — `gen` 1회 |
| **쪼갬이 링크를 사후 변형** | 배정 안에서 원자적으로 |
| **끝이 짝을 안 본다** | 형제 순서로 교차 회피 |
| **배정 순서가 붓기의 부산물** | 명시적 규칙 |
| **반쪽 배정**(한쪽만 앉은 링크) | 원자성으로 구조적 불가 |

### 안 푼다

| 남는 것 | 누구 몫 |
|---|---|
| 가운데 자식의 끝 | 트리로 판정 불가. `undefined` 로 둔다 |
| 거리(짧은 납품 경로) | 좌표가 필요 → 고리를 부른다. 교차만 본다 |
| `seat-blocked` · `seat-budget` | 사다리 2·3단(gap · 다이렉트) |
| `port-blocked` | `resolveSpanBlock` 의 미구현분 |
| **형제 y 순서** = 레시피 재료 순서 | 아래 *여는 문 ①* |
| `insertingPlanner` 통합 | `module-planning.md` §5 의 남는 비대칭 |

## §5 여는 문

```
① 형제 순서를 **정하는** 계획
   이 계획이 "형제 순서가 끝을 정한다" 로 만들면 그 순서가 지렛대가 된다.
   그런데 지금 그 순서는 **레시피의 재료 나열 순서**다
   (order = DFS pre-order → childIdsByParent → layoutY). 아무도 고른 적이 없다.

② **방출은 덧셈만** — R1 이 구조로 성립
   `gen` 이 한 번이면 "계획이 정한 것을 방출이 그대로 놓는다" 에 다시 돌 자리가 없다.
   그다음 과녁은 `emitModule` 의 여섯 `unroutedLines` — **방출이 줄을 떨어뜨리는** 자리다
   (그게 없어지면 extent 가 계획의 함수가 되고, 계획만으로 높이를 유도할 수 있게 된다).

③ 사다리 코드를 **지운다**
   Step 6 뒤 못이 구조적으로 안 생긴다면 resolveSpanBlock · splitLinkAtRows 가 통째로
   사라진다. **단, "0을 봤다"는 "0이 구조적이다"가 아니다** — 어떤 입력이면 다시
   생기는지 답할 수 있어야 지운다.
```
