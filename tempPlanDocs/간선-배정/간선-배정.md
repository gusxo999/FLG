## §0 낱말 — 범위를 여기서 못박는다

### 형태 셋 — 이 계획이 다루는 축

머신마다 필요한 벨트 용량이 다르고, 그 비율이 **형태**를 정한다:

| 형태 | 뜻 | 코드의 판독 |
|---|---|---|
| **fan-out** | 한 **머신**에 벨트가 여럿 | `fanOutMax > 1` (summarizeBeltForms) |
| **다이렉트** | 벨트 하나가 머신 하나만 | 양쪽 다 `machinesOn <= 1` |
| **트렁크** | 벨트 하나가 머신 여럿 | 한쪽이라도 `machinesOn > 1` |
| *(트렁크의 극단)* **관통** | 그 끝의 머신을 **전부** 만진다 | `spansAllMachines` |

> **fan-out 은 이 계획 밖이다**(2026-08-29 확정). 그건 *"어느 자식이 어느 부모를 얼마나
> 먹이나"* 의 문제이고 `allocateFlows` → `createLinks` 가 **줄이 나기 전에** 정한다.
> 이 계획은 **줄이 난 뒤 어디에 앉히나**만 본다 — 축은 **트렁크 ↔ 다이렉트**다.

### 「쪼갬」이 둘이다 — 섞으면 안 된다

| | 함수 | **무엇이 강제하나** | 언제 |
|---|---|---|---|
| **붓기** | `createLinks` | **양** — 벨트 용량이 넘치면 줄을 늘린다 | `P0`, 배정 전 |
| **쪼개기** | `splitLinkAtRows` | **자리** — 남의 포트에 막혀 토막낸다 | 배정 중 |

*"90/s 벨트로 25/s 머신 셋을 맡는다"* 는 **붓기**다. 이 계획이 손대는 것은 **쪼개기**이고,
그건 **한 면에 흐름이 둘 이상일 때만** 일어난다(막는 칸이 곧 남의 그룹 것이므로).

### 「간선」과 「간선 단위 배정」

**간선** = 자식 노드 → 부모 노드 하나. 품목 하나를 나르고, 양이 벨트 한 줄을 넘으면
**그룹(= Link = 벨트 한 줄)이 여럿** 난다. 신원은 `linkId`.

```
옛 축 (모듈 단위)
  for 모듈 M:  M 의 출력링크를 M 의 표에 · M 의 입력링크를 M 의 표에
  → 링크 L 하나가 **두 번, 서로 모르게** 배정된다

새 축 (간선 단위)
  tables: Map<모듈id, Map<면, FaceTable>>          ← 표는 여전히 **모듈마다**
  for 간선 e(자식 C → 부모 P):  for 그룹 g in e:
      C 의 표에 side="from",  P 의 표에 side="to"  를 **함께**
  → 링크 L 의 **양끝이 한 번의 결정**으로 정해진다
```

성질 넷: **원자성**(반쪽 배정 없음) · **국소성**(처방을 제자리에서) · **순서**(명시적 루프) ·
**무좌표**(양끝을 보므로 끝을 형제 순서로).

## §2 못은 어떻게 생기나 — **얕은 그룹의 포트가 깊은 레인을 찍는다**

배정이 청구하는 칸은 셋이다: **좌석(d1)** · **벨트 구간(레인 d)** · **포트 칸 둘**.
그리고 포트 칸의 자리가 갈린다(`portCells`):

```
옆 포트  (관통 아님)   → (topT, d+1) · (topT, d+2)     ← **더 깊은 레인을 먹는다**
기둥 끝  (관통)        → (topT∓1, d) · (topT∓2, d)     ← 기둥 밖이면 표에서 걸러진다
```

그래서 **얕은 레인 그룹의 옆 포트가 곧 깊은 레인의 못**이다.

```
d2 ▓▓▓▓ 구간A     d2 ▓▓▓▓ 구간B     d2 ▓▓▓▓ 구간C
d3    ◄ 못           d3    ◄ 못           d3    ◄ 못
        ↑ 이 세 칸이 d3 을 지나려는 **관통 흐름**을 막는다
```

**전제는 "관통이 깊다"이다.** electronic-circuit 이 정확히 그 꼴이었다 —
copper-cable(구간 4토막)이 먼저 d2 를 먹고, stone-tablet(관통 90대)이 d3 로 밀려 못에 걸렸다.

## §3 그래서 규칙 — **긴 흐름이 얕은 레인에** (2026-08-29 확정)

> **한 면에서, 담당 머신 수가 많은 흐름부터 얕은 레인을 갖는다.**

기하적 이유는 하나다 — **얕은 쪽 포트가 깊은 쪽을 건너야 하고, 관통 레인은 어떤 행에서도
못 건넌다**(`spansAllMachines` 주석). 그러니 건널 수 없는 것(관통)을 **위에** 두면 안 된다.

레인이 둘(`d2`·`d3`)인 지금 스펙에서 규칙이 서면:

```
관통 흐름 → d2.  포트가 **기둥 끝**으로 나가 표에 칸을 (거의) 안 잡는다
구간 흐름 → d3.  포트가 d4·d5 — **레인 목록 밖**이라 아무와도 안 다툰다
                 → 못이 찍힐 자리가 없다
```

**즉 규칙이 `span-blocked` 를 (거의) 없앤다.** *(거의 — 관통이 첫 좌석을 못 잡으면 topT 가
밀려 포트가 표 안으로 두 칸 들어온다.)*

### 어떻게 넣나 — **새 기전이 아니라 순서다**

`tryLinkFace` 의 레인 후보 정렬은 이미 *"팔 적은 순 → 얕은 순"* 이고, 얕은 레인은 짧은 팔
(빠른 인서터)이라 팔이 적다. **그래서 먼저 온 그룹이 얕은 레인을 갖는다.** 규칙은 그 앞에
정렬 하나를 두면 성립한다:

```
배정 순서 = 담당 머신 수 내림차순      ← 새로 정하는 것
레인 선택 = 지금 그대로(팔 적은 순 → 얕은 순)
```

| | 물음 | 후보 | 지금 기울기 |
|---|---|---|---|

### 확인된 사실 (합의됨 — 더 조사할 것 없음)

```
· 쪼개기는 **한 면에 흐름이 둘 이상일 때만** 일어난다
· 지금 쪼개기는 **운반량을 안 본다** — 토막이 원본 티어를 그대로 든다(...group 스프레드)
· 지금 쪼개기의 전제("관통이 깊다")는 **순서 규칙으로 깨진다**
· 옛 사다리는 언제나 "to" 로 잘라 **남의 자로 남의 축을 잘랐다** → Step 3 이 고쳤다
· 토막의 from/to 팔 수가 낡는다 — 오늘은 읽는 곳이 없다(carries 가 단일 출처)
· 붓기(양)와 쪼개기(자리)가 **줄 수를 따로 정한다** — 두 원칙이 충돌한다
  (*"쪼갬은 양이 강제할 때만"* 인데 쪼개기는 자리를 이유로 줄을 늘린다)
```

## §8 부록 — **높이를 계획만으로 유도하지 않는 이유**

### `extent`(모듈이 먹는 땅)가 무엇인가

```
        ←─────── w ───────→
      ┌───────────────────┐
   ↑  │      ▓▓▓▓▓▓       │   ▓ 벨트    ● 좌석 인서터
   │  │  ┌────┐           │   ◄ 포트(인서터+상자)   ═ 파이프
   h  │  │머신│ ● ▓   ◄   │
   │  │  └────┘           │   머신은 기둥 가운데 있고, 벨트·인서터·상자·파이프가
   ↓  │      ▓▓▓▓▓▓       │   **밖으로 삐져나온다**
      └───────────────────┘
        extent = 그 **전부를 감싸는 최소 사각형**
```

`moduleExtent(mod)` = 머신 bbox ∪ 놓인 셀 전부. 쓰이는 곳은 하나 — **tidy-tree 가 세로로
쌓을 때의 높이**. 틀리면 모듈이 겹치거나 땅을 버린다.

### ① 이득이 **0** 이다 — 고리를 없애면 gen 은 어차피 한 번이다

```
고리가 있는 지금   gen ─→ 높이 ─→ tidy-tree ─→ lineEnds ─→ gen      gen 2회
   유도가 있으면    유도 ─→ 높이 ─→ tidy-tree ─→ lineEnds ─→ gen    gen 1회  ← 하나 아낀다

고리를 없앤 뒤     gen ─→ 높이 ─→ tidy-tree ─→ 끝                   gen 1회
   유도가 있으면    유도 ─→ 높이 ─→ tidy-tree ─→ gen                 gen 1회  ← 같다
```

gen 은 **모듈-로컬 좌표**로 놓으므로 tidy-tree 앞에 와도 된다(tidy-tree 는 재고 옮길 뿐).
**유도의 값은 "gen 한 번 아끼기" 하나였고, 고리를 없애면 아낄 gen 이 없다.**

### ② 지금은 계획이 extent 를 **정하지도 못한다**

방출은 못 놓은 줄을 **떨어뜨린다**(`unroutedLines`). 여섯 자리 중 **넷**이 계획이 모르는 것
(`occupancy` — 방출이 놓으면서 채우는 집합)을 보고 판단한다:

| 자리 | 무엇을 보고 | 계획이 아나 |
|---|---|---|
| `:190` `:360` | `plan === undefined` | **안다** ✔ |
| `:286` `:394` `:439` `:608` | `occupancy` — 먼저 놓인 것이 나중 것을 막는다 | **모른다** ✘ |

유도하려면 그 넷을 계획으로 올려야 한다 — **§7 여는 문 ②** 가 그것이다.

### ③ 「두 번째 기하 모델」 — **실패 경로 얘기가 아니다**

> **같은 사실(모듈이 먹는 땅)을 두 코드가 각자 계산하면 어긋난다.**

```
방출  실제로 셀을 놓으면서 안다                  ← 진실
유도  계획을 보고 "이만큼 나갈 것이다" 라고 센다   ← 두 번째 답
```

둘이 다르면 **아무도 안 알려준다.** 타입도 테스트도 통과하고, 틀린 높이는 tidy-tree(겹침·
낭비) → 채널 폭까지 조용히 번진다(R3). **먼저 방출을 덧셈만 하게 만들고, 그다음에 유도한다.**
