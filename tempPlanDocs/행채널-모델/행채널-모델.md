# 행 채널 모델 — 가로 통로에 계획을 준다

## 0. 한 줄 요약

**[[용어사전#행 채널 (row channel)|행 채널]]** = 세로로 쌓인 두 모듈 **사이의 가로 띠**.
[[용어사전#채널 (channel)|채널]]을 90° 돌린 직교 짝으로 **2026-07-11 부터 이름이 있었으나
계획 모델이 없다.** 폭은 `STACK_GAP = 3` 으로 우연히 생기고 아무도 예약하지 않는다.

이 계획은 그 띠에 **트랙·폭 역전·도형**을 준다. 그리고 두 통로가 만나는
**환승(transfer)** 을 정의한다.

---

## 1. 문제 — 셋이 한 뿌리다

### 1.1 관측된 증상

```
① no free track in channel  × 6건
   반출이 **세로 채널의 트랙**을 두고 납품과 경쟁한다.
   원래 반출은 가로로 나가야 하는데 갈 띠가 없어 세로 채널로 몰린다

② planned = 0
   기둥 끝 포트끼리의 납품이 그릴 도형이 없다.
   계단꼴은 "포트가 채널 벽을 마주 본다" 를 전제한다([[layout-models]] §2③)

③ "블루프린트를 거의 관통하는 가로 벨트" 를 못 만든다 (사용자 요구)
```

**용어사전이 ①을 이미 예언해 놨다** — *"납품 경로가 이 띠를 가로막으면 상자가 perimeter 로
못 빠져나가는 **skip 의 무대**"*.

### 1.1.1 실험 셋 — **행 채널이 필요한지 실측으로 갈랐다** (2026-08-18)

`planned = 0` 이 **통로 문제인지 도형 문제인지**를 가르려고 `wrapAround` 도형을 세 번 바꿔
실측했다(코드 변경은 전부 되돌렸다).

| | 도형 | planned | 막은 것 |
|---|---|---|---|
| 원래 | 가로 먼저 → 세로 | 0 | **모듈 몸통** (12,0)·(12,6) |
| 실험1 | **세로 먼저** → 가로 | 0 | **남의 납품 예약** (17,1)·(17,5) |
| 실험2 | 짧은 세로 → 마진 가로 → 세로 | 0 | **남의 납품 예약** (17,-1) + 모듈 몸통 (17,0) |

**실험1이 결정적이다.** 도형을 바꾸자 *"모듈 관통"* 이 사라지고 **교착**으로 바뀌었다:

```
n1→n0  가 (17,1) 에서 n2 의 예약에 막힘
n2→n0  가 (17,5) 에서 n1 의 예약에 막힘
```

**둘 다 자기 상자 열(x=17)을 세로로 쓰려 한다.** 자식이 같은 깊이에 나란히 있으면 겹친다.

> **그래서 문제가 둘로 갈린다:**
> ① **도형** — 세로 먼저 / 가로 나중이 맞다. 실험으로 확인됐다
> ② **배정** — 그 구간을 어느 열·어느 행에? **없다. 그래서 교착**
>
> ②가 곧 채널이 하는 일이다. `wrapAround` 는 배정 없이 넣은 도형이라 교착한다.

### 1.1.2 그리고 "싼 길"은 반증됐다

*"`elbow` 의 가로 진입을 마진까지 넓히면 행 채널이 필요 없다"* 는 안을 실험2 가 반증했다.
가로 구간을 넓혀도 **여러 경로가 같은 행을 다툰다** — 둘 다 `min(s.y, e.y) - 1` 을 골랐다.

```
필요한 것   세로 구간의 **열 배정**  +  가로 구간의 **행 배정**
            세로 채널이 이미 한다        **행 채널이 해야 한다 — 없다**
```

### 1.1.3 계획서의 그림도 정정한다

```
처음 가정   포트 → 가로 띠(길게) → 환승 → 세로 채널
실측        포트 → **자기 열 세로**(길게) → 마진/띠 가로 → 목적지
                   ^^^^^^^^^^^^^^^ 이 구간도 배정이 없다.  세로 채널 **밖**이다
```

**환승보다 앞 구간이 먼저 문제다.** 기둥 끝 포트에서 나오는 세로 구간은 자식 모듈의
동/서쪽에 있어 세로 채널 장부 밖이고, 어느 장부도 관리하지 않는다. §3(환승) 앞에
**그 구간의 소속**을 정해야 한다 → [judgements.md](judgements.md) `J-진입구간`.

### 1.2 왜 지금인가

2026-08-17 에 관통 포트를 **기둥 끝**으로 보냈다(모듈 안쪽 이득: 면 d7 → d3,
반출 skip 1 → 0, penalty 13 → 8). **기둥 끝 포트는 본질적으로 행 채널을 쓰는 포트**인데
갈 데가 없어 세로 채널로 밀려들었고, 그 결과가 ①②다.

```
모듈 모델이 "어느 면에 포트를 둘까" 를 정하면 **그것이 곧 "어느 통로를 쓸까" 다.**
그런데 module/ 은 형제를 모르므로(설계상 옳다) 통로가 있는지 알 수 없다.
→ **통로가 먼저 있어야 한다.**
```

### 1.3 왜 이름만 있고 구현이 없었나

`행 채널` 은 세로 채널과 **같은 커밋**(`b9deaf4`, 2026-07-11)에서 정의됐다. 그 커밋이 실제로
푼 문제는 *"N/S 면 채널 우회 반출"* 이었고, **가로로 나가야 하는 경로를 세로 채널 안에서
풀었다**(`elbow` = 가로 진입 + 세로 주행 → N/S 변).

> 즉 **행 채널은 "그때 필요했지만 세로 채널로 우회한 것"의 이름**이다.
> 정의는 정확했고(사고까지 맞혔다) 구현만 미뤄졌다.

### 1.4 전제 재감사 — **트리거가 당겨졌다** (2026-09-04)

계획서가 승인 대기로 선 지 보름이 지났고 그 사이 코드가 움직였다(레인 합류 ·
유령 예약 수정 · `linkDepthNeed`). 착수 전 규칙대로 전제를 다시 걸었다.

#### 썩은 전제 하나 — Step 2 의 *"오늘 배치는 한 칸도 안 바뀐다"*

> (Step 2, 2026-08-18) *"통과 경로가 0이라 `channelWidthFromTracks(0, 3) = 3` 이고
> `STACK_GAP` 과 같다"*

**더 이상 0이 아니다.** 실측(2026-09-04, `electronic-circuit` 10/s · 모듈 4):

```
─ 행채널   띠 7개 · **통과 수요 6건**
          d1 marginN y-3..-1 높이 3 → **수요 4**     ← 3칸인데 4칸이 필요하다
          d1 between  y24..30 높이 7 · 트랙 2건
          d1 marginS  y38..40 높이 3 · 트랙 1건
```

그래서 Step 2 의 *"안 한 것"*(폭을 실제로 먹이기)이 **더 미룰 수 없는 것**이 됐다.

#### 그 미룸이 무엇을 열어 두었나 — **띠 밖으로 밀어낼 수 있다**

> **2026-09-04 정정.** 처음엔 *"이미 밀어내고 있다"* 고 적었다. **틀렸다** — 위의
> `높이 3 → 수요 4` 는 `wantHeight = trackCount + 2` 의 **여유 2칸**에서 온 값이고,
> 실제 트랙은 2개라 3칸에 **들어간다.** 넘치려면 한 띠에 트랙이 **4개 이상**이라야 하고,
> 그건 아직 관측되지 않았다. 아래는 **가능성**이지 관측이 아니다.

`wantHeight` 를 읽는 코드가 **보고서 한 줄뿐**이다. 실제 배치는 `STACK_GAP = 3` 이다.
그런데 트랙 번호에는 **상한이 없다**:

```ts
rowChannelEntryById.set(n.id, { row: band.top + t });   // t 가 높이를 넘어도 그대로
```

`marginN` 은 `top = bottom - 2` 라 `t = 3` 이면 `row = bottom + 1` — **모듈 몸통의 첫 행**이다.
그 경로는 `plannedChainClear` 가 `모듈 몸통` 으로 거부하고 탐색으로 떨어진다. 그러면
**사유가 「띠가 좁다」인데 화면에는 「체인이 막혔다」로 나온다.**

> **막을 자리가 없는 것이 문제다.** 안 일어난 일이라도, 일어나면 **다른 이름으로 보고된다.**

#### 새로 참이 된 것 — **소비자가 특정됐다**

계획서 §1.2 는 *"기둥 끝 포트는 본질적으로 행 채널을 쓰는 포트"* 라고 적었지만, 그것이
**유일한** 소비자인지는 열려 있었다. 2026-09-04 에 닫혔다 — 수요를 만드는 코드가 하나뿐이다:

```ts
if (port.face !== "N" && port.face !== "S") continue;   // 기둥 끝 포트만 띠를 지난다
```

W/E 면 포트는 세로 채널 벽을 바로 마주 봐 띠를 안 쓴다. **행 채널의 소비자 = 기둥 끝
포트에 붙는 경로, 그것뿐이다.** 그리고 그 수요는 **늘고 있다** — 레인 합류(`벨트-레인`
㉡)가 합류 쌍마다 기둥 끝을 하나씩 더 요구한다.

#### `J-교차` 의 착수 조건이 **충족됐다**

> (`judgements.md` J-교차) *"착수 조건: 계획서 Step 3 이후, **교차가 실제로 나는지부터
> 센다.** 띠 하나에 경로가 둘뿐이면 VCG 가 자명하다"*

**셌다. 난다.** 계획 체인 둘이 정확히 한 칸에서 겹쳤다:

```
copper-cable#2   포트(19,23) → 배정 행 26 → 트랙 13     가로선이 row 26 을 서진
stone-tablet#0   포트(18,31) → 배정 행 24 → 트랙 14     세로선이 x=18 · y24..31

겹친 칸  (18,26)  — copper 의 **가로선** × stone 의 **세로선**
```

`J-교차` 가 그린 그림 그대로다 — *"가로끼리는 안 부딪힌다. 세로 진입이 부딪힌다."*
그러므로 `J-교차` 는 더 이상 판단이 아니라 **계획서의 단계**다(§4 Step 4 로 승격).

#### 그리고 증상 둘이 이미 화면에 있다

```
[warning] delivery-dijkstra-fallback   계획을 못 쓰고 탐색으로 돌았다
[warning] perimeter-skip               상자가 트랙을 못 받아 모듈 안에 남았다  ×4
```

둘째는 용어사전이 **미리 적어 둔 증상**이다 — *"납품 경로가 이 띠를 가로막으면 상자가
perimeter 로 못 빠져나가는 skip 의 무대"*. 관측이 정의를 따라잡았다.

#### 여전히 참인 전제

| 전제 | 재확인 |
|---|---|
| 세로 채널이 `startY` 의 **출처를 안 가린다**(Step 0) | 참. `seed.startY = fb.row` 로 덮어써도 계단꼴이 그대로 선다 |
| 폭 순환(`topY → 통과 경로 → 폭 → topY`) | 참. 아무도 안 끊었다 |
| `assignTracksLeftEdge` 가 축과 무관 | 참. `planRowChannel` 이 그대로 쓴다 |
| 행 채널이 셀을 안 만든다(불변 1) | 참. `{ row }` 하나만 낸다 |

> **다만 Step 0 의 결론에 각주가 붙는다.** *"세로 채널이 출처를 안 가린다"* 는 이 계획을
> **싸게** 만든 전제인데, 그 무관심이 곧 **진입 다리를 아무도 안 보는 이유**이기도 했다.
> 전제가 틀린 것이 아니라, 그 대가가 이제 보인다 — Step 4 가 그 대가를 치른다.

## 2. 이미 있는 것 — **무엇을 새로 만들 필요가 없나**

> 계획서는 *"무엇을 만든다"* 앞에 *"무엇이 이미 있나"* 를 센다
> (2026-08-16 함정표 ★★★★ — 이 절이 없어 있는 기능을 다시 만들 뻔했다).

| 있는 것 | 어디 | 그래서 |
|---|---|---|
| **구간 겹침 → 최소 트랙** | `channelPlanner.assignTracksLeftEdge` | **축과 무관한 순수 알고리즘.** 그대로 쓴다 |
| 폭 역전 (트랙 수 → 폭) | `channelWidthFromTracks` | 공식이 이미 있다. 가로에 그대로 적용 |
| 도형 → 셀 순서열 | `staircaseCells` · `shapeFromCells` | 전치해 쓴다 |
| 지하 횡단 | `placeWithJumps` · `isJumpAllowed` | 교차 해소 수단. **이미 검증됐다** |
| 막힘 검사 + 사유 | `plannedChainClear` (막은 칸과 정체를 낸다) | 그대로 |
| 진단 | `flg.report()` 의 `planned/dijkstra/사유` | 전후를 **같은 잣대로** 잰다 |
| 띠의 존재 | `STACK_GAP = 3` | 자리는 이미 비어 있다. **예약만 없다** |

**새로 만드는 것은 셋이다: 행 채널의 장부 · 폭 역전 · 환승.**

## 2.5 gap 과 구별한다 — **같은 모양, 다른 자원**

자주 나올 질문이라 먼저 못 박는다.

```
gap (rowGaps)   모듈 **안**.  머신 사이.  `count - 1` 개
                소유자 = 모듈 모델(`planModulePorts` → `layoutCluster`)
                폭 = 그 gap 을 지나는 벨트 **깊이의 합**  ← **이미 폭 역전**(`gapRowsFromPlans`)
                벨트가 가로로 달리다 **W/E 변에서 꺾여** 포트가 된다

행 채널         모듈 **사이**.  스택 경계
                폭 = `STACK_GAP = 3` 상수  ← 폭 역전 **없음**(이 계획이 준다)
                기둥 끝 포트가 달린다 → 환승 → 세로 채널
```

**gap 벨트는 행 채널을 안 쓴다** — 포트가 모듈 옆 변에 서기 때문이다
(`emitModule`: `portFace = isGap ? "W" : face`). 둘은 하류에서 만날 뿐(둘 다 세로 채널로)
서로를 지나지 않는다.

### 행 채널이 gap 을 **통제할 수 없다** — 순서가 반대다

```
gap 폭 → 머신 좌표 → 모듈 extent → colWidth/topY → **모듈 배치** → 행 채널
^^^^^^                                                             ^^^^^^^^
배치보다 **먼저**                                          배치 **뒤**에야 안다
```

`module/CLAUDE.md` 의 *"이 폴더의 코드는 형제 모듈을 모른다"* 와도 맞는다 — gap 을 정할 때
이웃이 어디 있는지 알 수 없고, 알아서도 안 된다.

### 그래서 gap 은 **선례**다

```
gap        수요(벨트 깊이) → 폭      **구현돼 있다**
세로 채널  수요(트랙 수)  → 폭      구현돼 있다
행 채널    ???            → 상수 3  **없다**  ← 이 계획
```

같은 원리가 두 층에 이미 있다. **새 원리를 발명하는 게 아니라 세 번째로 같은 걸 한다.**

### 지켜볼 것 — 이중 계산

두 모듈이 인접하면 실제 빈 띠는 셋이 겹쳐 있다:

```
[위 모듈] … 마지막 머신
          ← 위 모듈이 자기 면 바깥으로 먹은 칸 (기둥 끝 포트 등)
  행 채널 ← STACK_GAP
          ← 아래 모듈이 먹은 칸
[아래 모듈] 첫 머신 …
```

**지금은 셋을 따로 센다.** 2026-08-17 에 기둥 끝 포트가 생기며 위/아래로 먹는 칸이 늘었으므로,
행 채널 폭을 재는 계획이 *"모듈이 이미 먹은 칸"* 을 **이중으로 세지 않도록** 한다
(모듈 extent 는 `moduleExtent` 가 이미 그 칸들을 포함한다 — 거기서부터 재면 안 겹친다).

## 3. 환승 — 이 계획의 진짜 설계 판단

### 3.1 두 통로는 **한 칸**에서 만난다

```
행 채널 R    가로 띠.  트랙 = **행**(y).  경로가 동서로 달린다
세로 채널 C  세로 띠.  트랙 = **열**(x).  경로가 남북으로 달린다

환승 지점 = (C 의 트랙 x,  R 의 트랙 y)   ← **한 칸**
```

### 3.2 그리고 세로 채널은 그 칸을 **이미 표현할 수 있다**

```ts
staircaseShape:  h: [ hseg(d.startY, track, capCol), … ]
                          ^^^^^^^^ "어느 **행**에서 벽으로부터 트랙까지 가로로"
```

세로 채널의 행 좌표는 **절대 y** 다(열만 가상). 그러니 `startY` 가 *포트의 y* 든
*행 채널 트랙의 y* 든 **모델은 구분하지 않는다.**

> **그래서 세로 채널 모델은 거의 안 고쳐도 된다.**
> 바뀌는 것은 *"`startY` 가 어디서 오나"* 하나다 — 포트가 벽을 마주 보면 포트의 행,
> 기둥 끝이면 **행 채널이 배정한 트랙 행**.

이것이 이 계획이 싸질 수 있는 근거이고, **가장 먼저 검증할 전제**다(§4 Step 0).

### 3.3 위험은 하나 — **누가 그 칸을 예약하나**

두 장부가 각자 소유하면 2026-08-17 의 사고가 재현된다(*"주체가 둘로 갈리면 무관한 판정이
이미 끝난 예약을 삼킨다"* — `planner/CLAUDE.md`).

                             넘긴다" 만 말하고 그 뒤는 C 의 일 — **접점이 수 하나**

(나) 행 채널이 소유한다       대칭이지만, C 의 도형(계단꼴)이 그 칸에서 시작하므로

### 3.4 ~~아직 모르는 것~~ → **실측된 것** — 교차 (2026-09-04)

B: 행 t_h^B 로 오다가 열 t_v^B 에서 꺾는다

```

> **2026-09-04: 실제로 났다**(§1.4). 위 조건식이 그대로 성립한 좌표가 `(18,26)` 이다 —

### Step 4 — **세로 진입까지 안 부딪히게** ✅ 완료 (2026-09-04, `J-교차` ⓐ)

`RowCrossing` 에 **`side`**(위 모듈에서 오나 아래에서 오나)를 넣고, 서쪽 끝이 공통일 때
**전순서**로 배정한다:

```
위에서 오는 것이 아래에서 오는 것보다 **언제나 위 행**
  위쪽 무리   동쪽 끝이 가까운 것부터
  아래쪽 무리 동쪽 끝이 먼 것부터 (거울)
```

유도는 `rowChannelPlanner` 머리말에 있다. 요지: A 의 세로선이 `[top, r_A)` 를 먹고 B 의
가로선이 `r_B` 에서 서쪽 끝까지 뻗으므로, `x_A ≤ x_B` 면 `r_B < r_A` 일 때만 만난다 →
`r_A ≤ r_B`. 아래쪽은 부호가 뒤집히고, 섞이면 양쪽 부등식이 **둘 다** *"위쪽이 위"* 로 모인다.

**트랙은 안 는다** — 통과 경로는 전부 서쪽 변까지 달려(`x1: 0`) 구간이 전부 겹치므로,
left-edge 도 어차피 경로마다 트랙 하나를 준다. **바뀌는 것은 개수가 아니라 순서**다.

**그리고 순환이 없다** — 위 규칙이 전순서라 위상정렬이 막힐 데가 없다. `J-교차` 의
ⓑ(dogleg)·ⓒ(지하)는 **필요 없다.** 다만 그 근거는 *"서쪽 끝이 공통"* 하나이므로,
공통이 아니면 코드가 **옛 left-edge 로 정직하게 물러선다**(보장 없이, 오늘 동작 그대로).

```
전제:  통과 경로의 서쪽 끝이 공통이다(`x1: 0`) — 호출부 한 곳이 그렇게 만든다
불변:  트랙 수가 안 는다 = **폭이 안 는다**
       (기전: 서쪽 끝이 공통이면 구간이 전부 겹쳐 left-edge 도 경로마다 하나를 준다)
관문:  **계획 체인끼리 겹치는 칸이 0.** 지금은 겹쳐 놓고 나중에 거부한다
```

**측정:** 띠 안 셀 겹침 0 — 단위 테스트가 경로마다 **가로 + 세로 진입** 칸을 실제로 펴서
쌍마다 대조한다(6테스트, **대조군 포함** — 순서를 뒤집으면 실제로 부딪힌다).

> **확정이 아니라 방향.** Step 5 를 끝낼 때 전제를 다시 확인한다.

경쟁이 풀린다 — 오늘 `perimeter-skip` **4건**이 여기서 사라질 것으로 본다(용어사전이
이 띠를 *"skip 의 무대"* 라고 이미 적어 뒀다).

## 5. 불변 — 기전으로

```
불변 1   행 채널은 **셀을 만들지 않는다** — 트랙 번호와 "넘기는 행" 만 낸다
         → 환승 칸의 소유자가 하나로 유지된다.  주체가 둘이 될 수 없다

불변 2   폭은 배정 결과에서 나온다 (STACK_GAP 상수 소멸)
         → `rg "STACK_GAP"` 이 0 이면 상수 경로가 안 남았다는 뜻

불변 3   세로 채널의 도형이 안 바뀐다
         → `staircaseShape`·`elbowShape`·`sameSideOfCut` 의 diff 가 0
```

> **"산출물이 안 바뀐다" 를 불변으로 쓰지 않는다.** 이 계획은 배치를 바꾼다 —
> 띠 폭이 상수에서 수요 유도로 바뀌면 모듈 세로 간격이 달라진다.

## 6. 검증 — 착수 전에 정한다

> **기준선을 2026-09-04 로 다시 잡았다.** 옛 기준(`planned > 0 (오늘 0)` ·
> `no free track 6건`)은 그 사이 계획 체인이 서면서 낡았다.

```
기준선(2026-09-04, electronic-circuit 10/s · 모듈 4 · 레인 합류 ON)
            납품       planned 3 / dijkstra 2 / 실패 0
            행채널     띠 7개 · 통과 수요 6건 · 넘치는 띠 **0**(트랙 2 · 높이 3)
            경고       delivery-dijkstra-fallback · perimeter-skip 4건
            계획 겹침   **1건** (18,26)

성공 기준   Step 3 ✅ 모자람이 **자기 이름으로** 보고된다 (`row-channel-short`)
            Step 4 ✅ 띠 안 셀 겹침 = **0** (단위 테스트 · 대조군 포함)
            남은 것  실물에서 `delivery-dijkstra-fallback` 이 실제로 주는지

> 이 계획이 푸는 문제가 화면에서 줄어든다. 끈 실행은 **대조군**으로만 쓴다.

> 전부 움직인다. 비교는 **같은 커밋 안에서 켜고 끄며** 한다.
