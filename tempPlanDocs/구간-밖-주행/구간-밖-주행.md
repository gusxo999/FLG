# 구간-밖-주행 — 신고한 구간 **밖**을 달리는 부분에 자리를 준다

**한 줄 요약:** 자리 장부는 줄이 **신고한 구간**만 본다. 그런데 실제로 깔리는 벨트에는
신고에 없는 부분이 둘 있고, 그 부분은 **어느 장부에도 없어서 먼저 잡는 사람이 임자**다.

---

## 1. 푸는 문제

### 1.1 이 저장소가 자리를 판정하는 방식 — **신고한 구간**

같은 칸을 다투는 곳마다 장부가 하나씩 있고, 전부 같은 모양이다:

```
줄이 자기 구간을 신고한다  →  겹치면 배정이 거절한다  →  안 겹치면 나눠 쓴다
```

| 장부 | 신고하는 구간 | 낟알 |
|---|---|---|
| `FaceTable` | 좌석 **행 구간** × 깊이 | `(행, 깊이)` |
| 열 채널 | 경로의 **y 구간** | 트랙 번호(열) |
| 행 채널 | 경로의 **x 구간** | 트랙 번호(행) |

**이 전제 위에 실제 이득이 서 있다.** `linkPlanner` 가 그것을 이렇게 적는다:

> 이제 벨트는 **자기 좌석 구간만 덮고 끝에서 포트 쪽으로 꺾으므로**, 행 구간이 안 겹치는
> 그룹끼리는 **같은 depth 를 그냥 나눠 쓴다. 다툴 게 없으니 장부도 없다.**

예전엔 벨트가 면을 따라 끝까지 달려 같은 깊이 두 줄이 반드시 부딪혔고, 그래서 **한 면의 줄
수가 팔 길이 종류 수에 묶여** 있었다. *"자기 구간만 덮는다"* 가 그 한도를 풀었다.

### 1.2 그런데 **자기 구간 밖을 달리는 것이 둘** 있다

```
㉠ 진입 다리         기둥 끝 포트의 상자 → 그 경로가 배정받은 **행 채널 트랙 행**까지, 세로로
㉡ 기둥 밖 포트 사슬   기둥 끝 포트가 기둥(머신 열) **밖**에 내는 칸들
```

둘 다 **신고에 없다.** 그래서 배정이 못 보고, **방출에서야 갈린다** — 이 저장소가 반복해서
밟은 그 함정이다(`layout-models` §5 의 *"장부 밖이라 방출에서야 갈렸다"*).

## 2. ㉠ 진입 다리 — 길게 정의한다

### 2.1 왜 생기나

납품 경로는 자식 상자에서 **열 채널**(그 열의 서쪽)로 가야 한다. 그런데 **기둥 끝 포트**는
상자가 기둥 위/아래로 튀어나가 있어서 **채널 벽을 정면으로 못 본다** — 서쪽으로 곧장 가면
자기 모듈 몸통을 관통한다.

```
      ┌─ 자식 모듈 ─┐
      │      [상자] │   ← 기둥 끝 포트. 여기서 서쪽은 모듈 몸통이다
      │             │
      └──────┼──────┘
             │  ㉠ 진입 다리 (세로)
   ═══◄══════┘     행 채널 트랙을 따라 서쪽으로 (가로)
      ║
      ║ 열 채널
      ▼
```

그래서 **먼저 행 채널까지 내려온 뒤** 가로로 달린다.

### 2.2 계획이 아는 것과 모르는 것

행 채널에 신고하는 자료는 이것뿐이다:

```ts
interface RowCrossing { id: string; side: "top" | "bottom"; x1: number; x2: number; }
//                                                          ~~~~~~~~~~~~~~~~~~~~~~
//                                                          **가로 구간만**
```

그리고 다리를 그리는 코드는 **방출의 한 줄**이다:

```ts
// deliveryRoute.buildPlannedChain
const s = g.fromRowChannel ? { x: s0.x, y: g.fromRowChannel.row } : s0;
…
if (g.fromRowChannel) push(s);   // 상자 → 행 채널 트랙 행, 세로로
```

**즉 다리는 계획에 자료가 없다.** 방출이 그 자리에서 계산한다. 그래서:

```
계획이 아는 것    이 경로가 행 채널의 몇 번 트랙에 앉나 (한 행)
계획이 모르는 것  그 행까지 내려오는 세로선이 어느 칸들을 지나나
```

### 2.3 오늘의 대응 — **순서만** 맞춘다 (J-교차 ⓐ, 구현됨)

`RowCrossing.side` 가 *"이 경로가 행 채널로 **위에서** 들어오나 **아래서** 들어오나"* 를 말한다.
위에서 오는 것을 전부 위쪽 트랙에, 아래서 오는 것을 아래쪽 트랙에 두면 **다리끼리는** 안
건넌다(전순서). 실측으로 탐색 폴백 2 → 0 을 냈다.

**이것이 막는 것과 못 막는 것이 갈린다:**

| | |
|---|---|
| ✅ 다리 ↔ 다리 | 전순서가 막는다 |
| ❌ 다리 ↔ **반출 트랙** | 반출은 다리를 모른다 |
| ❌ 다리 ↔ **다른 납품의 예약** | 예약에 다리가 없다 |
| ❌ 다리 ↔ **마진 프레임** | 프레임은 bbox 만 키우고 셀을 안 적는다 |

전수표가 이미 그 자국을 적어 두었다:

```
#15  ⑤ 행 채널 ↔ C 예약   C — **가로질러도 아무도 모른다**   행 채널에 예약이 없다   ✗
#16  마진 프레임 ↔ B       B — bounds 가 마진을 포함          직선만 예약            ✗
```

### 2.4 증상이 어떻게 나타나나 — **사유가 한 겹 아래 가려진다**

다리를 밟힌 반출은 `reservation not emittable` 로 나온다:

```ts
if (!res.ok) { fail(port.chest.id, `reservation not emittable: ${res.reason}`); continue; }
```

화면에는 `perimeter-skip — 상자 N개가 외곽으로 못 나가 모듈 안에 남음` 으로 뜬다.
**진짜 사유(*"행 채널을 가로지르는 다리를 밟았다"*)는 어디에도 안 나온다.**

> 이 저장소는 같은 모양을 한 번 겪었다 — 행 채널이 좁아 자리를 못 받은 경로가 화면에는
> *"계획 체인이 막혔다"* 로 나왔고, 사유를 갈라 놓고서야 보였다(옛 `row-channel-short`).

## 3. ㉡ 기둥 밖 포트 사슬 — 길게 정의한다

### 3.1 무엇이 기둥 밖에 서나

**관통 줄**(그 면의 머신을 전부 지나는 줄)은 포트를 **기둥 끝**에 낸다. 이유는 상자를
안 가두기 위해서다:

> 상자에 바깥에서 닿으려면 **그보다 더 깊은 줄들을 가로질러야** 하는데, W/E 면의 깊이는
> 세로줄이라 **관통 줄은 어떤 행에서도 못 건넌다.** 포트를 옆에 두면 그 면의 깊은 관통이
> 자기 상자를 가둔다. 기둥 끝에 두면 상자가 기둥 **밖**이라 면 깊이와 무관해진다.

그래서 이런 칸들이 기둥 밖에 선다:

```
                    관통 줄            레인 합류 쌍
  기둥 밖 +1        [팔]              [합류 칸]      ← 뒤 유입이 없어야 하는 칸
  기둥 밖 +2        [상자]            [팔]
  기둥 밖 +3         —                [상자]
```

### 3.2 **두 장부 사이에 낀 자리다**

```
FaceTable 이 아는 것   행 0 … rowsPerMachine × 머신수 − 1        ← 기둥뿐
행 채널이 아는 것      모듈 extent **밖**의 가로 통로
```

그런데 `moduleExtent` 는 **모든 셀**을 감싼다:

```ts
for (const c of mod.cells) mk(c.x, c.y);   // moduleTransform.moduleExtent
```

**그러니 기둥 밖 사슬은 extent 안이다.** 행 채널은 그 뒤에서 시작한다. 결과:

```
표에 없다(기둥이 아니다)  +  행 채널도 아니다(extent 안이다)  =  **아무 장부에도 없다**
```

`portCells` 가 그 사실을 코드로 보여 준다 — 표 밖 행은 **걸러 버린다**:

```ts
return cells.filter(([r]) => r >= 0 && r <= last);   // 기둥 밖 행은 아무도 청구할 수 없다
```

### 3.3 오늘의 대응 — `ends`, **면마다 둘**

그 자리를 관리하는 유일한 것이 이것이다:

```ts
/** 기둥 끝 장부 — `${면}` → 이미 쓴 끝들. 면마다 N·S 둘뿐이다.
 *  **이것만 표 밖에 남는다** — 기둥 끝은 면의 칸이 아니라 그 **바깥**이라
 *  `(행, 깊이)` 로 표현되지 않는다. */
ends: Map<PortFace, Set<"N" | "S">>;
```

**낟알이 「면 × 끝」이다.** 한 줄이 N 을 잡으면 **그 끝 바깥이 통째로** 잠긴다.

### 3.4 그 거친 낟알이 치르는 값 둘

**값 ①  — 세 번째 관통이 조용히 물러난다.**

> 끝은 면마다 **둘**(N·S)뿐이다. **세 번째 관통은 못 받아 옆으로 물러난다.**

그런데 두 관통 줄의 포트 칸은 **각자 자기 깊이**에 선다(`portCells` 가 `cand.clusterBeltDepth`
를 쓴다). 깊이가 다르면 **같은 끝 바깥에서도 안 부딪힌다.** 지금은 그걸 못 나눠 쓴다 —
**실패가 아니라 저하**라 화면에 안 보인다.

**값 ②  — 방향을 사려고 자리를 산다.**

레인 합류는 두 줄이 **같은 끝**으로 나가야 한 행에서 만난다. 방향을 말할 수단이 `portEnd`
뿐이던 때, 합류는 **방향을 사려고 희소한 끝을 샀다.** `exitEnd`(2026-09-05)가 방향을 공짜로
만들자 **예약도 함께 사라졌고**, 두 합류 도형이 같은 자리에 겹쳤다:

```
occupancy 덤프:  -2,-1 · -3,-1 · -3,-2 · -4,-2 · -5,-2
                 (앞선 쌍의 합류 칸·꺾는 칸·팔·상자가 그 자리를 이미 먹고 있었다)
```

**이것이 ㉣(합류 칸 ↔ 포트 분리)이 세 번 막힌 이유 중 하나다.**

### 3.5 **발견 — 전수표 #2 가 이 자리에서 거짓이다**

`layout-models` §5 가 이렇게 적는다:

```
#2  A ↔ A (같은 모듈)  **배정이 판정한다**  FaceTable(계획) → occupancy(확인)   ○
```

**기둥 밖 사슬에는 안 맞는다.** `FaceTable` 밖이라 배정이 못 보고, `ends` 가 거칠게 가려
왔을 뿐이다. 그것을 떼는 순간 드러난다(2026-09-05 실측). 표를 고친다(§6 Step A0).

## 4. 왜 지금까지 안 터졌나

| | 왜 안 터졌나 | 그 대신 무엇을 치렀나 |
|---|---|---|
| ㉠ | 실물 트리의 행 채널 수요가 적었다(행 채널마다 트랙 1~2개) | 터지면 `perimeter-skip` 으로 나와 **사유가 가려진다** |
| ㉡ | `ends` 의 거친 한도가 우연히 막았다 | 세 번째 관통이 **조용히 옆으로 물러난다** |

**둘 다 「안 터진다」가 아니라 「안 보인다」다.** ㉠ 은 사유가 한 겹 아래 있고, ㉡ 은 실패가
아니라 저하다.

## 5. 이 계획이 **안 푸는** 것

- **행 채널 안에서 가로선과 세로선을 함께 배정하는 것** — VLSI 채널 라우팅의 dogleg·via 다.
  → `채널-양보-명세/judgements.md` **J-교차 ⓑⓒ**. 이 계획은 **다리를 자료로 만들고
  예약에 싣는 데까지**이고, 그러고도 겹치면 그때 ⓑⓒ 를 연다.
- **셀장부의 `Claim` 구조** — 저쪽 계획 4 가 *"등록하는 자리"* 를 만든다. 이 계획은
  **등록할 자료**를 만든다. 저쪽이 서면 여기서 만든 자료가 그 장부로 옮겨 간다.
- **`FaceTable` 의 행을 물리 행으로** — 머신 틈(`rowGaps`)이 좌석 순번과 물리 행을 가르는
  문제. 같은 축이지만 다른 계획이고, 오늘 실물에선 틈이 0이라 안 문다.
- **㉣ 합류 포트 분리 자체** — A 트랙이 **바닥**을 놓을 뿐이다. 그 위에 도형을 세우는 것은
  `벨트-레인` ㉣ 소관이다.
- **열 채널** — 계단꼴·절단선·같은 쪽 판정 전부 그대로.

## 6. 단계

### 트랙 A — 기둥 밖에 **칸 장부**를 준다

> ㉡ 이 대상. **먼저 한다** — ㉣ 이 세 번 여기서 막혔고, `ends` 한도를 푸는 이득이 즉시 난다.

#### Step A0 — 전수표를 고친다 (코드 변경 0)

`layout-models` §5 #2 의 `○` 옆에 **예외**를 적는다: *기둥 밖 포트 사슬은 `FaceTable` 밖이라
배정이 못 본다. `ends` 가 면당 둘로 거칠게 가릴 뿐이다.*

- **전제:** `portCells` 의 마지막 `filter` 가 표 밖 행을 버린다.
- **불변:** 없다(문서만).
- **관문:** 착수한 사람이 **표를 믿을 수 있게** 된다. 틀린 `○` 하나가 다음 시도를 오도한다.

#### Step A1 — `outside` 장부를 넣되 `ends` 와 **나란히 돌린다** ✅ **완료** (2026-09-06)

```ts
/** 기둥 밖의 칸 장부 — `${끝}:${오프셋}:${깊이}`. `offset 0` 이 기둥 바로 바깥 행. */
outside: Map<PortFace, Set<string>>;
```

`portCells` 가 내는 칸을 **표 안 / 기둥 밖**으로 가르고(`splitByTable`), 검사와 청구가
**같은 함수**를 부르게 한다.

- **전제:** 기둥 끝 포트가 먹는 칸이 `portCells` 하나에서 나온다(방출도 같은 값을 쓴다).
- **불변:** `ends` 를 아직 안 없앤다. **두 장부가 같은 답을 내는지 단언**한다 —
  *"`ends` 가 거절한 후보는 `outside` 도 거절한다"*. 어긋나면 그 자리가 곧 §3.4 값 ①의 실물이다.
- **관문:** 기둥 밖이 `(끝, 오프셋, 깊이)` 로 **표현된다.** A2 가 그 위에 선다.

**실측 (2026-09-06):**

```
                        배정   끝 낟알로 잃음   장부 어긋남
  거대출력 2×36 (gap 넘침)  14        **2**            0
  관통 넷 한 면            17         0               0
```

**불변이 섰다**(어긋남 0) **그리고 이득이 실재한다**(거친 낟알로 관통 **둘**을 잃고 있었다).
배치는 한 칸도 안 바뀐다 — 결정은 여전히 `ends` 가 한다.

**덤으로 찾은 것:** `splits` 계수기가 **누적되지 않고 있었다**(선언·초기화·보고는 다 있는데
`recordFaceDepthStats` 의 더하는 목록에만 빠져 있었다). `쪼갬 0` 은 *"안 일어났다"* 가 아니라
*"안 세었다"* 였다 — 그 수를 관문으로 읽던 글이 거짓을 읽고 있었다. 같은 줄에서 고쳤다.

#### Step A2 — `ends` 를 걷어내고 `outside` 만으로 판정 ⏸ **되돌림** (2026-09-06)

> **구현해서 실측했고, 되돌렸다.** 능력은 실제로 열렸는데 **㉠ 이 그만큼 더 드러난다.**
>
> **선 것 — 관문을 통과했다:**
> - `endPortDenied` 가 두 실물 트리에서 **0** 이 됐다(거절 없이 전부 기둥 끝을 받았다).
> - 테스트로 못 박았다: *"깊이가 다르면 두 관통 줄이 **같은 끝을 나눠 쓴다**"*.
>   같은 깊이면 여전히 물러난다 — 칸이 겹치기 때문이다.
> - **합류 발자국도 장부에 넣어야 했다.** 합류 쌍은 포트를 `d+1` 에 두는데 **벨트는 `d` 로
>   기둥 밖까지 달린다**. 그 `offset0:d` 를 안 적으니 같은 깊이의 남의 관통 포트가 그
>   자리를 받아 방출에서 부딪혔다(`unrouted-lines`). 옛 `ends` 가 끝을 통째로 잠가
>   **우연히** 막고 있던 것이다 — 이 사실이 §3 의 정의를 한 번 더 확인해 준다.
>
> **막힌 것 — `점대점` 트리에서 납품 폴백 0 → 2.** 실패는 아니고(길은 난다) **계획이
> 못 낸 것**이다. 사유를 뽑으니 둘 다 ㉠ 이었다:
>
> ```
> chain-blocked:남의 납품 예약 c→p:x#3 (15,-1)
> chain-blocked:모듈 몸통 (15,2)
> ```
>
> A2 가 포트를 하나 더 기둥 끝/gap 으로 보내면서 **행 채널을 쓰는 경로가 둘에서 셋**이 됐고,
> 그 셋의 신고가 전부 `x 0..0` — **길이 0의 가로 구간**이었다.

##### 이 실측이 ㉠ 의 정의를 넓힌다 — **다리는 행 채널 안에만 있지 않다**

계획서 §2 는 다리를 *"포트에서 행 채널 트랙 행까지"* 로 적었다. 그건 **기둥 끝 포트**의
이야기다. **gap 포트**는 다르다:

```
행 채널 자리:  d1 marginN y-4..-1,  트랙 [#0→0, #3→1]  = 행 -4, -3
신고한 가로:   #0 x0..0 (portY 0) · #3 x0..0 (portY 6)   ← 둘 다 **길이 0**
실제 다리:     #0 행 0 → -4  ·  #3 행 6 → -3            ← **같은 x 를 함께 올라간다**
```

`assignTracksLeftEdge` 는 길이 0 구간 둘을 보고 *"안 겹친다"* 며 다른 트랙을 준다. 그런데
**다리는 같은 열을 공유한다** — `#3` 의 다리는 모듈 몸통(행 5…0)을 지나 올라온다.

**이건 배정으로 못 푼다.** 두 다리의 x 는 상자 위치라 **고를 수 없기 때문**이다. 같은 x 에서
둘이 겹치면 하나는 다른 길로 가야 한다(깊이를 바꾸거나, 지하로 건너거나 — J-교차 ⓑⓒ).

**그래서 A2 는 B 뒤로 간다.** 순서가 뒤집혔다 — 원래 *"A 가 ㉣ 의 바닥이니 먼저"* 였는데,
**A2 가 ㉠ 을 더 드러내므로 B 가 선행**이다. A1(장부)은 그대로 남아 A2 를 기다린다.

- **전제:** A1 의 단언이 통과했다(두 장부의 답이 같거나, 다른 자리가 전부 §3.4 값 ①이다).
- **불변:** *"같은 끝 · 같은 오프셋 · 같은 깊이"* 가 겹치는 두 줄은 여전히 거절된다 —
  기전 단언으로 건다(수로 못 박지 않는다).
- **관문:** **깊이가 다른 두 관통 줄이 같은 끝을 나눠 쓴다.** 그 순간 *"세 번째 관통은
  옆으로 물러난다"* 가 거짓이 된다. 계측: `면깊이` 통계의 **옆면 배정** 대비 관통 수.

#### Step A3 — 그 바닥 위에서 ㉣ 을 다시 시도한다 *(방향)*

`벨트-레인` ㉣ 3차가 남긴 프로브부터 친다: **막힌 칸의 표 주인을 청구 시점과 방출 시점에
각각 찍는다.** A1·A2 가 서면 셋 중 ⑴⑵는 배정에서 잡히므로, 남는 것은 ⑶(표에 안 올라오는
방출)뿐이라 **탐색 범위가 좁아진다.**

- **관문:** 합류가 기둥 끝 **자리**는 쓰되 `ends` **한도**는 안 먹는다.

---

### 트랙 B — 진입 다리를 **자료로 만든다**

> ㉠ 이 대상. A 와 **독립**이다(파일도 안 겹친다).

> **B 의 범위가 넓어졌다**(A2 실측). 다리는 행 채널 **안**에만 있는 것이 아니다 —
> gap 포트의 다리는 **모듈 몸통 옆을 세로로 지난다**(위 §6 A2 되돌림). 그러니 B1 이 낼
> 자료는 *"행 채널 안의 몇 행"* 이 아니라 **`(x, 행 구간)` 통째**여야 한다.

#### Step B1 — 다리를 계획의 자료로 올린다

오늘 `RowChannelEntry` 는 행 하나뿐이다:

```ts
export interface RowChannelEntry { row: number; }
```

다리가 지나는 구간을 함께 낸다 — **행 채널이 이미 아는 값에서 유도된다**(포트 행 · 트랙 행 ·
상자의 x). 새로 정할 것이 없다.

- **전제:** 다리는 **상자의 x 에서 수직**이고 `side` 가 방향을 말한다(`buildPlannedChain`
  이 그렇게 그린다). 그러니 `(x, 행 구간)` 으로 완전히 표현된다.
- **불변:** `buildPlannedChain` 이 그리는 칸과 여기서 낸 구간이 **같다** — 방출의 결과를
  자료와 대조하는 단언을 건다(둘이 갈리면 등록이 거짓이 된다).
- **관문:** 다리가 **말할 수 있는 것**이 된다. B2 가 그것을 예약에 싣는다.

#### Step B2 — 그 자료를 예약에 싣는다

반출 트랙 배정(`planTracks`)과 채널 기하 예약이 다리를 **보게** 한다.

- **전제:** 다리의 x 는 상자의 절대 x 이고, 그 값은 `colX` 확정 뒤에 나온다 —
  **예약 단계와 시각이 맞는지 먼저 확인한다**(순서 미확인이 가장 흔한 함정이다).
- **불변:** 다리가 없는 경로(옆 포트)는 이 단계 전후로 **같은 갈래를 탄다** —
  기전: `fromRowChannel`/`toRowChannel` 이 `undefined` 면 낼 구간이 없다.
- **관문:** `perimeter-skip` 의 `reservation not emittable` 중 **다리를 밟아 생긴 것**이
  사라진다. 사라졌는지 세려면 **사유를 갈라야 한다** — 그것이 B3.

#### Step B3 — 사유를 가른다

`reservation not emittable: <reason>` 에 *"행 채널을 가로지르는 다리"* 를 별개 사유로 넣는다.

- **관문:** 이 계획의 성패가 **화면에서 세어진다.** 안 갈라 두면 B2 의 관문을 못 센다.

---

### 순서와 이유 — **A2 실측으로 뒤집혔다** (2026-09-06)

```
전:  A0 → A1 → A2 → A3   ·   B3 → B1 → B2
후:  A0 ✅ → A1 ✅ → **B3 → B1 → B2** → A2 → A3
```

**A2 가 ㉠ 을 더 드러내기 때문**이다(위 되돌림 기록). `ends` 를 걷으면 포트가 기둥 끝·gap
으로 더 가고, 그 경로들이 전부 행 채널을 쓴다 — ㉠ 이 안 닫힌 채로는 그 이득이 폴백으로
샌다. **A1 은 이미 서 있고 배치를 안 바꾸므로 그대로 기다려도 값이 안 썩는다.**

**A 와 B 는 파일이 안 겹친다**(A = `linkPlanner`·`planModulePorts`, B = `rowChannelPlanner`·
`deliveryRoute`·`modulePacking`·`modulePerimeterPass`). 순서를 바꿔도 되고 나눠 해도 된다.

---

## 7. 이게 끝나면 열리는 문

- **㉣ 이 설 바닥이 생긴다** — 합류가 기둥 끝 **자리**는 쓰되 **한도**는 안 먹는다.
  세 번 막힌 그 계획이 네 번째에 다른 지형에서 시작한다.
- **`ends` 한도가 풀린다** — *"세 번째 관통은 옆으로 물러난다"* 가 깊이별로 갈리면서
  면당 관통 수가 늘어난다. `known-limits` §10(면당 깊이 부족)의 한쪽이 완화된다.
- **`perimeter-skip` 의 사유가 하나 갈린다** — *"행 채널을 가로지르는 다리를 밟았다"* 가
  화면에 나온다. 지금은 `reservation not emittable` 아래 묻혀 있다.
- **셀장부 계획 4 가 등록할 자료가 준비된다** — 저쪽이 *"등록하는 자리"* 를 만들 때
  넣을 것이 `band.tracks` 의 가로선만이 아니라 **다리까지**라는 것이 이 계획의 산출물이다.
- **전수표가 다시 믿을 만해진다** — #2 의 예외가 적히고 #15·#16 이 닫힌다.
