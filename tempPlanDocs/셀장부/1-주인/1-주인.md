# 계획 1 · 주인 — **셀에 임자를 단다**

> 전체 설계는 [../셀장부.md](../셀장부.md). 이 계획은 그 **첫 축(`owner`)** 이다.
> 다루는 줄: **#1 · #4 · #5 · #10** (전수표 → [[layout-models]] §3.5)

---

## 1. 왜 이게 첫 계획인가

**발견 1 이 이 계획을 낳았다** — 지금 셀은 *"차 있다/비었다"* 만 말한다.

```
지금:      Set<셀>          "여기 오지 마라"        ← 금지 구역
바꾼 뒤:   Map<셀, 주인>     "여기는 X 의 자리다"    ← 소유
```

**금지 구역은 되돌릴 수 없다.** 누가 잡았는지 모르니
*비켜 달라*(양보)도, *내 것을 놓겠다*(승격)도, *누가 막았는지 말한다*(사유)도 못 한다.

그래서 **뒤 세 계획이 전부 이 계획에 매여 있다** — `stage` 는 승격을 부르고,
`what` 은 *"누구의 유체냐"* 를 부르고, 누락 넷은 *"누가 등록하나"* 를 부른다.
**owner 없이는 셋 다 못 쓴다.**

## 2. 무엇을 여나 (관문)

> **`ownerOf(칸)` 이 답을 낸다.** 지금은 그 질문이 성립하지 않는다.

이것 하나로 세 가지가 따라온다 — 전부 **이 계획이 아니라 다음 계획들의 재료**다:

```
사유에 임자가 실린다     "반출 예약 (8,15)"  →  "반출 예약 (8,15) — 상자 X"
승격이 가능해진다        promote(owner)              계획 2
양보를 물을 수 있다      "X 야, 비켜 줄 수 있나"       J-정책전환 이후
```

## 3. 다루는 네 줄

| # | 쌍 | 지금 | 이 계획 뒤 |
|---|---|---|---|
| 1 ○ | 머신 ↔ 전부 | `buildOccupancy` **×2** | 장부 하나 · `path:"A"` |
| 4 ○ | A ↔ B | `deliveryRoute.base` | `snapshot({path:["A"]})` |
| 5 ○ | A ↔ C | `perimeterPass.occ` | `snapshot({path:["A","B"]})` |

**#1 이 두 계획을 하나로 만드는 줄이다** — `buildOccupancy` 가 두 벌인 것이 §2 의
*"순수성의 대가"* 이고, 장부가 **패스 사이를 흐르는 값**이 되면 한 벌로 준다.

## 4. 착수 목록

> 방향이 정해졌으므로 세부는 따라온다. 아래는 **순서**를 위한 것이지 명세가 아니다.

**주인을 잃는 자리가 넷이고 처방이 둘이다**(→ [../셀장부.md](../셀장부.md) 축 1):

```
㉮ 평탄화형 셋 — 상류에 주인이 있다.  **넘기기만** 하면 된다
   A       pl.module.cells        →  pl 이 주인
   B       route.cells            →  route.key 가 주인 (같은 루프에 이미 있다)
   C방출   relocations 의 belts   →  chestId 가 주인

㉯ 경계형 하나 — **시그니처를 고쳐야** 한다
   C예약   addSeg(from, to)       →  임자를 받을 인자가 없다.  a.id 가 루프에 있다
```

```
① planner/cellLedger.ts (신규)
   Claim{owner, path} · CellLedger{add, snapshot, ownerOf}
   **PackResult 를 안 받는다** — placements 배열만 (제약 나: 파이프라인 소유물)

② tree/build.ts

   addSeg 가 도는 루프에 `a.id` 가 **이미 있다** — 넘기기만 하면 된다

③ link/build.ts · execution/modulePerimeterPass.ts
   buildOccupancy 둘 다 삭제 → snapshot 질의로

④ run/build/module.ts
   pack 직후 장부 생성 → delivery 결과 등록 → perimeter 에 주입
```

### ③ 의 네 `if` 가 하나가 되는 기전 — **union 으로는 안 된다**

`plannedChainClear` 의 네 검사는 술어가 전부 `has(k)` 로 **같은 질문**이다. 다른 것은
*어느 집합을 보나*와 *어떤 문자열을 내나* 뿐이다:

```ts
if (base.has(k))           return `모듈 몸통 …`;
if (deliveryBelts.has(k))  return `이미 깔린 납품 벨트 …`;
if (reservedExport.has(k)) return `반출 예약 …`;
if (fluidBlocked?.has(k))  return `유체 합류 가드 …`;   // ← 2항.  **안 합친다**(제약 마)
for (const [k2, cells] of reservedDelivery)
  if (k2 !== ownKey && cells.has(k)) return `남의 납품 예약 …`;
```

**넷을 그냥 union 하면 깨진다** — 마지막 줄의 `k2 !== ownKey`(*자기 예약은 밟아도 된다*)가
사라져 **모든 계획 체인이 자기 자신에게 막힌다.** 주인을 달아야 그 구분이 살아난다:

```ts
const owner = ledger.ownerOf(c);
if (owner && owner.id !== ownKey) return `${label(owner)} (${c.x},${c.y})`;
```

**이것이 "집합 넷을 합친다"가 아니라 "주인을 달아서 합친다"인 이유다** — 합칠 수 있어서
주인을 다는 게 아니라, **주인을 달았기 때문에 합칠 수 있다.**
덤: `reservedDelivery` 의 선형 스캔(`O(납품 수)` × 체인 셀)이 조회 하나가 된다.

## 6. 이 계획이 **안 하는 것**

| | 왜 |
|---|---|
| `stage` 를 넣는다 | 계획 2. 지금은 예약과 실물이 **둘 다 그냥 claim** 이다 |
| `what`(유체 등)을 넣는다 | 계획 3 |
| 행 채널·마진 등록 | 계획 4 |
| 사유 문자열을 실제로 바꾼다 | **owner 를 심기만 한다.** 쓰는 것은 계획 2 — 근거는 회귀가 아니라 **표현력**이다(아래) |
| 판정 정책을 손댄다 | 정책 A(먼저 온 쪽) 그대로 |

**사유를 미루는 진짜 이유 (2026-08-21 정정):** 회귀 위험이 아니다 — **사유 문자열을 검사하는
테스트는 0개**다(확인). 미루는 이유는 `Claim{owner, path}` 만으로는 **B 실물과 B 예약이 둘 다
`path:"B"`** 라서, 지금 갈려 있는 *"이미 깔린 납품 벨트"* 와 *"남의 납품 예약"* 을 **구분할 수
없기** 때문이다. 그 둘을 가르는 것이 계획 2 의 `stage` 다.
**owner 만으로는 판정은 합쳐지지만 이름은 아직 다 못 짓는다.**

