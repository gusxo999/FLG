# 셀장부 — 공통 컨텍스트

> 상태: **계획 1 승인 대기** · 계획 2·3·4 는 방향만

**같은 칸을 두고 다투는 17쌍의 판정을 장부 하나가 맡게 한다.** 뼈대는
[[layout-models]] **§3.5 전수표**. 양이 많아 **네 계획으로 나눴고, 나누는 축은
일정이 아니라 "장부가 무엇을 새로 알게 되나"** 다 — 전체 설계는 [셀장부.md](셀장부.md).

```
1 · 주인 (owner)  #1·4·5·10   ← 확정.  1-주인/
2 · 시간 (stage)  #6·8·9      ← 방향
3 · 무엇 (what)   #7·13       ← 방향
4 · 누락 (등록)    #15·16      ← 방향
안 옮김            #2·3·14·11·12·17   이유를 docs/ 에 남긴다
```

**계획 하나가 `Claim` 필드 하나를 더한다.** 그래서 각각 독립으로 되돌릴 수 있고,
순서가 강제된다 — `stage`·`what` 은 `owner` 없이 쓸모가 없다.

## 착수하는 사람이 먼저 알아야 할 것 — **아무도 실수하지 않았다**

장부가 넷이 된 것은 게으름이 아니라 **지역적으로 옳은 결정 셋**의 결과다:

```
① 모듈 로컬     생성이 배치보다 먼저다 — 그 시점엔 절대좌표가 없다.  강제였다
④⑥ 두 buildOccupancy
                두 패스가 "Area·store 의존 0" 을 계약으로 선언한다. 순수하려면 입력을
                스스로 유도해야 하고, 앞 패스 것을 물려받을 통로가 없다
②⑤ 예약과 실물  같은 격자인데 **생기는 시각**이 다르다. 그릇이 시각을 따라 갈렸다
```

**그래서 주의·검사·이름 같은 대비는 안 통한다** — 사람이 틀린 게 아니기 때문이다.
그리고 **고칠 때 그 이유를 깨면 안 된다.**

## 전 계획 공통 제약 다섯 — 깨면 구조정리가 아니다

```
가.  장부는 **라우터 안으로 안 들어간다**       계획·판정은 장부, 탐색은 라우터
     → containerRouting 은 blocked 에서 has() 밖에 안 쓴다.  그게 옳다 —
       장부가 들어가면 탐색이 배치 개념에 묶여 재사용이 죽는다(수동편집도 같은 라우터)

나.  장부는 **파이프라인이 소유하고 주입**한다
     → 패스가 소유하면 테스트 45곳이 전부 장부를 알아야 한다.  옵셔널 주입

다.  **정책 A(먼저 온 쪽)** 로만 판정한다        오늘 그대로.  피해 등급은 J-정책전환
라.  **판정 없는 넷은 규칙을 비운다**            claim 은 들어오되 규칙이 없다 (사용자 결정)

마.  **장부는 아리티 1(겹침)만 맡는다**          인접은 칸 **쌍**, 페어링은 **직선 구간** —
     → 담을 수 없어서 안 담는다.  pipeFlow·UndergroundCorridor 는 남는다 (J-인접흡수·J-구간흡수)
```

**다·라가 "동작 불변"의 근거다.**

## 세 가지 결정 (2026-08-19 사용자)

| | |
|---|---|
| **장부의 책임** | 저장 + **판정** + **우선권**. 소비처는 규칙을 모르고 묻기만 한다 |
| **전수표의 역할** | **계획의 뼈대.** 17줄을 하나씩 다룬다 |
| **판정 없는 넷** | **자리만 만들고 규칙은 비운다.** 동작 불변 |

**우선권은 추가 기능이 아니라 드러내기다** — 오늘도 우선권은 있고 **호출 순서로**
적혀 있다. 장부로 옮기면 이름을 가져야 한다. 그래서 정책 A 가 *"오늘을 재현한다"* 다.

## 착수 전 반드시 읽을 것

| 무엇 | 왜 |
|---|---|
| [docs/layout-models.md](../../docs/auto-layout/common/layout-models.md) **§3.5** | **뼈대 그 자체.** 17쌍 전수표 · 좌표계가 경쟁을 만든다 · 피해 등급 |
| `planner/deliveryRoute.ts` — 머리 주석 · `buildOccupancy` · `plannedChainClear` | 순수 계약이 **중복의 이유**다. 사유 문자열이 **장부의 요구사항 명세** |
| `execution/modulePerimeterPass.ts` — 머리 주석 · `buildOccupancy` · *"모듈 그래프 미변형"* | 같은 계약, 같은 유도. **장부는 이 계약을 안 건드린다** |
| `shared/route.ts` — `dijkstraWithJumps` 의 `blocked` | **제약 가의 근거.** 라우터가 장부를 모른다는 경계선 |
| `module/clusterModule.ts` — `origin: {x: pos.dx, …}` | 생성 시점엔 절대좌표가 **없다**. ①이 로컬인 이유 |
| `planner/channelGeometryPlanner.ts` — `items` 구성 · `yieldedExports` | 경쟁이 이미 풀린 곳(#14)이자 **정책 B 의 원본** |
| `shared/pipeFlow.ts` 머리 주석 | #11·12 의 규칙. **인접은 칸 쌍의 성질**이라 왜 못 흡수하는지 |
| `debug/checkRules.ts` — `checkOverlap` | 사후 탐지기. 장부의 **대조군**으로 남긴다 — 없애지 않는다 |

## 하지 않는 것 (전 계획 공통)

- **판정 없는 넷의 규칙을 채우지 않는다.** 자리만 만든다(제약 라).
- **정책 B(피해 등급)로 안 바꾼다** → [judgements.md](judgements.md) J-정책전환.
- **`pipeFlow`(인접)를 안 흡수한다** → J-인접흡수. **#7·13 과 #11·12 가 같은 판단이다.**
- **양보·선점을 안 넣는다.** 정책 B 다음.
- **로컬(#2·3·14)을 안 건드린다** — **로컬 좌표는 경쟁을 없애는 장치다.**
  통합 대상이 아니라 보존 대상. 특히 #14(세로 채널)는 §3.5 에서 *경쟁이 풀리는
  유일한 곳*이었고 그 이유가 로컬 좌표를 가져서다.
- **배정 알고리즘을 안 바꾼다.** dijkstra 폴백도 그대로.
