# 셀장부 — 전체 설계와 **네 계획으로 나눈 이유**

> **뼈대는 전수표 17쌍이다**(→ [[layout-models]] §3.5).
> 17줄을 한 번에 처리하기엔 양이 많아 **네 계획으로 나눈다.**
> 나누는 축은 일정이 아니라 **장부가 무엇을 새로 알게 되나** 다.

---

## 1. 방향성 있는 발견 넷 — **코드가 무엇을 믿고 있나**

드라이런(2026-08-19, 코드 변경 0)에서 나온 것 중 **방향을 정하는 것만** 남겼다.
*"소비처 7곳이 `ReadonlySet` 으로만 쓴다"* 같은 것은 방향이 정해지면 따라오므로 뺐다.

### 발견 1 — 예약에 주인이 없다 = **예약을 "금지 구역"으로 설계했다**

`reservedExportCells: Set<셀>` 은 *"여기 오지 마라"* 만 말하고
*"여기는 상자 X 의 자리다"* 를 **안 말한다.** 그 차이가 전부다:

```
금지 구역   되돌릴 수 없다.  누가 잡았는지 모르니 비켜 달라 할 수도, 승격시킬 수도 없다
소유       주인에게 물을 수 있다.  승격도 양보도 **주인이 있어야** 성립한다
```

**#8(예약은 C 승) · #9(방출은 B 승)의 모순도, 양보의 부재도, 사유에 상자를 못 싣는 것도
전부 이 한 가지 선택에서 나온다.** `Set → Map` 은 계측이 아니라 **예약의 성격을 바꾸는 일**이다.

#### 왜 `Map` 이라야 하나 — **`Set` 은 이미 `Map` 이고, 값 자리가 비어 있을 뿐이다**

```
Set<K>  ≅  Map<K, Unit>        Unit = 값이 하나뿐인 타입 = 정보량 0비트
```

키 공간은 같다. 바뀌는 것은 **값 칸의 폭**뿐이고, 거기서 셋이 따라온다:

```
① 소속이 자료구조 안으로   지금 "이 칸은 반출 예약이다" 는 `reservedExport` 라는 **변수 이름**에
                          적혀 있다 — 타입이 못 보는 곳이다.  `path` 가 그 이름표를 값으로 들인다

② 병합 규칙이 강제된다      Set union 은 (Unit,Unit)→Unit 이라 **정책을 적을 자리가 없다.**
                          Map 은 같은 칸에 값 둘이면 (Claim,Claim)→Claim 을 정해야 하고 정답이 없다
                          → **정책 A 에 이름을 붙여야 하는 구조적 이유가 이것**이다

③ 역인덱스가 생긴다        Map<칸,주인> 은 Map<주인,Set<칸>> 을 유도한다.  Set<칸> 에는 "주인"
                          이라는 항이 없어 역을 물을 대상이 없다 → 승격·양보·철회가 이 역방향을 쓴다
```

**`Set` 은 우선권을 못 가진 게 아니라 적을 칸이 없어 호출 순서로 밀려난 것이고, 되돌리기가
금지된 게 아니라 되돌릴 대상을 가리킬 이름이 없었던 것이다.** 값 칸 하나가 둘을 코드 안으로 들인다.

> **방향:** 장부의 첫 축은 `owner` 다. 나머지 축은 owner 없이는 쓸모가 없다 —
> 승격도 양보도 주인을 부른다. **그래서 계획 1 이 소유다.**

#### 추가(2026-09-10) — **주인 없는 등록부가 하나 더 늘었다.** 다만 이사가 준비돼 있다

`직진-장부` 계획이 실행되면서 반출 배정에 **직진 × 직진 장부**(`DirectRay[]`)가 생겼다.
같은 칸을 다투는 판정이 이제 넷이다:

```
채널 통합 장부        납품 × 환승      동시 배정 + 백트래킹  (가장 셈)
reservedExportCells  직진 × 납품      금지 구역 — **주인이 없다**  ← 발견 1
방출의 occ           모두 × 모두      사후 · 먼저 온 쪽 · 대가는 skip
DirectRay[]          직진 × 직진      배정 시점 · 먼저 온 쪽 · 대가는 환승   ← 새로 늘어난 것
```

**발견 1 의 실수를 되풀이한 것이 아니다** — `DirectRay` 는 처음부터 **주인과 함께** 산다
(`{ id, ray }` 쌍으로 들고 다니고, 낙선 기록이 `{상자, 승자, 칸}` 을 남긴다). 계획 1 이
`Claim` 을 세우면 **그 자료가 그대로 옮겨 가고 버려지는 것은 판정 두 줄뿐이다.**

> 감수한 근거가 이것 하나였다 — *"자료가 이식 가능하다."* 이사할 때 이 문단을 지운다.
> → `docs/auto-layout/perimeter/perimeter-export.md` §3② **직진 장부**

### 발견 2 — 두 `buildOccupancy` 의 차이가 한 줄 = **두 뷰의 차이는 공간이 아니라 시간**

차이는 `deliveryCells` 한 줄, 즉 *"B 가 이미 놓였나"* 뿐이다.
같은 격자를 **다른 시각에** 본 것이지 다른 영역을 본 게 아니다.

그리고 이건 §2③(*예약과 실물이 그릇을 가른 이유*)과 **같은 축**이다 —
`reservedExportCells` 와 `deliveryBelts` 도 시각이 갈라 놓은 것이었다.

> **방향:** 장부의 둘째 축은 `stage` 다. **그릇을 나누던 시각 차이를 값으로 옮기면
> 두 뷰가 저절로 갈린다.** 새 시각이 생겨도 그릇이 안 늘어난다. **계획 2 가 시간이다.**

### 발견 3 — `dijkstra.blocked: ReadonlySet` 는 **허물면 안 되는 경계선**이다

라우터(`containerRouting`)는 `blocked` 에서 `.has()` 밖에 안 쓴다.
**라우터는 장부를 모르는 순수 격자 알고리즘이고, 그게 옳다** — 장부가 라우터 안으로
들어가면 탐색이 배치 개념에 묶여 재사용이 죽는다(수동편집도 같은 라우터를 쓴다).

> **방향:** 장부의 책임 경계가 여기서 정해진다 — **계획·판정은 장부, 탐색은 라우터.**
> **정정:** 옛 성공기준의 *"집합 복사 0회"* 를 **뺀다.** 그건 이 경계를 허무는 목표였다.
> 복사는 결함이 아니라 **경계의 값**이다.

### 발견 4 — 테스트 45곳은 **"각 패스는 자족적이다"** 라는 계약의 크기다

45곳이 `pack` 하나만 주고 나머지를 기대한다. 스타일이 아니라 §2 의 순수성 계약이
**테스트 문화로 굳은 것**이다.

> **방향:** 장부는 **파이프라인의 소유물이지 패스의 소유물이 아니다.**
> 패스가 장부를 소유하면 45곳이 전부 장부를 알아야 한다 — 그 숫자가 이미 답하고 있다.
> 호출자(`moduleWizard`)가 만들어 **주입**한다.

## 2. 왜 **이 네 축**인가 — 코드의 네 자리에서 나왔다

`Claim` 에 필드가 넷이라서 계획이 넷인 게 아니다. **거꾸로다** —
*"지금 코드가 알고 있는데 적을 곳이 없는 정보"* 가 넷이고, 필드는 그 결과다.

각 축은 **정보가 없어서 못 하는 일이 서로 다르다** — 그래서 겹치지 않는다.

---

### 축 1 · 주인 — **A·B·C 가 전부 버린다. 다만 버리는 자리가 둘로 갈린다**

> **`addSeg` 는 C 의 예약 하나에만 있다**(`modulePacking` 안, 호출 4곳 전부 같은 블록).
> A·B 는 안 쓴다 — 그런데도 셋 다 주인을 잃는다. **잃는 방식이 다르다.**

#### ㉮ 평탄화형 — 상류에 주인이 **있는데** `Set.add` 에서 좌표만 남는다

**A (모듈 안)** — `pl` 이 곧 주인인데 한 줄 아래서 사라진다:

```ts
for (const pl of pack.placements) {        // ← pl 이 주인이다
  for (const c of pl.module.cells) occ.add(cellKey(c.x, c.y));
}                                          //   ↑ 좌표만.  pl 이 증발
```

**B (납품)** — **같은 루프 안에서** 신원을 route 에는 싣고 장부에는 안 싣는다:

```ts
routes.push({ ...route, key: k });          // ← 신원을 찍는다
                                            //   (2026-08-04 사고로 추가된 줄)
for (const c of route.cells) {
  cells.push(c);
  deliveryBelts.add(cellKey(c.x, c.y));     // ← 그런데 장부엔 좌표만
}
```

**이게 가장 선명한 증거다.** 코드는 신원의 필요성을 **이미 안다** — 주석에 *"위치로 되찾는
대신 신원을 싣는다"* 는 사고 기록까지 있다. 다만 **장부 쪽에는 실을 자리가 없다.**

**C 방출** — 이사 기록에는 임자가 있는데 장부엔 또 좌표만:

```ts
relocations.push({ chestId: port.chest.id, origin: chestCell, belts });  // ← 주인 있음
for (const b of belts) occ.add(cellKey(b.x, b.y));                       // ← 좌표만
```

> **처방:** 상류 객체를 이미 손에 들고 있으므로 **장부에 넘길 때 함께 주면 끝**이다.

#### ㉯ 경계형 — 애초에 **받을 인자가 없다** (C 예약 하나뿐)

```ts
const addSeg = (from, to) => {
  for (const c of segment(from, to)) reservedExportCells.add(`${c.x},${c.y}`);
};                                    //   ↑ 좌표 둘.  임자를 받을 인자가 없다

for (const a of trackPlan.assignments) {   // ← a.id 가 **여기 있다**
  addSeg(anchor, corner);                 // ← 클로저 경계에서 끊긴다
}
```

> **처방:** 시그니처를 고쳐야 한다. **계획 1 의 유일한 구조 변경이 여기다.**

#### 왜 이 구별이 중요한가

```
㉮ 평탄화형   되찾으려면 상류를 **읽으면** 된다   routes · placements · relocations
㉯ 경계형     되찾으려면 예약을 **다시 계산**해야 한다   assignments 를 다시 훑어 segment 를 다시 그림
```

**그래서 사유 문자열에서 유독 반출 예약만 임자를 못 댄다** —
`chain-blocked: 반출 예약 (8,15)` 가 칸만 말하는 이유가 이것이다.

> **없으면 못 하는 일: 묻기.** `ownerOf(칸)` 이 성립하지 않는다 →
> 사유에 상자를 못 싣고, 승격도 양보도 부를 대상이 없다.
> **㉮ 셋은 값 전달, ㉯ 하나는 시그니처 변경** — 계획 1 의 작업이 정확히 이 넷이다.

### 축 2 · 시간 — **같은 주체의 셀이 시각 때문에 두 그릇에 있다**

`routeDeliveryRoutes` 안에서 B(납품)의 셀이 두 군데다:

```ts
const deliveryBelts     = new Set<string>();              // B 의 **실물** (이미 깐 것)
const reservedDelivery  = new Map<string, Set<string>>();  // B 의 **예약** (계획된 체인)
```

둘은 **같은 종류의 셀**이고 차이는 *"벌써 깔았나"* 뿐이다. 그런데 그릇이 갈렸으니
판정 함수도 갈린 채로 받아야 한다:

```ts
function plannedChainClear(chain, ownKey,
  base, deliveryBelts, reservedExport, reservedDelivery, fluidBlocked?) : string | null
//      ↑ A       ↑ B실물      ↑ C예약        ↑ B예약        ↑ 유체
```

**시각이 자료형이 아니라 파라미터 자리로 표현돼 있다.** 새 시각이 생기면 파라미터가 는다.

> **없으면 못 하는 일: 승격.** `reserved → placed` 가 *"그릇 옮기기"* 라서,
> C 는 예약을 다시 못 알아본다 → #9(방출에선 B 가 이김)가 여기서 나온다.

---

### 축 3 · 무엇 — **"무엇"이 필드가 아니라 맵의 키로 있다**

유체 금지 칸은 **유체 이름마다 지도가 따로** 있다:

```ts
fluidBlocked?: ReadonlyMap<string, ReadonlySet<string>>;   // "water" → 금지 칸들
…
const mergeGuard = isFluid ? config.fluidBlocked?.get(delivery.item) : undefined;
//                                              ↑ **어느 지도를 꺼내느냐**가 곧 "무엇"이다
```

`Set<string>` 은 좌표만 담으므로 *"이 칸은 물 파이프다"* 를 못 적는다. 그래서 유체는
**셀 집합 위에 지도 계층을 하나 더** 쌓아야 했다.

그 결과 **B 가 깐 유체는 어디에도 안 적힌다** — `fluidBlocked` 는 모듈(A)의 파이프에서
만들어지고 납품 **전에 얼기** 때문이다. 적을 그릇이 없어서 안 적는 것이다.

#### 왜 얼 수밖에 없나 — **2항을 1항으로 접었기 때문이다(부분적용)**

인접은 *"칸 A 와 칸 B 가 닿나"* 라서 **2항**이다. 그런데 소비처가 받는 것은 1항이다:

```ts
fluidBlocked.set(fluid, pf.blockedTilesHard);          // moduleWizard — Set<칸>
…
if (fluidBlocked?.has(k)) return `유체 합류 가드 …`;    // deliveryRoute — 겹침 검사 넷 **한가운데**
```

`blockedTilesHard` 는 *"칸 B 자리에 이미 놓인 파이프를 다 넣어 두고 남은 칸 A 만 묻는"*
**부분적용**이다. 그래서 1항 검사 넷 사이에 자연스럽게 끼어 있다 — 위장이다.

**부분적용의 대가가 시각 고정이다.** 고정한 인자는 *어느 시점의* 파이프냐가 정해져야 하고,
`pipeFlowByFluid` 는 A 의 파이프로 만들어져 납품 **전에** 언다. B 가 깔 파이프는 그때
아직 존재하지 않으므로 **원리적으로** 들어갈 수 없다.

> **#7·#13 은 "규칙이 없어서"가 아니라 "2항을 1항으로 접었기 때문"이다.**
> 축 2(시간)와 같은 축이고, 위의 *"지도 계층을 하나 더"* 가 곧 **접힌 두 번째 인자**다.

> **없으면 못 하는 일: 규칙 달기.** 좌표만 있으면 *"다른 유체면 인접도 금지"* 를 물을
> 상대가 없다 → #7·#13 이 여기서 나온다.

### 축 4 · 등록 — **셀로 적는 코드가 아예 없다**

행 채널은 폭까지 계산해 놓고 **그 결과가 디버그로만 나간다**:

```ts
band.wantHeight = plan.height;
band.tracks     = plan.tracks;      // 696행
…
const t = plan.tracks.get(n.id);    // 699행 — 진입 행 하나 뽑고 끝
```

`pack.rowChannels` 를 읽는 곳을 전부 세면:

```
moduleWizard.ts:532   recordRowChannelStats  ← 통계
debug/report.ts:103                          ← 통계
debug/runStats.ts                            ← 통계
```

**배치가 읽는 곳이 0이다.** 마진 프레임도 같다 — `expandBbox` 로 bbox 만 키우고
*"여기는 통로다"* 를 셀로 적지 않는다.

> **없으면 못 하는 일: 존재.** 앞의 세 축을 다 갖춰도 **입력이 안 들어오면 없는 칸**이다
> → #15·#16 이 여기서 나온다.

### 그래서 넷이고, **순서가 강제된다**

| 축 | 정보가 없어서 못 하는 일 | 코드의 증거 |
|---|---|---|
| 1 주인 | **묻기** — 누가 잡았나 | ㉮ A·B·C방출이 `Set.add` 에서 평탄화 · ㉯ `addSeg` 는 인자조차 없다 |
| 2 시간 | **승격** — 내 예약을 내 실물로 | 같은 B 가 그릇 둘, 파라미터 둘 |
| 3 무엇 | **규칙 달기** — 유체끼리 인접 금지 | "무엇"이 맵의 키다 |
| 4 등록 | **존재** — 아예 안 보인다 | `rowChannels` 소비처가 디버그뿐 |

```
2 는 1 을 부른다   promote(owner) — 승격은 임자가 있어야 성립
3 은 1 을 부른다   "누구의 유체냐" 를 알아야 같은 유체 합류를 허용
4 는 1·2·3 을 부른다   등록해도 임자·시각·종류가 없으면 판정에 못 쓴다
```

**축이 하나씩 늘어나므로 각 계획이 독립으로 되돌릴 수 있다.**

### 계획 2 · 시간 — *(방향)*

`stage: "reserved" | "placed"` 를 `Claim` 에 더하고 `promote(owner)` 를 만든다.

> **정정(2026-08-21) — 옛 문장 *"#9 는 규칙을 안 고쳐도 사라진다 · 구조가 규칙을 대신하는
> 유일한 줄"* 은 틀렸다.** 코드를 읽고 내린다:
>
> B 가 C 의 예약 위에 오는 경로는 **`reservationOverrun` 하나뿐**이다 — 폴백의 **첫 시도도**
> `extra = new Set(reservedExport)` 로 예약을 피한다(`deliveryRoute`). 즉 #9 의 자리에는
> **B 의 벨트가 물리적으로 이미 놓여 있다.** 승격해도 그건 안 없어진다 —
> `reservation not emittable` 이 사라지는 대신 **진짜 겹침**이 나올 수 있다.
>
> **#9 의 처방은 소유가 아니라 비용 모델이다.** 그 자리 주석이 이미 적어 뒀다 —
> *"예약을 '막힘'이 아니라 '비싼 칸'으로 줘서 최소한만 밟게"*. 라우터에 **가중치 맵**을
> 넘기는 것이라 `blocked` 와 같은 모양이고 **제약 가를 안 깬다.** → J-정책전환으로 옮긴다.

**그래도 `stage` 는 필요하다 — 다만 하는 일이 "승격"이 아니라 "분류"다.**
지금 `reservation not emittable` 은 처방이 정반대인 두 원인을 한 문장으로 뭉갠다:

```
가.  C 가 자기 예약을 자기가 못 알아봤다        → 승격이 답이다
나.  B 가 예약을 밟았다(reservationOverrun)    → 비용 모델이 답이다.  **승격하면 겹친다**
```

**둘을 가르려면 `owner` 와 `stage` 가 둘 다 있어야 한다.** 그리고 갈라야 J-정책전환이
*"바꾸면 몇 건이 달라지나"* 를 셀 수 있다.

관문: *"예약과 실물이 같은 것의 두 시각"* 이 자료형으로 굳고, **위 가/나가 수치로 갈린다.**
전제(확인 필요): 계획 1 이 `owner` 를 심었을 것. `promote` 는 owner 없이 못 만든다.

그리고 그 수치가 **J-인접흡수의 계측기**다 — 0건이면 자료구조를 안 바꾼다.

관문: *"어디에 넣나"* 가 사라진 뒤라 **`add` 한 줄**이 된다.

## 5. 전 계획 공통 제약 — 발견 3·4 와 J-구간흡수 에서 유도

```
가.  장부는 **라우터 안으로 안 들어간다**       계획·판정은 장부, 탐색은 라우터 (발견 3)
나.  장부는 **파이프라인이 소유하고 주입**한다   패스가 소유하면 테스트 45곳이 안다 (발견 4)
다.  **정책 A(먼저 온 쪽)** 로만 판정한다        오늘 그대로. 피해 등급은 J-정책전환
라.  **㉢ 의 규칙은 비운다**                    claim 은 들어오되 규칙이 없다 (사용자 결정)
마.  **장부는 아리티 1(겹침)만 맡는다**          인접은 2항, 페어링은 구간 — 담을 수 없다 (J-구간흡수)
```

**다·라가 "동작 불변"의 근거다.** 다섯 중 하나라도 깨면 그 계획은 구조정리가 아니다.

**마 — 아리티가 장부의 경계다.** *"답을 내려면 칸을 몇 개 동시에 봐야 하나"* 로 갈린다:

```
겹침    칸 **하나**의 성질        장부 Map<칸, 주인>        ← 지금 넷.  이 계획이 합치는 것
인접    칸 **쌍**의 성질          pipeFlow                  → J-인접흡수
페어링  **직선 구간**의 성질      UndergroundCorridor       → J-구간흡수
```

새 사실이 오면 *"어느 장부에 넣나"* 가 아니라 **"몇 항인가"** 를 묻는다 — 행 채널(#15)과
마진(#16)은 1항이라 장부로 가고, *"다른 유체면 인접 금지"*(#7·#13)는 2항이라 **장부에 넣으면
안 된다.** 계획 4 의 주장(*고르는 일이 없어진다*)이 성립하는 범위가 정확히 **아리티 1** 이다.

  "반출 예약 재생 — 예약을 켜도 skip 이 끈 것보다 늘지 않는다"

계획이 아니기 때문이다. 초록으로 만드는 것은 **비용 모델**(§4 계획 2 정정 · J-정책전환)이다.

> 이 줄은 *"다음에 무엇을 해야 하나"* 의 과녁으로 남긴다.
