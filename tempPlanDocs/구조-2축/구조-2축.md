# 구조 2축 — 폴더는 관심사, 파일은 일의 종류

> 상태·공통 컨텍스트·하지 않는 것은 [CLAUDE.md](CLAUDE.md) 가 든다. 여기는 **목표와 순서**다.

## 1. 무엇을 고치려는가

세 가지가 같은 뿌리에서 나온다.

| 증상 | 실측 |
|---|---|
| **파일을 찾으려면 두 축을 알아야 한다** | `module` 이라는 이름이 세 폴더에 있고, `link` 는 폴더(`planner/link/`)와 파일(`module/arith/trunk/link.ts`)이 동명 |
| **변경이 폴더를 넘나든다** | 2026-07-26 이후 2~12파일 커밋 61개 중 **한 폴더에서 끝난 것은 15개**. 함께 바뀐 파일 쌍의 74%가 경계를 넘는다. 조율자 둘을 빼고 폴더 기준을 바꿔 다시 세면 국소율이 26% → 58% 로 오른다 |
| **거대 파일** | 결정 종류를 셋 이상 겸한 파일 일곱이 **전부 500줄 이상** → [work-kinds §5](../../docs/auto-layout/common/work-kinds.md) |
| **거대 함수** | 200줄 넘는 함수 **여덟**. `packModuleTree` **868** · `runModulePipeline` **714**. 60줄 넘는 *중첩* 함수는 셋뿐(최대 87)이라 **본문이 그냥 길다** — 파일만 옮기면 이 수는 하나도 안 준다 |

셋 다 **축이 하나 모자라서** 생긴다. 오늘의 폴더는 *"무엇에 대한 일인가"* 와 *"계획인가 실행인가"* 로
나뉘는데, 실제로 파일 안을 가르는 선은 **일의 종류**다.

## 2. 목표 — 규칙 세 줄

1. **폴더 = 관심사.** `run`(한 번의 실행 전체) · `tree` · `module` · `link` · `channel` · `perimeter`, 관심사가 없는 것은 `shared`.
2. **파일 = 종류.** `types`(타입) · `arith`(셈) · `ledger`(장부) · `shape`(도형) · `policy`(정책) ·
   `emit`(찍기) · `build`(조율) · `late`(늦은 결정).
3. **한 종류가 300줄을 넘으면 그 파일을 폴더로 승격**한다(`module/shape/body/`).
   근거는 실측이다 — 종류 하나만 담은 파일의 최대가 335줄이었다(타입·조율 제외).
4. **함수는 종류로 먼저, 시점으로 다음.** ①**종류가 바뀌는 곳**에서 가르면 조각이 다른
   파일로 간다(규칙 2 를 함수 안으로). 그러고도 한 종류가 크면 ②**단계마다 아는 것이
   달라지게** — 조각 하나는 *"무엇을 알고 들어와 무엇을 알고 나가나"* 로 정의된다.
   길다는 것 자체는 자를 이유가 아니고, **붙은 두 블록이 같은 것을 알면 경계가 아니다.**
   **②가 답을 안 주면 안 가른다**(탐색이 그렇다 — 아는 것이 안 자란다).
   축은 함수마다 다르다 — 좌표는 `packModuleTree` 에서 그 변화가 나타난 **형태**일 뿐이다.
   이 규칙으로 계획 2 가 실제로 자른 기록은 [work-kinds §5](../../docs/auto-layout/common/work-kinds.md) 가 든다.

이름이 겹치는 것이 의도다 — `shape.ts` 가 **다섯**(tree·module·link·channel·perimeter)이고,
그 다섯은 폴더가 구분한다. `types.ts` 도 여섯이다.
지금처럼 `module` 이 세 폴더에 흩어지는 것의 반대다.

## 3.5 계획 3 — **계획서를 따로 쓰지 않는다**

**남은 것이 결정이 아니라 이동이라서다.** 큰 파일 일곱의 행선지는 §3 이 들고, 자르는 판정은
계획 2 가 끝냈다. 계획 3 이 새로 정할 것은 **§3 이 안 덮은 파일들의 주소** 하나뿐이고,
그 판정은 이미 적힌 기준(폴더 = 관심사 · 파일 = 종류 · 규칙 3)이 답한다. 아래 표가 그 답이고,
**이 표가 계획서 자리를 대신한다** — 실행이 끝나면 [code-folders](../../docs/auto-layout/common/code-folders.md) 가 이어받는다.

### 게이트 — 단계마다 셋 다 본다

```
npx tsc -p tsconfig.app.json --noEmit     타입 0
npx vitest run                            62파일 784테스트(기존 실패 2 — trunkPipe 유체 면)
대조 덤프 32 픽스처 × 플래그 다섯          **바이트 단위로 같아야 한다**   ← 이동이 배치를 안 바꿨다는 유일한 증거
```

기준선 덤프는 **이관 직전 커밋**(`20d74d9`)에서 뜬 것을 쓴다. 덤프가 달라지면 그 단계는
이동이 아니라 **변경**이었다는 뜻이므로 멈춘다.

### 순서 — 아래에서 위로

```
1 shared   ✅   2 run   3 tree   4 module   5 link   6 channel   7 perimeter   8 docs·CLAUDE.md
```

관심사 하나가 커밋 하나다. `shared` 가 먼저인 것은 **바닥이라서**다 — 나중에 옮기면 그 위를
두 번 고치게 된다.

## 4. 이 구조가 만드는 import 규칙 다섯

산문으로 적힌 규칙이 검사 가능한 문장이 된다(계획 4).

| 규칙 | 무엇을 지키나 |
|---|---|
| `shape` → `ledger` **금지** | **도형이 자원 상태를 모른다.** 계획과 방출이 같은 함수를 부를 수 있는 근거 |
| `emit` → `policy` **금지** | 찍기는 고르지 않는다 |
| `shared/*` → 관심사 폴더 **금지** | 공용은 위를 모른다 |
| `module` → `link`·`channel`·`perimeter` **금지** | 관심사 경계 |
| 스토어는 **진입점**(`run/build.ts`)**만** | 오늘 `useGameDataStore.getState()` 가 다섯 곳에 흩어져 있다. 처음엔 *"`shared/gamedata.ts` 만"* 으로 적었는데 인터뷰 확정 문장이 *"진입점 한 곳으로 모아 주입"* 이다 — 2026-09-13 고침(계획 2 §4.2) |

첫 줄이 핵심이다. 오늘 도형이 두 벌인 이유가 **계획 쪽 도형이 장부를 읽으면서 계산하기**
때문이다(`beltRowSpan` 이 표에서 빈 좌석을 찾아 그 결과로 포트 칸을 구한다). 장부 읽기를
정책으로 올리고 도형은 **배정 결과만** 받게 하면 방출도 같은 함수를 부를 수 있다.

## 5. 정직하게 잃는 것

**트리가 실행 순서를 말하지 않는다.** 폴더를 먼저 보는 사람에게는 실제 손해다.
완화책은 실행이 `run/` 한 폴더에서 시작한다는 것 — 그 폴더의 `build.ts` 뼈대가 단계를 순서대로 부른다.

폴더에 번호를 붙여 순서를 드러내는 안은 **기각했다. 거짓말이 되기 때문이다** —
`module` 과 `link` 는 얽혀 돈다. 링크 하나를 앉히려면 두 모듈의 장부를 함께 봐야 해서
`seatLinkEdge` 가 **링크 축으로 돌면서 모듈 장부를 쓴다**. 번호는 이 사실을 감춘다.
