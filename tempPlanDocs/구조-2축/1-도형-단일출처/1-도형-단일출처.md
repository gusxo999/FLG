# 계획 1 · 도형 단일 출처 — 계획과 방출이 같은 함수를 부른다

> 상태·미확인·이 계획 고유의 맥락은 [CLAUDE.md](CLAUDE.md), 전체 설계는 [../구조-2축.md](../구조-2축.md).

## 1. 문제 — 도형이 두 벌이다

한 링크 그룹이 면에 앉으면 그 배정은 **칸을 여럿 먹는다**: 좌석(d1) · 벨트(d`clusterBeltDepth`) ·
포트 인서터와 상자(두 칸) · gap 이면 반출 줄까지. 그 칸이 어디인지를 **두 곳이 각자 계산한다.**

| 어디 | 무엇을 계산하나 | 무엇에 쓰나 |
|---|---|---|
| `planner/module/linkPlanner.ts` | `beltRowSpan`(행 범위) → `portCells`(포트 칸 둘) → `splitByTable`(표 안 / 기둥 밖) | 장부에 **청구**하고 충돌을 검사한다 |
| `execution/module/emitModule.ts` | `topT`/`botT` → `path`(반출 · 올라오기 · 수집) → `span`(포트 두 칸 포함) | 실제로 **셀을 놓는다** |

**둘이 갈리면 조용히 깨진다.** 계획이 안 센 칸에 방출이 놓으면 남의 자리를 밟고, 계획이 센
칸을 방출이 안 쓰면 그 자리가 낭비된다. 코드가 이미 그 위험을 알고 있다 —
`splitByTable` 의 주석은 *"검사와 청구가 **같은 함수**를 부르게 해서 둘이 갈리지 않게 한다.
갈리면 배정이 못 본 다툼이 방출에서 터진다"* 라고 적는다. **그 원칙이 계획–방출 사이에는
적용돼 있지 않다.**

지금 둘을 붙들고 있는 것은 `portCells` 주석의 줄 번호(`emitModule.ts:66`·`:214`·`:381`)뿐이다.
→ [work-kinds §7 D1](../../../docs/auto-layout/common/work-kinds.md)

### 왜 이렇게 됐나 — 계획 쪽 도형이 **장부를 읽는다**

`beltRowSpan` 은 표에서 **빈 좌석을 앞에서부터** 집어(`freeSeatRows`) 행 범위를 구한다.
즉 계획 쪽 도형은 *"아직 안 정해진 배정"* 을 전제로 도형을 **미리 그려 보는** 함수다.
방출 쪽은 이미 확정된 `slots` 로 같은 도형을 다시 그린다. 입력이 달라서 함수를 공유할 수가 없다.

**그래서 순서가 이렇게 된다:** 장부 읽기를 정책으로 올리고 → 도형은 **확정 배정만** 받게 하고
→ 그러면 두 곳이 같은 함수를 부를 수 있다.

## 2. 어떻게 하나 — 네 단계

### 1단계 · 대조 계측 (동작 변화 0)

두 도형이 실제로 같은 답을 내는지 **먼저 잰다.** 이 저장소가 이미 쓰는 방법이다 —
`endsDisagree`·`endsCoarse` 가 옛 판정과 새 판정을 나란히 돌려 대조한다.

```
계획 쪽   확정된 배정(LinkFacePlan + LinkSeats.slots)에서 (face, depth, t) 집합을 유도
          ※ try 시점의 예측이 아니라 **commit 된 값**에서 유도해야 방출과 비교된다
방출 쪽   emitOutputLinks · emitInputLinks 가 faceCell(...) 을 부르기 직전의 (face, d, t) 를 모은다
대조      linkId 로 짝지어  onlyPlan / onlyEmit 을 센다
```

- 기록은 `debug/runStats.ts` 에 카운터 하나(`recordShapeDiff`) — **이름 규약 `record*` 를 따른다.**
- `flg.report()` 에 한 줄 — `도형대조  일치 N · 계획만 a · 방출만 b`.
- 계측 코드에 **관측 전용** 표식 주석을 단다(*"지워도 배치가 안 바뀐다"*).

### 2단계 · 실측 — **멈춤 게이트**

실게임 데이터로 여러 레시피를 돌려 대조 수를 본다(`flg.run()` → `flg.report()`).

| 결과 | 다음 |
|---|---|
| 전부 0 | 3단계로. 합쳐도 배치가 안 바뀐다는 것이 **측정으로** 보장된다 |
| 0 이 아니다 | **멈추고 보고한다.** 불일치의 내용이 곧 [CLAUDE.md](CLAUDE.md) 의 미확인 셋에 대한 답이다 |

### 3단계 · 도형을 한 곳으로

새 파일 `src/autoLayout/module/linkShape.ts` — **오늘 트리 안에 둔다**(폴더 이관은 계획 3).
`module/` 이 맞는 자리인 이유: 모듈 안쪽 도형이고, `planner/` 와 `execution/` 양쪽이 아래로
내려다보는 위치라 계층이 안 뒤집힌다.

```ts
/** 확정된 배정 하나가 먹는 칸 — 좌표가 아니라 (면, 깊이, 면 위 위치)다. */
export interface ShapeCell {
  kind: "seat" | "belt" | "portInserter" | "portChest" | "corner";
  face: PortFace; depth: number; t: number;
}
/** 배정 → 칸. **장부를 안 본다**(입력이 이미 확정된 배정이다). */
export function linkShapeCells(seated: LinkSeats, geom: { count; machine }): ShapeCell[];
```

- **계획 쪽**(`commitLinkFace`·검사)은 `ShapeCell` 을 장부 청구에 쓴다 — `portCells` 는 지운다.
- **방출 쪽**(`emitOutputLinks`·`emitInputLinks`)은 같은 목록을 `faceCell` 로 절대 좌표에 얹고
  `cellBuilder` 로 찍는다 — `path`/`span` 의 도형 계산은 지운다.
- `tryLinkFace` 의 **예측**(아직 안 앉은 후보의 행 범위)은 정책 쪽에 남는다. 도형이 아니라
  *"이 후보를 앉히면 어떤 배정이 되나"* 이기 때문이다. 그 산출을 `linkShapeCells` 에 넣어
  같은 칸 목록을 얻는다 — **예측과 확정이 같은 도형 함수를 쓰게 된다.**

### 4단계 · 계측을 지운다

`recordShapeDiff` 와 그 배관, `flg.report()` 의 한 줄을 지운다.
`work-kinds.md` §7 의 **D1 을 지우고**, D2(방출이 고른다)·D3(모순 주석)이 함께 해소됐는지 본다.

## 3. 대안 검토

| 안 한 것 | 왜 |
|---|---|
| **바로 합친다**(계측 없이) | 두 도형이 미세하게 다르면 합치는 순간 배치가 바뀌는데, 그때는 *"리팩토링이 깨뜨렸다"* 와 *"원래 갈려 있었다"* 를 구분할 수 없다 |
| **플래그 뒤에서 새 경로** | 도형은 계획·방출 양쪽이 부르는 것이라 플래그를 걸면 **네 조합**이 생긴다. 계측은 조합을 안 늘린다 |
| **방출을 계획 쪽으로 흡수** | 방출에는 도형 말고 찍기(엔티티 이름·방향 규약)도 있다. 통째로 옮기면 종류가 다시 섞인다 |
| **유체(`emitTrunkPipe`)까지 포함** | 유체는 배정을 안 한다 — `fluid_boxes` 가 정한 답을 받아쓴다. 도형의 입력이 배정이 아니라 프로토타입이라 성격이 다르다. 이번 범위 밖 |

## 4. 실패하면 어떻게 되나

- 1단계는 관측뿐이라 실패해도 배치가 안 바뀐다.
- 3단계에서 좌표 덤프가 달라지면 **되돌린다**(커밋 하나로 유지한다).
- 합치는 도중 `exitDepth`·레인 합류 둘째 줄처럼 한쪽만 아는 값이 나오면, **그 값을 도형의
  입력으로 올린다** — 도형 안에서 장부나 배정을 다시 읽지 않는다(그러면 D1 이 재발한다).
