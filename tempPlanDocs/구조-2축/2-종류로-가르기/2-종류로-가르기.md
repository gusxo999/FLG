# 계획 2 · 종류로 가르기 — 파일 하나가 한 가지 일만 하게

> 상태·이 계획 고유의 맥락·하지 않는 것은 [CLAUDE.md](CLAUDE.md), 전체 설계는
> [../구조-2축.md](../구조-2축.md), 종류의 정의는
> [work-kinds](../../../docs/auto-layout/common/work-kinds.md).

## 1. 푸는 문제

### 1.1 이미 아는 것 — 크기는 증상이고 원인은 섞임이다

> **"파일이 크다"는 증상이고 원인은 "종류가 섞였다"이다.** 줄 수 상한을 규칙으로 두는
> 대신 종류를 묻는다 — 500줄이 넘는데 종류가 하나면(조율·타입) 그건 정상이다.
> — [work-kinds §5](../../../docs/auto-layout/common/work-kinds.md)

결정 종류(셈·장부·도형·정책)를 셋 이상 겸한 파일 일곱은 예외 없이 500줄을 넘고, 종류
하나만 담은 파일의 최대는 335줄이다. 그 사실은 이미 측정돼 있다.

### 1.2 새로 잰 것 — **타입이 파일의 1/4을 덮고 있다**

착수 전 전수 측정했다(타입·인터페이스 선언 + 그 머리말 주석의 줄 수).

|---|---:|---:|---:|
| `containerModel.ts` | 432 | 524 | **82%** |
| `module/clusterModule.ts` | 249 | 612 | **41%** |
| `planner/perimeterExitPlanner.ts` | 208 | 593 | 35% |
| `planner/module/linkPlanner.ts` | 262 | 1038 | 25% |
| `planner/containerRouting.ts` | 117 | 581 | 20% |
| `module/link.ts` | 178 | 918 | 19% |
| `planner/modulePacking.ts` | 226 | 1358 | 17% |
| `planner/module/planModulePorts.ts` | 146 | 935 | 16% |

두 끝이 뜻을 갖는다. `containerModel` 82% 는 **이미 타입 파일**이고 work-kinds 가 그것을

`containerModel` 을 뺀 열한 파일에서 타입이 **1,648줄**이다.

> **이 표가 뜻하지 않는 것 — 타입을 떼도 결정 종류의 경계는 안 드러난다.**
> work-kinds §5 의 일곱 파일에서 타입을 뺀 잔량이다.
>
> ```
> modulePacking 1132 · planModulePorts 789 · linkPlanner   776 · channelGeometryPlanner 646
> deliveryRoute  619 · containerRouting 464 · perimeterExitPlanner 385
> ```
>
> **여섯이 여전히 400줄을 넘는다.** 이 표는 *"타입이 어디에 얼마나 흩어져 있나"* 만
> 말한다. 타입을 먼저 떼는 이유는 §1.3 이 따로 댄다.

### 1.3 그래서 무엇이 아픈가 — **타입을 가지러 가는 길이 계층 위반이 된다**

타입이 크다는 것만으로는 아프지 않다. 아픈 것은 **타입이 어느 폴더에 사느냐**다.
`src/autoLayout` 의 폴더 간 import 를 값(런타임)과 타입(컴파일에 지워짐)으로 갈라 전수
세었더니 셋이 나왔다.

#### ① 런타임 순환은 저장소에 정확히 **하나**이고, 원인은 **6줄짜리 순수 함수**다

```
execution/module/emitModule.ts  →  module/clusterModule.ts  →  execution/module/emitModule.ts
```

`emitModule.ts:45` 의 `import { trunkEndKey }` 한 줄이다. 그 바로 위 44줄이 이유를 적는다:

> *"trunkEndKey 는 계획 산출물(트렁크 종착 키)이라 clusterModule 소유 — 런타임 import."*

**소유권 판단은 옳고 주소가 틀렸다.** `trunkEndKey` 는 `PlannedLine` 과 `lineEnds` 를 읽어
문자열 키를 만드는 6줄짜리 순수 함수 — 자원도 좌표도 안 보고 답이 하나인 **셈**이다. 그것이
조율자(`clusterModule`) 파일에 얹혀 있어서, 방출기가 그 6줄을 쓰려면 조율자를 런타임으로
불러야 한다.

**그리고 이 순환은 코드가 스스로 부인하고 있다.** 두 곳이 같은 거짓을 적는다:

| 어디 | 무엇이라 적나 |
|---|---|
| [emitModule.ts:18-19](../../../src/autoLayout/execution/module/emitModule.ts) | *"`clusterModule` 과의 관계: 이쪽이 저쪽 타입을 **`import type` 으로만** 본다(런타임 간선은 `clusterModule → emitModule` 한 방향뿐 — 순환 아님)."* |
| [execution/CLAUDE.md](../../../src/autoLayout/execution/CLAUDE.md) 끝줄 | *"역방향은 `import type` 이라 순환이 아니다."* |

→ [work-kinds §7 **D4**](../../../docs/auto-layout/common/work-kinds.md)

#### ② `execution/module → planner/module` 간선은 **정확히 두 줄**이고 둘 다 타입이다

```ts
emitModule.ts:22   import type { IoLine, PlannedLine, PortSide } from "../../planner/module/ioLine";
emitModule.ts:40   import { flowEnd, type LinkSeats } from "../../planner/module/linkPlanner";
```

방출기가 계획 계층을 올려다보는 이유가 **타입 넷과 함수 하나**뿐이다. `flowEnd` 는
`cand.portEnd ?? cand.exitEnd ?? "N"` — 3줄짜리 단일 출처 유도다.

#### ③ `module/ → planner/module` 타입 간선 셋도 같은 모양이다

```ts
clusterModule.ts:23-28  import { type IoLine, type PlannedLine, type PortSide, type SupplyCapacity } from "../planner/module/ioLine";
clusterModule.ts:35     import type { DepthShortage, LinkFacePlan, LinkSeats } from "../planner/module/linkPlanner";
link.ts:34              import type { IoLine, SupplyCapacity } from "../planner/module/ioLine";
```

`module/` 은 [code-folders 축 2](../../../docs/auto-layout/common/code-folders.md) 가
*"형제 모듈을 모른다"* 로 정의한 **가장 아래 관심사**인데, 자기 타입을 위층에서 빌려 온다.

### 1.4 저장소가 이 처방을 **이미 한 번 썼다**

`planner/module/ioLine.ts` 머리말:

> **여기엔 판단이 없다** — 타입뿐이다. 그래서 계획·배정·방출이 다 같은 타입을 쓰면서도
> 서로를 import 하지 않는다.
>
> > **이 타입들은 `clusterPortPlanner.ts` 에 있었다**(2026-09-02 분리).

**그 판단은 옳았고, 주소만 미완이었다.** 타입을 떼어 낸 것까지는 했는데 그 파일이
`planner/module/` 에 남았고, 그래서 지금 `module/` 과 `execution/` 이 타입을 가지러 위로
올라간다(§1.3 ②③). 계획 2 는 새 규칙을 만드는 것이 아니라 **그때 시작한 일을 끝낸다.**

### 1.5 진짜 단위는 파일이 아니라 **함수**다

**파일을 갈라도 함수가 안 갈라지면 아무것도 안 읽힌다.** 그래서 같은 방식으로 함수를
셌다(문자열·주석을 지운 사본에서 중괄호 짝을 맞춰 잰 길이).

| 줄 | 함수 | 어디 |
|---:|---|---|
| **868** | `packModuleTree` | `planner/modulePacking.ts:337` |
| **714** | `runModulePipeline` | `planner/moduleWizard.ts:147` |
| 317 | `planModulePorts` | `planner/module/planModulePorts.ts:618` |
| 253 | `emitOutputLinks` | `execution/module/emitModule.ts:205` |
| 230 | `planChannelGeometry` | `planner/channelGeometryPlanner.ts:518` |
| 209 | `emitInputLinks` | `execution/module/emitModule.ts:467` |
| 208 | `tryLinkFace` | `planner/module/linkPlanner.ts:495` |

60줄 이상 28개 · 100줄 이상 15개 · **200줄 이상 8개**.

**함수 안의 함수는 문제가 아니다** — 60줄 넘는 중첩 함수가 셋뿐이고 최대 87줄이다.
즉 큰 함수는 *"작은 함수를 많이 품은 것"* 이 아니라 **본문이 그냥 길다.** 파일을 옮기는
것만으로는 이 수가 하나도 안 준다.

#### 이 표가 계획 밖에서 2위를 데려왔다 — `moduleWizard`

`runModulePipeline` 714줄은 [work-kinds §5](../../../docs/auto-layout/common/work-kinds.md) 가
**면제해 둔 파일**에 있다: *"500줄 이상 12파일 … 나머지 둘은 결정하지 않는 일만 담았다:
moduleWizard 913(조율)."*

**그 분류가 틀렸고, work-kinds 가 같은 문서 안에서 스스로 반박한다** — §3 이 *"게임데이터
조회가 파이프라인 안쪽 네 곳에 흩어져 있는데 그 넷이 전부 [어댑터]"* 라고 적었고
`moduleWizard.ts:150` 이 그 넷 중 하나다. **조율만 하는 파일에 어댑터가 있을 수 없다.**

읽어 보니 한 함수 안에 최소 넷이 있다.

| 종류 | 어디 | 무엇 |
|---|---|---|
| **어댑터** | `:150` + `entityMap`·`recipeMap` 조회 **9곳** | 게임데이터 → 우리 타입 |
| **정책** | `:172-290` 0-)·0) 적격성 | 벨트·인서터 미선택 거절 · 유체가 범위 밖이면 **옛 경로로 폴백** — 대안 중에서 고른다 |
| **장부** | `:508-560` | `pipeFlowByFluid` 를 쌓고 유체별로 질의해 `fluidBlocked` 를 낸다 |
| **조율** | 전체 뼈대 | `packModuleTree` → `routeDeliveryRoutes` → `rePathToPerimeter` |

**이 발견은 계획을 무너뜨리지 않고 좁힌다.** *"크다 = 섞였다"* 의 반례로 서 있던 파일이
반례가 아니었다 — 500줄 넘는 12파일 중 **종류 하나인 것은 `containerModel`(타입) 하나**다.

## 3. 무엇을 가르나 — 판정

### 3.1 타입을 어디까지 한 파일로 모으나 — 판정 둘

**타입의 정체는 work-kinds §3 이 이미 정했다** — 실행되지 않으면 타입이다, 그뿐이다.
여기서 정하는 것은 다른 질문이다: 타입인 것들 중 **어디까지 한 파일로 모으나.**
*"타입이면 전부"* 는 너무 넓다 — 그러면 함수의 서명까지 딸려 가서 계약이 두 파일로 갈린다.

```
① 타입 파일에 **모으는** 것은 여러 종류가 함께 읽는 어휘다.
   한 종류만 쓰는 것도 타입이다(정체는 안 바뀐다) — 다만 모아 낼 짝이 없어
   **그 함수의 서명 자리에 남는다** → 제자리.
② 값(함수·상수)은 **그 어휘를 읽어 답하면서 층을 건널 때만** 함께 간다.
```

②가 있는 이유는 **보수성**이다. 값을 옮기는 것만이 런타임 간선을 옮기고, 옮길 이유가
없는 값까지 옮기면 *"배치가 안 바뀐다"* 는 보장이 그만큼 약해진다. 판독 함수라도 같은
층에서만 불리면(`beltLineForm`·`groupRate`·`rungOfLine`) **제자리에 둔다.**
②를 통과하는 값은 실측으로 **둘뿐이다**: `trunkEndKey`(6줄) · `flowEnd`(3줄). 둘은 타입이 아니라 **셈**이라 타입 파일이 아니라 `module/arith.ts` 로 간다(§4.1).

①에 걸러져 **안 옮기는 것들** — 판정이 실제로 일하는지 보이라고 적는다:

| 안 옮기는 타입 | 어디 | 왜 |
|---|---|---|
| `FaceTable` | `planner/module/faceTable.ts` | 좌석표 자신과 배정기만 읽는다. 장부의 *모양*이라 떼면 `claimSeats`·`depthClear` 의 계약이 두 파일로 갈린다 → 장부째 옮기는 것은 Step 3 |
| `ShapeCell`·`LinkShape` | `module/linkShape.ts` | **이미 관심사 폴더의 단일 종류 파일**에 산다. 계획 1 이 그렇게 세웠고 주소가 안 틀렸다 |
| `LinkLimits` | `module/link.ts` | `createLinks` 의 인자 — 셈 하나의 서명 |
| `BeltFormCounters` | `module/link.ts` | 관측 계수기의 서명. 읽는 곳이 `debug/` 뿐이고 `debug/` 는 계층 축 밖이다 |
| `LinkFaceCandidate` | `planner/module/linkPlanner.ts` | export 도 안 된 국소 타입 |

### 3.2 함수는 어디서 가르나 — **종류가 먼저, 그다음 시점**

**기준은 둘이고 순서가 있다.**

> ① **종류가 바뀌는 곳에서 가른다.** [work-kinds](../../../docs/auto-layout/common/work-kinds.md)
> 의 여덟이 그 축이다. 이것이 조각을 **다른 파일로** 내보낸다.
>
> ② 그러고도 한 종류가 크면 — **단계마다 아는 것이 달라지게 가른다.** 조각 하나는
> *"무엇을 알고 들어와서 무엇을 알고 나가나"* 로 정의된다. 이것은 조각을 **같은 파일
> 안에서** 이름 붙은 단계로 나눈다. (2026-09-13 사용자 확정)

둘이 하는 일이 다르다. ①은 *"이 코드가 무엇을 묻나"*, ②는 *"이 코드가 무엇을 아나"* 다.

#### ②가 자를 자리만큼 **자르면 안 되는 자리**를 정한다

②는 경계를 찾아 주기만 하는 게 아니다. **붙어 있는 두 블록이 같은 것을 알고 있으면
거긴 경계가 아니다** — 길어도 붙여 둔다. `packModuleTree` 의 `2) 납품 짝짓기` 145줄이
그렇다: 안에서 새로 알게 되는 것이 없으므로 **한 덩어리로 남긴다.**

그리고 검사된다 — **앞 단계는 뒤 단계의 산출을 안 읽는다.** 어기면 이름 하나로 잡힌다.

#### 축은 함수마다 다르다 — 좌표는 한 함수에서 나타난 **형태**일 뿐이다

*"좌표를 아나"* 를 규칙으로 굳히면 안 된다. 그건 `packModuleTree` 의 뒤쪽 두 단계에서
변화가 드러난 모습이었을 뿐이고, 다른 함수는 다른 것을 알아 간다.

| 함수 | 아는 것이 어떻게 자라나 |
|---|---|
| `packModuleTree` | 링크 → 모듈 모양 → 포트 짝 → 폭 수요 → **평면 위치** → 절대 좌표 |
| `runModulePipeline` | 게임데이터·트리 → 머신 수·rate → **배치** → 납품 경로 → 최종 배치 |

두 사슬에 공통인 것은 좌표가 아니라 **"한 칸 갈 때마다 모르던 것이 하나 정해진다"** 는
모양뿐이다. 그것이 기준이다.

#### 적용 ① — `packModuleTree` 의 사슬 여섯

| # | **새로 아는 것** | 줄 | 오늘 주석 |
|---|---|---:|---|
| ① | 링크가 무엇인가 — 어느 간선이 몇 줄로 갈리나 | 337-705 | `P0` |
| ② | 모듈이 어떻게 생겼나 — 높이·로컬 포트 | 706-742 | `1) 생성 — 한 번뿐이다` |
| ③ | 누가 누구에게 주나 — 포트 짝 | 743-887 | `2) 납품 짝짓기 — **좌표 없이**` |
| ④ | 얼마나 넓어야 하나 — 세로 순서·트랙 수요 | 888-957 | `3) … **전부 좌표가 없다**` |
| ⑤ | 평면 어디에 앉나 | 958-1140 | `4) 세로 좌표` · `5) 폭·출구·colX` |
| ⑥ | 절대 좌표 | 1141-1205 | `6/7) absById · placements` |

**①과 ②의 순서가 이 함수의 핵심 사실이다** — 끝 선호를 `gen` **앞**에서 확정한 덕에
생성이 한 번으로 끝난다(`:719` *"되먹임 0"*). 사슬로 가르면 **그 사실이 구조로 보인다.**

주석만 믿지 않고 쟀다. ⑤가 정말 새 정보인지는 코드가 스스로 적어 두었다 — ③ 안의
좌표 여섯 줄은 전부 **모듈-로컬**이고, 평면 값은 자리표시자로 비워 둔다:

```ts
796  /** **나중에 채운다** — 절대 행은 세로 좌표가 선 뒤에 온다(6단계). */  portY: number;
798  /** 포트의 **모듈-로컬** 행. `portY` 를 나중에 계산하는 재료다. */    anchorY: number;
836  portY: 0,                          // ← 6단계가 채운다
839  x2: port.anchor.x - ownerExt.x,    // 상자의 로컬 x
```

`portY: 0` 이 곧 경계 표지다 — **그 조각은 답을 모른다고 스스로 적는다.** 평면 값을
지는 이름 셋은 전부 958줄 뒤에 처음 나온다(`topY` 972 · `colX` 1136 · `absById` 1141).
그래서 ④→⑤ 는 **검사되는 경계**다.

#### 적용 ② — `runModulePipeline` 은 사슬을 찾을 필요가 없었다

경계가 곧 호출 지점이다 — `:449 packModuleTree` · `:610 routeDeliveryRoutes` ·
`:696 rePathToPerimeter`. 세 호출이 각각 새 정보를 들여온다(§4.2 표).

#### 두 기준을 겹치면

```
①종류  →  타입 226 · 정책 350 · 장부 70 · 도형 366  을 다른 파일로 내보낸다
②시점  →  남은 조율 ~280 을 사슬의 이름 붙은 단계로 나눈다
```

**①이 파일을 정하고 ②가 함수를 정한다.** 순서가 있는 이유는, 종류를 안 뺀 채 사슬로
가르면 한 단계 안에 여전히 넷이 섞여 있기 때문이다.

#### 사슬이 없는 함수는 안 가른다

`searchWithJumps` 207줄에는 이 사슬이 없다 — 탐색은 진행하면서 아는 것이 **자라지 않고**
같은 질문을 반복한다([work-kinds §6](../../../docs/auto-layout/common/work-kinds.md) 이 이미
판정했다). `planChannelGeometry` 의 백트래킹 `search` 도 같다. **②가 답을 안 주면
안 가른다** — 기준 없이 가르면 다음 사람이 그 경계를 안 믿는다.


## 4. 단계

**목표 지표는 함수다** — 200줄 넘는 함수 여덟(§1.5). 각 단계가 그 수에 무엇을 하나:

| Step | 200줄+ 함수 | 무엇을 하나 |
|---|---|---|
| **1** 타입 | 8 → **8** | **아무것도 안 한다.** 의존의 바닥을 놓고 D4 를 닫는다 |
| **2** 어댑터 | 8 → **7** | `runModulePipeline` 714 → 조율 ~150 + 넷(§4.2) |
| **3** 결정 종류 | 7 → **?** | `packModuleTree` 868 · `planModulePorts` 317 · `tryLinkFace` 208. 기준은 §3.2 로 **확정**(종류 → 시점) — 남은 것은 함수마다 시점 사슬을 재는 일 |
| **4** eslint | — | 규칙을 검사로 |

**Step 1 이 지표를 안 움직이는 것을 숨기지 않는다.** 그런데도 먼저 하는 이유는 둘이다.

1. **타입은 다른 모든 종류가 의존하는 바닥**이라, 나중에 떼면 이미 가른 함수를 다시 건드린다.
2. **타입 이동은 런타임에 존재하지 않는 변경**이다. 그래서 좌표 덤프가 한 칸이라도 움직이면
   그건 이 계획의 실패가 아니라 **검증 절차에 구멍이 있다는 발견**이다. 그 시연을 가장
   위험한 단계(Step 2 — 살아 있는 코드 ~500줄을 옮긴다) **앞에서 한 번 하고 간다.**

②가 Step 1 의 진짜 값이다 — 지표가 아니라 **다음 단계의 안전**을 산다.

— store 를 안 본다."* 오늘은 산문이고, 어댑터가 서면 경로 하나로 확인된다.

### 4.3 Step 3 · 결정 종류를 가른다 — **방향**

**어디로 갈지는 이미 정해져 있다** — [../구조-2축.md](../구조-2축.md) §3 이 일곱 파일을
전부 배정했다(2026-09-13). 이 단계가 정하는 것은 *"어디로"* 가 아니라 **커밋 단위와 순서**다.
타입을 뺀 잔량과 남은 섞임은 이렇다.

| 파일 | 타입 뺀 뒤 | 섞인 결정 종류 |
|---|---:|---|
| `modulePacking` | ~1132 | 조율(트리 순회·짝짓기) · **도형**(`topY` 누적합 · `colX` · `absPortY` · `materializeChannelGeometry`) · 정책(끝 선호 · 형제 순번) |
| `emitModule` | 905 | 찍기 · **도형**(gap 기하) · 정책(`unroutedLines` 여섯 곳 = D2) |
| `planModulePorts` | ~789 | 조율(⓪①②③④ 순서) · **정책**(`seatLinkEdge` 큐 · `spillPair` 면 순서 · `restByPriority`) · 관측 |
| `linkPlanner` | ~773 | **장부**(`tableOf`·`splitByTable`·`commitLinkFace`) · **정책**(`tryLinkFace` 후보 정렬·끝 선택) · 셈 |
| `link.ts` | ~740 | 셈(`createLinks` 붓기) · 정책(`shareLanes` 짝짓기) · 관측(`summarizeBeltForms`) |
| `clusterModule` | ~357 | 조율(`generateModule`) · 정책(`buildTrunkContext` 점프 게이트 넷) |
| `channelGeometryPlanner` | ~646 | **장부**(백트래킹 배정) · **도형**(계단꼴·한꺾임꼴) · **정책**(같은 쪽 판정 · 해소 사다리) |
| `deliveryRoute` | ~619 | 조율 · **도형**(`buildPlannedChain`) · 찍기(`finishChain`) · 정책(계획 경로 ↔ dijkstra) · 셈 |
| `containerRouting` | ~464 | ⚠ **안 가른다** — [work-kinds §6](../../../docs/auto-layout/common/work-kinds.md) 이 판정한 미분리 자리. 주소만 `shared/route.ts` 로 |
| `perimeterExitPlanner` | ~385 | **정책**(후보 나열 · 강등 · 강행) · 장부(직진) · 관측. 타입 35% 라 **가장 얇아진다** |

첫 칼의 후보는 **`linkPlanner` 의 장부와 정책**이다 — 그 경계가 이미 함수 단위로 갈려
있고(`try*` 는 장부를 안 건드리고 `commit*` 만 건드린다), 계획 4 의 첫 규칙
(`shape → ledger` 금지)이 검사하려는 바로 그 경계다. 다만 **확정은 이 단계에 착수할 때**
한다 — 지금 적으면 검증된 Step 1 과 개략인 이 단계가 글에서 구분되지 않는다.

### 4.4 Step 4 · 조율자를 제자리로 — **방향**

Step 1 이 끝나도 남는 간선 둘이 여기 과녁이다.

```
module/clusterModule → planner/module/planModulePorts   값 1   (계획을 부른다)
module/clusterModule → execution/module/emitModule       값 2   (방출을 부른다)
```

`clusterModule.generateModule` 은 **조율자**인데(계획을 부르고 → 좌표를 만들고 → 방출을
부른다) `module/` 에 있다. 그래서 `module/` 이 위아래를 다 부른다. 목표 트리의
`module/build.ts` 가 그 자리이고, 축 자체가 사라지는 것은 계획 3 이다.

채널·외곽·링크 관심사의 타입(`perimeterExitPlanner` 208 · `channelGeometryPlanner` 125 ·
`deliveryRoute` 98 · `containerRouting` 117)도 같은 규칙으로 이 언저리에서 뗀다.

## 5. 대안 검토

| 안 한 것 | 왜 |
|---|---|
| **타입을 나중에 뗀다**(결정 종류부터) | 과녁은 원안대로 결정 종류를 가르는 것이고 바뀐 것은 **순서뿐**이다. 타입이 먼저인 이유는 *"떼야 경계가 보여서"* 가 **아니라**(그 주장은 철회했다 — §1.2) ① 타입이 모든 종류가 의존하는 **바닥**이라 나중에 떼면 이미 갈라 둔 파일을 다시 건드리고, ② 그 이동 하나가 **D4 와 상향 간선 다섯을 함께 닫아** 나중 자르기가 안 뒤집히게 하기 때문이다(§1.3) |
| **타입을 제자리에 두고 재수출만** | 타입은 재수출이 공짜지만 **값은 아니다** — `trunkEndKey` 를 `clusterModule` 에서 재수출하면 런타임 간선이 그대로 남아 D4 가 안 닫힌다. 그리고 이름 하나에 주소가 둘이 된다 |
| **관심사마다 `types.ts` 하나**(925줄) | 규칙상 허용되지만(타입은 300줄 규칙에서 빠져 있다) 읽히지 않는다. 셋으로 가른 기준은 **질문**이지 줄 수가 아니다 — 무엇을 나르나 · 어디에 앉나 · 무엇을 받고 내나 |
| **`FaceTable` 까지 옮긴다** | 층을 안 건넌다(읽는 곳이 셋 다 배정 계층). 장부의 모양과 불변식이 갈린다 → §3 경계 사례 |
| **`emitModule` 부터 자른다**(가장 크고 D2 가 거기 있다) | **타입이 0% 라 이 계획의 칼이 안 든다.** 그 파일은 찍기·도형·정책이 섞인 것이라 Step 3 의 대상이고, gap 도형은 계획 1 이 *"청구가 없어 검증할 계측이 없다"* 고 남겨 둔 자리다 |

## 6. 검증

```powershell
npx tsc -p tsconfig.app.json --noEmit   # 반드시 -p
npx vitest run                          # 기준선: 62파일 784테스트 (기존 실패 2 — trunkPipe 유체 면)
```

여기에 더해 **간선을 직접 센다** — 이 계획의 과녁이 곧 간선이므로 통과/실패가 수로 나온다.
①②는 **0줄**, ③은 `module/types/` 밖에서 **0줄**이어야 한다.

```powershell
# ① 방출기가 조율자를 아예 안 본다      — 오늘 2줄(:39 타입 · :45 런타임 = D4)
rg -n 'from ".*clusterModule"' src/autoLayout/execution/module/ --glob '!*.test.ts'

# ② 방출기가 계획 계층을 안 본다        — 오늘 2줄(:22 ioLine · :40 linkPlanner)
rg -n 'from ".*planner/module' src/autoLayout/execution/module/ --glob '!*.test.ts'

# ③ 타입의 주소가 하나다 — 옛 자리에 남으면 이름 하나에 출처가 둘이 된다
rg -n 'export (interface|type) (IoLine|PlannedLine|Link|LinkFacePlan|LinkSeats|ModuleInput|ModulePort|GeneratedModule|BeltMerge)\b' `
   src/autoLayout --glob '!**/types/*'
```

**시험 파일은 뺀다** — `emitOutputLinks.test.ts` 등이 `generateModule` 을 부르는 것은 정상이다
(모듈을 만들어야 방출을 볼 수 있다). 막는 것은 **산 코드의 간선**이다.

**좌표 덤프 전후 비교**는 규약대로 한다(`flg.run(cfg)` → `flg.snapshot` → 복원 → `flg.diff`).
다만 이 단계에서 그것이 **증명하는 것은 적다** — §4.1 불변이 이미 기전으로 서 있고,
*"안 바뀌었다"* 는 미완성 기준선을 안심시키는 값이기 때문이다. 그래도 돌린다: 기전이
틀렸다면 싸게 알아채는 것이 좌표다.

## 7. 이게 끝나면 무엇이 **가능해지나**

로드맵이 아니라 **열리는 문**이다. 열고 안 들어갈 수도 있다.

- **계획 3(폴더 이관)이 기계적이 된다.** 옮길 것이 종류별로 갈려 있으면 이동이 판단을
  안 부른다 — 지금은 파일 하나를 옮길 때마다 *"이 안의 어느 부분이 이 폴더 것인가"* 를
  다시 물어야 한다.
- **계획 4 의 첫 규칙을 검사할 수 있게 된다.** `shape → ledger` 금지는 두 종류가 서로 다른
  파일일 때만 eslint 가 볼 수 있다.
- **D4 를 work-kinds §7 에서 지운다.** 남는 결함은 D2 하나가 된다.
- **`module/CLAUDE.md` 와 `execution/CLAUDE.md` 의 산문 몇 줄이 구조로 대체된다** —
  *"여기서 셀을 만들고 싶어지면 계층이 새는 것이다"* 같은 문장이 경로로 확인된다.
- **타입 파일이 [용어사전](../../../docs/용어사전.md)의 코드 쌍둥이가 된다.** 개념 사전과
  타입 선언이 마주 보면 *"이 말이 코드에서 무엇이냐"* 를 한 번에 답할 수 있다.
  (인터뷰에서 용어사전은 **개념 사전 유지·청소만** 으로 확정됐으므로, 합치지는 않는다.)
