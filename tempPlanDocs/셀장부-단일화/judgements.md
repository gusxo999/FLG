## J-주인입도 — `CellOwner.owner` 를 **무엇으로 하나**

**전제(2026-08-19):** 구조정리만 하면 owner 는 *"사유 문자열에 이름을 싣는다"* 는
용도뿐이라 무엇이든 된다. 하지만 후속(양보·선점)이 이걸 **양보의 단위**로 쓴다 —
자료형에 박히므로 Step 0 에서 정해야 하고, 나중에 바꾸면 파급이 크다.

| | 입도 | 성질 |
|---|---|---|
| **가** | 납품 경로 하나(`deliveryKey`) · 반출 상자 하나(`chest.id`) · 모듈 하나 | **자연스러운 배정 단위.** `LaneAssignment.options` 가 이미 이 입도라 후속이 공짜 |
| 나 | 경로의 **구간**(계단꼴의 조각) | 부분 양보가 가능. 조각 사이 연속성을 장부가 못 본다 |
| 다 | 문자열 태그(`"A"`, `"delivery"`) — 신원 없음 | 가장 싸다. 사유에 *누구* 를 못 싣는다 → 지금과 같아진다 |

**착수 조건:** Step 0. 미룰 수 없다.
**잠정:** (가). 후속을 막지 않는 유일한 선택이고, (다)는 이 계획의 관문 하나
(*"막은 칸의 주인을 낸다"*)를 못 연다.
**코드 역참조:** `planner/perimeterLanePlanner.ts` `LaneAssignment.options` 주석
— *"장부가 뒤 후보로 양보시켜도 된다"* 의 그 장부가 이것이다.
**전제가 썩는 조건:** 양보를 영영 안 하기로 하면 (다)가 더 싸다.

## J-인접흡수 — **유체 인접 지도를 장부가 흡수하나**

**전제(2026-08-19):** 이 계획이 끝나면 셀을 아는 곳이 **둘**이다 — 장부(절대좌표 셀)와
`pipeFlow`(유체 인접 규칙). 둘로 줄인 것이 구조정리의 결과이고, 하나로 합치는 것은
**충돌 규칙을 주인에 붙이는 설계 변경**이라 이 계획 밖이다.

```
지금:  겹침 = 셀 Set 넷,  인접 = pipeFlow 지도
끝나면: 겹침 = 장부 하나,  인접 = pipeFlow 지도   ← 여기서 멈춘다
```

| | 무엇 | 성질 |
|---|---|---|
| **가** | 그대로 둘로 둔다 | 둘 다 단일 출처라 더 안 갈린다. **#7·#13 은 pipeFlow 쪽 결함으로 남는다** |
| 나 | 주인에 `what`(pipe/fluid/belt…)을 달고 장부가 인접까지 판정 | 하나가 된다. `pipeFlow` 의 hard/soft·지하 방향 규칙을 **옮겨 적지 말고 대조**해야 한다 |
| 다 | 반대로 — 장부를 `pipeFlow` 가 흡수 | `pipeFlow` 는 유체 이름마다 지도를 새로 만든다. 아이템까지 그러면 비싸다 |

**착수 조건:** 이 계획의 Step 2 완료 **그리고** #7·#13 을 실제로 고치기로 할 때.
둘 중 하나라도 아니면 (가)가 맞다 — **결함을 안 고칠 거면 합칠 이유가 없다.**
**코드 역참조:** `util/pipeFlow.ts` 머리 주석 §*"벨트 가드와 뭐가 다른가"* — 합치려면
그 두 가지 차이(방향 유무 · 처리량)를 장부가 표현할 수 있어야 한다.
**전제가 썩는 조건:** `collectBeltFlow`(수동편집 쪽 벨트 합류 가드)가 자동배치에도
쓰이기 시작하면 지도가 셋이 되고, 그때는 (나)의 값이 커진다.
