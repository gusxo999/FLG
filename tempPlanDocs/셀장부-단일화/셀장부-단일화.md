# 셀장부 단일화 — **17쌍의 판정을 한 곳으로**

> **뼈대는 전수표 17쌍이다**(→ [[layout-models]] §3.5). 이 계획은 그 17줄을 하나씩 들고
> *"지금 누가 판정하나 → 어디로 가나 → 끝났는지 어떻게 아나"* 를 답한다.
> **17줄이 전부 목적지를 가지면 끝난 것이고, 하나라도 비면 안 끝난 것이다.**

---

## 1. 왜 표가 뼈대인가

전수표는 이미 **요구사항 명세**다 — *"같은 칸을 두고 다투는 쌍이 전부 몇이고 각각 누가
판정하나"* 에 코드로 답한 것이다. 그러니 계획을 따로 지어낼 이유가 없다.

그리고 표를 뼈대로 안 쓰면 **끝났는지 알 수 없다.** 중복 제거나 파라미터 축소 같은 지표는
*"덜 지저분해졌다"* 만 말하고, **빠진 쌍이 있는지는 말하지 않는다** — 그 빠짐이 원래 문제였다.

> **완료 조건이 표에서 나온다.** 17줄 × (목적지 있음) 이 이 계획의 정의다.

---

## 2. 왜 장부가 넷이 됐나 — **아무도 실수하지 않았다**

고치기 전에 이해해야 한다. 중복이 게으름이면 주의·검사·이름으로 막을 수 있지만,
**셋 다 지역적으로 옳은 결정의 결과**라 그 대비가 안 통한다.

| | 왜 | 근거 |
|---|---|---|
| **① 모듈 로컬** | `generateModule` 이 `packModuleTree` **보다 먼저** 돈다. 그 시점엔 절대좌표가 **존재하지 않는다** — 강제였다 | `moduleWizard.ts:417` · `clusterModule.ts:249` (`origin: {x: pos.dx, …}`) |
| **④⑥ 두 `buildOccupancy`** | 두 패스가 *"Area·store 의존 0"* 을 계약으로 선언한다. **순수하려면 입력을 스스로 유도**해야 하고, 앞 패스 것을 물려받을 통로가 없다 | `deliveryRoute.ts:42` · `modulePerimeterPass.ts:33` |
| **②⑤ 예약과 실물** | 같은 격자인데 **생기는 시각**이 다르다. 그릇이 시각을 따라 갈렸다 | 계획 단계 vs 방출 단계 |

**중복이 순수성의 값이었다.** 그러니 고칠 때 그 이유를 깨면 안 된다 — 전역 mutable 격자는
오답이다. 장부는 **전역 상태가 아니라 패스 사이를 흐르는 값**으로 만든다(§4).

## 3. 17줄의 목적지 — **다섯 갈래**

`○` 판정 있음 · `△` 방향 어긋남 · `✗` 판정 없음 (전수표의 상태 열)

### ㉠ 장부가 판정한다 — 7줄

지금도 셀 단위 판정이 있다. **규칙을 장부로 옮긴다.**

| # | 쌍 | 지금 판정하는 곳 | 장부에서 |
|---|---|---|---|
| 1 ○ | 머신 ↔ 전부 | `buildOccupancy` ×2 | `what: machine` · 겹침 |
| 4 ○ | A ↔ B | `deliveryRoute.base` | `{path:["A"]}` |
| 5 ○ | A ↔ C | `perimeterPass.occ` | `{path:["A"]}` |
| 6 ○ | B ↔ B (아이템) | `deliveryBelts` + `reservedDelivery` | `{path:["B"], not: k}` |
| 8 △ | B ↔ C **예약** | `reservedExport` | `{path:["C"], stage:"reserved"}` |
| 9 △ | B ↔ C **방출** | `occ ⊇ deliveryCells` | **8과 같은 claim 이 된다** ↓ |
| 10 ○ | C ↔ C | `occ` 증분 | `{path:["C"]}` |

> **#8·#9 는 규칙을 안 고쳐도 사라진다.** 지금은 *예약에선 C 가 이기고 방출에선 B 가 이기는*
> 모순인데, 장부가 하나면 **그 모순을 표현할 수 없다** — C 의 예약과 방출이 같은 claim 의
> `stage` 차이라서, 방출은 새로 다투는 게 아니라 `reserved → placed` 승격이다.
> **구조가 규칙을 대신하는 유일한 줄이라 따로 적어 둔다.**

### ㉡ 장부 밖에 남는다 — 3줄 (**로컬 좌표라 옳다**)

| # | 쌍 | 왜 안 옮기나 |
|---|---|---|
| 2 ○ | A ↔ A (같은 모듈) | `clusterModule.occupancy`. 생성 시점엔 **절대좌표가 없다**(§2①) |
| 3 ○ | A ↔ A (다른 모듈) | `modulePacking` 겹침 스윕. **모듈 bbox 단위**라 셀 판정이 아니다 |
| 14 ○ | ③ 안의 B ↔ C | 채널 로컬에서 **공동 배정**(백트래킹 + `yieldedExports`). §3.5 에서 *경쟁이 풀리는 유일한 곳*이었고 그 이유가 **로컬 좌표를 가져서**다 |

> **로컬 좌표는 경쟁을 없애는 장치다** — 통합 대상이 아니라 **보존 대상**이다.
> 셋은 결과가 **절대화될 때만** 장부에 등록된다(㉠4·5가 그 등록을 읽는다).

### ㉢ **자리만 만들고 규칙은 비운다** — 4줄 (사용자 결정)

판정이 아예 없는 넷. **장부가 "이 쌍은 규칙이 없다" 를 명시적으로 안다.**
동작은 지금과 같다 — 그래서 이 계획이 구조정리로 남는다.

| # | 쌍 | 자리를 만든다는 것은 | 규칙을 켜면 |
|---|---|---|---|
| 7 ✗ | B유체 ↔ B유체(다른 유체) | 유체 셀에 `what: pipe(fluid)` 를 **기록한다**. 인접 판정은 **끈다** | 인접 스위치 하나 |
| 13 ✗ | B유체 ↔ C파이프 | 위와 같음 — B 의 유체가 장부에 들어오는 것 자체가 지금은 없다 | 위와 같이 닫힌다 |
| 15 ✗ | 행 채널 ↔ C 예약 | `RowChannelEntry.row` 를 **등록하는 자리**를 만든다(지금은 등록 코드가 0) | `add` 한 줄 |
| 16 ✗ | 마진 프레임 ↔ B | 마진 프레임을 등록하는 자리 | `add` 한 줄 |

> **"자리"의 정의:** 장부에 **claim 은 들어오되 판정 규칙이 비어 있다.**
> 그래서 `flg` 로 *"규칙이 비어 있는 claim 이 몇 개 부딪혔나"* 를 셀 수 있다 —
> **결함이 수치가 된다.** 지금은 셀 수조차 없다.

### ㉣ 인접이라 아직 `pipeFlow` — 2줄

| # | 쌍 | 왜 |
|---|---|---|
| 11 ○ | A유체 ↔ B유체 | `fluidBlocked` — **인접까지** 판정한다. 규칙이 있고 잘 돈다 |
| 12 ○ | A유체 ↔ C파이프 | `pipeFlowByFluid` — 같음 |

**겹침은 칸 하나의 성질이고 인접은 칸 쌍의 성질이다.** `Map<칸, 주인>` 으로는
*"이 칸 옆에 다른 유체가 있으면 안 된다"* 를 표현할 수 없다. 흡수하려면 충돌 규칙을
주인에 붙여야 하고 그건 설계 결정이라 이 계획 밖이다 → **J-인접흡수**.

**다만 ㉢7·13 이 켜지는 순간 ㉣과 같은 규칙이 되므로, 이 둘은 같은 판단으로 묶인다.**

### ㉤ 판정이 필요 없다 — 1줄

| # | 쌍 | 왜 |
|---|---|---|
| 17 ○ | 행 채널 ↔ A | 행 채널은 `STACK_GAP` 이 만든 **빈칸**이라 A 와 겹칠 수 없다. 확인만 하고 넘어간다 |

### 합계

```
㉠ 장부로      7  ┐
㉡ 로컬 유지   3  │
㉢ 자리만      4  ├─ 17  ✔
㉣ pipeFlow    2  │
㉤ 불필요      1  ┘
```

**이 합이 17이 아니면 표를 잘못 읽은 것이다.** 착수 전에 다시 센다.

## 4. 장부가 **판정과 우선권**까지 갖는다 (사용자 결정)

### 왜 우선권이 추가가 아니라 **드러내기**인가

오늘도 우선권은 **있다** — 다만 **호출 순서로 적혀 있다.**

```
C 가 먼저 예약한다  →  B 가 그것을 존중한다     = "C 가 이긴다" 는 결정
```

**그런데 아무 데도 그렇게 적혀 있지 않다.** 장부로 옮기면 둘 다 `test` 를 부르므로
장부가 답해야 하고, **답하려면 그 결정이 이름을 가져야 한다.**
즉 우선권을 빼면 **오늘 동작을 재현할 수조차 없다.**

### 그래서 두 정책으로 나눈다 — **동작 변화를 한 곳에 가둔다**

```
정책 A  "먼저 온 쪽"      오늘 그대로.  동작 불변.  하지만 **순서가 이름을 갖는다**
정책 B  "피해 등급"        동작이 바뀐다.  별도 단계 + 실측 후 판단
```

피해 등급(§3.5)은 이미 코드에 있다 — 세로 채널의 `yieldedExports`(*유체가 갇히면 반출이
물러난다*)가 그것이다. **채널 안에서만 쓰인다.** 정책 B 는 그걸 전역으로 만드는 것이고,
**이 계획은 정책 A 까지만 한다**(정책 B 는 **J-정책전환**).

### 자료형

```ts
export interface Claim {
  owner: string;                       // 납품 key · 상자 id · 모듈 id
  path: "A" | "B" | "C";               // 전수표의 "누가" 축
  stage: "reserved" | "placed";        // §2③ 시각 차이를 **값으로** 흡수
  what: ClaimWhat;                     // 전수표의 "무엇" 축 — 규칙이 여기서 나온다
}

export type ClaimWhat =
  | { kind: "machine" } | { kind: "belt" } | { kind: "inserter" } | { kind: "chest" }
  | { kind: "pipe"; fluid: string };   // ㉢7·13 의 **자리**. 인접 규칙은 비어 있다
```

```ts
export interface CellLedger {
  add(cells: Iterable<Cell>, c: Claim): void;
  /** 놓을 수 있나. 막혔으면 **누가 막았는지** 낸다 — 사유 문자열이 여기서 나온다. */
  test(cells: Iterable<Cell>, c: Claim): Blocked | null;
  /** `reserved → placed` 승격. #9 가 여기서 사라진다. */
  promote(owner: string): void;
  ownerOf(cell: Cell): Claim | null;
}

export interface Blocked { cell: Cell; by: Claim; rule: string }
```

`rule` 이 규칙의 **이름**이다. `"겹침"` · `"인접(다른 유체)"` · `"규칙 없음"` —
㉢의 넷은 `"규칙 없음"` 으로 세어진다.

### 순수성은 안 깨진다

장부는 호출자(`moduleWizard`)가 만들어 넘기는 **값**이다. 지금도 `deliveryBelts`·`occ` 를
지역 변수로 누적한다 — **그 지역 변수의 수명을 함수 밖으로 늘리는 것**뿐이다.
순수성의 대상은 **모듈 그래프(`pack`)** 이지 스크래치가 아니다
(`modulePerimeterPass.ts:321` — *"설명 축적(모듈 그래프 미변형)"*).

## 5. 단계 — **갈래를 하나씩**

> 규약대로 **Step 1 까지만 확정**. Step N 을 끝낼 때 N+1 의 전제를 다시 확인한다.

### Step 0 — 자료형 + ㉠#1·#4·#5 (두 `buildOccupancy` 를 하나로)

정책 A(먼저 온 쪽). 규칙은 `겹침` 하나. **드라이런으로 확인한 착수 목록:**

```
① planner/cellLedger.ts (신규)
   Claim · ClaimWhat · Blocked · CellLedger
   ledgerFromPlacements(placements)   ← PackResult 를 **안 받는다**(⑤ 참조)
   snapshot(filter): ReadonlySet<string>   ← Step 0 은 Set 을 낸다(④ 참조)

② planner/deliveryRoute.ts
   - buildOccupancy 삭제
   - routeDeliveryRoutes(pack, config, ledger?)   ← **옵셔널**(③ 참조)
   - const base = (ledger ?? ledgerFromPlacements(pack.placements))
                    .snapshot({ path: ["A"] })
   - base 를 쓰는 나머지 7곳은 **안 건드린다**(여전히 ReadonlySet)

③ execution/modulePerimeterPass.ts
   - buildOccupancy 삭제
   - rePathToPerimeter(pack, stripped, deliveryCells, config, ledger?)
   - const occ = new Set(ledger.snapshot({ path: ["A", "B"] }))
     ↑ 지역 사본이라 아래 occ.add(...) 증분은 **그대로 둔다**(#10 은 Step 1)

④ planner/moduleWizard.ts   — 장부 하나를 만들어 나른다
   pack 직후:      const ledger = ledgerFromPlacements(pack.placements)
   delivery 직후:  ledger.add(deliveryRes.cells, { path: "B", stage: "placed", … })
   perimeter 호출: rePathToPerimeter(…, ledger)
```

```

       차이는 시그니처 1줄 + `deliveryCells` 1줄뿐이고, 후자는 ④가 대신한다
       — 옛 계획서의 *"문자 단위로 같다"* 는 부정확했다. 정정한다

관문:  장부가 **패스 사이를 흐르는 값**이 된다. 지금은 두 함수가 각자 만들고 버려서
       무엇을 더 넣고 싶어도 넣을 자리가 없다

### Step 1 — ㉠ 나머지(#6·#8·#9·#10)를 **재현하고 대조**한다

옛 집합을 **그대로 두고** 장부에도 넣는다. 판정 때 둘 다 물어 답이 다르면 낸다.

```
① 선행 — 예약에 주인을 싣는다   ⚠ 이게 없으면 #8·#9 를 못 옮긴다
   modulePacking: reservedExportCells: Set<셀> → Map<셀, chestId>
   addSeg 가 도는 자리에 이미 `a.id` 가 있다 — 넘기기만 하면 된다
   읽는 곳은 deliveryRoute 한 곳뿐(grep 확인) → 파급 1곳

② #6  B ↔ B
   deliveryBelts · reservedDelivery 를 두고, 같은 셀을 ledger.add(path:"B") 로도
   판정: 옛 has() 로 하고, ledger.test() 를 **비교용으로만** 부른다

③ #8  B ↔ C 예약
   reservedExport → ledger.add(path:"C", stage:"reserved", owner: chestId)
   plannedChainClear 의 사유가 `반출 예약 (8,15) — 상자 X` 가 된다

④ #9  C 예약 → 방출
   perimeterPass 가 놓을 때 test 가 아니라 ledger.promote(chestId)
   **자기 예약과 다투지 않는다는 것**을 여기서 확인한다

⑤ #10 C ↔ C
   occ.add 증분 → ledger.add(path:"C", stage:"placed")

⑥ 대조 — flg.report() 에 "옛 답 ≠ 장부 답" 건수를 낸다
```

```

### Step 2 — 옛 집합 삭제 *(방향)*

`plannedChainClear` 파라미터 7 → 3. 납품마다 `new Set(base)` 로 배치 전체를 복사하던 것
(`deliveryRoute.ts:422`·`341`) 제거.

### Step 3 — ㉢ 넷의 **자리**를 만든다 *(방향)*

유체 셀에 `what: pipe(fluid)` 기록(#7·#13) · 행 채널 등록 자리(#15) · 마진 등록 자리(#16).
**규칙은 비운 채**로 `"규칙 없음"` 충돌을 센다. 넷이 **수치가 된다.**

### Step 4 — 문서 이관, 폴더 삭제 *(방향)*

§3 의 17줄 목적지표를 `layout-models` §3.5 로 옮긴다. §2(*왜 넷이 됐나*)도 함께 —
**그 이유를 모르면 같은 이유로 다시 갈린다.**

| 부수 4 | 배치 전체 집합 복사 납품마다 → 0회. **단 `containerRouting.dijkstraWithJumps` 의 `blocked` 를 술어로 바꿔야 달성된다**(드라이런 발견 ④) — Step 2 |
| 부수 5 | **`"규칙 없음"` 충돌이 수치로 나온다** — 지금은 셀 수조차 없다 |
| 동작 | **같다.** 정책 A + ㉢ 규칙 비움이 그 보장이고, Step 1 이 원소 대조로 확인한다 |

## 7. 이 계획이 **안 하는 것**

| | 왜 |
|---|---|
| ㉢ 넷의 **규칙**을 채운다 | 동작이 바뀐다. 구조 변경과 섞으면 회귀 원인을 못 가른다. Step 3 뒤 별건 |
| 정책 B(피해 등급)로 전환 | 동작이 바뀐다 → **J-정책전환** |
| ㉣ `pipeFlow` 흡수 | 인접은 칸 **쌍**의 성질이라 자료구조가 다르다 → **J-인접흡수** |
| ㉡ 로컬(①③) 통합 | **로컬 좌표는 경쟁을 없애는 장치다.** 통합하면 오히려 나빠진다 |
| 양보·선점 | 정책 B 다음. 지금은 주인을 물을 자리조차 없다 |

## 8. 위험

| | 위험 | 대비 |
|---|---|---|
| 가 | Step 1 에서 안 갈리는 줄이 나온다 | **그게 목적이다.** §3 을 고치라는 신호 |
| 나 | ㉢ 의 `what` 을 기록만 하고 규칙을 비우는 것이 어색하다 | **스위치가 코드에 보이는 것**이 값이다. 지금은 어디에 넣을지부터 골라야 한다 |

## 9. 착수 노트 — **드라이런 (2026-08-19, 코드 변경 0)**

계획서대로 착수했다고 가정하고 Step 0·1 을 **코드를 안 고치고** 끝까지 따라가 본 기록이다.
목적은 상세화이고, 실제로 **계획을 정정해야 하는 발견이 여섯** 나왔다.

> **드라이런의 한계:** 컴파일러를 안 거쳤다. 아래를 **[확인]**(코드로 봄) 과
> **[미확인]**(타입을 붙여야 앎) 으로 갈라 적는다. 미확인을 확정으로 읽으면 안 된다.

### ① [확인] 두 `buildOccupancy` 는 **문자 단위로 같지 않다** — 전제 정정

`diff` 결과 차이가 둘이다: 시그니처 1줄(`deliveryCells` 파라미터) + 본문 1줄.
**공유부 8줄만 동일하다.** 옛 전제 *"본문이 문자 단위로 같다"* 는 부정확했다.
실질은 안 변한다(추가 1줄은 호출자가 대신함) — Step 0 전제를 그렇게 고쳤다.

### ② [확인] 장부를 **필수 파라미터로 만들면 테스트 45곳이 깨진다**

```
routeDeliveryRoutes  테스트 36곳 (10개 파일) · 프로덕션 1곳 (moduleWizard)
rePathToPerimeter    테스트  9곳 ( 3개 파일) · 프로덕션 1곳 (moduleWizard)
```

**설계 결정:** `ledger?` 를 **옵셔널**로 두고 없으면 내부에서 만든다.
45곳을 안 건드리고, 프로덕션 경로만 장부를 공유한다. 나중에 필수로 조이는 것은 별건.

> 이건 드라이런이 없었으면 착수 첫날에 45개 빨간 줄로 만났을 것이다.

### ③ [확인] `base` 소비처 8곳 중 7곳을 **안 건드려도 된다**

`deliveryRoute` 안에서 `base` 는 생성 1 + 사용 7이고, 사용 7은 전부 `ReadonlySet` 으로만
쓴다(`new Set(base)` ×2 · 파라미터 전달 ×4 · `base.has` ×1).
`snapshot()` 이 `ReadonlySet` 을 내면 **생성 한 줄만 바뀐다.**

### ④ [확인] *"복사 0회"* 는 **dijkstra 를 건드려야** 달성된다 — 성공기준 정정

`containerRouting.dijkstraWithJumps` 가 `blocked: ReadonlySet<string>` 을 받고
**`.has()` 만 쓴다**(318·357행. `.add` 는 다른 함수의 지역 변수라 무관).
술어 `(k) => boolean` 으로 바꾸면 `new Set(base)` 복사가 사라지지만, 그건
**`containerRouting.ts` 변경**이라 장부 파일 밖이다 → **Step 2 범위**로 명시했다.
Step 0·1 에서는 복사가 그대로 남는다.

### ⑤ [미확인 — 컴파일 필요] `cellLedger` 는 `PackResult` 를 **안 받는 게 좋다**

`modulePacking` 은 무겁고 `execution/` 에서도 import 된다. `ledgerFromPlacements(placements)`
로 배열만 받으면 의존이 `PlacedCell`·`Container` 로 얇아진다.
**import 사이클이 실제로 생기는지는 타입을 붙여야 안다.**

### ⑥ [확인] Step 1 에 **선행 작업**이 있다 — 예약에 주인 싣기

`reservedExportCells: Set<셀>` 에는 **주인이 없다.** 그래서 #8 의 사유에 상자를 못 싣고,
#9 의 `promote(owner)` 도 못 한다. `Map<셀, chestId>` 로 바꾸는 것이 **#8·#9 의 선행 조건**이다.

싸다 — `addSeg` 가 도는 루프에 `a.id` 가 **이미 있고**, 읽는 곳은 `deliveryRoute` 한 곳뿐이다.
Step 1 의 ①로 명시했다.
