# 셀장부 단일화 — **구조정리**

> 기능을 안 만들고 결함을 안 고친다. 산출물은 바뀌지 않는다.
> **그래서 "무엇을 하나" 보다 "왜 그래야 하나" 가 이 문서의 본문이다** — 이유를 모르면
> 정리한 구조가 다시 흩어진다.

---

## 1. 왜 장부가 넷이 됐나 — **아무도 실수하지 않았다**

이게 이 계획에서 가장 먼저 이해해야 할 것이다. 중복이 게으름의 결과라면 주의·검사·이름으로
막을 수 있다. **그런데 셋 다 지역적으로 옳은 결정의 결과다.** 그래서 사람을 고치는 대비는
안 통한다.

### ① 모듈 로컬 장부 — **강제였다**

`generateModule` 은 `packModuleTree` **보다 먼저** 돈다(`moduleWizard.ts:417`).
그 시점엔 모듈이 어디 놓일지 모른다:

```ts
origin: { x: pos.dx, y: pos.dy }     // clusterModule.ts:249 — 모듈 로컬
```

**절대좌표가 존재하지 않는 시점이라 로컬일 수밖에 없다.** 선택이 아니었다.

### ④⑥ 두 `buildOccupancy` — **순수성의 대가였다**

두 패스 모두 *"Area·store 의존 0"* 을 계약으로 선언한다:

```
deliveryRoute.ts:42          무배선·순수 — Area·store 의존 0
modulePerimeterPass.ts:33    순수 — Area·store 의존 0
```

순수하려면 **입력을 스스로 유도**해야 한다. 둘 다 `pack` 하나만 받으므로, 둘 다 `pack` 에서
셀을 유도한다. 앞 패스가 이미 유도해 둔 것을 물려받을 **통로가 없다**.
그래서 같은 유도가 두 번 있고, 코드가 글자까지 같아졌다.

> **중복이 순수성의 값이었다는 것이 핵심이다.** 그러니 고칠 때 순수성을 깨면 안 된다 —
> 그러면 이유가 있던 것을 이유 없이 없앤 게 된다.

### ②⑤ 예약과 실물 — **시점의 대가였다**

같은 격자인데 **생기는 시각이 다르다.** 예약(②)은 계획 단계에, 실물(⑤)은 방출 단계에
생긴다. 그릇이 갈린 것은 시각이 갈렸기 때문이지 담는 것이 달라서가 아니다.

---

## 2. 왜 그것이 문제인가 — **고르는 일이 생긴다**

넷이 각자 옳아도, 합쳐 놓으면 새 셀을 만들 때마다 이 질문이 생긴다:

```
"이 셀을 넷 중 어디에 넣나"
```

그리고 **안 넣어도 아무 일도 안 일어난다.** 타입이 안 막고, 테스트가 안 잡고, 화면은 멀쩡하다.
실제로 넷을 놓쳤다(→ [[layout-models]] §3.5 전수표 #7·#13·#15·#16). 그중 둘은
라우팅이 **"성공"이라고 보고**한다.

증상은 판정 함수의 모양에 그대로 나온다:

```ts
function plannedChainClear(
  chain, ownKey,
  base,              // 장부 ④
  deliveryBelts,     // 장부 ⑤
  reservedExport,    // 장부 ②
  reservedDelivery,  // 또 다른 예약
  fluidBlocked?,     // pipeFlow
): string | null
```

*"이 칸 비었나"* 를 묻는데 **집합 다섯 개를 들고 다닌다.** 종류가 늘면 파라미터가 늘고,
**안 넘기면 조용히 통과한다** — 옵셔널이라 타입도 안 막는다.

> **그래서 목표는 "실수를 줄인다" 가 아니라 "고르는 일을 없앤다" 다.**
> 고를 것이 하나뿐이면 안 넣은 것이 즉시 드러난다.

## 3. 왜 하필 인덱스 하나 + 질의인가

### 먼저 관찰 — **넷의 차이는 데이터가 아니라 필터였다**

넷이 무엇을 담는지 나란히 놓으면 담는 것이 같다. 다른 것은 **누구를 피하느냐** 다:

| 옛 집합 | 무엇을 담나 | **누구를 피하나** |
|---|---|---|
| ④ `base` | 절대좌표 셀 | 모듈이 놓은 것 |
| ⑤ `deliveryBelts` | 절대좌표 셀 | 이미 깐 납품 |
| ② `reservedExport` | 절대좌표 셀 | 반출이 잡아 둔 것 |
| `reservedDelivery` | 절대좌표 셀 | **나 말고** 다른 납품의 계획 |
| ⑥ `occ` | 절대좌표 셀 | 모듈 + 납품 |

**넷이 같은 격자의 서로 다른 자름이었다.** 그러면 자료를 하나로 두고 자름을 인자로 주면 된다.

### 대안 셋 — 왜 아닌가

| | 무엇 | 왜 아닌가 |
|---|---|---|
| A | `buildOccupancy` 를 공용 헬퍼로 뺀다 | 코드 중복은 사라지지만 **유도는 여전히 두 번**이고 그릇은 여전히 넷이다. §2 의 *고르는 일* 이 그대로 남는다 |
| B | 앞 패스가 자기 집합을 반환해 다음 패스가 받는다 | 유도는 한 번이 된다. 그런데 **파라미터가 더 는다**(㉡이 악화). 넷도 그대로 |
| C | 전역 mutable 격자 | 순수성이 깨진다. 패스가 호출 순서에 묶여 단위 테스트가 성립하지 않는다 — **①④⑥이 순수했던 이유를 버리는 것** |
| **채택** | 인덱스 하나를 **인자로 나르고**, 차이는 질의로 | 유도 한 번 · 그릇 하나 · 순수성 유지 |

### 왜 순수성이 안 깨지나

장부는 **전역 상태가 아니라 패스 사이를 흐르는 값**이다. 호출자(`moduleWizard`)가 만들어
넘기고, 각 패스는 받은 것을 채우고 묻는다. 지금도 `deliveryBelts`·`occ` 를 지역 변수로
누적하고 있다 — **그 지역 변수의 수명을 함수 밖으로 늘리는 것**뿐이다.

그리고 순수성의 대상은 **모듈 그래프(`pack`)** 이지 스크래치가 아니다
(`modulePerimeterPass.ts:321` — *"설명 축적(모듈 그래프 미변형)"*). 그 계약은 그대로다.

### 자료형 — 최소로

```ts
/** 한 칸의 주인. **지금 이미 흐르고 있는 정보만** 담는다 — 새 지식이 아니다. */
export interface CellOwner {
  /** 누가. 납품 key · 상자 id · 모듈 id. */
  owner: string;
  /** 경로 넷 중 하나(→ layout-models §3.5). 위 표의 "누구를" 축이다. */
  path: "A" | "B" | "C";
  /** 예약인가 실물인가. §1 의 **시점의 대가**를 필드로 흡수한다. */
  stage: "reserved" | "placed";
}
```

`stage` 가 있는 이유가 §1③ 이다 — 그릇을 나누던 시각 차이를 **필드 하나**로 옮긴다.
그릇이 아니라 값으로 표현되면 새 시각이 생겨도 그릇이 안 늘어난다.

### 질의표 — **이게 설계의 증명이다**

```
④ base              { path: ["A"] }
⑤ deliveryBelts     { path: ["B"], stage: "placed" }
② reservedExport    { path: ["C"], stage: "reserved" }
  reservedDelivery  { path: ["B"], stage: "reserved", not: k }
⑥ occ               { path: ["A", "B"] }
```

**다섯 줄이 전부 채워진다는 것이 "자료구조가 넷일 이유가 없었다" 의 증명이다.**
채워지지 않는 줄이 하나라도 나오면 그 줄은 **정말로 다른 자료**이므로 설계를 고쳐야 한다.
Step 1 이 이것을 실측한다.

## 4. 왜 여기서 멈추나 — 경계 넷의 이유

### 왜 결함(#7·#13·#15·#16)을 같이 안 고치나

**구조 변경과 동작 변경을 섞으면 회귀가 났을 때 원인을 못 가른다.** 산출물이 달라졌을 때
*"정리하다 깨진 것"* 인지 *"고친 결과 달라진 것"* 인지 판별할 수단이 없다.

그리고 순서가 반대다 — **지금은 고칠 자리가 없다.** #15(행 채널 무예약)를 고치려면
*"넷 중 어디에 넣나"* 를 골라야 하고, 그 고르는 일이 바로 §2 의 문제다.
구조정리가 끝나면 넷은 각각 **`add` 한 줄**이 된다.

### 왜 `pipeFlow`(유체 인접)를 안 합치나

**겹침은 칸 하나의 성질이고, 인접은 칸 쌍의 성질이다.** 자료구조가 다르다 —
`Map<칸, 주인>` 으로는 *"이 칸 옆에 다른 유체가 있으면 안 된다"* 를 표현할 수 없다.

합치려면 *"충돌 규칙"* 이라는 개념을 새로 세워 주인에 붙여야 한다. 그건 **설계 결정이지
정리가 아니다** → [judgements.md](judgements.md) **J-인접흡수**.

그래서 이 계획이 끝나면 셀을 아는 곳이 **정확히 둘**이 된다:

```
겹침 = 장부 하나        (이 계획)
인접 = pipeFlow 지도    (남는다 — #7·#13 이 사는 자리)
```

**넷에서 둘로 줄이는 것까지가 구조정리다.** 그리고 남은 하나가 **어디인지 이름이 붙는다** —
지금은 넷 어딘가에 흩어져 있어서 그 말조차 못 한다.

### 왜 로컬 장부(①③)는 **합치면 오히려 나빠지나**

①은 §1 에서 봤듯 **절대좌표가 없는 시점**의 장부다. 억지로 전역에 올리려면 배치를 먼저
확정해야 하는데, 그러면 *"모듈을 부모-무시로 생성한다"* 는 파이프라인의 전제가 깨진다.

③(세로 채널)은 채널 로컬 추상좌표에서 **B·C 를 공동 배정**한다 — §3.5 에서 *경쟁이 풀리는
유일한 곳*이었다. 그 이유가 **로컬 좌표를 가져서**다. 전역으로 올리면 그 성질을 잃는다.

> **로컬 좌표는 경쟁을 없애는 장치다.** 통합의 대상이 아니라 보존의 대상이다.
> 통합할 것은 *이미 절대좌표인* 넷뿐이다.

### 왜 우선권·양보를 안 넣나

새 능력이다. 그리고 **장부가 생기기 전에는 설계할 수 없다** — 양보는 *"이 칸의 주인에게
비켜 달라고 한다"* 인데, 지금은 주인을 물을 자리가 없다. 순서가 이 계획 다음이다
→ `행채널-모델/judgements.md` **J-양보**.

## 5. 왜 그림자 단계가 필요한가

*"질의가 옛 집합과 같다"* 는 **주장이지 사실이 아니다.** 타입은 그걸 증명 못 한다.
그리고 규약이 *"산출물이 안 바뀐다"* 를 불변으로 쓰는 것을 금한다 — 안 바뀌었다는 것은
**틀린 것을 그대로 보존했다는 뜻일 수도** 있기 때문이다.

그래서 **집합의 원소 단위로 대조**한다. 옛 집합으로 판정하면서 장부에도 물어 답이 다르면
그 자리를 낸다. 불일치가 나오면 §3 질의표가 틀린 것이고, **그 자리에서 설계를 고친다.**

> 대조가 안 되게 만들면 Step 2 는 *검증 없이 옛 집합을 지우는 일*이 된다.

---

## 6. 단계

> 규약대로 **Step 1 까지만 확정**하고 뒤는 방향으로 적는다.
> Step N 을 끝낼 때 Step N+1 의 전제를 다시 확인한다.

### Step 0 — 두 `buildOccupancy` 를 장부로 (§1② 를 없앤다)

`planner/cellLedger.ts` 를 만들고 **동일 코드인 두 곳**만 갈아 끼운다.
질의는 `{ path: ["A"] }` 하나면 된다.

```
전제:  두 함수 본문이 문자 단위로 같다(2026-08-19 확인). 다른 것은
       modulePerimeterPass 가 deliveryCells 를 더 넣는 것뿐 — 호출자가
       add 를 한 번 더 부르면 된다
불변:  두 소비처가 받는 집합의 **원소가 같다** — 같은 입력을 같은 순서로 훑고
       같은 cellKey 를 만들므로 다른 답을 낼 수 없다(기전)
관문:  장부가 **패스 사이를 흐르는 값**이 된다. 지금은 두 함수가 각자 만들고
       버려서, 무엇을 더 넣고 싶어도 넣을 자리가 없다
```

### Step 1 — 나머지 셋을 질의로 재현하고 **대조**한다 (§5)

②⑤와 `reservedDelivery` 를 **그대로 두고**, 같은 셀을 장부에도 `add` 한다.
판정 때 둘 다 물어 답이 다르면 콘솔에 낸다.

```
전제:  §3 질의표의 다섯 줄이 넷을 빠짐없이 재현한다. 확인 방법 — 표를 단위
       테스트로 먼저 쓰고(코드보다 먼저) 실트리에서 대조한다
불변:  판정에는 **옛 집합의 답만** 쓴다. 장부 질의의 답은 비교·기록 외에
       소비처가 없어서 배치가 다른 답을 낼 수 없다(기전)
관문:  §3 의 증명이 **글이 아니라 실측**이 된다
```

### Step 2 — 옛 집합 삭제, 파라미터 축소 *(방향)*

`plannedChainClear` 7 → 3. 납품마다 `new Set(base)` 로 배치 전체를 복사하던 것
(`deliveryRoute.ts:422`·`341`)이 사라진다.

### Step 3 — 문서 이관, 폴더 삭제 *(방향)*

`layout-models` §3.5 를 갱신한다 — 장부 여섯 → **로컬 둘 + 절대 하나 + 인접 하나**.
§1 의 *"왜 넷이 됐나"* 는 `docs/` 로 옮긴다. **그것을 모르면 다시 흩어진다.**
