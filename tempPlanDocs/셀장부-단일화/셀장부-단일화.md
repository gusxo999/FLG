# 셀장부 단일화 — **구조정리**

> **이 계획은 기능을 안 만들고 결함을 안 고친다.** 같은 일을 하는 코드가 흩어진 것을
> 한 자료구조로 모은다. 산출물은 바뀌지 않는다.

## 0. 무엇이 중복인가 — 실측

### ㉠ 같은 루프가 두 파일에 **글자까지 같다**

```
deliveryRoute.ts:216-222        modulePerimeterPass.ts:175-181
  for (const pl of pack.placements) {          ← 동일
    for (const m of pl.module.machines)        ← 동일
      for (let dx …) for (let dy …)            ← 동일
        occ.add(cellKey(m.origin.x+dx, …));    ← 동일
    for (const c of pl.module.cells) occ.add(…) ← 동일
  }
```

둘 다 함수 이름까지 `buildOccupancy` 다. 한쪽이 `deliveryCells` 를 더 넣는 것만 다르다.

### ㉡ 판정 함수의 **파라미터가 곧 증상**이다

```ts
function plannedChainClear(
  chain, ownKey,
  base,              // ← 장부 ④
  deliveryBelts,     // ← 장부 ⑤
  reservedExport,    // ← 장부 ②
  reservedDelivery,  // ← 또 다른 예약
  fluidBlocked?,     // ← pipeFlow
): string | null
```

*"이 칸 비었나"* 를 묻는데 **집합 다섯 개**를 들고 다닌다. 새 종류가 생기면 파라미터가
여섯이 되고, 안 넘기면 **조용히 통과한다**.

### ㉢ 납품 하나마다 **전체 집합을 복사**한다

```ts
const blocked = new Set<string>(base);           // routeOneDelivery:422
for (const k of deliveryBelts) blocked.add(k);   // 매 납품마다
```

`base` 는 배치 전체의 셀이다. 납품 N 개면 N 번 복사한다.
`deliveryRoute.ts:341` 의 `new Set<string>(reservedExport)` 도 같다.

### ㉣ 그래서 지금 절대좌표 셀 집합이 **넷**이다

```
② modulePacking.reservedExportCells    C 의 예약
④ deliveryRoute.buildOccupancy         전 모듈의 셀   ← ㉠ 중복
⑤ deliveryRoute.deliveryBelts          이미 깐 B
⑥ modulePerimeterPass.occ              ④ + B          ← ㉠ 중복
```

**넷이 같은 격자를 본다.** 각자 따로 만들고, 서로를 모르고, 필요할 때 복사해서 합친다.

## 1. 목적과 성공 기준

> **목적:** 절대좌표 셀을 **한 인덱스**가 알게 하고, 지금의 넷을 그 인덱스에 대한
> **질의**로 재현한다.

성공은 관측 가능한 수치로만 적는다:

| | 지금 | 끝나면 |
|---|---|---|
| `buildOccupancy` 정의 | **2개**(동일 코드) | 1개 |
| 절대좌표 셀 집합 선언 | **4개** | 1개 |
| `plannedChainClear` 파라미터 | 7 | 3 (`chain`, `ownKey`, `ledger`) |
| `new Set<string>(base)` 전체 복사 | 납품마다 | 0회 |
| 산출물 | — | **같다**(§4 그림자로 대조) |

## 2. 왜 구조정리가 재발을 막나

**결함을 안 고치는데 재발을 막는다** — 이 계획의 유일하게 미묘한 주장이라 근거를 적는다.

```
지금:  새 셀을 만들면 "넷 중 어디에 넣나" 를 고른다.  안 넣으면 **조용하다**
       실제로 넷을 놓쳤다(→ layout-standards §3.5 #7·#13·#15·#16)

끝나면: 넣을 곳이 하나다.  안 넣으면 **아무 데도 안 보인다** — 즉시 드러난다
       그리고 넷은 각각 "질의 한 줄" 이 된다
```

**고르는 일이 없어지는 것**이 이 계획이 사는 이유다. 이름을 고치거나 검사를 늘리는 것은
사람의 기억에 기대는 대비라 다시 실패한다.

## 3. 설계 — 인덱스 하나 + 질의

### 자료형 (최소)

```ts
/** 한 칸의 주인. **지금 이미 흐르고 있는 정보만** 담는다 — 새 지식이 아니다. */
export interface CellOwner {
  /** 양보·해제의 단위. 납품 key · 상자 id · 모듈 id. */
  owner: string;
  /** 경로 넷(→ layout-models §3.5). 지금의 넷을 가르는 축이 이것이다. */
  path: "A" | "B" | "C";
  /** 예약인가 실물인가. `reservedExport` vs `deliveryBelts` 를 가른다. */
  stage: "reserved" | "placed";
}

export interface CellLedger {
  add(cells: Iterable<Cell>, o: CellOwner): void;
  /** 이 칸의 주인. **사유 문자열이 여기서 나온다.** */
  ownerOf(cell: Cell): CellOwner | null;
  /** 조건에 맞는 주인이 이 칸을 잡았나 — 옛 Set 의 `has` 를 대체한다. */
  taken(cell: Cell, by: OwnerFilter): CellOwner | null;
}

export type OwnerFilter = { path?: Path[]; stage?: Stage; not?: string };
```

### 넷이 전부 **질의**로 재현된다 — 이게 이 설계의 검증이다

| 옛 집합 | 질의 |
|---|---|
| ④ `base` | `{ path: ["A"] }` |
| ⑤ `deliveryBelts` | `{ path: ["B"], stage: "placed" }` |
| ② `reservedExport` | `{ path: ["C"], stage: "reserved" }` |
| `reservedDelivery`(k 제외) | `{ path: ["B"], stage: "reserved", not: k }` |
| ⑥ `occ` | `{ path: ["A", "B"] }` |

**넷이 같은 격자의 서로 다른 자름이었다.** 자료구조가 넷일 이유가 없었다는 것이 여기서
증명된다 — 이 표가 안 채워지는 항목이 있으면 설계가 틀린 것이다.

### 장부에 **안 들어오는 것 하나** — 정직하게

`fluidBlocked`(유체 인접 지도)는 `pipeFlow` 가 셀이 아니라 **인접 규칙**으로 만든다.
이 계획은 그걸 안 옮긴다. 그래서 끝나면 남는 것이 **정확히 하나**다:

```
절대좌표 셀 → 장부       (이 계획)
유체 인접   → pipeFlow   (남는다.  #7·#13 이 사는 자리)
```

**둘로 줄이는 것까지가 구조정리다.** 하나로 합치려면 충돌 규칙을 claim 에 붙여야 하고,
그건 새 능력이라 이 계획 밖이다 → `judgements.md` **J-인접흡수**.

### 순수성은 안 깨진다

`deliveryRoute`·`rePathToPerimeter` 는 *"pack 미변형"* 이 계약이다. 장부는 **pack 이
아니라 스크래치**다 — 지금도 `deliveryBelts`·`occ` 를 지역 변수로 누적하고 있고, 그것을
호출자가 만들어 넘기는 것으로 바꿀 뿐이다. 모듈 그래프는 여전히 안 건드린다.

## 4. 단계

> 규약대로 **Step 1 까지만 확정**하고 뒤는 방향으로 적는다.
> Step N 을 끝낼 때 Step N+1 의 전제를 다시 확인한다.

### Step 0 — `buildOccupancy` 중복 제거

`planner/cellLedger.ts` 를 만들고, **동일 코드인 두 곳**(㉠)만 갈아 끼운다.
질의는 아직 안 만든다 — `add` 와 `taken({path:["A"]})` 하나면 된다.

```
전제:  두 함수의 본문이 문자 단위로 같다(2026-08-19 확인). 다른 것은
       modulePerimeterPass 가 deliveryCells 를 더 넣는 것뿐이고, 그건
       호출자가 add 를 한 번 더 부르면 된다
불변:  두 소비처가 받는 집합의 **원소가 같다** — 같은 입력을 같은 순서로 훑고
       같은 cellKey 를 만들므로 다른 답을 낼 수 없다(기전)
관문:  장부가 **파이프라인을 관통하는 물건**이 된다. 지금은 두 함수가 각자
       만들고 버려서, 무엇을 더 넣고 싶어도 넣을 자리가 없다
```

### Step 1 — 나머지 셋을 질의로 **재현하고 대조**한다 (그림자)

옛 집합 ②⑤와 `reservedDelivery` 를 **그대로 두고**, 같은 셀을 장부에도 `add` 한다.
판정할 때 옛 집합과 장부 질의를 **둘 다** 물어 답이 다르면 콘솔에 낸다.

```
전제:  §3 의 질의표가 넷을 빠짐없이 재현한다. 확인 방법 — 표의 다섯 줄을
       하나씩 옛 집합과 대조하는 단위 테스트를 먼저 쓴다(코드보다 먼저)
불변:  판정에는 **옛 집합의 답만** 쓴다. 장부 질의의 답은 비교·기록 외에
       소비처가 없어서 배치가 다른 답을 낼 수 없다(기전)
관문:  "자료구조가 넷일 이유가 없다" 가 **글이 아니라 실측**이 된다.
       불일치가 나오면 §3 표가 틀린 것이고, 그 자리에서 설계를 고친다
```

> **이 단계가 계획의 대조군이다.** 불일치가 안 잡히게 만들면 Step 2 는 검증 없이
> 옛 집합을 지우는 일이 된다.

### Step 2 — 옛 집합 삭제, 파라미터 축소 *(방향)*

`plannedChainClear` 7 → 3. `routeOneDelivery` 의 `new Set(base)` 복사 제거.
②⑤와 `reservedDelivery` 선언 삭제.

### Step 3 — 문서 이관, 폴더 삭제 *(방향)*

`layout-models` §3.5 를 갱신한다(장부 여섯 → 로컬 둘 + 절대 하나 + 유체 인접 하나).

## 5. 이 계획이 **안 하는 것** — 전부 후속

| | 왜 여기가 아닌가 |
|---|---|
| 결함 넷(#7·#13·#15·#16) 수정 | **동작이 바뀐다.** 구조정리가 끝나면 각각 질의 한 줄이 된다 |
| 우선권 등급 · 양보 · 선점 | 새 능력. 장부가 생긴 뒤 `행채널-모델/judgements.md` **J-양보** 로 |
| 유체 인접을 장부로 흡수 | 충돌 규칙을 claim 에 붙여야 한다 → **J-인접흡수** |
| 모듈 로컬 장부(①) 통합 | 로컬 좌표라 경쟁하지 않는다. 합치면 오히려 나빠진다 |
| 세로 채널 추상 장부(③) 통합 | 채널 로컬. 결과가 절대화될 때만 장부에 실린다 |

## 6. 위험

| | 위험 | 대비 |
|---|---|---|
| **가** | Step 1 에서 불일치가 나온다 | **그게 목적이다.** §3 표를 고치는 신호 |
| 나 | 질의가 `has` 보다 느리다 | 필터 3필드 비교. 대신 ㉢의 전체 복사가 사라져 총량은 준다 |
| 다 | 장부를 인자로 나르느라 시그니처가 번진다 | ㉡에서 파라미터 5개가 1개로 주는 것과 상쇄. 순증이면 설계가 틀린 것 |
| 라 | 구조만 바꾸고 결함이 그대로라 값이 없어 보인다 | §1 의 수치가 값이다. 결함은 **후속에서 한 줄**이 된다 |
