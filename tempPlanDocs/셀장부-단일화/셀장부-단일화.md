# 셀장부 단일화 — 같은 칸의 판정을 한 곳에서

## 0. 왜 — **이름을 고쳐도 재발한다**

2026-08-19 전수 조사(→ [[layout-models]] §3.5)가 판정이 **아예 없는 자리를 넷** 찾았다:

```
#7   B유체 ↔ B유체(다른 유체)   겹침만 본다.  인접 미검사 → 두 유체가 한 통이 된다
#13  B유체 ↔ C파이프           pipeFlow 가 납품 **전에** 얼어 B 를 모른다
#15  행 채널 ↔ C 예약          행 채널에 예약이 없다 — 가로질러도 아무도 모른다
#16  마진 프레임 ↔ B           bounds 가 마진을 포함, 직선만 예약
```

**넷을 하나씩 고치면 다음 기능에서 또 생긴다.** 원인은 누락이 아니라 구조다 —
장부가 여섯이면 새 셀을 만들 때마다 *"여섯 중 어디에 넣나"* 를 **사람이 기억해야 한다**.
기억은 반드시 실패한다. 실제로 넷을 놓쳤고, 그중 둘(#7·#13)은 화면상 멀쩡해서
라우팅이 "성공"이라 보고한다.

> **이 계획이 고치는 것은 결함 넷이 아니라 결함이 계속 생기는 자리다.**

## 1. census 에서 유도되는 원칙 다섯

| | 원칙 | 근거 |
|---|---|---|
| **1** | **로컬 좌표는 경쟁하지 않는다** — 자기 안에서 배정을 끝내고 절대좌표로 나온다 | §3.5 좌표계 표. ①③⑤ 를 안 건드리는 이유 |
| **2** | **절대 좌표는 장부 하나만 본다** — 절대화되는 **그 순간** 장부에 싣는다 | 여섯이 나눠 보는 것이 원인 |
| **3** | **충돌 규칙은 claim 이 들고 다닌다** — 전역 *"겹치면 안 됨"* 이 아니다 | `pipeFlow` 가 이미 그 모양. 유체는 인접도 충돌, 같은 유체는 무해 |
| **4** | **우선권은 피해 등급이 정한다** — 호출 순서로 흉내내지 않는다 | 순서로 흉내내다 방향이 어긋났다(#8 예약은 C 승, #9 방출은 B 승) |
| **5** | **양보는 장부가 중재한다** — 당사자끼리 안 만난다 | `LaneAssignment.options` 가 이미 자유도인데 **읽는 코드가 0곳** |

**원칙 3 이 이 설계의 심장이다.** 겹침 하나로 통일하려 들면 유체를 못 담고, 유체를
특별 취급하면 다음 예외에서 또 갈린다. `pipeFlow` 가 이미 *"유체 이름마다 지도가 다르다"*
로 그 답을 냈다 — **claim 마다 지도가 다르다** 로 일반화한다.

## 2. 자료형 — `planner/cellLedger.ts` (신규)

```ts
/** 한 칸을 잡은 주체. */
export interface Claim {
  /** 양보·해제의 단위. 납품 key · 상자 id · 모듈 id. */
  owner: string;
  /** 경로 넷 중 하나(→ layout-models §3.5). 등급의 입력. */
  path: "A" | "B" | "C" | "D";
  /** 예약인가 실물인가. **예약만 양보 대상**이다. */
  stage: "reserved" | "placed";
  /** 이 칸이 무엇인가 — 충돌 규칙이 여기서 나온다. */
  what: ClaimWhat;
}

export type ClaimWhat =
  | { kind: "machine" }                                    // 절대 안 밀린다
  | { kind: "belt" } | { kind: "inserter" } | { kind: "chest" }
  | { kind: "pipe"; fluid: string }                        // 사방으로 잇는다
  | { kind: "pipeUnderground"; fluid: string; face: PortFace } // 한 면만
  | { kind: "fluidBox"; fluid: string; role: "in" | "out" } // 밟으면 생산물이 샌다
  | { kind: "width" };                                     // 폭만 잡는 예약(실물 없음)
```

**충돌은 대칭 술어다** — 순서를 바꿔도 같은 답이라야 장부가 방향을 안 갖는다.

```ts
/** `d` = 두 칸 거리. 0 = 같은 칸, 1 = 4-인접. */
export function conflicts(a: ClaimWhat, b: ClaimWhat, d: 0 | 1): boolean;
```

| a ↔ b | d=0 겹침 | d=1 인접 |
|---|---|---|
| 아이템끼리(belt·inserter·chest) | 충돌 | 무해 |
| `machine` ↔ 무엇이든 | 충돌 | 무해 |
| `pipe(F)` ↔ `pipe(F)` — **같은 유체** | 충돌 | **무해**(자연 병합, 처리량 무한) |
| `pipe(F)` ↔ `pipe(G)` — 다른 유체 | 충돌 | **충돌** |
| `pipeUnderground(F,면)` ↔ `pipe(G)` | 충돌 | **그 `면` 쪽만** 충돌 |
| `fluidBox(G,"out")` ↔ `pipe(F)` | 충돌 | **충돌** — 생산물이 샌다 |
| `width` ↔ `width` | 충돌 | 무해 |

**이 표는 새 지식이 아니다** — `pipeFlow` 머리 주석의 hard/soft 규칙을 claim 축으로 옮긴 것이다.
그러니 구현은 `collectPipeFlow` 를 **감싸지 말고 그 규칙을 이 표로 흡수**한다.

### 장부 API

```ts
export interface CellLedger {
  /** 놓을 수 있나. 장부를 안 바꾼다 — 계획 단계가 묻는 용도. */
  test(cells: Cell[], claim: Claim): Conflict | null;
  /** 잡는다. 충돌하면 안 잡고 Conflict 를 낸다. */
  claim(cells: Cell[], claim: Claim): Conflict | null;
  /** owner 의 모든 칸을 놓는다 — 계획을 버릴 때(dijkstra 폴백). */
  release(owner: string): void;
  /** 이 칸의 주인. **사유 문자열이 여기서 나온다.** */
  ownerOf(cell: Cell): Claim | null;
}

export interface Conflict {
  cell: Cell;
  incumbent: Claim;
  /** 새 claim 의 등급이 더 세다 — 양보를 물을 자격이 있다(Step 4). */
  canPreempt: boolean;
}
```

## 3. 우선권 — **실패했을 때의 피해**로 매긴다

```
0  machine              머신이 굶는다.  §0.1 목적 직접 위반
1  유체(pipe·fluidBox)   조용히 오염된다.  화면상 멀쩡해서 더 나쁘다
2  납품(B)               실패 → 부모 머신이 굶는다 → 0 으로 귀결
3  반출(C)               상자가 안에 남는다.  **물류는 이어진다**
4  width                 폭 낭비.  미관
```

**이 규칙은 이미 코드에 있다** — 세로 채널의 `yieldedExports`(*"유체가 갇히면 반출이
물러난다"*)가 1>3 을 옮긴 것이다. 채널 안에서만 쓰인다. 장부는 그걸 **전역으로** 만든다.

> **등급이 `path` 가 아니라 `what` 에서도 나온다** — 유체 납품(B)은 path 로는 2인데
> what 으로는 1이다. 어느 쪽을 쓰나가 미결이다 → `judgements.md` **J-등급**.

## 4. 단계

> 규약대로 **Step 2 까지만 확정**하고 뒤는 방향으로 적는다.
> Step N 을 끝낼 때 Step N+1 의 전제를 다시 확인한다.

### Step 0 — 예약에 **주인**을 싣는다 (동작 불변)

`reservedExportCells: Set<셀>` → `Map<셀, owner>`. `plannedChainClear` 의 사유를
`반출 예약 (8,15)` → `반출 예약 (8,15) — 상자 <id>` 로.

```
전제:  reservedExportCells 를 읽는 곳은 deliveryRoute.ts:267 하나뿐이다
       (grep 확인 완료 2026-08-19). 자료형을 바꿔도 파급이 한 곳이다
불변:  Map 의 **키 집합이 Set 과 같다** — 값만 늘었으므로 `has` 기반 판정이
       다른 답을 낼 수 없다(기전)
관문:  "막은 칸의 주인이 그때 다른 선택지를 가지고 있었나" 를 **물을 수 있게 된다**.
       지금은 칸만 알아서 못 묻는다 → 행채널-모델 J-양보 1단계와 같은 작업
```

### Step 1 — 장부 자료형을 만든다 (**아무도 안 쓴다**)

`planner/cellLedger.ts` + 단위 테스트. 규칙표(§2)를 테스트로 고정한다.

```
전제:  pipeFlow 의 hard/soft 규칙이 §2 표로 손실 없이 옮겨진다.
       확인 방법 — pipeFlow.test.ts 의 케이스를 cellLedger 규칙으로 다시 세워
       같은 답이 나오는지 본다(옮겨 적는 게 아니라 **대조**한다)
불변:  cellLedger 를 import 하는 프로덕션 코드가 0개 — 소비처가 없어서
       다른 답을 낼 수 없다(기전)
관문:  §2 의 규칙표가 **글이 아니라 실행되는 것**이 된다
```

### Step 2 — **그림자 장부** (동작 불변, 검증만)

기존 여섯 장부를 **그대로 두고**, 같은 셀을 장부에도 `claim` 한다. 충돌이 나와도
**거절하지 않고 센다**. 결과를 `flg.report()` 에 등급별로 낸다.

```
전제:  각 생산자가 자기 셀을 절대좌표로 확정하는 지점이 하나씩 있다
       (A→moduleTransform 후, B→routeOneDelivery 반환, C→addedCells,
        ②→addSeg). 확인 완료 — 계획서 §5 의 자리표
불변:  claim 의 반환값을 **콘솔 카운터 외에는 아무도 안 읽는다** — 소비처가
       없어서 배치가 다른 답을 낼 수 없다(기전)
관문:  **#7·#13·#15·#16 이 실측된다.** 기존 장부가 잡던 것 = 장부도 잡는다(일치),
       기존이 못 잡던 것 = 장부만 잡는다 → 그게 넷의 실물 증거다
```

> **이 단계가 계획 전체의 대조군이다.** 여기서 불일치가 0이면 §3.5 진단이 틀린 것이고,
> 계획을 접는 게 옳다. **틀릴 수 있게 만들어 두는 것이 이 단계의 값이다.**

### Step 3 — 소비처를 하나씩 갈아탄다 *(방향)*

작고 자족적인 것부터. 매 단계 기준선(타입 0 · 572 중 569) 확인.

```
3-1  ② 반출 예약        Step 0 에서 이미 Map 이다.  가장 싸다
3-2  ④⑤ 납품(B)         base + deliveryBelts + fluidBlocked 셋이 장부 하나로
3-3  ⑥ 반출 방출(C)      여기서 #13(B유체 ↔ C파이프)이 **저절로** 닫힌다 —
                        장부가 하나면 "납품 전에 얼었다" 는 일이 성립하지 않는다
```

### Step 4 — **양보를 켠다** *(방향)*

`claim` 이 `canPreempt` 인 `Conflict` 를 내면, 장부가 incumbent 에게 다음 후보를 묻는다.
`LaneAssignment.options` 가 여기서 살아난다(지금 읽는 코드 0곳).

### Step 5 — 빠진 것을 장부에 넣는다 *(방향)*

행 채널 띠(#15) · 마진 프레임(#16). **장부가 생긴 뒤에는 "넣는다"가 한 줄이다** —
지금은 어느 장부에 넣을지부터 골라야 한다. 이것이 이 계획의 값을 보여 주는 자리다.

### Step 6 — 옛 장부 삭제, 문서 이관 *(방향)*

§3.5 를 갱신하고(장부 여섯 → 하나) 폴더를 지운다.
