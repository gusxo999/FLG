## 0. 이 표가 답하는 것

> **좌석 경로에서 "여러 후보 중 하나를 고르는" 일이 몇 개이고, 각각 어디서 고르며, 어디서 골라야 하나.**

폴더(관심사)와 파일 이름(종류)은 **코드를 어디에 두나**의 답이다. 이 표는 **결정을 어디서 내리나**의 답이다.
구조-2축이 앞의 둘을 정리했고, 셋째는 비어 있었다 — 파일 단위의 축은 **장부 함수 안의 한 줄**에 숨은 결정을 못 본다.

## 1. 낱말

- **결정** — 여러 후보 중 하나를 고르는 일. *규칙 + 입력 → 답*. `sort` · `find` · 첫 번째 · 기본값(`??`) · 순서 있는 목록 ·
  `slice(0, k)` · 반복문의 순서가 결정의 흔한 모양이다. **셈**(답이 하나뿐인 산술 — 팔 수 · 깊이 목록 · gap 폭)은 결정이 아니다.
- **집** — 그 결정이 내려지는 **단 하나의 이름 있는 자리**(함수 하나). 조건 넷:

```
① 하나    그 결정을 내리는 코드는 거기뿐이다. 다른 곳은 답(값)을 받는다
② 이름    결정이 이름을 갖고, 규칙이 그 자리에 문장으로 적혀 있다
③ 앎      규칙이 필요로 하는 것을 **전부 아는 가장 이른 단계**다
           너무 이르면 모르는 것을 추측하고, 너무 늦으면 앞 단계가 기본값으로 대신 정해 버린다
④ 주소    고르는 일이므로 파일 종류는 정책(policy). 폴더는 그 결정이 누구의 사정이냐가 정한다
           — 양끝이 합의해야 하면 link/, 한 모듈 안에서 끝나면 module/, 트리 전체를 봐야 하면 tree/
```

- **집이 없는 모양 넷**

| 모양 | 뜻 | 흔적 |
|---|---|---|
| **숨은 결정** | 결정처럼 안 보인다 — 기본값 · 첫 번째 · `slice` | 주석이 *"무관하다"* 고 적는다 |
| **여러 집** | 부르는 쪽마다 같은 결정을 다시 내린다 | 목록 여럿 · 사본 · 규칙이 갈라진다 |
| **이름 없는 집** | 제어 흐름의 차례로만 있다 | `if … else if …` 의 순서가 곧 규칙 |
| **남의 집** | 집은 하나인데 관심사가 다른 폴더다 | 두 모듈을 쥐는 함수가 `module/` 에 |

**결정은 그 값을 처음 쓰는 곳에 생긴다.** 도장을 찍는 순간 행이 필요하면 장부에, 반복문을 돌리는 쪽이 순서가 필요하면 그 반복문에 생긴다.
하나하나는 그 자리에서 옳다. 흩어짐은 그 옳은 결정들이 모인 결과다.

## 4. 결정마다 — 근거

### 결-1 면 — **목록 다섯, 그리고 둘이 갈라졌다**

```
링크 · 간선 축    선호  출력 W · 입력 E                       seatLinkEdge 가 tryLinkFace 에 "W"/"E" 를 넘긴다
                 넘침  OUT ["W","S","N"]   IN ["E","S","N"]      spillPair
                       플래그(OPPOSITE_FACE) 켜면 ["W","E","S","N"] · ["E","W","S","N"]
링크 · 모듈 축    선호 W/E → 넘침 ["W","S","N"] · ["E","S","N"]   seatModuleLinks (제품 안 탐)
나머지 줄         출력  W → ["E","W","S","N"]                    seatRestLines
                 공급  E → ["W","E","S","N"]
                 원료  E → [...nsExposure, "W","E","S","N"]
유체 면           선호 단계는 비켜 간다(반대 면도 유체면 안 비켜 감) · 넘침 단계는 허용     avoidsPipeFace
```

**갈라진 자리.** 플래그를 켜면 링크의 넘침은 **선호 면 재시도(유체 허용)를 반대 면보다 먼저** 본다(`["W","E",…]`).
나머지 줄은 **반대 면을 먼저** 본다(`["E","W",…]`). 이유는 나머지 줄 쪽에만 적혀 있다 — *"반대 면은 공짜지만 유체 면은 앉는 순간
파이프가 물러나 폭을 먹고, gap 은 기둥을 벌린다."* 링크 쪽 주석(*"반대 옆면은 gap 앞에 온다 … 자매 경로와 같다"*)은 반대 면과
gap 의 순서만 말하고 이 차이는 말하지 않는다. **집이 둘이면 규칙이 조용히 갈라진다**의 실례다. 기본 경로(플래그 꺼짐)에는 영향이 없다 —
그 플래그의 주인은 `부분-링크` J14 다.

**링크의 면은 짝을 안 본다 — 그래서 창구 안에 있어야 한다.** `spillPair` 는 자식 면 × 부모 면을 이중 루프로 돌며 첫 성공을 쓴다.
부모 쪽 시도(`tryLinkFace(부모.ctx, …)`)는 자식 쪽이 무엇을 골랐는지를 인자로 받지 않으므로, 이 루프의 답은
**양쪽이 각자 처음 되는 면을 따로 고른 것과 같다.** [[module-planning]] §4.6 표도 *"① 면 — 무엇을 안 보고: 짝이 어디 있나"* 라고 적었다.

### 결-4 인서터 행 — **숨은 결정 · 네 벌**

| 자리 | 코드 |
|---|---|
| `beltRowSpan` | 머신마다 `freeSeatRows(t, mi)` 의 첫 칸 · k 번째 칸 |
| `fitOnFace` | 못 앉은 이유(`seatRows`)용으로 `freeSeatRows(table, mi).slice(0, k)` |
| `commitLinkFace` | W/E 는 `freeSeatRows(table, mi).slice(0, k)`, gap 의 집는 쪽은 `rowsPerMachine - 1 - base - …`(동쪽부터) |
| `seatOnSharedBelt` | `freeSeatRows(table, mi).slice(0, k)` |
| 문서 | [[trunk-assignment]] §3 ③ TR3 *"얕을수록 흐름 반대쪽 끝"* — 코드에 없다 |

장부 머리말은 *"**고르지 않는다**"* 고 적었다. 주석 *"(W/E 면은 나가는 쪽이 면과 수직이라 이 순서와 무관하다)"* 가 이 결정을
결정이 아닌 것으로 만든 문장이다 — 옆 포트에는 맞고 **기둥 끝 포트에는 틀리다**(`(topT∓1, d)` · `(topT∓2, d)` — 행 방향).
`fitOnFace` 는 좌석 **수**만 세고 위에서 k 개를 고른 뒤 깊이 칸을 본다 — 고른 행이 막혔는지는 **고른 뒤에야** 안다.

### 결-5 gap 반출 깊이 — **숨은 결정**

`fitOnGap`: `exitDepth: LINK_LANE_DEPTH + nth`, `nth = groupsOn(gapTable, mi)` — **그 면에 먼저 온 그룹 수가 곧 반출 깊이**다.
주석은 *"탐색 없이 순번으로 결정"* 이라고 적었고, 그 순번은 도착 순서다. 막힌 면이 성립하려면 *"포트에 가까운 그룹이 얕은 줄"* 이어야 하는데
([[용어사전]] ParallelBelt), 그것을 보장하는 것은 `commitLinkFace` 의 **동쪽부터** 좌석 순서와 이 도착 순서의 조합이다 — 한 규칙이 두 함수에 나뉘어 있다.

### 결-6 · 7 · 8 합류 · 쪼갬 · 원자성 — **남의 집**

셋 다 양끝의 일이다(계획서 §2). 집은 하나씩 있는데 폴더가 `module/` 이다. [[code-folders]] 가 이 사실을 *"정직하게 잃는 것"* 으로 적어 두었다.
`splitLinkAtRows` · `resolveSpanBlock` 은 `module/arith/link.ts` 에 있다 — 토막은 **양끝이 함께** 갈라지는 링크의 일이다
(주석: *"양끝이 같은 객체를 보므로 자식 출력과 부모 입력이 함께 갈라진다"*).

### 결-9 수단 사이의 순서 — **이름 없는 집**

```ts
if (candFrom && candTo) { … 확정 … continue; }                    // ① 선호 면 둘 다
if (opts.split && budget > 0) { … 쪼개서 앞에 넣는다 … continue; }  // ② 쪼개기 (막힌 쪽의 막힌 행으로)
const spilled = spillPair(fromSeat, toSeat, g);                   // ③ 다른 면
if (spilled) { … continue; }
keep(g, undefined, undefined, fw, tw);                            // ④ 포기 — 사유는 선호 면의 것
```

**규칙은 이 코드의 차례뿐이다.** *"쪼개기가 다른 면보다 먼저"* 는 어디에도 문장으로 없다. `allocateLinkFaces` 의
*"선호 면의 사유만 모은다 — 사다리는 그 줄이 원래 앉고 싶던 면의 못으로 자른다"* 가 가장 가까운 근거다.
쪼갬 예산(`그룹 수 × 4`)도 이 흐름 안의 결정이다.

이 결정이 **링크 쪽**인 이유: 링크 쪽 수단(쪼개기)과 모듈 쪽 수단(다른 면)의 **사이** 순서라서, 둘을 다 아는 쪽이어야 한다.

### 결-10 링크 줄의 앉는 순서 — **여러 집 · 규칙 없음**

`seatTree`: *"순서는 `specs`(트리 DFS pre-order)를 그대로 쓴다 — 순서를 고르는 것은 Step 6 의 일이다."*
`seatLinkEdge`: 합류 쌍을 큐 앞에, 나머지는 받은 순서. 토막은 `queue.unshift` 로 바로 뒤에.
옛 `간선-배정` Step 6(순서 규칙)은 2026-08-30 계획을 합칠 때 **옮겨지지 않았다**(`조사-순서.md` 머리말 — 옛 `자리-배정` 에서 이 폴더로 옮겨 왔다).

## 5. 이 표가 계획을 바꾼 것

**좌석 창구의 묻기에서 면 인자를 뺀다.** 표를 만들기 전의 계획서는 `ask(line, side, face, …)` — **링크 쪽이 면을 고르는** 모양이었다.
결-1 은 모듈의 결정인데 경계 밖에 남는다. 그대로 두었다면 Step 3(잠수)에서 창구 모양을 다시 바꿔야 했다
(잠수가 되는 면과 안 되는 면을 링크 쪽이 알아야 하므로).

```
전   ask(line, side, face, 선택지…)           링크 쪽이 "W" · spillPair 의 목록을 쥔다
후   ask(line, side, "near" | "far", 제약?)   near = 선호 면에서 창구 안 수단을 다 써 본 자리
                                             far  = 창구의 넘침 순서에서 처음 되는 자리
                                             제약 = 합류 쌍의 기하(끝 강제 · 끝 선호 · 깊이 선호) — 링크의 결정(결-6)
```

`near` · `far` 를 링크 쪽이 고르는 것은 결-9(쪼개기가 다른 면보다 먼저)가 **링크의 결정**이기 때문이다.
`far` 를 미리 계산해 두지 않고 **물을 때만** 계산하는 것은 관측 계수기(`recordEndsAudit`)가 `tryLinkFace` 성공 **횟수**를 세기 때문이다
— 미리 계산하면 오늘과 호출 수가 달라진다(계획서 Step 1 불변 참조).

새로 생기는 결정은 **처음부터 집을 갖고** 태어난다.

## 7. 짓는 때 — **규칙을 바꾸기 직전에 짓는다**

집의 모양(함수의 인자 · 사는 단계)은 **그 규칙이 무엇을 알아야 하나**가 정한다. 그래서 집은 규칙을 바꾸는 단계의 **바로 앞**에
동작 불변으로 짓는다. 규칙을 안 바꾸는 결정은 **표에 집만 적어 두고 짓지 않는다** — 지금 지으면 오늘 규칙에 맞춘 모양이 되고,
규칙을 바꾸는 날 다시 짓게 된다.
