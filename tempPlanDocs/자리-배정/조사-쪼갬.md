# 조사 · 쪼갬 — 결함인가 미완성인가 (2026-08-29)

> **사실 문서** — 계획이 아니라 조사 결과다. 계획이던 `간선-배정.md` 는 2026-08-30 에
> 이 폴더로 합쳐지며 사라졌다 — 지금 계획서는 같은 폴더의 `부분-트렁크.md`.
>
> **판정 렌즈:** 이 저장소의 규칙(`docs/auto-layout/link/machine-link.md` — *무엇을 재나*)대로
> **먼저 기능의 큰 그림을 세우고**, 그다음 *"이건 만든 적이 없는가(미완성), 만들었는데 틀렸는가
> (결함)"* 를 가른다. 남은 실패를 전부 결함으로 읽으면 없는 버그를 쫓게 된다.

## 큰 그림 — 쪼갬은 **무엇을 겨냥해 만들어졌나**

```
겨냥한 문제   한 줄이 앉으려는 레인이 **점**(남의 포트)들로 막혀 있다
              → 그 점들 사이에 내 좌석이 있으면, 점 앞에서 끊으면 앉는다
판정          resolveSpanBlock(내 좌석 행, 막힌 행) → 자를 경계 (한쪽 면의 기하만 본다)
값을 매긴 대가 "토막 하나가 포트 하나"                (machine-link.md — 대가)
```

**설계가 처음부터 한쪽 면만 봤다.** 판정 함수의 인자가 행 목록 둘뿐인 것이 그 증거다 —
반대쪽 모듈을 볼 **자리 자체가 없었다**. 그리고 그럴 수밖에 없었다: 옛 모듈 축에서는
배정이 자기 모듈만 봤으므로, 반대쪽을 물어볼 방법이 없었다.

## 흐름의 실제 모양 — **계단꼴이지 완전 팬이 아니다**

`allocateFlows` 는 **손가락 하나로 훑는 탐욕 배분**이다(`link/arith/flows.ts:85`):

```ts
let ci = 0;                       // 자식 손가락 — 다 비운 자식만 넘긴다
for (let pj = 0; pj < parentNeed.length; pj++)
  while (parentNeed[pj] > EPS) { ... links.push({ fromMachine: ci, toMachine: pj, ... }) }
```

```
자식 0 ──→ 부모 0, 1
자식 1 ──→ 부모 1, 2          ← 경계에서만 겹친다
자식 2 ──→ 부모 2, 3
```

**이 모양이 쪼갬의 대가를 정한다.** 부모 기준으로 자르면 각 토막의 자식 명단은
**연속 구간**이고, 경계에 걸친 자식 하나만 두 토막에 함께 든다.

```
토막 k 개 → 자식 쪽 경계 k−1 개 → 자식 좌석 최대 **+(k−1)**
            (경계 자식은 rate 가 갈려 각각 올림되므로 팔도 최대 +1씩)
```

> **앞서 "자식 쪽이 3배" 라고 적은 것은 틀렸다.** 그건 완전 팬일 때의 수이고,
> `allocateFlows` 는 완전 팬을 만들지 않는다. 실제 대가는 **경계 수**만큼이다.

같은 이유로 *"토막마다 자식 기둥을 관통해 기둥 끝(N·S) 둘을 다 먹고 셋째가 갇힌다"* 도
**일반적으로는 안 일어난다** — 토막의 자식 명단이 연속 구간이라 `spansAllMachines` 가
대개 거짓이다.

## 결함 A 재판정 — **미완성이다. 그리고 두 군데를 내가 잘못 봤다**

### 정정 ① — *"토막 전체가 미배정"* 은 틀렸다

`seatLinkEdge` 는 토막을 큐에 넣고 **하나씩** 앉힌다. 못 앉은 토막만 미배정이다.

```ts
queue.unshift(...parts);           // 토막을 앞에 넣어 이어서 앉힌다
... 토막마다 tryLinkFace 양끝 → 되면 확정 / 안 되면 넘침 → 그래도 안 되면 그 토막만 미배정
```

### 정정 ② — 바뀐 것은 실패의 **모양**이고, 그건 **좋아진 쪽**이다

| | 옛 모듈 축 | 지금 간선 축 |
|---|---|---|
| 자식이 못 앉음 | 자식만 `plans[i] = undefined` → `unroutedLines` | **양쪽 다 미배정** |
| 부모는? | **따로 앉는다**(자식을 모른다) | 함께 안 앉는다 |
| 결과 | 부모 쪽에 짝 없는 포트가 남는다 → `linkMismatches` / raw 포트 | 정직한 미배정 하나 |

**반쪽 배정이 조용히 새던 것을 Step 2 가 막았다.** 나빠진 게 아니다.

### 그래서 A 의 실체

> **미완성:** 쪼갬 판정이 **반대쪽 면의 예산을 안 본다.** 만든 적이 없는 기능이지,
> 만들어 놓고 틀린 것이 아니다.

**남는 진짜 위험**은 하나다 — 경계 자식이 먹는 좌석 `+(k−1)` 이 **그 면의 다른 줄을 밀어낼 수
있다.** 배정에는 되돌리기가 없으므로(R1) 사후에 못 고친다. 처방은 판정에 반대쪽을 넣는 것이고,
**Step 2 가 그 자리를 처음 만들었다** — 이제 `seatLinkEdge` 안에서 양끝을 다 볼 수 있다.

> **다만 넣기 전에 재야 한다.** *"경계 좌석 때문에 밀린 줄이 실물에 있나"* 를 안 재고 넣으면
> 없는 문제에 비용을 치른다. 계측 지점: `면레인 · 쪼갬 N` 과 `unrouted-lines` 의 이름표.

## 그리고 — **Step 3 이 옛 코드의 진짜 버그를 하나 고쳤다**

옛 사다리는 **언제나 부모 쪽으로 잘랐다**:

```ts
const parts = splitLinkAtRows(groups[at], "to", rows, parent?.machine.h ?? 0);
//                                        ^^^^        ^^^^^^^^^^^^^^^^^^^^
```

그런데 그것이 읽던 `depthShortages` 는 **출력(자식 면)과 입력(부모 면)을 둘 다** 담는다
(`planModulePorts` 가 `[outLinks, outFaces], [inLinks, inFaces]` 를 함께 돈다).
그래서 **자식 면에서 막힌 줄**을 만나면:

```
blockedRows  = 자식 면의 행 (= 자식머신 × 자식.h + 칸)
나눗셈       = ÷ 부모.h            ← **단위가 다르다**
자르는 축    = 부모 머신(`to`)      ← **막힌 쪽이 아니다**
```

**행 번호를 남의 자로 나눠 남의 축을 잘랐다.** 지금은 실패한 후보의 쪽에서, 그 쪽의 `h` 로
자른다:

```ts
const cut = !candTo
  ? { side: "to",   rows: cutRows(tw), h: toSeat.ctx.machine.h }
  : { side: "from", rows: cutRows(fw), h: fromSeat.ctx.machine.h };
```

## 결함 B 재판정 — **결함도 미완성도 아니다. 잠복한 불변식 위반이다**

### 큰 그림 — `carries` 가 단일 출처이고 `from`/`to` 는 그 **파생**이다

`module/arith/trunk/link.ts` 가 그렇게 적어 두었다:

```
carries   이 줄이 무엇을 얼마나 싣나          ← **계약**. 단일 출처
from/to   머신 → 그 머신이 쓰는 팔 수         ← carries 에서 유도(armsFromCarries)
```

그리고 `armsAt` 은 **carries 가 있으면 그쪽에서 다시 센다**:

```ts
if (!group.carries || !inserter) return group[side];   // 폴백 — 수량을 모르면 지어내지 않는다
return armsFromCarries(group.carries, side, inserter);
```

### 실체

`splitLinkAtRows` 의 `narrow` 는 **머신은 거르고 값은 원본 그대로** 둔다:

```ts
const narrow = (m, s) => new Map([...m].filter(([mi]) => carries.some((c) => c[s] === mi)));
```

토막마다 **원본의 팔 수**가 남는다. 그런데 **오늘은 아무도 안 읽는다:**

| 읽는 곳 | 무엇을 읽나 | 낡은 값에 걸리나 |
|---|---|---|
| `armsAt` | 팔 수 — **carries 를 먼저 본다** | ✘ (토막은 carries 가 언제나 있다 — 함수의 전제) |
| `machinesOn` · `spansAllMachines` | `.size` / `.keys()` | ✘ 명단은 올바로 좁혀졌다 |
| `splitLinkAtRows` 자신 | `.keys()` | ✘ |
| `summarizeBeltForms` | `.keys()` | ✘ |

> **그래서 지금 틀린 답을 내는 곳이 없다.** 다만 *"같은 사실을 두 곳이 세지 않는다"*(R3)를
> 어긴 상태로 놓여 있고, **`carries` 없는 경로가 하나만 생기면 조용히 원본 수로 센다.**
> 이 저장소는 그 종류의 함정에 이미 값을 치렀다(`tapCapacity` 세 출처).

**처방:** `splitLinkAtRows` 가 `armsFromCarries` 로 **다시 유도**한다. 인서터가 필요하므로
인자가 하나 는다 — 부르는 곳(`seatLinkEdge`)은 `ctx.inserters` 를 갖고 있다.
**급하지 않지만 싸다.**

# 추가 조사 — `트렁크벨트-경로모델` 과 대조 (2026-08-30)

## ① 잠수(TR7-나)는 **없다**

지하 벨트는 스펙에 있고(`undergroundBeltEntityName` · `beltMaxUndergroundDistance`)
**세 곳이 쓴다** — `emitPath`(납품 경로) · `facadeRouting`(수동 편집) · `emitTrunkPipe`
(유체 **파이프**의 점프). **모듈 면의 아이템 레인은 지하로 안 간다.**

→ TR7 의 두 수단 중 **(가) 끊기만 있고 (나) 잠수가 없다.** 만들어야 한다.

## ② 깊이 배정은 TR2 도, 옛 TR2 도 아니다 — **도착 순**이다

```ts
// tryLinkFace — 한 그룹의 레인 후보 정렬
.sort((a, b) => a.total - b.total || a.clusterBeltDepth - b.clusterBeltDepth)
//               ^^^^^^^^^^^^^^^^^ 그 레인의 팔 수 합. 얕을수록 빠른 팔이라 **언제나 최소**
```

**그래서 모든 그룹이 `d2` 를 원하고, 먼저 온 그룹이 갖는다.**

| | 무엇으로 깊이를 정하나 |
|---|---|
| **TR2**(모델) | `a(j,d) = ⌈per_j/tp(d)⌉` 로 **후보를 거르고**, `Σ_j a ≤ h` 를 만족하면 **아무거나** |
| 옛 TR2(폐기) | 구간 적은 줄이 얕게 |
| **지금 코드** | **도착 순** — 모두가 얕은 것을 원하고 선착순으로 갖는다 |

**차이가 결과를 가른다.** TR2 의 `Σ_j a(j,d_j) ≤ h` 는 면의 **모든 줄을 함께 보는** 제약인데,
코드는 머신마다 증분으로 확인한다(`seatsTaken + k > seatRows`). **탐욕이라, 합쳐 놓고 보면
성립하는 배정이 있어도 도착 순이 얕은 레인을 낭비하면 실패한다.**

> 사장님 말씀대로 *"완전히 같은 조건의 후보끼리는 순서가 안 중요하다"* 가 §14-3 의 뜻이다.
> 조건이 다르면 순서는 중요하고, **지금은 그 조건을 아무도 안 보고 있다.**

## ③ 막힘에는 **방향이 둘**이고, 모델은 하나만 다뤘다

```
모드 1 (§14-8 이 그린 것)     깊은 관통이 얕은 줄의 **진출**을 막는다
   d2 ║ 나무 구간   ← 진출하려면 d3 을 건너야 하는데
   d3 ▓ 구리 관통   ← 통째로 차 있다
   처방: TR7 (가) **막는 쪽(관통)을 끊어** 구멍을 낸다 · (나) 잠수

모드 2 (실측 electronic-circuit)  얕은 구간들의 **포트**가 깊은 줄의 **레인**을 막는다
   d2 ▓▓▓ 구간A  ▓▓▓ 구간B  ▓▓▓ 구간C
   d3     ◄ 못        ◄ 못        ◄ 못     ← 관통이 지나갈 수 없다
   처방: 지금 코드는 **막힌 쪽(관통)을 끊는다**
```

**둘은 막는 주체와 처방의 대상이 서로 반대다.**

| | 코드의 이름표 | 해소자 |
|---|---|---|
| 모드 1 | `port-blocked` | **없다** — TR7 이 미구현이다 |
| 모드 2 | `span-blocked` | 쪼개기(막힌 쪽을 끊는다) |

> **모델은 모드 2 를 안 그렸다.** 모델의 전제는 TR2(처리량)가 깊이를 정한다는 것이고,
> 그러면 관통(= `per` 작음)은 **깊은 레인이 정상**이라 모드 2 가 일상적으로 난다.
> 그런데 §14-8 은 관통이 **깊을 때 얕은 줄을 막는** 경우만 봤다.

## 그래서 부분 충돌의 실체

```
처리량 논리   per 큰 줄에 얕은 레인(빠른 팔)   →  Σ a ≤ h 를 지키는 **하드** 제약
기하 논리     관통이 얕아야 못을 안 박는다     →  TR7 이 있으면 **소프트**(회피 가능)
```

**하드가 이겨야 하고, 기하는 TR7 이 흡수해야 한다** — 그게 모델의 답이다.
지금 코드는 **둘 다 없다**: 깊이는 도착 순이고, TR7 은 절반(끊기)뿐이며 그 절반마저
**모드 2 에만** 붙어 있다.

## 남은 물음

```
· 모드 2 에서 "막는 쪽(얕은 구간들)을 끊는" 처방이 성립하나?
  구간을 더 잘게 쪼개면 못이 **늘어난다** — 모드 1 과 방향이 반대라 같은 처방이 안 통한다
· 모드 2 의 올바른 처방은 (나) 잠수뿐인가?
  관통이 못 밑을 지나면 얕은 구간들의 포트를 건드리지 않는다
· 그렇다면 쪼개기(모드 2 용)는 **잠수가 생기면 필요 없어지나**
```

# Q4 조사 — `g` 와 `d` 의 순환을 어디서 끊나 (2026-08-30)

## 두 낱말을 길게

### `d` — **레인 깊이**: 그 줄의 벨트가 머신 면에서 몇 칸 바깥에 눕나

```
머신 ┃ d1 ┃ d2 ┃ d3 ┃ d4 …
     ┃ ●  ┃    ┃    ┃          ● 좌석 — 인서터가 서는 칸. **언제나 d1 이고 벨트는 못 눕는다**
     ┃ ●  ┃ ▓  ┃    ┃          ▓ 벨트가 d2 에 누우면 → 인서터가 **1칸** 뻗어 집는다
     ┃ ●  ┃    ┃ ▓  ┃          ▓ 벨트가 d3 에 누우면 → **2칸** 뻗어야 한다
```

**그래서 `d` 는 "어느 인서터가 이 줄을 먹이나" 와 같은 말이다.**

```
d2 → reach 1 → 짧은 팔 → **빠르다**    (실측 모드팩 10/s)
d3 → reach 2 → 긴 팔  → **느리다**    (실측 3.6/s — 약 1/3)
```

한 머신이 그 줄에서 `per` 만큼 받아야 한다면 필요한 팔 수는

```
a(d) = ⌈ per / 그 깊이 팔의 처리량 ⌉        깊을수록 팔이 **더 많이** 든다
```

그리고 팔은 좌석에 서는데 **좌석은 면당 `h` 개뿐이다**(머신 높이). 그래서
`Σ(그 면 모든 줄의 팔) ≤ h` 가 면의 **하드 예산**이다.

### `g` — **묶음 크기**: 벨트 한 줄이 몇 대의 머신을 맡나

```
g = 1     머신 하나에 벨트 하나              → **다이렉트**
g = N     벨트 하나가 기둥 전체를 지난다      → **관통**
1<g<N     기둥이 c = ⌈N/g⌉ 개 **구간**으로 나뉜다
```

**상한이 왜 `min(k, N)` 인가** — `k` 는 *처리량이 허락하는 최대 머신 수*다:

```
k = ⌊ 벨트 한 줄의 처리량 / 머신 하나가 쓰는 양 ⌋

  예)  벨트 90/s,  머신 하나가 25/s  →  k = ⌊3.6⌋ = 3
       한 벨트로 **3대까지** 먹인다. 4대를 물리면 벨트가 굶는다
```

`N` 은 그 기둥의 머신 수 — 있지도 않은 머신을 맡을 수는 없으니 `min` 이다.
**즉 `g = min(k, N)` 은 "고른 값" 이 아니라 "넘으면 안 되는 선"이고, 지금 코드는 언제나
그 선을 그대로 쓴다.** 쪼개기는 그 선 아래로 내려가는 것이고 — **특수 연산이 아니라
`g` 를 작게 고르는 것**이다.

## 순환 — 실재하고, 지금은 **낙관으로 덮여 있다**

```
g  ──→ 이 줄이 한 머신에서 나르는 양(`carries`)
     ──→ 그 깊이에서 필요한 팔 수 a(d)
     ──→ 좌석에 들어가나 ──→ **d**

d  ──→ 팔 처리량 tp(d)
     ──→ 한 줄이 머신 하나에 쓸 수 있는 최대 rate(좌석 예산)
     ──→ **g**
```

**코드는 이 고리를 "언제나 `d2`" 라고 못박아 덮는다**(`link/policy/edge.ts`):

```ts
const inserter = inserterForReach(config.inserters, 1);     // ← reach 1 고정
const seatCap = (h: number) => faceSeatArms(h, 0) * inserter.throughput;
createLinks(flows, item, { tiers, inserter, fromSeat: seatCap(child.h), toSeat: seatCap(parent.h) });
```
주석: *"**`reach 1` 이다** — 내부 링크의 팔은 좌석(d1)에서 바로 옆 벨트(d2)를 집는다."*

**그런데 배정은 `d3` 에도 앉힌다**(`clusterBeltDepthsOf` 가 reach 종류마다 레인을 낸다).

```
붓기가 가정한 좌석 예산   h × 10/s
d3 에 앉았을 때 실제      h × 3.6/s        →  **같은 rate 에 팔이 약 2.8배**
```

→ 그 줄은 좌석 검사에서 떨어진다(`seat-budget`). **망가지지는 않는다** — 정직하게 거절된다.
**대신 피할 수 있었던 실패가 난다**: `g` 를 작게 골랐으면 `d3` 에서도 들어갔을 줄이다.

## 끊는 자리 — **`per`(머신 하나의 수요)** 다

핵심은 이것이다: **`per` 는 `g` 와 `d` 둘 다와 무관하다.** 레시피와 대수가 준다.

```ts
// link/policy/edge.ts — edgeFlows
childProduction: outTotal / child.count,     // 자식 머신 하나가 내놓는 양
parentDemand:    inTotal  / parent.count,    // 부모 머신 하나가 필요한 양
```

그러면 순서가 열린다:

```
① per          레시피 · 대수에서 나온다                    g·d 와 무관
② a(j,d) = ⌈per_j / tp(d)⌉                                 **g 를 안 본다**
③ d           Σ_j a(j,d_j) ≤ h 를 만족하는 깊이 배정        ← 여기서 d 가 정해진다
④ k = ⌊벨트/per⌋                                           **d 를 안 본다**(벨트 처리량은 인서터와 무관)
⑤ g ≤ k, 그리고 좌석 제약은 ③이 정한 tp(d) 로 **알려진 값**
```

**`d` 를 `per` 로 먼저 정하면 고리가 없다.** `g` 는 그다음에 정해지고, 그때는 팔 처리량이
이미 확정이라 좌석 예산이 참값이다.

> **이게 §14-9 가 옛 TR2 를 폐기한 이유와 같은 논리다.** 옛 TR2 는 `c`(구간 수 = `g` 의 함수)를
> 깊이의 **입력**으로 써서 고리를 만들었다. 새 TR2 는 `a(j,d)` 만 보고, `a` 는 `per` 의 함수라
> `g` 를 안 본다. **모델은 이미 고리를 끊어 놓았고, 코드가 그걸 안 따르고 있다.**

## 남는 결합 하나 — **경계 머신의 올림**

`per` 가 `g` 와 무관하다는 것에 예외가 하나 있다. 구간 경계에 걸친 머신은 **두 구간에
나뉘어** 각각 올림된다:

```
한 줄로 받으면    ⌈per / tp⌉
두 구간에 걸치면  ⌈per₁ / tp⌉ + ⌈per₂ / tp⌉        (per₁ + per₂ = per)   →  최대 **+1**
```

**구간이 `c` 개면 경계가 `c−1` 개이므로 팔이 최대 `c−1` 만큼 는다.** 이건 진짜 결합이지만
**단조롭고 상한이 있다** — `g` 를 줄일 때의 대가로 식에 넣으면 되고, 고리를 만들지 않는다.

## 그래서 Q4 의 답

```
순환은 실재한다.  코드는 "언제나 d2" 로 덮어 두었고, d3 에 앉는 줄에서 그 가정이 깨진다.
끊는 자리는 `per` 다 — d 를 per 로 먼저 정하면 g 는 그 뒤에 참값으로 정해진다.
남는 결합은 경계 머신의 올림(최대 c−1)뿐이고, 그건 고리가 아니라 **비용 항**이다.
```

# 옛 TR2 — 쉬운 말로, 그리고 **왜 죽었나** (2026-08-30 정정판)

## 먼저 못박을 것 — **깊이는 처리량을 안 정한다**

```
깊이 d  →  reach = d − 1 을 지목한다             ← 깊이가 하는 일은 여기까지
reach   →  그 reach 의 인서터 중 **가장 빠른 것**  ← inserterForReach
빠름/느림  →  **사용자가 넣은 목록**이 정한다
```

**얕은 레인이 빠르다는 보장이 없다.** 바닐라만 봐도 뒤집혀 있다:

```
실측 모드팩   reach 1  bulk 10/s        >  reach 2  kr-superior-long 3.6/s
바닐라        reach 1  inserter 0.83/s  <  reach 2  long-handed 1.2/s     ← **깊은 쪽이 빠르다**
```

> 이 저장소는 이 함정에 이름을 붙여 두었다 — `LinkFacePlan.reach` 주석:
> *"**깊이에서 되유도하지 않는다.** 오늘은 `clusterBeltDepth = reach + 1` 이 항등이라 두 방법이
> 같은 답을 내지만, 축은 깊이가 아니라 `(인서터, 그 팔이 집는 타일)` 이고 … 그 항등이
> 깨지는 날 **조용히 틀린다.**"*
> 그리고 계획서 §16 이 같은 말을 한다 — *"깊이는 결과이지 입력이 아니다."*

## 옛 TR2 가 무엇이었나

```
"구간이 **적은** 줄을 머신 가까이(얕게), 구간이 **많은** 줄을 멀리(깊게)"
```

`구간(c)` = 그 줄이 그 면에서 벨트 토막 몇 개로 나뉘나(`c = ⌈N/g⌉`).
`c` 작다 = 한 줄이 많은 머신을 맡는다 = **긴 벨트**.

**근거는 진출할 구멍이었다.** 얕은 줄은 포트로 나가려면 깊은 레인을 건너야 하고,
건너려면 그 행이 비어 있어야 한다.

```
깊은 레인이 긴 벨트 하나   →  모든 행이 차 있다 → 구멍 없음 → 못 건넌다
깊은 레인이 토막 여럿      →  토막 **사이**가 빈다 → 건넌다
```

→ *"구멍 많은 줄(c 큼)을 깊게"*. **기하로는 옳은 관찰이다.**

## 왜 죽었나 — 셋

**① 진출 수단을 하나로 가정했다.** 지상으로 건너는 것 말고 TR7 이 둘을 준다 —
**(가) 막는 줄을 끊어 구멍을 만든다 · (나) 지하로 지난다.** 수단이 있으면 깊이로 미리
피할 필요가 없다.

**② `c` 가 같으면 아무 말도 안 한다.** 서로 바꿔도 타일 하나까지 같은 배치다.

**③ 깊이를 처리량의 **대리**로 썼다 — 그게 결정적이다.**

`c` 와 수요는 묶여 있다:

```
c 작다  ⟺  g 크다  ⟺  k 크다  ⟺  per(머신 하나의 수요) **작다**
                              ( k = ⌊벨트 / per⌋ )
```

그러니 옛 TR2 는 *"수요 작은 줄을 얕게"* 와 같은 말이다. **그런데 얕은 것이 좋은지 나쁜지는
스펙이 정한다** — 그래서 이 규칙은 **스펙에 따라 맞기도 하고 틀리기도 한다:**

```
줄 A  per = 2/s (수요 작음 → 구간 적음)      줄 B  per = 8/s (수요 큼 → 구간 많음)

[실측 모드팩]  d2 = 10/s,  d3 = 3.6/s
   옛 TR2  A→d2, B→d3   팔 = ⌈2/10⌉ + ⌈8/3.6⌉ = 1 + 3 = **4**
   거꾸로  A→d3, B→d2   팔 = ⌈2/3.6⌉ + ⌈8/10⌉ = 1 + 1 = **2**   ← 옛 TR2 가 **두 배 쓴다**

[바닐라]      d2 = 0.83/s, d3 = 1.2/s
   옛 TR2  A→d2, B→d3   팔 = ⌈2/0.83⌉ + ⌈8/1.2⌉ = 3 + 7 = **10**
   거꾸로  A→d3, B→d2   팔 = ⌈2/1.2⌉ + ⌈8/0.83⌉ = 2 + 10 = **12**  ← 옛 TR2 가 **낫다**
```

**규칙이 데이터에 따라 뒤집힌다.** 그게 폐기 사유다 — *"틀렸다"* 가 아니라
**"깊이라는 대리 변수로 적혀 있어서 스펙이 바뀌면 조용히 뒤집힌다."**

그리고 고리도 만든다: `c` 를 깊이의 **입력**으로 쓰는데 `c ← g ← 좌석 예산 ← tp(d) ← d` 다.

## 그래서 옳게 쓰면

```
처리량 규칙(대리 없이)   per 가 큰 줄에 **처리량이 높은 레인**을 준다
                          — 그게 얕은지 깊은지는 **스펙이 답한다**
                          — 코드는 이미 그렇게 한다: 후보를 `팔 수 합` 으로 정렬한다

옛 TR2 의 관찰            "구멍 많은 줄을 깊게" — 처리량이 **동률일 때의 타이브레이크**로는 산다

TR7                       그래도 막히면 끊거나 잠수한다
```

**옛 TR2 를 되살린다면 반드시 `c` 로 적어야지 `깊이` 로 적으면 안 된다** — 후자가 폐기 사유다.
