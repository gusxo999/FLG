## §1 조사 — 먼저 온 그룹과 늦게 온 그룹은 **어디를 먹나**

배정은 `groups.forEach` 다. 먼저 온 그룹이 `commitLinkFace` 로 칸에 도장을 찍고, 늦게 온
그룹은 **남은 자리**를 본다. 자리마다 규칙이 다르다:

| 자원 | 규칙 | **먼저** | **늦게** |
|---|---|---|---|
| **레인**(`clusterBeltDepth`) | 후보를 팔 적은 순 → **얕은 순** | **`d2`**(짧은 팔) | `d2` 가 자기 구간에서 막혔으면 **`d3`**(긴 팔) |
| **좌석**(`slotIndex`) | `freeSeatRows(...).slice(0, k)` — **빈 칸을 앞에서부터** | 머신 면의 **위쪽** 칸 | **아래쪽** 칸 |
| **기둥 끝**(`portEnd`) | `["N","S"].find(안 찼음)` | **N** | S → 셋째는 **옆**으로 |
| **면**(`face`) | 선호 면이 차면 넘침 | 선호 면(W/E) | **gap**(N/S) → 그다음 **실패** |

> **레인은 "찼다/비었다"가 아니라 "내 행 구간이 겹치나"다.** 행이 안 겹치는 두 그룹은
> 같은 `d2` 를 **나눠 쓴다**(벨트가 자기 좌석 구간만 덮고 끝에서 꺾으므로). 그래서 짧은
> 줄 여럿은 `d2` 에 나란히 앉을 수 있다.

### 그림 — 지금 일어나는 일

```
             d1(좌석)   d2        d3
머신 0..29  │ ● ● ●  │ ▓▓▓▓▓  │        │   ① 짧은 줄 A 가 먼저 앉는다
            │        │   ◄    │        │      그 포트가 d3 에 **못**을 박는다
머신 30..59 │ ● ● ●  │ ▓▓▓▓▓  │        │   ② 짧은 줄 B
            │        │   ◄    │        │
머신 60..89 │ ● ● ●  │ ▓▓▓▓▓  │        │   ③ 짧은 줄 C
            │        │   ◄    │        │
                        ↑         ↑
                 d2 가 통째로   d3 는 못 셋에
                 먹혔다        찍혀 있다
            → 관통 줄 D(머신 0..89 연속 필요)가 **갈 곳이 없다**
```

**실측(`electronic-circuit`)이 정확히 이 모양이었다** — `copper-cable` 토막 4개가 `d2` 를
`[0,87] [90,177] [180,267] [270,297]` 로 먹고 `d3` 의 행 `0·90·180·270` 에 못을 박았다.
`stone-tablet`(머신 90대 관통)이 나중에 와서 `d2` 는 통째로 막히고 `d3` 는 행 **90·180**
두 칸에 막혔다 — **268행짜리 레인이 두 칸 때문에 못 쓰였다.**

### 늦게 오면 **비싸진다** — 대가가 셋이다

```
① 깊은 레인 = 긴 팔 = 처리량 ↓   (실측: reach-1 10/s → reach-2 3.6/s)
                    → 같은 양을 나르려면 **팔이 더 많이** 필요
                    → **좌석을 더 먹는다** (좌석은 유일하게 못 늘리는 자원)
② 못이 는다        — 얕은 레인 줄의 포트가 깊은 레인의 못이다. 줄이 조각날수록 못이 는다
③ 넘침 → gap      — 모듈이 **세로로 벌어진다**(gapRowsFromPlans)
```

**그래서 순서가 공짜가 아니다.** 늦게 오는 것은 그냥 "나중"이 아니라 **더 비싼 자리**다.

## §2 그래서 무엇을 얻나 — 순서를 정하는 이유

**자유도가 낮은 줄을 먼저 앉히면 못이 애초에 안 생긴다.**

| 줄의 성질 | 자유도 | 늦게 오면 |
|---|---|---|
| **관통**(머신 전부, 연속 구간 필요) | **가장 낮다** — 조각난 레인에 **못 앉는다** | 갈 곳이 없다 → 사다리 → 되먹임 |
| **구간**(머신 몇 대) | 높다 — 조각 **사이**에 앉을 수 있다 | 대개 앉는다 |
| **팔이 많은 줄** | 낮다 — 좌석을 많이 먹는다 | 깊은 레인 → 팔이 더 늘어남(악순환) |

이건 짐싸기의 오래된 규칙(**큰 것부터**)과 같다. 그리고 **결정 1(되먹임 제거)의 실질적
경로**다 — 못이 없으면 사다리가 필요 없고, 사다리가 없으면 되먹임 ②가 없다.

# 조사 · ⑤ 모듈 단위 tap/direct 모드 (2026-08-30)

## `supply.mode` 는 무엇인가

`insertingPlanner` 가 모듈 하나마다 내는 **한 값**이다:

```ts
type InsertingDecisionResult =
  | { mode: "tap";    plan: { ok: true; lines: PlannedLine[] } }
  | { mode: "direct"; reason: string }
```

## 언제 `direct` 가 되나 — **넷, 그리고 전부 "하나라도 안 되면"**

```
① complex: fluid-handled-by-generateModule   유체 줄이 있는데 fluidTrunk 가 없다
② complex: no-inserter                        팔을 모른다
③ complex: seats-exceed-capacity (역할:품목)   **줄 하나**가 두 면 어디에도 못 앉았다
④ belt: demand>beltCap (품목)                  **줄 하나**의 수요가 벨트 한 줄을 넘는다
```

**③과 ④는 실패한 줄의 이름을 사유에 싣는다** — 즉 **어느 줄이 문제인지 알면서도** 모듈 전체를
떨어뜨린다.

```ts
// ③ — 첫 실패 하나가 overflow 에 남고
overflow ??= `${line.role}:${line.name}`;
if (overflow) return { ok: false, complex: true, reason: `seats-exceed-capacity (${overflow})` };

// ④ — 첫 실패에서 즉시 반환
if (rate > capacity.beltCapacity) return direct(`belt: demand>beltCap (${planned.line.name})`);
```

> **한 줄이 안 되면 그 모듈의 모든 줄이 다이렉트가 된다.** 그것이 ⑤가 말하는 문제다.

## 그런데 — **기하를 바꾸는 소비처가 하나뿐이다**

`supply.mode` 를 읽는 곳을 전수했다:

| 읽는 곳 | 무엇에 쓰나 | |
|---|---|---|
| `module/policy/port.ts` `perMachine: supply.mode !== "tap"` | **`g` 를 `1` 로 할지 `N` 으로 할지** | ← **유일한 기하 소비처** |
| `module/build.ts` (`:303 → :336 · :407`) | `GeneratedModule.supply` 로 **그대로 내보낸다** | 진단 |
| `run/build/module.ts` | `unrouted-lines` 이슈 문장의 사유 | 진단 |
| `module/shape/transform.ts` (`:168 · :285`) | 모듈을 옮길 때 필드 보존 | 통과 |

**즉 모드가 기하에 남기는 것은 `perMachine` 하나뿐이다.** 코드 주석도 그렇게 적었다:

> *"모드가 남기는 것은 **쪼개기 여부** 하나뿐이다: 탭이면 묶은 그룹(벨트 하나가 전 머신),
> 다이렉트면 머신마다 하나. 그 둘은 `g = N` 과 `g = 1` 이라는 **같은 축의 두 끝**이다."*

## `perMachine` 이 실제로 하는 일 — **붓기의 낟알**

```ts
const batches: number[][] = opts?.perMachine
  ? Array.from({ length: n }, (_, i) => [i])       // 머신마다 따로 붓는다 → g = 1
  : [Array.from({ length: n }, (_, i) => i)];      // 한꺼번에 붓는다     → g = 상한
for (const batch of batches) made.push(...pour(batch));
```

**`g` 를 정하는 것이 아니라 "몇 명씩 묶어서 붓느냐"를 정한다.** 그리고 붓기(`createLinks`)는
받은 묶음 안에서 **언제나 최대로** 채운다. 그래서:

```
batch = [전 머신]        →  createLinks 가 벨트·좌석 상한까지 채운다  →  g = min(k, N)
batch = [0],[1],…,[n-1]  →  머신마다 따로라 섞일 수가 없다            →  g = 1
```

**`1 < g < N` 을 내려면 `batches` 를 `g` 명씩 끊으면 된다.** 지금은 그 두 극단만 만든다.

## 그래서 ⑤의 실제 크기

```
바꿀 것   ① insertingPlanner 가 **모듈 판정**을 그만두고 **줄마다** 판정한다
          ② planModulePorts 가 `perMachine`(모듈 하나의 불리언) 대신
             **줄마다의 낟알**을 넘긴다
          ③ externalLineGroups 의 `batches` 가 그 낟알을 받는다

안 바뀔 것 방출기 · 배정기 · 좌석표 — **아이템 줄은 이미 갈래가 하나다**
           (`clusterModule` *"아이템 줄 방출 — 갈래가 없다"*)
```

**그리고 ③이 곧 ③(부분 트렁크)이다** — `batches` 가 낟알을 받게 되면 `g` 명씩 끊는 것이
같은 자리에서 된다. ⑤와 ③은 **같은 함수의 앞뒤**다.

## 걸림돌 — 하나 있다

`insertingPlanner` 의 `tap` 산출은 **`PlannedLine[]` 한 벌**이고, 그것이 트렁크 기하
(`buildTrunkContext` · `emitTrunkPipe`)의 입력이다. 줄마다 모드를 갈면 **한 모듈 안에
탭 줄과 다이렉트 줄이 섞이고**, `plan.rest.lines` 가 그 둘을 함께 담아야 한다.

```
지금   supply.mode === "tap"  →  plan.rest.lines = 탭 줄 전부
                                 아니면          →  rest.lines = []  (전부 링크 경로로)
바꾼 뒤 rest.lines 에 **탭인 줄만** 담기고, 나머지는 링크 경로로 간다
```

**이것이 ⑤의 진짜 일이다.** 나머지(②③)는 인자를 넓히는 것이다.

> 유체 줄은 영향이 없다 — 언제나 `pipePlanned` 로 따로 가고 인서터를 안 쓴다.

## 정정 — **걸림돌은 없다. 이미 지나갔다** (2026-08-30)

앞 절에서 *"`rest.lines` 가 탭 줄과 다이렉트 줄을 함께 담아야 한다"* 고 적었다. **틀렸다.**
코드를 끝까지 읽으니 셋이 드러났다.

### ① `emitTapInserting` 은 **함수로 존재하지 않는다**

`rg emitTapInserting src` 의 결과가 **전부 주석**이다. 아이템 줄을 놓는 코드는
`emitOutputLinks`/`emitInputLinks` 하나뿐이다. `module/emit.ts:545` 의
*"아이템은 [emitTapInserting] 이 처리한다"* 는 **낡은 주석**이다.

### ② `rest.lines` 는 **언제나 빈 배열**이다

```ts
// module/policy/port.ts — 반환문
rest: fluidUnplaceable
  ? { ok: false, unplaced: [...] }
  : { ok: true, lines: [] }          // ← 아이템 PlannedLine 이 **하나도 안 들어간다**
```

주석도 그렇게 적혀 있다: *"**아이템 [ClusterBelt] 가 하나도 없다** — 줄들은 전부
`restLinks` 가 들고 있고, 못 앉은 그룹의 실패는 링크와 똑같이 자기 방출에서 갈린다."*

### ③ 그러면 `PlannedLine[]` 은 지금 무엇인가

```
PlannedLine  = "이 줄을 어느 면 · 어느 깊이 · 어느 reach 로 먹이나" 한 줄짜리 배정 기록
               (line · side · clusterBeltDepth · reach · beltEntityName · requiredInserterCount)

지금 실제로 담기는 것   **유체 줄뿐**이다 (`pipePlanned`)
쓰이는 곳               clusterModule 이 `[...rest.lines, ...pipePlanned]` 로 합쳐
                        `buildTrunkContext` 에 넣는다
```

**「트렁크 기하」란 그 `TrunkContext` 다** — 파이프가 어디에 눕고 어디서 지하로 뛰나:

```
beltMaxOn(면)   그 면에서 벨트가 먹은 **가장 깊은 칸**
                = max( plan.lines 의 깊이,  linkFaceDepths[면] )
                        ^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^
                        오늘은 유체뿐        **링크 배정이 답한다**
pipeJumpMode(면) 파이프가 좌석 줄을 비우고 밖으로 점프해야 하나
maxDepthAtEnd    끝에서 파이프끼리 어긋나게 두는 stagger 기준
```

즉 **`ClusterPipe` 를 어디에 둘지 정하는 계산**이고, 아이템 배정은 이미 `linkFaceDepths`
라는 **다른 통로**로 거기 들어간다.

## 그래서 ⑤의 크기가 다시 줄어든다

```
안 건드린다   방출기 · 트렁크 기하 · rest.lines   — 아이템은 이미 전부 링크 경로다
건드린다      insertingPlanner 가 모듈 판정 대신 **줄마다** 판정하고,
              그 판정이 `externalLineGroups` 의 **낟알**로 간다
```

**남는 물음은 하나다: `insertingPlanner` 가 지금 무엇을 위해 도는가.**
아이템 `PlannedLine` 을 아무도 안 쓰는데(②), 그 함수의 산출은 `supply.mode` 라는
**불리언 하나**로 좁혀져 `perMachine` 에 들어간다. 그렇다면 ⑤는 *"판정을 줄마다로 바꾼다"*
가 아니라 **"이 판정이 아직 필요한가"** 부터 물어야 한다.

```
직접 확인할 것
· insertingPlanner 의 산출 중 `mode` 말고 실제로 읽히는 필드가 있나
· `direct` 사유 넷(①유체 ②무인서터 ③좌석초과 ④벨트초과)을
  **줄마다** 물으면 각각 무엇이 되나 — 그게 곧 낟알이다
· ③·④는 이미 배정(tryLinkFace)과 붓기(createLinks)가 각자 보는 것과 겹치나
```

## 확인 — 셋 다 사실이다 (2026-08-30)

### 확인 1 — `insertingPlanner` 의 산출 중 **`mode` 말고는 아무도 안 읽는다**

```
rg "\.plan\.lines|supply\.plan|mode === \"tap\"" src   →  **주석 하나뿐**
```

그 함수는 아이템 줄 전부를 훑어 `PlannedLine[]`(면·깊이·reach·팔 개수)을 만드는데,
`planModulePorts` 가 그것을 **버린다**(`rest: { ok: true, lines: [] }`).
살아남는 것은 `mode`(사실상 불리언)와 `reason`(진단 문자열)뿐이다.

### 확인 2 — ③(좌석 초과)은 `tryLinkFace` 가 **이미 보는 사실**이다

```
planClusterPorts   seatRowsOf(면) = 면 칸 − 유체 행 − seatRowsUsed[면]     ← **면**마다 센다
tryLinkFace        seatsTaken(표, 머신) + k > faceSeatArms(machine.h, 유체행) ← **머신**마다 센다
```

**같은 사실을 두 곳이 다른 낟알로 센다.** 이 비대칭은 이미 문서에 적혀 있다
(`docs/auto-layout/module/module-planning.md` §5 — *남는 비대칭*). 다른 점은 **결과**다:

```
tryLinkFace 가 못 앉히면   그 줄만 미배정 → 이름표(seat-budget)
planClusterPorts 가 못 앉히면  **모듈 전체가 direct** → 그 모듈의 모든 줄이 g=1
```

### 확인 3 — ④(벨트 초과)는 `createLinks` 가 **다르게 답하는** 같은 사실이다

```ts
// insertingPlanner — 거절한다
if (rate > capacity.beltCapacity) return direct(`belt: demand>beltCap (${line.name})`);

// createLinks — 줄을 늘린다
if (room <= POUR_EPS) { cur = openLine(); continue; }   // 벨트가 차면 새 줄
```

**하나는 "수요가 벨트를 넘으니 포기"** 라 하고 **하나는 "그러니 줄을 늘린다"** 고 한다.
같은 물음에 두 답이다(R3). *(다만 ④는 `beltLineMap` 에 티어가 없는 줄에만 걸린다 —
`determineBeltCount` 가 줄 수를 못 정한 경우다.)*

# ⑤ 란 정확히 무엇인가 — 길게

## 지금 있는 것

`insertingPlanner` 라는 함수가 **모듈 하나마다 한 번** 돌아, 그 모듈의 아이템 줄을 전부 훑고
**낱말 하나**를 낸다:

```
"tap"     이 모듈의 줄들은 **벨트 하나를 여러 머신이 나눠 집는** 방식으로 먹인다
"direct"  **머신마다 자기 벨트**를 갖는 방식으로 먹인다
```

그 낱말이 딱 한 곳으로 간다:

```ts
externalLineGroups(..., { perMachine: supply.mode !== "tap", ... })
```

그리고 거기서 **붓기의 낟알**이 된다:

```ts
const batches = opts?.perMachine
  ? Array.from({ length: n }, (_, i) => [i])     // 머신마다 따로 붓는다  → g = 1
  : [Array.from({ length: n }, (_, i) => i)];    // 한꺼번에 붓는다      → g = min(k, N)
```

## 그래서 ⑤ 는 무엇을 없애자는 것인가

> **"이 모듈은 탭이다/다이렉트다" 라는 모듈 단위의 낱말을 없애고,
> 「몇 명씩 묶어 부을까」를 **줄마다** 정하게 한다.**

## 왜 없애야 하나 — 넷

```
① 낟알이 모듈이다
   한 줄이 안 되면 **그 모듈의 모든 줄**이 g=1 로 떨어진다.
   그 한 줄의 이름을 사유에 싣고 있으면서도 그렇게 한다
   (`seats-exceed-capacity (입력:구리선)` · `belt: demand>beltCap (철판)`)

② 두 극단뿐이다
   g = min(k, N) 아니면 g = 1.  **1 < g < N 이 없다**
   그래서 "조금만 작게 묶으면 앉을 줄" 이 통째로 다이렉트가 된다

③ 판정이 중복이다
   좌석(③)은 tryLinkFace 가, 벨트(④)는 createLinks 가 이미 본다.
   같은 사실을 두 곳이 세고(R3), 그중 **거친 쪽이 먼저 이긴다**

④ 산출이 버려진다
   PlannedLine[] 을 아무도 안 읽는다.  훑는 일은 하고 결과는 안 쓴다
```

## 없애면 무엇이 남나

```
남는다   유체 줄의 PlannedLine (pipePlanned) — 트렁크 기하(ClusterPipe 자리)의 입력
         `direct` 사유 ①(유체) ②(무인서터) — 이건 줄이 아니라 **모듈**의 문제라 모듈 판정이 맞다
사라진다 아이템 줄의 모듈 판정과 그 산출
바뀐다   `perMachine: 불리언`  →  **줄마다의 낟알**
```

## 그리고 ③(부분 트렁크)이 곧바로 따라온다

낟알이 줄마다가 되면 `batches` 를 **`g` 명씩** 끊는 것이 같은 자리에서 된다:

```ts
// 지금 — 두 극단
batches = perMachine ? [[0],[1],…] : [[0..n-1]]

// 부분 트렁크 — 같은 줄 하나
batches = chunk([0..n-1], g)      // g = 1 이면 다이렉트, g = n 이면 관통, 그 사이가 부분
```

**⑤와 ③은 같은 함수의 앞뒤다** — ⑤가 `g` 를 줄마다 정할 자리를 만들고, ③이 그 자리에
`min(k, N)` 과 `1` 사이의 값을 넣는다.

# 여러 형태가 한 면에 어떻게 공존하나 (2026-08-30)

## 먼저 — **이미 공존하고 있다**

부모 모듈의 `E` 면에는 **자식 여럿의 간선 그룹이 전부** 앉는다(`seatLinkEdge` 가 부모 무대의
같은 표를 쓴다). 그리고 간선마다 `g` 가 이미 다르다:

```
간선 A (구리선)   per 가 작다 → 한 벨트가 많이 맡는다 → g 크다
간선 B (철판)     per 가 크다 → 한 벨트가 조금 맡는다 → g 작다
```

`createLinks` 가 간선마다 그 간선의 벨트·좌석 상한까지 채우므로 **`g` 는 이미 줄마다 다르다.**
⑤가 새로 만드는 것은 *"형태가 섞이는 상황"* 이 아니라, **나머지 줄(원료·완제품)도 그 대열에
들어오는 것**이다.

## 충돌을 막는 기전 — **좌석표 하나, 청구 세 종류**

형태가 무엇이든 배정이 청구하는 것은 **똑같이 셋**이다:

```
좌석(d1)    claimSeats(표, 머신, 칸번호[])      두 줄이 같은 칸을 못 갖는다
벨트 구간   claimDepth(표, 깊이, lo, hi)          겹치면 depthClear 가 거절한다
포트 칸     claimDepth(표, 깊이', 행, 행) × 2     인서터 + 상자
```

**형태는 "무엇을 청구하나"를 안 바꾸고 "얼마나 청구하나"만 바꾼다.** 그래서 다이렉트·부분·
관통이 섞여도 충돌 판정은 한 곳(`FaceTable`)이고, 하나다.

```
g = 1     좌석: 머신 하나에 k칸        구간: 그 머신의 행만        포트: 옆
1<g<N     좌석: g대에 걸쳐             구간: 그 g대의 행 구간      포트: 옆
g = N     좌석: 전 머신                구간: 전 행                 포트: **기둥 끝**
```

**형태가 실제로 가르는 것은 `portEnd` 하나**이고, 그건 이미 `spansAllMachines` 가 판정한다.

## 그래서 새로 생기는 상호작용 — 넷, 전부 **이미 아는 것**

```
① 레인 공유와 못
   행 구간이 안 겹치면 같은 깊이를 나눠 쓴다. 부분 트렁크가 늘면 한 레인에 구간이 여럿
   앉고, 그 **옆 포트들이 다음 레인의 못**이 된다
   → 우리가 아는 그 문제다. `조사-쪼갬.md` 모드 2

② 순서
   확정된 규칙: **도피처가 없는 것 먼저**(관통 먼저). 부분 트렁크가 생기면 이진이 아니게
   되고, 그 원칙의 일반화는 **`g` 내림차순**이다 — `g` 가 클수록 자리를 찾기 어렵고
   gap 으로도 못 간다(`machinesOn !== 1`)
   → **이것은 폐기된 옛 TR2 가 아니다.** 옛것은 `c` 로 **깊이**를 정했고, 이것은 자유도로
     **순서**를 정한다. 깊이는 여전히 처리량이 정한다

③ 기둥 끝 경쟁
   기둥 끝은 면당 **둘**(N·S)뿐이다. 관통이 셋이면 셋째는 옆으로 물러나고 갇힐 위험이 있다.
   **부분 트렁크는 이 압박을 줄인다** — 관통이던 줄이 부분이 되면 기둥 끝을 안 쓴다

④ 경계 머신
   구간 경계에 걸친 머신은 두 그룹에 들어 좌석을 `+1` 먹는다.
   구간 `c` 개면 경계 `c−1` 개 → 좌석 최대 `+(c−1)`
```

## 열린 물음 하나 — **균등 분할로 충분한가**

`chunk([0..n-1], g)` 는 **균등**하다. 그런데 계획서 §14-2 는 이렇게 적었다:

> *"**균등은 못이 없을 때의 특수해다** — 못이 0개면 `c` 대로 앞에서부터 `g` 대씩 자른다."*

즉 못이 있으면 **불균등**하게(못을 피해) 잘라야 한다는 뜻이었고, 오늘의 쪼개기가 그것이다.

```
`g` 를 줄마다 제대로 고르면 못이 안 생기나?   →  그러면 균등으로 충분하다
아니면 불균등이 여전히 필요한가?              →  그러면 쪼개기가 살아남는다
```

**이것은 ③(부분 트렁크)을 만들어 봐야 갈린다** — 개념만으로는 못 가른다. `g` 를 줄마다
고르는 자리가 생긴 뒤에 *"못이 남는가"* 를 보는 것이 순서다.

# ⑤ 재판단 — **모듈 판정과 gap 판정은 다른 판정이다** (2026-08-30 정정)

## 내가 틀린 자리

판정을 지웠더니 테스트 13개가 떨어졌고, 나는 그것을 *"판정이 필요하다는 증거"* 로 읽었다.
**틀렸다.** 동작을 바꿨으니 **옛 동작을 잠그던 테스트가 떨어지는 것은 당연**하다.
테스트가 말한 것은 그게 아니라 이것이다:

> **gap 으로 가야 할 줄이 못 가게 됐다** — 즉 **탈출을 대신할 것이 아직 없다.**

*"그러니 판정을 남겨야 한다"* 가 아니라 *"탈출을 따로 만들어야 한다"* 가 결론이다.

## 물음은 셋이고, 서로 다른 것이 답한다

```
① 이 줄의 `g` 는 얼마인가        →  **처리량**이 답한다   g = min(⌊벨트÷per⌋, N)    ✅ 넣었다
② 이 줄이 gap 으로 가야 하나     →  **좌석**이 답한다     W/E 에 자리가 없나
③ gap 으로 가려면 무엇이 필요한가 →  오늘은 `g = 1`       (가로 벨트가 머신 하나만 맡는다)
```

**모듈 판정은 셋을 한꺼번에, 모듈 통째로, 미리 답한 것**이다. 그래서 거칠었다 —
한 줄의 사정으로 모든 줄의 `g` 가 1이 됐다.

그리고 ③의 *"`g = 1` 이라야 한다"* 는 **원리가 아니라 오늘 gap 능력의 그림자**다
(`machinesOn !== 1`). gap 이 여러 대를 먹이면 덜 낮춰도 된다.

## 그리고 모듈 판정에 남는 것은 — **없다**

`direct` 사유 넷을 다시 본다:

| 사유 | 실제 상태 |
|---|---|
| ① `fluid-handled-by-generateModule` | **죽은 가지다.** `planModulePorts` 가 넘기는 `restLines` 는 `kind !== "pipe"` 로 이미 걸러져 있어 `beltLines.length !== lines.length` 가 **참이 될 수 없다**. 유체 실패는 `fluidCannotPlace` 가 따로 잡는다 |
| ② `no-inserter` | **중복이다.** `externalLineGroups` 가 인서터를 모르면 빈 손으로 돌아오고 그 줄은 `unpourableLines` 로 간다 |
| ③ `seats-exceed-capacity` | **중복이다.** `tryLinkFace` 가 머신마다 본다 — 다만 결과가 다르다(그 줄만 vs 모듈 전체) |
| ④ `belt: demand>beltCap` | **중복이고 답이 다르다.** `createLinks` 는 같은 사실에 *"줄을 늘린다"* 고 답한다 |

**넷 중 하나는 죽었고 셋은 중복이다. 그러니 모듈 판정은 지워도 된다** — 다만 ②(gap 탈출)를
대신할 것을 함께 만들어야 한다.

> 사장님 말씀대로 **모듈이라는 낟알 자체가 여기서는 의미를 잃었다.** 모듈은 *논리적 경계*를
> 긋는 개념이었지, *줄의 형태*를 정하는 낟알이 아니다.

## 그래서 ⑤ 를 둘로 가른다

```
⑤-a  모듈 판정을 지운다
      사유 넷 중 하나는 죽었고 셋은 중복이다. 진단 문자열만 다른 데서 다시 만든다

⑤-b  **배정 중 `g` 낮추기** — 탈출을 그 자리에서 만든다
      W/E 에서 못 앉으면 그 줄의 `g` 를 낮춰 다시 시도하고, `1` 까지 내려가면 gap 으로 간다
      → 링크의 쪼개기와 **같은 기전**이다. 둘을 하나로 만들 수 있다(옛 D2)
```

**⑤-b 가 핵심이다.** 지금의 `bundle: mode !== "tap" ? 1 : undefined` 는 **자리를 지키는
임시값**이지 답이 아니다 — 판정이 미리 최대로 낮춰 두는 방식 그대로다.

## 남는 물음

```
· ⑤-b 를 어디에 두나
  `externalLineGroups` 는 배정 **앞**에서 한 번 붓는다. 낮추려면 배정이 그 결과를 되돌려야
  하는데 그건 되먹임이다. 링크는 `seatLinkEdge` 안에서 **제자리 수선**으로 푼다 —
  나머지 줄도 같은 자리로 옮겨야 하나?

· `g` 를 얼마나 낮추나
  1 까지 한 번에? 아니면 한 단계씩? 한 단계씩이면 시도 횟수가 는다
```

# ⑤ 착수 기록 — **네 번 시도하고 되돌렸다** (2026-08-30)

전부 `③′ 나머지 줄` 블록만 고쳤다. 타입은 매번 0, 되돌린 뒤 기준선 복귀 확인.

| # | 무엇을 했나 | 새로 깨짐 | **그것이 드러낸 것** |
|---|---|---|---|
| 1 | 판정을 지우고 `g` 를 유도로만 | **13** | `g > 1` 은 gap 으로 못 간다(`machinesOn !== 1`) — **탈출을 대신할 것이 없다** |
| 2 | 실패 시 **마지막 시도**(`g=1`)의 그룹을 넘김에 넘긴다 | **22** | 반대 면에 앉을 수 있는 **큰 묶음을 공연히 부순다** |
| 3 | 줄 단위 원자성 + 두 바퀴(유도 → 1), 각 바퀴가 선호-전체 → 넘침-전체 | **4** | **가장 가까웠다.** 남은 넷은 전부 유체 면 픽스처 |
| 4 | 그룹 단위 배치 + 남은 머신만 재붓기 | **14** | 부분 배치를 얻는 대신 **넘침 순서가 무너진다** |

## 그래서 배운 것 — 셋

```
① 탈출(`g` 낮추기)은 **넘침보다 나중**이어야 한다
   반대 면에 앉을 수 있으면 부수지 않는다.  시도 2가 그걸 어겼다

② 한 바퀴는 **선호-전체 → 넘침-전체**여야 한다
   줄마다 독립으로 (선호→넘침) 하면 먼저 온 줄이 넘침 면을 먼저 먹는다.  시도 4가 그랬다

③ 줄 단위 원자성과 부분 배치는 **맞바꿈이다**
   원자성 → 재붓기가 안전하지만 부분 배치를 잃는다(시도 3)
   부분 배치 → 남은 머신만 다시 부어야 하고 그러면 넘침 순서가 흔들린다(시도 4)
```

## 남은 넷(시도 3)의 정체 — **`g` 유도가 팔을 안 본다**

넷 다 유체 면 픽스처이고, 그 픽스처들은 **`throughput: 0` 인 인서터**로 *"레인이 모자란
상황"* 을 만든다. 그런데 유도식은

```
g = min(⌊벨트 처리량 ÷ per⌋, N)      ← **벨트만 본다**
```

라 **팔이 없다는 사실을 못 본다.** 벨트는 넉넉하니 `g = N` 을 내고, 좌석에서 떨어지고,
그다음 바퀴(`g = 1`)로 내려간다. 옛 판정은 그 결핍을 **미리** 보고 `g = 1` 로 시작했다.

> **그래서 ⑤의 진짜 남은 조각은 이것이다:**
> *"`g` 유도가 **좌석(팔)** 도 봐야 하나, 아니면 못 앉으면 낮추는 것으로 충분한가."*
>
> 시도 3의 넷은 **낮추기가 늦어서** 나는 실패이지 낮추기가 틀려서가 아니다.
> 유도에 좌석을 넣으면(`g ≤ ⌊좌석 예산 ÷ 팔⌋`) 첫 바퀴부터 맞는 값이 나온다.

## 되돌린 이유

**테스트 수를 보고 고치는 것은 이 저장소가 금지한 방법이다**(`machine-link.md` — *무엇을 재나*).
네 번의 수치는 *"겨냥한 문제가 풀렸나"* 를 말해 주지 않는다. 다음 착수는 위 ③의 맞바꿈을
**먼저 정하고** 시작한다.
