# 자리 배정 — **어느 면·어느 깊이에 앉나**

> 상태·읽을 것·범위는 같은 폴더의 `CLAUDE.md`.
> 모델은 여기 없다 — `docs/auto-layout/module/` 의 `face-occupancy` · `trunk-blocked`.

## §0 푸는 문제

> 줄이 앉을 **면과 깊이**를 지금은 **도착 순으로 앉혀 보며** 정한다.
> 그 순서에 근거가 없고(도착 순), 못 앉았을 때 **왜** 못 앉았는지가 한 칸(`포트막힘`)에서
> 멈춘다. **순서에 근거를 주고, 그 칸을 열자.**

### 안 푸는 것

```
`g`(한 줄이 몇 대)        `부분-트렁크` 가 끝냈다. `planBundles` 가 붓기 앞에서 정한다
링크(간선)의 `g`          `부분-링크` 의 몫
게임의 좌/우 두 레인       `벨트-레인` 의 몫
포트의 방향(N/S)          ㉮ — `행채널-모델` 이 먼저다
```

### 끝나면 열리는 문

```
· 실패가 **한 칸 더** 내려간다 — 오늘 화면에 뜨는 `포트막힘` 에 해소자가 생긴다
· 면 순서가 **실측이 아니라 기전**으로 선다 → 바꿔도 무섭지 않다
· `trunkPipe` 기존 실패 2건의 사유가 드러난다(W·E·S 가 왜 전부 거절했나)
```

## §1 지금 무엇이 일어나나

```
붓기        줄마다 `g` 가 정해져 그룹이 난다              ← 여기까지 계산이다
배정 ①      링크: seatLinkEdge → tryLinkFace
배정 ③      나머지 줄: allocateLinkFaces(선호 면) → spillLinkFacesToGap(넘침 순서)
   tryLinkFace  면이 주어지면 **깊이 후보를 정렬**해(팔 적은 순 → 얕은 순) 첫 성공을 쓴다
                실패하면 사유를 `DepthShortage` 로 쌓는다 — 그게 화면 처방의 유일한 출처다
```

**후보 루프는 되먹임이 아니다**(CLAUDE.md 의 확인된 사실). 그러니 이 계획은 그 루프를
없애는 일이 **아니다** — 루프가 **무엇을 보고 고르나**를 고치는 일이다.

## §2 어긋난 자리 셋

### (가) 줄의 처리 순서가 **도착 순**이다

```ts
// planModulePorts — 오늘
const outPlans = allocateLinkFaces(faceCtx, out, "from", "W");   // groups.forEach 순
```

옛 `간선-배정` Step 6 이 그 자리에 규칙을 넣으려 했고(**자유도가 낮은 줄을 먼저**),
근거가 `조사-순서.md` §1·§2 에 그대로 있다. 두 계획을 합칠 때 **할 일로 안 옮겨졌다.**

### (나) 면의 시도 순서가 **실측으로 굳었다**

```
② 처리 순서(자식-공급 먼저, 원료 나중)      2026-08-05 실측 — 납품 1건 실패
④ 면 순서(반대 면 → 노출 끝면 → gap)        2026-07-12 실측 — 반출 skip 3건
```

*"왜 그 순서여야 하는가"* 를 **코드로 재유도할 수 없다.** 실물을 돌려 실패를 본 기록만
있다. 그래서 안 건드렸고 — **이건 소극적인 이유이지 좋은 이유가 아니다.**

### (다) 사다리가 **1단뿐**이라 화면의 실패가 안 풀린다

```
1단 구간막힘  ✅ 있다(`resolveSpanBlock`) — 그런데 실물에서 **한 번도 안 걸린다**
2단 포트막힘  ❌ 없다 — **실물에서 실제로 뜨는 실패가 이것이다**
```

`조사-사다리-재점검.md`: 실측 13회 전부 `쪼갬 0`, ON/OFF 동일. 깊은 깊이가 쓰인 실행에서
나온 사유는 **전부 `포트막힘`** 이었다.

## §3 할 일 — **다음 한 단계만 확정한다**

### Step 1 — **포트막힘이 무엇을 막고 있나를 수로 낸다** (확정)

```
전제  `DepthShortage.blockedPort` 는 이미 `(행, 깊이)` 쌍을 담는다(`linkPlanner`).
      확인: `tryLinkFace` 의 `why?.push({ face, clusterBeltDepth, blockedPort: hitPort })`
불변  진단이 안 줄어든다 — `summarizeRungs` 가 읽는 이름표는 그대로 난다
      기전: 이 단계는 **읽기만** 한다. `why` 에 쓰는 자리를 안 건드린다
관문  *"막은 것이 누구의 포트인가"* 가 답해진다.  지금은 **막혔다는 사실만** 알고
      막은 주인이 관통인지 구간인지 `g` 가 얼마인지를 모른다 —
      그걸 알아야 2단의 처방(그 줄을 관통으로 밀까 · 깊이 방향 포트를 열까)이 갈린다
```

**왜 이것부터인가.** (다)가 화면에 실제로 뜨는 실패이고, (가)·(나)는 그 실패를 **줄이는**
일이지 없애는 일이 아니다. 그리고 (가)의 순서 규칙이 옳은지도 *"못이 실제로 어디서
생기나"* 를 알아야 잰다 — `조사-순서.md` 의 근거가 바로 그 가정 위에 서 있다.

### Step 2 — 순서 규칙 (방향)

Step 1 이 못의 주인을 알려 주면, *"자유도가 낮은 줄을 먼저"* 가 **실제로 못을 줄이나**를
잴 수 있다. 잰 뒤에 넣는다. → `조사-순서.md`

### Step 3 — 사다리 2단 (방향)

후보는 둘이고 **둘 다 `g` 와 얽힌다** — 그 줄을 관통으로 밀어 포트를 기둥 끝으로 보내거나
(그러면 `부분-링크`·레인 예산과 만난다), 깊이 방향 포트(TR6)를 연다.
