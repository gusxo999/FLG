# 제1부 — 현재 상태 (격리 완료분)

수동 편집 코드 약 2,000줄을 `manualEdit/` 으로 모으고 **호출자를 0 으로** 만들었다.
타입검사·테스트 대상에서 제외해 앞으로의 리팩토링이 이 코드에 발이 묶이지 않게 했다.

## 1.3 남긴 것 — 배치 파이프라인이 쓰는 부분

같은 파일에 있었지만 **격리하면 안 되는** 것들이다.

| 심볼 | 남은 파일 | 쓰는 곳 |

> **함정이었던 것:** `unifyAreas` 는 파일 이름 때문에 드래그 기능처럼 보이지만 **배치 결과를
> 화면 좌표로 평탄화하는 표시 경로**다. 파일째 옮겼으면 배치 결과 표시가 깨졌다.

## 1.4 store 처리 — 두 액션이 다르게 갈렸다

| 액션 | 처리 | 이유 |
|---|---|---|
| `moveAssemblerGroup` | **본체 전부**(534–803, 270줄) 이관. store 에는 `() => false` 스텁 | 536행이 `if (!routingEditSession) return false;` — **전체가 세션 종속** |
| `moveEntityById` | **재라우팅 분기만**(921–1091, 171줄) 이관 | 세션과 무관한 **단순 이동 경로**가 있어 그건 살아 있어야 한다 |

### 왜 "동작하는 함수"로 안 뺐나 (결정 10)

추출 경계를 실측하니 `moveEntityById` 의 분기가 **바깥 지역변수 15개 이상**
(`grid`·`workGrid`·`newCells`·`viewport`·`shiftExtra`·`set`·`pushHistory` …)을 참조했다.
동작하는 함수로 빼려면 **원본에 없던 15필드 인자 객체**를 만들어야 한다.

그런데 이 코드는 타입검사 제외 대상이라 **그 인자 객체가 맞는지 검증할 방법이 없다.**
그리고 재구현 때 읽을 것은 *"원본이 무엇을 했나"* 이지 우리가 만든 껍데기가 아니다.

> **결론: 원본 보존이 목적에 더 맞는다.** 결과물(store 875줄)은 어느 쪽이든 같고,
> **위험과 참고 가치가 다르다.**

이 파일만 **생성과 제외가 같은 단계**이고, 나머지 넷은 규칙대로 검증 후 제외했다.

# 제2부 — 재구현 계획

> 지금 코드를 되살리는 것이 아니라 **새로 짜는** 것을 전제한다.
> *"구현을 다시 하게 되면 논리적으로 상당히 달라질 것. 어떤 기능이 존재하고 왜 필요한지
> 의도만 파악하면 충분하다."* (사용자, 2026-08-02)

## 2.1 왜 새로 짜야 하나 — 전제가 통째로 바뀌었다

| 격리된 코드의 전제 | 지금의 배치 파이프라인 |
|---|---|
| 파사드가 *"포트 페어 → 완성된 라우팅"* 을 돌려준다 | **예약** — 자리를 먼저 잡고 **탐색 없이** 방출 |
| 실패하면 **다른 포트 조합을 탐색**(enumeration 폴백) | 실패는 우회할 일이 아니라 **예약 불변식이 깨졌다는 신호** |
| `Area`(internal/external)를 직접 mutate | `ModulePortPlan` → 좌표 입히기 → 방출의 **3계층** |
| 드래그가 **Dijkstra 로 벨트를 다시 찾는다** | 채널·lane 이 **미리 예약**돼 있다 |

**핵심 질문이 바뀐다:**

```
옛 코드:  "어디로든 길을 찾아라"
새 구조:  "예약된 자리 안에서 옮길 수 있나"
```

## 2.2 가장 큰 미해결 질문 — 드래그는 **예약을 깨는 행위**다

사용자가 상자를 옮기면 그 상자에 배정됐던 **lane·트랙이 무효**가 된다.

옛 코드는 *"그 자리에서 길을 다시 찾는"* 방식이었다. 새 구조에서는 그게 성립하지 않는다 —
길은 **미리 예약된 것**이고, 예약은 **전역 배정의 결과**이기 때문이다.

> **유력한 답: 부분 재실행(re-plan).**
> 드래그를 "경로 재탐색"이 아니라 **"planner 입력을 바꿔 다시 배정"** 으로 본다.
> 이건 옛 코드에 없던 개념이라, 재구현이 아니라 **새 설계**에 가깝다.

풀어야 할 하위 질문:

1. **범위** — 상자 하나를 옮기면 어디까지 다시 배정하나? 그 모듈만? 그 채널만? 전체?
2. **안정성** — 재배정이 **관련 없는 부분을 흔들면** 사용자가 놀란다. 배정이 결정적이라
   입력이 조금 바뀌면 출력도 조금만 바뀌어야 한다(연속성).
3. **거절** — 옮길 수 없는 자리면 어떻게 알리나. 지금 예약 철학은 *"실패는 skip 하고 사유를
   남긴다"* 인데, 사용자 조작에는 **즉각적인 거절 피드백**이 필요하다.

## 2.3 자료구조가 바뀌어도 **유효한 요구사항**

격리 코드에서 건져낸 것 중, 구현이 달라져도 지켜야 하는 것들이다.
(전체 목록과 상세는 **`manualEdit/README.md`**)

| 요구사항 | 왜 여전히 유효한가 |
|---|---|
| **rollback 프로토콜** | 실패한 드래그가 배치를 오염시키면 안 된다 — 구현 무관 불변 |
| **간격 0 스냅** | 기계에 딱 붙이면 인서터 자리가 없다 — **게임 규칙**이라 안 바뀐다 |
| **단일 외곽선 불변식** | 벨트가 레이아웃 밖으로 새면 안 된다 — 반출 설계와 같은 원칙 |
| **유체 역할 보존** | 재료 칸과 결과물 칸이 다르다 — prototype 이 정한다 |
| **합류 가드** | 옛 코드의 **결함**([known-limits §9](../docs/auto-layout/common/known-limits.md)). 재구현 시 **반드시 넣어야 한다** |

## 2.4 버려도 되는 것

전부 *"탐색으로 길을 찾는다"* 는 전제 위에 있어, 예약 구조에서는 의미가 없다.

- 포트 페어 **enumeration 폴백** (`routeWithFallback` 의 manhattan 정렬 재시도)
- **꺾임 penalty** 튜닝 (`DRAG_BELT_TURN_PENALTY = 2`)
- **`pickBest`** 최소 셀 경로 선택

## 2.5 착수 조건

재구현은 **Phase 6 이후**에 검토한다. 그전에 다음이 끝나야 판단할 재료가 생긴다.

| # | 선행 | 왜 필요한가 | 상태 |
|---|---|---|---|
| 1 | **Phase 3·4** | 배치 파이프라인의 계층이 확정돼야 *"드래그가 어느 계층을 건드리는가"* 가 정해진다 | ✅ 완료 — 계획 진입점은 `planner/module/planModulePorts` 하나다 |
| 2 | **Phase 6** | `modulePacking` 재검토가 끝나야 **예약 장부의 최종 모양**이 나온다 | ⬜ 남음 |
| 3 | 위 둘 이후 | 그제야 *"예약을 사용자 입력으로 갱신할 수 있나"* 라는 진짜 설계 질문에 답할 수 있다 | ⬜ |

## 2.6 재구현하지 않는 선택지도 열려 있다

배치가 충분히 좋아지면 **수동 편집 자체가 불필요할 수 있다.** 옛 드래그 기능의 상당 부분은
*"자동 배치가 만족스럽지 않아서"* 존재했다.

재구현 착수 전에 먼저 물어야 할 것: **지금도 손으로 고쳐야 할 만큼 배치가 나쁜가?**
아니라면 이 폴더는 그대로 두고, `known-limits` 개선에 그 시간을 쓰는 편이 낫다.
