# 포트 자리 — 되먹임 · 짝 · 순서

> 상태·읽을 것·범위는 같은 폴더의 `CLAUDE.md`.

## 왜 셋으로 갈렸나 — **되먹임이 주(主)이고, 2·3 이 그 제거 경로다** (2026-08-29 재구성)

`1-되먹임` 이 파이프라인 전체를 전수한 결과, 되먹임은 **정확히 둘**이고 **둘 다
`generateModule` 로 닫힌다.** 그리고 **각 고리를 깨는 길이 정확히 하나씩** 있다:

```
     A  gen ─→ extent ─→ tidy-tree ─→ lineEnds ─→ gen      (2026-07-11~ · b9deaf4)
        └ 깨는 길: 끝 방향을 gen **앞**에서 안다              ⇒ **2-짝**

     B  gen ─→ laneShortages ─→ 사다리 ─→ linkCache ─→ gen   (2026-08-26~ · 46648dd)
        └ 깨는 길: 못을 애초에 안 만든다                       ⇒ **3-순서**
```

**그래서 2·3 은 "포트를 더 잘 놓는 개선"이 아니라 `되먹임 제거`의 두 절반이다.** 짝을 보게
되는 것과 순서가 생기는 것은 그 과정에서 **함께 오는 이득**이다.

`1-되먹임` 자체는 **코드를 안 고친다** — 조사 결과와 제거 지도를 남기고, 2·3 이 끝난 뒤
다시 세어 **0** 인지 확인하는 것이 그 몫이다.

배경은 `docs/auto-layout/module/module-planning.md` **§4.6 — 포트 위치를 정하는 것 전부**
(다섯 수 · 누가 쓰나 · 파생과 되먹임 · 어긋남 둘).

## 목표 상태 — **변경 후 파이프라인** (2026-08-29 사장님 제안에서)

계획을 *"무엇을 고친다"* 가 아니라 **"파이프라인이 어떤 모양이어야 하나"** 에서 유도한다.
아래가 그 모양이고, 각 계획은 **지금과의 차이**를 메운다.

```
지금                                          목표
────────────────────────────────────────────────────────────────────
P0   linkCache 조립                           P0   linkCache 조립
                                                    └ **끝(Link.end) 을 여기서 채운다**  (2-짝)
P1   gen ×N   ← 높이 재려고
P1b  사다리 — linkCache 를 **사후 변형**       P0b  **배정만** 돌린다(방출 없음)
P1′  gen ×N   ← 쪼갠 것으로 다시                     └ 못이 있으면 여기서 쪼갠다  (3-순서 뒤엔 안 돈다)
P2   tidy-tree                                P1   **gen ×N — 한 번**
P3   lineEnds ← tidy-tree                     P2   tidy-tree
P4   gen ×N   ← 끝 선호 반영                   ─    (P3·P4 없음)
P5   채널 · 짝짓기                             P5   채널 · 짝짓기
P6   좌표                                     P6   좌표
P7   납품 경로                                 P7   납품 경로

gen 3회 · 되먹임 2                             gen **1회** · 되먹임 **0**
```

### 왜 이 모양인가 — 세 판단

**① 높이 재기는 `P1` 의 *이유*가 아니다.** `P1` 은 *"모듈을 만든다"* 이고 높이는 부산물이다.
지금 그것이 **따로 한 번 더 도는 이유**는 `P1` **뒤에서 `P1` 의 입력이 바뀌기 때문**이다
(사다리가 링크를, `lineEnds` 가 끝 선호를). **입력을 앞으로 옮기면 `P1` 은 저절로 한 번이
되고, "높이용 패스" 라는 것 자체가 사라진다.**

> 높이를 **계획만으로 유도**하는 길(방출 없이 extent 계산)도 있지만 **지금은 안 한다** —
> 유도가 방출과 어긋나면 조용히 틀리고, `gen` 1회를 얻는 데 필요하지도 않다.

**② 쪼개기는 링크 생성의 일이다.** 쪼개면 **포트가 늘고 = 흐름이 갈리고 = 링크가 더 태어난다.**
그러니 `linkCache` 를 **뒤에서 고치는** 지금 모양이 잘못이다. `P0` 근처가 제자리다.

**③ 그런데 옮기는 것만으로는 고리가 안 없어진다 — 싸질 뿐이다.**

```
지금    배정 → 사유 → 링크 수정 → **배정 + 방출** 재실행     (비싸다)
옮기면  배정 → 사유 → 링크 수정 → **배정만** 재실행           (싸다. 고리는 남는다)
```

**고리를 실제로 없애는 길은 하나뿐이다 — 쪼갤 일이 없게 만드는 것**(`3-순서`).
쪼갬을 배정 **안**으로 넣는 길은 막혀 있다: 자식 출력과 부모 입력이 **같은 `Link` 객체**를
봐야 하는데(`pairDeliveryPorts` 가 `linkId` 로 짝짓는다) 모듈 배정은 자기 모듈만 본다.
한쪽만 쪼개면 짝이 깨진다.

### 이 모양이 가능한 근거 — **계획은 이미 방출과 분리돼 있다**

```ts
// clusterModule.ts:260 — generateModule 의 첫 줄
const plan = planModulePorts(input, count);   // ← 좌표도 방출도 없다. 순수 함수
// 아래는 전부 방출이다
```

`planModulePorts` 는 `ModulePortPlannerInput`(= `toModuleInput` 의 부분집합)만 받으므로
**`P0` 에서 그대로 부를 수 있다.** 그게 `P0b`(배정만 돌린다)를 가능하게 하는 지렛대다.

### 단계별 도달 상태

| 끝난 것 | `gen` 횟수 | 되먹임 |
|---|---|---|
| (지금) | 3 | 2 |
| `2-짝` Step 1~3 | 3 | 2 — 링크 절반만 열렸다 |
| `2-짝` Step 4 | **2** | **1** (사다리만) |
| `3-순서` — 사다리를 끔 | **1** | **0** |
| (선택) 사다리를 `P0b` 로 옮김 | 1 | 0 — 켜도 방출을 다시 안 한다 |

> **마지막 줄이 중요하다.** `3-순서` 가 못을 0으로 못 만들 수도 있다. 그때 사다리를 켠 채로
> 되먹임을 0으로 두려면 **쪼갬이 방출을 다시 부르지 않아야** 하고, 그게 `P0b` 로 옮기는
> 이유다. **끄는 것과 옮기는 것은 다른 처방이고, 둘 다 필요할 수 있다.**

## 왜 이 순서인가

**① 은 이미 끝났다**(조사). 남은 것은 그 문서를 **기준선**으로 삼는 일이다 —
착수 전 고리 수 = **2**, 끝난 뒤 = **0** 이어야 한다.

②와 ③은 **서로 독립**이다. ②는 *"어느 끝으로 나가나"*(y 방향), ③은 *"누가 먼저 앉나"*
(레인·좌석)이라 건드리는 필드가 겹치지 않는다. **다만 ②가 더 싸다** — 깨야 할 고리가
`lineEnds` 하나뿐이고, `gen` 의 다른 입력은 전부 이미 `gen` 이전에 확정돼 있다.

## 세 계획이 공유하는 결정 (2026-08-29 사장님)

1. **되먹임은 개념적으로 존재해서는 안 된다.** 지금 있는 것은 고쳐야 할 것이지 설계가 아니다.
2. **짝의 생성 로직은 `Link` 의 자료구조에서 파생돼야 한다.** (판정은 `2-짝` §1 에)
3. **그룹 배정 순서는 정한 적이 없다.** 붓기의 부산물이 흘러 들어온 것이므로 **정하면 된다.**

## 완료 판정

셋을 다 끝내면 이렇게 되어야 한다:

```
모듈 생성 1회         ← 되먹임이 없으므로
배정이 짝을 안다      ← 끝이 Link 의 필드
배정 순서가 규칙이다  ← 붓기 순서가 아니라
```

**중간 상태도 정직하게 산다.** 하나만 끝내도 나머지는 오늘 동작 그대로다 —
각 계획의 *불변*이 그것을 단언한다.
