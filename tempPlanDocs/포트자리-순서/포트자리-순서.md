# 포트 자리 — 되먹임 · 짝 · 순서

> 상태·읽을 것·범위는 같은 폴더의 `CLAUDE.md`.

## 왜 셋으로 갈렸나

`module-planning.md` §4.6 이 포트 자리를 정하는 것을 전수했고, **문제가 셋으로 갈렸다.**

```
                    포트 자리를 정하는 흐름
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   ① 되먹임              ② 짝                  ③ 순서
   앞을 다시 돈다        끝을 짝 없이 고른다     붓기 순서가 배정 순서
   (생성이 3회)          (["N","S"] 선착순)     (누가 못을 박나)
```

셋은 **증상이 다르고 처방도 다르다.** 한 계획으로 묶으면 어느 처방이 어느 증상을 고쳤는지
못 가른다 — *"기능 변경 후 결과가 좋아졌나가 아니라, 겨냥한 문제가 풀렸나로 잰다"*
(`machine-link.md` — *무엇을 재나*).

## 왜 이 순서인가

**① 이 먼저다.** ②와 ③은 둘 다 *"고리를 안 늘리고"* 를 조건으로 하는데, 지금 고리가
**몇 개인지 확정되지 않았다.** §4.6 은 되먹임이 둘로 **보인다**고 적었지만, 그중 하나는
고리가 실제로 닫히는지 안 재 봤다(→ `1-되먹임`).

②와 ③은 **서로 독립**이다. ②는 *"어느 끝으로 나가나"*(y 방향), ③은 *"누가 먼저 앉나"*
(레인·좌석)이라 건드리는 필드가 겹치지 않는다.

| | ② 짝 | ③ 순서 |
|---|---|---|
| 바꾸는 필드 | `LinkFacePlan.portEnd` | `laneDepth` · `slotIndex` (순서를 통해) |
| 노리는 것 | 납품 경로 길이 ↓ → 채널 폭 ↓ | 못 ↓ → 못 앉는 줄 ↓ · 깊은 레인 ↓ |
| 재는 것 | 납품 경로 총 |Δy| · 채널 폭 | 사다리 자름 횟수 · `seat-blocked` 수 · d3 사용 수 |

## 세 계획이 공유하는 결정 (2026-08-29 사장님)

1. **되먹임은 개념적으로 존재해서는 안 된다.** 지금 있는 것은 고쳐야 할 것이지 설계가 아니다.
2. **짝의 생성 로직은 `Link` 의 자료구조에서 파생돼야 한다.** (판정은 `2-짝` §1 에)
3. **그룹 배정 순서는 정한 적이 없다.** 붓기의 부산물이 흘러 들어온 것이므로 **정하면 된다.**

## 완료 판정

셋을 다 끝내면 이렇게 되어야 한다:

```
모듈 생성 1회         ← 되먹임이 없으므로
배정이 짝을 안다      ← 끝이 Link 의 필드
배정 순서가 규칙이다  ← 붓기 순서가 아니라
```

**중간 상태도 정직하게 산다.** 하나만 끝내도 나머지는 오늘 동작 그대로다 —
각 계획의 *불변*이 그것을 단언한다.
