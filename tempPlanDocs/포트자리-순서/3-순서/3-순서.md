# 3 · 배정 순서를 **정한다** — 못을 애초에 안 만든다

## §1 조사 — 먼저 온 그룹과 늦게 온 그룹은 **어디를 먹나**

배정은 `groups.forEach` 다. 먼저 온 그룹이 `commitLinkFace` 로 칸에 도장을 찍고, 늦게 온
그룹은 **남은 자리**를 본다. 자리마다 규칙이 다르다:

| 자원 | 규칙 | **먼저** | **늦게** |
|---|---|---|---|
| **레인**(`laneDepth`) | 후보를 팔 적은 순 → **얕은 순** | **`d2`**(짧은 팔) | `d2` 가 자기 구간에서 막혔으면 **`d3`**(긴 팔) |
| **좌석**(`slotIndex`) | `freeSeatRows(...).slice(0, k)` — **빈 칸을 앞에서부터** | 머신 면의 **위쪽** 칸 | **아래쪽** 칸 |
| **기둥 끝**(`portEnd`) | `["N","S"].find(안 찼음)` | **N** | S → 셋째는 **옆**으로 |
| **면**(`face`) | 선호 면이 차면 넘침 | 선호 면(W/E) | **gap**(N/S) → 그다음 **실패** |

> **레인은 "찼다/비었다"가 아니라 "내 행 구간이 겹치나"다.** 행이 안 겹치는 두 그룹은
> 같은 `d2` 를 **나눠 쓴다**(벨트가 자기 좌석 구간만 덮고 끝에서 꺾으므로). 그래서 짧은
> 줄 여럿은 `d2` 에 나란히 앉을 수 있다.

### 그림 — 지금 일어나는 일

```
             d1(좌석)   d2        d3
머신 0..29  │ ● ● ●  │ ▓▓▓▓▓  │        │   ① 짧은 줄 A 가 먼저 앉는다
            │        │   ◄    │        │      그 포트가 d3 에 **못**을 박는다
머신 30..59 │ ● ● ●  │ ▓▓▓▓▓  │        │   ② 짧은 줄 B
            │        │   ◄    │        │
머신 60..89 │ ● ● ●  │ ▓▓▓▓▓  │        │   ③ 짧은 줄 C
            │        │   ◄    │        │
                        ↑         ↑
                 d2 가 통째로   d3 는 못 셋에
                 먹혔다        찍혀 있다
            → 관통 줄 D(머신 0..89 연속 필요)가 **갈 곳이 없다**
```

**실측(`electronic-circuit`)이 정확히 이 모양이었다** — `copper-cable` 토막 4개가 `d2` 를
`[0,87] [90,177] [180,267] [270,297]` 로 먹고 `d3` 의 행 `0·90·180·270` 에 못을 박았다.
`stone-tablet`(머신 90대 관통)이 나중에 와서 `d2` 는 통째로 막히고 `d3` 는 행 **90·180**
두 칸에 막혔다 — **268행짜리 레인이 두 칸 때문에 못 쓰였다.**

### 늦게 오면 **비싸진다** — 대가가 셋이다

```
① 깊은 레인 = 긴 팔 = 처리량 ↓   (실측: reach-1 10/s → reach-2 3.6/s)
                    → 같은 양을 나르려면 **팔이 더 많이** 필요
                    → **좌석을 더 먹는다** (좌석은 유일하게 못 늘리는 자원)
② 못이 는다        — 얕은 레인 줄의 포트가 깊은 레인의 못이다. 줄이 조각날수록 못이 는다
③ 넘침 → gap      — 모듈이 **세로로 벌어진다**(gapRowsFromPlans)
```

**그래서 순서가 공짜가 아니다.** 늦게 오는 것은 그냥 "나중"이 아니라 **더 비싼 자리**다.

## §2 그래서 무엇을 얻나 — 순서를 정하는 이유

**자유도가 낮은 줄을 먼저 앉히면 못이 애초에 안 생긴다.**

| 줄의 성질 | 자유도 | 늦게 오면 |
|---|---|---|
| **관통**(머신 전부, 연속 구간 필요) | **가장 낮다** — 조각난 레인에 **못 앉는다** | 갈 곳이 없다 → 사다리 → 되먹임 |
| **구간**(머신 몇 대) | 높다 — 조각 **사이**에 앉을 수 있다 | 대개 앉는다 |
| **팔이 많은 줄** | 낮다 — 좌석을 많이 먹는다 | 깊은 레인 → 팔이 더 늘어남(악순환) |

이건 짐싸기의 오래된 규칙(**큰 것부터**)과 같다. 그리고 **결정 1(되먹임 제거)의 실질적
경로**다 — 못이 없으면 사다리가 필요 없고, 사다리가 없으면 되먹임 ②가 없다.

## Step 1 — **순서 규칙을 세우고 계측만 한다**

먼저 정렬 규칙을 정해 두고, **적용하지 않은 채** 실물 트리에서 *"오늘 순서와 얼마나 다른가"*
를 잰다. 다르지 않으면 이 계획은 여기서 끝난다(= 이득이 없다).

**정렬 규칙 후보(1차안):**

```
① 관통 먼저      spansAllMachines(group, side, count)  — 연속 구간이 필요한 쪽
② 그다음 긴 구간  machinesOn(group, side) 내림차순
③ 그다음 팔 많은  Σ arms 내림차순                       — 좌석을 많이 먹는 쪽
④ 동률이면 오늘 순서(붓기 순) — **결정성 유지**
```

```
전제: 관통 줄이 실물 트리에 실제로 있다
      → 확인 방법: 트리마다 spansAllMachines 인 그룹 수를 센다. 0이면 ①이 무의미
불변: 코드가 정렬을 **적용하지 않는다** — 배치가 한 칸도 안 움직인다
관문: "순서를 바꾸면 실제로 달라지나" 를 연다
```

## Step 2 — 정렬을 적용한다 (플래그 뒤)

`allocateLinkFaces` 가 `groups` 를 그대로 돌지 말고 **정렬된 index 순서**로 돈다.
**`plans` 배열의 index 는 그대로여야 한다** — 호출자가 `groups[i]` 와 짝지어 읽는다.

```ts
const order = [...groups.keys()].sort(byFreedom(groups, side));
for (const i of order) {
  const cand = tryLinkFace(ctx, groups[i], side, prefer, false, shortages[i]);
  if (cand) plans[i] = commitLinkFace(ctx, cand, side);
  else deferred.push(i);
}
```

```
전제: 호출자는 `plans[i] ↔ groups[i]` 만 보고, **앉은 순서**에는 안 기댄다
      → 확인 방법: `plans` 를 읽는 곳 전수(`rg "\.plans" src`). `deferred` 의 순서에
        기대는 곳이 있는지도 함께 본다
불변: 정렬이 항등일 때(그룹 하나뿐인 면) **오늘과 완전히 같다** — 기전: `order` 가 `[0]` 이다
관문: **못을 덜 만드는 배정**을 연다
```

## Step 3 — 잰다. **그 문제가 풀렸나로**

```
① 겨냥한 문제:  자유도 낮은 줄이 늦게 와서 갈 곳을 잃는 것
② 풀렸나:      **관통 줄이 앉았나** (사다리 없이)
③ 나머지는:    분류만 한다 — seat-budget · seat-blocked 는 2·3단의 몫
```

| 재는 값 | 기대 | 왜 |
|---|---|---|
| 사다리 **자르는 횟수** | ↓ (0이면 사다리를 끌 수 있다 → **되먹임 ② 제거**) | 못이 줄었다는 직접 증거 |
| `d3` 에 앉은 줄 수 | ↓ | 얕은 레인을 덜 낭비했다 |
| `seat-budget` 수 | ↓ | 긴 팔이 덜 필요해져 좌석을 덜 먹는다 |
| 못 앉은 줄 총수 | — | **판정 기준으로 안 쓴다**(미완성 기능의 총계) |

> **`perTarget` 을 고정하고 잰다.** 2026-08-28 에 그 값이 100↔10 으로 흔들려 두 실행이
> 다른 트리였고, 비교가 통째로 무의미했다.

## Step 4 — 되먹임 ②를 끌지 판정한다

`1-되먹임` Step 2 가 세운 기준을 그대로 적용한다:

> 자름 횟수가 **0**이면 사다리를 끄고 되먹임을 없앤다. 0이 아니면 남은 것을
> **`span-blocked` 인지**로 분류하고 다시 판단한다. **총계로는 끄지 않는다.**

## §5 이 계획이 **푸는 문제** — 그리고 **안 푸는 것**

### 푼다

| 문제 | 지금 | 끝난 뒤 |
|---|---|---|
| **되먹임 B** — 사다리가 `linkCache` 를 갈아 `gen` 을 다시 부른다 | `gen` 이 한 번 더 | 못이 안 생기면 **사다리를 끌 수 있다** → 고리 없음 |
| **못**(`span-blocked`) | 짧은 줄이 먼저 앉아 얕은 레인을 조각내고 그 포트가 못이 된다 | 자유도 낮은 줄(관통)이 먼저 → **못이 안 생긴다** |
| **깊은 레인 낭비** | 늦게 온 줄이 `d3` → 긴 팔(3.6/s) → 팔이 늘어 좌석을 더 먹는다 | 얕은 레인을 필요한 줄이 쓴다 |
| **정한 적 없는 순서** | 붓기의 부산물이 배정 순서 | **규칙이 있다** |

### 안 푼다

| 남는 것 | 왜 | 누구 몫 |
|---|---|---|
| `seat-blocked` · `seat-budget` | 못 앉는 줄을 *더* 앉히는 능력이 없다 | 사다리 2·3단(gap · 다이렉트) |
| `port-blocked` | `resolveSpanBlock` 이 포트 칸을 안 본다 | 사다리 1단의 미구현분 |
| 끝(N/S) · 짝 | 건드리는 필드가 다르다 | **`2-짝`** |
| **형제 y 순서** | 이건 배정 순서가 아니라 tidy-tree 의 순서다 | `2-짝` 의 후속 ①(같은 병, 다른 자리) |

## §6 이게 끝나면 **무엇이 가능해지나**

### ① 사다리를 **끌 수 있다** — 되먹임 B 제거

`1-되먹임` 이 세운 기준 그대로: **자름 횟수가 0** 이면 끈다. 0이 아니면 남은 것을
`span-blocked` 인지로 분류하고 다시 판단한다. **총계로는 끄지 않는다.**

`2-짝` 과 **함께** 끝나면 `gen` 이 **한 번만** 돈다.

### ② 배정 순서가 자료가 되면, **다른 축도 같은 자리에서 정할 수 있다**

지금은 "누가 먼저 앉나" 를 정하는 자리가 없어서, 새 규칙을 넣으려면 매번 `forEach` 를
건드려야 한다. 정렬 함수가 생기면 축을 **더하는** 일이 된다 — 예:

```
· 짝 방향이 같은 줄끼리 묶어 앉힌다        (2-짝 과 합류)
· 유체 면을 피해야 하는 줄을 먼저 앉힌다
· 같은 부모로 가는 줄끼리 붙여 앉힌다      (납품 경로 다발화)
```

### ③ **못이 안 생기는 것이 증명되면** 사다리 코드를 지울 수 있다

지금 사다리는 `resolveSpanBlock` · `splitLinkAtRows` · `linkCache` 변형 · 재생성까지
네 조각이다. 못이 구조적으로 안 생긴다면 그 넷이 통째로 사라지고, `LaneShortage` 도
**진단 전용**으로 단순해진다.

> **다만 "0을 봤다" 는 "0이 구조적이다" 가 아니다.** 지우기 전에 *"어떤 입력이면 못이 다시
> 생기나"* 를 답할 수 있어야 한다. 못 답하면 **플래그로 꺼 두는 데까지**가 이 계획의 끝이다.

## §7 사다리를 `P0b` 로 옮긴다 — **쪼개기는 링크 생성의 일이다** (2026-08-29 추가)

### 왜 지금 자리가 잘못인가

쪼개면 **포트가 늘고 → 흐름이 갈리고 → 링크가 더 태어난다.** 그러니 쪼개기는
*"링크가 몇 개인가"* 를 정하는 일이고, 그건 `P0`(`linkCache` 조립)의 관심사다.
지금은 `P1b` 가 이미 만들어진 `linkCache` 를 **뒤에서 고친다.**

```
지금    P0 링크 생성 → P1 gen(계획+방출) → P1b 링크 **수정** → P1′ gen 다시
목표    P0 링크 생성 → P0b **계획만** → 쪼갬 → P0b 다시 → P1 gen **한 번**
```

`P1′`(1차 재생성)이 **사라진다.**

### 가능한 근거

`planModulePorts` 는 `generateModule` 의 첫 줄에서 불리는 **순수 함수**이고
(`clusterModule.ts:260`), 방출을 안 한다. 받는 것도 `ModulePortPlannerInput` 뿐이라
**`P0` 에서 그대로 부를 수 있다.**

### 다만 — **옮겨도 고리는 남는다. 싸질 뿐이다**

```
지금    배정 → 사유 → 링크 수정 → **배정 + 방출** 재실행
옮기면  배정 → 사유 → 링크 수정 → **배정만** 재실행        ← 여전히 고리
```

**고리를 없애는 길은 쪼갤 일이 없게 만드는 것뿐**이고, 그건 `3-순서` 다. 쪼갬을 배정
**안**으로 넣는 길은 막혀 있다 — 자식 출력과 부모 입력이 **같은 `Link` 객체**를 봐야 하는데
(`pairDeliveryPorts` 가 `linkId` 로 짝짓는다) 모듈 배정은 자기 모듈만 본다.

### 그래서 이 단계의 값은 **둘**이다

```
① 구조가 옳아진다 — 링크 집합을 바꾸는 일이 링크 생성의 자리로 간다 (R1)
② 3-순서가 못을 0으로 **못 만들어도** 되먹임이 0이 된다
   — 사다리가 켜져 있어도 방출을 다시 안 부르므로
```

**끄는 것과 옮기는 것은 다른 처방이다.** `3-순서` 가 0을 못 만들면 ②가 유일한 길이다.

```
전제:  planModulePorts 를 P0 에서 부르는 데 필요한 입력이 그 시점에 다 있다
       → 확인: toModuleInput 의 인자(spec · config · childFedItems)가 P0 이전에 확정인지
전제:  배정만 돌리는 비용이 방출까지의 비용보다 뚜렷이 싸다
       → 확인: 착수 시 한 번 잰다. 안 싸면 이 단계의 값 ②가 약해진다
불변:  쪼갬 판정의 **입력과 출력이 같다** — 같은 laneShortages 로 같은 행을 자른다
       → 기전: resolveSpanBlock·splitLinkAtRows 를 손대지 않고 **부르는 자리만** 옮긴다
관문:  사다리를 **켠 채로도** 되먹임 0
```

> **순서 주의.** 이 단계는 `3-순서` 의 결과를 보고 착수를 판단한다 — 못이 0이면 사다리를
> 끄면 그만이라 옮길 필요가 없다. **0이 아닐 때만 값이 있다.**
