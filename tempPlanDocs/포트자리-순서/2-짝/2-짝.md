> 이 계획이 여는 고리: **A** = `gen → extent → tidy-tree → lineEnds → gen`

## §0 생애 주기 — **누가 무엇을 언제 정하나**

*짝* = 이 벨트 줄의 반대쪽 끝. 자식의 **출력 포트**와 부모의 **입력 포트**가 한 쌍이고,
둘을 잇는 것이 **납품 경로**다.

### `Link` 의 필드 전부

| 필드 | 정하는 곳 | 시점 | 무엇을 보고 |
|---|---|---|---|
| `item` | `edgeLinkGroups` | P0 (생성 전) | 자식의 출력 품목 |
| `carries` | `createLinks` — **붓기** | P0 | `edgeFlows` 의 흐름 + 벨트 티어 상한 + 좌석 상한 |
| `from` / `to` | `armsFromCarries` | P0 | `carries` + **reach 1** 인서터 |
| `beltEntityName` | `createLinks` | P0 | `determineBeltCount` 가 총량에서 고른 티어 |
| `id` | `makeLinkId` (**유일 출처**) | P0 | 자식 id · 부모 id · 품목 · 순번 |
| *(쪼개지면)* | `splitLinkAtRows` | P1b | `id → id/k`, `carries`·`from`·`to` 좁힘. **`...group` 스프레드라 새 필드는 따라간다** |

**`Link` 는 P0 에서 완성되고, 그 뒤로는 사다리만 건드린다.**

### 짝에 관한 값은 **셋으로 흩어져 있고, 열쇠가 다르다**

| 값 | 정하는 곳 | 시점 | **열쇠** |
|---|---|---|---|
| **끝 선호**(`lineEnds`) | `modulePacking` 3) | **P3** — tidy-tree 뒤 | **품목 이름** `output:품목` |
| **실제 끝**(`portEnd`) | `tryLinkFace` | gen 안 | `ctx.ends` **선착순**(N 먼저) |
| **실제 짝짓기** | `pairDeliveryPorts` | P5 | **`linkId`** |

```
한 개념(짝)이 세 시점에 세 열쇠로 결정된다.
그리고 가운데 것(실제 끝)은 앞의 것(끝 선호)을 **안 본다.**
```

**그래서 실제로 틀린다:**

| 상황 | 지금 무슨 일이 나나 |
|---|---|
| 한 간선에 벨트 줄이 셋 | 열쇠가 품목이라 **셋이 같은 끝 선호**를 받는다 |
| 사다리가 줄을 쪼갬 | `id` 는 갈리는데 **끝 선호는 안 갈린다** |
| 관통 링크 | `portEnd` 가 선착순 — **끝 선호를 아예 안 읽는다** |

### 판정 — "짝의 생성 로직은 `Link` 의 자료구조에서 파생돼야 한다"

> **맞습니다.** 열쇠가 `linkId` 여야 하고, `linkId` 를 드는 것은 `Link` 다.
>
> 다만 **`Link` 는 답을 담고, 답을 구하지는 않는다** — *"짝이 위냐 아래냐"* 는 두 모듈의
> 상대 위치라 트리가 안다. 이건 새 규칙이 아니라 **`id` 가 이미 그렇게 산다**: *"양끝을 아는
> 호출자(`modulePacking`)가 채우고, 이 폴더는 파싱하지 않는다"*(`module/link.ts:66`).

### 그리고 `lineEnds` 는 링크에 대해 **이미 사실상 죽어 있다** (코드로 유도 — 재확인 필요)

```
linkedKeys = 링크 그룹이 있는 품목      ← restLines 에서 제외된다
restLines  → insertingPlanner → PlannedLine → emitTrunkPipe/emitTapInserting → lineEnds 소비

즉 링크가 난 품목은 PlannedLine 이 안 생기고, 링크 배정은 lineEnds 를 안 본다
→ 그 품목의 lineEnds 항목은 `meta.endPreference`(메타데이터)로만 남는다
```

**살아 있는 것은 (가) 유체 간선**(`edgeLinkGroups` 가 유체를 거절 → 트렁크가 맡는다)
**(나) 링크 생성이 실패한 아이템 간선**뿐이다. → **고리 A 는 그 둘을 통해서만 물고 있다.**

## §1 판단 — **트리도 정확한 위치는 모른다** (2026-08-29 정정)

> 사장님 지적이 맞습니다. 첫 판의 *"자식 순번으로 위/아래를 정확히 안다"* 는 **과했습니다.**

`layoutY` 가 보장하는 것은 **형제 중심의 순서**뿐이다:

```ts
const centers = kids.map(layoutY);                 // DFS · cursor.y 단조 → centers 단조 증가
const center = (centers[0] + centers.at(-1)) / 2;  // 부모 중심 = **첫·마지막의 중점**
topY.set(id, center - heightOf(id) / 2);
```

그런데 `lineEnds` 가 비교하는 것은 중심이 아니라 **모서리**다:

```ts
const ends = (id) => ({ min: topY.get(id), max: topY.get(id) + heightOf(id) });
```

**모서리는 높이가 있어야 안다.** 그리고 높이는 `gen` 이 준다 — 그게 고리 A 다.

### 반례 — 첫 자식인데도 `min` 을 고른다

```
부모 P: 자식 둘의 중심이 11 과 50 → P 중심 30.5, 높이 100 → P.min = -19.5, P.max = 80.5
자식 C(첫째): topY 10, 높이 2                          → C.min = 10,    C.max = 12

  |C.min - P.min| = 29.5   ← 최소
  |C.max - P.min| = 31.5
```

**첫 자식인데 `bestC = "min"` 이다.** 부모가 자식들의 퍼짐보다 크면 부모의 윗 모서리가
모든 자식보다 위에 있어, 자식들이 전부 자기 `min` 을 고른다. 순번으로는 못 맞힌다.

## §2 그래서 **목표를 바꾼다** — 거리가 아니라 **교차**

지금 목표(*"가장 가까운 끝"*)는 **좌표를 요구하고**, 좌표는 `gen` 을 요구한다. 그 목표를
지키는 한 고리는 못 연다.

**바꿀 목표: 교차하지 않는 끝.**

```
가까운 끝   |dy| 최소   ← **모서리**가 필요 → 높이 필요 → gen 필요 → 고리
교차 없음   순서 보존   ← **중심 순서**만 필요 → 트리만으로 안다 → 고리 없음
```

**그리고 채널이 값을 매기는 것은 교차 쪽이다.** `channelGeometryPlanner` 의 자기 모델이
그렇게 말한다 — *"납품끼리: 분리 = 트랙 공유, 부분 겹침 = 열 갈아타기, **완전 교차 = 사다리로**"*.
**교차는 트랙을 나눠 쓸 수 없게 만들어 채널을 넓힌다.** 거리는 그다음 문제다.

### 트리만으로 확정되는 것 / 안 되는 것

| | 확정? | 근거 |
|---|---|---|
| 형제끼리의 **중심 순서** | ✅ | `cursor.y` 단조, 서브트리 구간이 서로 안 겹침 |
| **첫** 자식이 부모 중심 위 · **마지막**이 아래 | ✅ | 부모 중심 = 첫·마지막의 중점 |
| **가운데** 자식이 부모 중심의 어느 쪽 | ❌ | 간격(= 높이)에 달렸다 |
| 모듈이 **겹치나**(모서리 순서) | ❌ | 높이에 달렸다 |

**그래서 규칙은 부분적이고, 모르는 곳은 `undefined` 로 둔다** — 지어내지 않는다.

### 규칙 (1차안)

```
같은 면의 기둥 끝(N·S)을 관통 그룹 둘이 다투면
    순번이 **앞선** 자식 쪽 링크가 N,  **뒤인** 쪽이 S      ← 서로 안 교차한다

자식 자신의 출력 끝
    첫 자식    → 부모가 아래  → S 로 나간다
    마지막     → 부모가 위    → N 으로 나간다
    그 외·외동 → **undefined**(오늘처럼 선착순)
```

## §3 단계 — **왜 넷으로 쪼개나**

`tempPlanDocs/CLAUDE.md` 의 *"바뀌었을 때 싸게 알아채고 싸게 고친다"* 를 따른다.
**Step 3 전까지 배치가 한 칸도 안 움직인다** — 그래서 어디서 깨졌는지가 자명하다.

```
Step 1  자리를 만든다   →  배치 무변경.  깨지면 **타입·전달** 문제
Step 2  값을 채운다     →  배치 무변경.  깨지면 **규칙(순번 판정)** 문제
Step 3  값을 읽는다     →  배치 변경.    깨지면 **기하** 문제
Step 4  트렁크 절반     →  고리 A 가 실제로 닫힌다
```

넷을 한 번에 하면 배치가 달라진 이유가 넷 중 무엇인지 못 가른다.

### Step 1 — `Link` 에 담을 자리를 만든다

**목적: 짝 정보가 배정까지 갈 *통로*를 연다.** 지금은 통로 자체가 없다 —
`ModulePortPlannerInput` 이 `lineEnds` 를 안 받으므로 어떤 값을 계산해도 배정에 못 닿는다.
`Link` 에 넣으면 `outputLinks`/`inputLinks` 를 **타고 이미 들어와 있다** — 그게 §0 판정의
실질이고, 입력 타입을 넓히지 않아도 되는 이유다.

```ts
interface Link {
  /**
   * **짝이 있는 쪽 끝** — 이 줄의 포트가 기둥 어느 끝에 서야 짝과 **안 교차하나**.
   * `undefined` = 모른다(가운데 자식·외동) → 배정이 오늘처럼 선착순으로 고른다.
   * `id` 와 같은 규칙으로 산다: 위층이 채우고 이 폴더는 안 만든다.
   */
  end?: { from: "N" | "S"; to: "N" | "S" };
}
```

`from`/`to` 로 나누는 이유: **한 줄의 두 끝은 서로 반대쪽을 본다.** 하나만 들면 어느 쪽
이야기인지 매번 되유도해야 한다.

```
전제:  Link 를 만드는 곳은 createLinks 하나, id 를 얹는 곳은 edgeLinkGroups 하나
       → 확인: Link 리터럴이 그 둘뿐인지 재검색
불변:  필드를 **아무도 안 읽는다** — 기전: 읽는 코드가 없으므로 다른 답을 낼 수 없다
관문:  짝 정보가 배정까지 갈 통로
```

### Step 2 — 위층이 채운다 (**`gen` 앞에서**)

**목적: 값을 *고리 밖에서* 만든다.** `modulePacking` 의 `linkCache` 조립 자리(`:397-404`)는
`gen`(`:431`)보다 **앞**이고 트리만 본다. 여기서 채우면 그 값은 `gen` 의 출력에 안 기댄다 —
**그게 고리를 여는 유일한 조건이다.**

```
자식 순번 i, 형제 수 n
  i === 0   && n > 1  →  { from: "S", to: "N" }
  i === n-1 && n > 1  →  { from: "N", to: "S" }
  그 외               →  undefined
```

```
전제:  layoutY 가 kids 를 배열 순서대로 위→아래로 놓는다
       → 확인: modulePacking.ts:489-501. 확인함(2026-08-29)
전제:  이 자리가 gen 보다 앞이다 → 확인: modulePacking.ts:397 < :431
불변:  `end` 를 아무도 안 읽으므로 여전히 배치 무변경
관문:  값이 실제로 채워지는가 — `flg.report()` 에 채운 수를 낸다
```

### Step 3 — 배정이 그것을 본다

**목적: 선착순을 선호 순으로 바꾼다.** 여기서 처음 배치가 움직인다.

```ts
const want = group.end?.[side];
const order = want ? ([want, want === "N" ? "S" : "N"] as const) : (["N", "S"] as const);
const portEnd = spanning ? order.find((e) => !endsTaken?.has(e)) : undefined;
```

```
전제:  Link.end 가 배정까지 그대로 온다
       → 확인: splitLinkAtRows 가 `...group` 스프레드다(link.ts:431). 따라간다 ✔
불변:  `end` 가 undefined 인 줄은 오늘과 **한 칸도** 안 다르다
       → 기전: order 가 ["N","S"] 로 같아진다(관통이 아니면 portEnd 자체가 undefined)
관문:  **짝을 보는 배정**
```

### Step 4 — 트렁크 절반 · 고리 A 를 실제로 닫는다

**목적: `gen` 을 한 번만 돌게 한다.** Step 1~3 은 **링크 절반**만 연다. `lineEnds` 는
유체 트렁크 줄(과 링크 생성 실패분)에도 살아 있어(§0 마지막), 그게 남으면 `gen` 은
**여전히 두 번 돈다.**

같은 규칙을 그쪽에도 준다 — 끝 선호를 `PlannedLine`(또는 그 입력)이 들고, 값은 같은
**순번 규칙**으로 `gen` 앞에서 채운다. 그러면 `lineEnds` 를 tidy-tree 뒤에서 만들 이유가
없어지고, **2차 생성이 사라진다.**

```
전제:  lineEnds 소비처가 emitTrunkPipe · emitTapInserting · meta 셋뿐이다
       → 확인: 착수 시 재검색. 지금까지 그 셋 ✔
불변:  이 단계는 **gen 호출 횟수를 줄인다**
       → 기전: lineEnds 인자가 사라지면 `:597` 의 재호출 이유가 없어진다
관문:  **고리 A**
```

## §5 이게 끝나면 **무엇이 가능해지나**

### ① 형제 순서를 **정하는** 계획 — 지금 아무도 안 정했다

이 계획은 *"형제 순서가 끝을 정한다"* 로 만든다. 그러면 **형제 순서 자체가 지렛대**가 되는데,
지금 그 순서는 **레시피의 재료 나열 순서**다:

```
order          = 레시피 트리의 DFS pre-order          (moduleWizard.ts:70)
childIdsByParent = specs 순회 순서 = order 순서        (modulePacking.ts:327-330)
layoutY        = kids 배열 순서대로 위 → 아래          (modulePacking.ts:489-501)

즉  모듈의 **세로 순서 = 게임데이터의 재료 나열 순서**.  아무도 고른 적이 없다.
```

**`3-순서`(배정 순서)와 정확히 같은 병이다** — 부산물이 흘러 들어와 결정이 됐다.
이 계획이 끝나면 *"형제를 어떤 순서로 쌓을 것인가"* 가 **답할 수 있는 질문**이 된다
(예: 연결이 교차하지 않게, 또는 큰 모듈을 가운데로).

### ② `gen` **1회** — S-LAYER 계약이 구조로 성립한다

`2-짝`(고리 A) + `3-순서`(고리 B) 가 끝나면 `generateModule` 이 **한 번만** 돈다. 그러면
*"계획이 정한 것을 방출이 그대로 놓는다"* 가 **관례가 아니라 구조**가 된다 — 다시 돌 자리가
없으므로 계획을 못 지키면 그 자리에서 정직하게 실패한다. 예약 철학 R1 이 실제로 강제된다.

부수 효과로 **실행 시간이 1/3 로** 준다(모듈 생성이 지배적일 때).

### ③ 가운데 자식 — **높이 없이 순서를 정하는** 축이 필요하다

이 계획은 첫·마지막만 답하고 가운데는 `undefined` 로 남긴다. 그것을 풀려면 *"모서리를 알아야
한다"* 는 요구 자체를 깨야 하고, 길은 둘이다:

```
(가) 높이를 배정 전에 안다      — 계획만으로 extent 를 유도한다(방출 없이)
(나) 끝을 좌표가 아니라 **역할**로 정한다 — 예: 부모의 입력 포트를 자식 순서대로 배분
```

**(나)가 이 계획의 자연스러운 연장이다** — 이미 "교차 없음" 을 목표로 잡았으므로, 끝이 둘
(N·S)뿐이라는 제약을 풀면(= 포트를 기둥 안 여러 위치에 둘 수 있게 하면) 자식 n 명을
순서대로 배분할 수 있다. **다만 그건 기하 능력이 하나 더 필요하다.**

### 의존도

```
2-짝  ──┬─→ ① 형제 순서 계획        (이 계획이 순서를 지렛대로 만든다)
        ├─→ ② gen 1회               (3-순서와 **함께** 라야 도달)
        └─→ ③ 가운데 자식           (이 계획이 남긴 undefined 를 겨냥)
```

## 무엇을 얻나 (재는 법)

> `docs/auto-layout/link/machine-link.md` — *무엇을 재나* 의 순서로 잰다.

```
① 겨냥한 문제:  관통 링크의 포트가 짝과 **교차하는** 끝에 선다
② 풀렸나:      `end` 가 있는 줄이 **원하는 끝을 받았나**
③ 나머지는:    undefined(가운데 자식)가 몇이고 왜인지 분류만 한다
```

| 재는 값 | 어디서 |
|---|---|
| `end` 를 채운 줄 / 그중 원하는 끝을 받은 줄 | 새 계측 |
| `gen` 호출 횟수 (3 → 2 → 1) | 직접 셈 |
| 채널 트랙 수 · 폭 | `flg.report()` |
| 납품 경로 총 세로 거리 | `deliverySeeds` |

**총 폭이 줄었는지는 ②가 끝난 뒤에 본다.** 미완성 기능의 총계로 판정하지 않는다.
