# 부분 트렁크 — **`g` 를 줄마다 정한다**

> 상태·읽을 것·범위는 같은 폴더의 `CLAUDE.md`.
> **모델은 여기 없다** — `docs/auto-layout/module/trunk-assignment.md` 에 있다.
> 이 문서는 **아직 안 한 일**만 든다.

## §0 한 문장

> 한 벨트 줄이 맡는 머신 수 **`g`** 를, 지금은 모듈 하나의 스위치가 `N` 아니면 `1` 로
> 정한다. **줄마다, 그 사이 값도** 정할 수 있게 한다.

```
g = N   벨트 하나가 기둥 전체        = 관통 = 트렁크
g = 1   머신마다 벨트 하나            = 다이렉트
1<g<N   **부분 트렁크 — 오늘 없다**
```

**`g` 의 상한은 처리량이 준다**(`k = ⌊벨트 처리량 / 머신 하나가 쓰는 양⌋`). 지금 코드는
그 상한을 쓰거나 `1` 로 떨어지거나 둘뿐이고, 그 이분법을 정하는 것이 **모듈 단위 스위치**다:

```ts
// planner/module/planModulePorts.ts
externalLineGroups(..., { perMachine: supply.mode !== "tap", ... })
//                        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                        모듈 하나의 값이 **그 모듈의 모든 줄**을 정한다
```

## §1 왜 이것이 문제인가

```
① 줄마다 사정이 다른데 모듈 하나가 정한다   fan-out + 트렁크 공존이 여기서 막힌다
② 사이 값이 없다                            g 를 조금만 낮추면 앉을 줄이 통째로 다이렉트가 된다
③ 그래서 "쪼개기" 가 따로 났다              자리가 없을 때 사후에 토막내는 특수 연산이 생겼다
```

**③이 핵심이다.** 쪼개기는 특수 연산이 아니라 **`g` 를 상한보다 작게 고르는 것**이다
(`조사-쪼갬.md`). `g` 를 줄마다 고를 수 있으면 쪼개기는 **별도 기전일 이유가 없다.**

## §2 할 일 — 셋이고 순서가 있다

> 출처: 옛 `트렁크벨트-경로모델` §19.4. 순서도 거기서 왔다.

```
⑤ **모듈 단위 tap/direct 모드 폐기** — 형태가 **줄마다** 갈린다
   `perMachine: supply.mode !== "tap"` 이 모듈 하나의 값으로 모든 줄을 정한다
   → ③의 전제다. 모드가 살아 있으면 줄마다 g 를 재도 반영할 데가 없다

③ **부분 트렁크** — `externalLineGroups` 가 `g = min(⌊벨트 ÷ per⌋, N)` 을 재서
   `c = ⌈N/g⌉` 개로 묶는다. 오늘의 이분법이 그 **특수해**가 된다(g=N → 1개 · g=1 → N개)

㉮ **포트의 방향을 계획이 알게 한다** — `meta.side` 가 N/S 를 내는데 소비처가 W/E 만 안다
   → `행채널-모델` 이 먼저다. 기둥 끝 포트는 본질적으로 **행 채널**을 쓰는 포트다
```

## §3 흡수된 것 — 옛 `간선-배정` 의 남은 항목

옛 계획의 Step 1~5(되먹임 제거)는 **끝났다**(`gen` 1회 · 되먹임 0). 남았던 것은 여기로 접힌다:

| 옛 항목 | 어디로 |
|---|---|
| Step 6 — 레인 순서 규칙 | **③ 안에서 정해진다.** `g` 가 줄마다 정해지면 무엇이 관통이고 무엇이 구간인지가 배정 시점에 정해진다 |
| D1~D5 — 쪼개기를 어떻게 고치나 | **③이 답이다.** 쪼개기는 `g` 를 낮추는 것의 사후 특수해였다 |

**그리고 배정 순서에 대해 하나가 확정됐다**(2026-08-30):

> **관통 줄이 먼저 앉는다.** 도피처가 없기 때문이다 — gap 은 가로 벨트가 머신 하나만 맡아
> 못 가고, 반대 옆면은 납품 방향이 뒤집힌다. **제약이 가장 센 것 먼저**(스도쿠 원칙 —
> `planModulePorts` ⓪ 이 유체 면을 먼저 보는 것과 같은 규칙).
>
> 이것은 **폐기된 옛 TR2 가 아니다.** 옛 TR2 는 `c` 로 **깊이**를 정했고(깊이는 대리 변수라
> 스펙 따라 뒤집힌다), 이것은 도피처 유무로 **순서**를 정한다. 깊이는 여전히 처리량이 정한다.

# 이월 — 목표(옛 §0)

## 0. 목표 — 한 문장

> **자리가 붓기를 되먹인다.** 벨트 줄 수를 정하는 상한에 **레인 × 행**을 더하고,
> 모자라면 그 줄만 사다리를 내려간다(구간 → gap → 다이렉트 → 정직한 실패).

### 0.0 옛 목표 문장은 **달성됐다** (2026-08-24 확인 — 코드를 읽어 판정)

원래 목표는 *"트렁크 벨트는 다이렉트 벨트 여럿을 한 줄로 합친 결과다. 그 합치기를 모델로
만든다"* 였다(`trunk-redesign` §4). **그 문장은 [[배선-형태]] 가 끝냈다:**

```
module/link.ts  createLinks     흐름을 벨트 줄에 순서대로 붓는다 — **형태를 고르는 if 가 없다**
                beltLineForm    트렁크·다이렉트는 그 붓기의 결과를 *읽은* 이름이다
```

한 줄에 흐름이 여럿 쌓이면 그 줄이 트렁크고 하나면 다이렉트다. 별도 배분기도 별도 방출기도
없다 — `emitTapInserting` 은 호출자가 0이 되어 삭제됐고 `emitOutputLinks` 하나가 둘을 다 낸다.
**옛 §0 문장으로 남은 결함은 없다.**

> 목표를 형용사(*"온전한 트렁크"*)로 적으면 목표가 아니다 — 이 폴더가 이미 밟은 함정이다
> (CLAUDE.md: *"결함으로 환원되지 않으면 목표가 아니다"*). 그래서 **남은 결함**으로 다시 적는다.

### 0.1 남은 결함 하나 — 줄 수를 정하는 상한에 **자리가 없다**

`createLinks` 가 보는 상한은 둘뿐이다(`module/link.ts:138`):

```ts
LinkLimits { tiers,             // ① 벨트 용량
             fromSeat, toSeat   // ② 그 면의 좌석 수 x 팔 하나
           }                    // ← ③ **레인이 없다**
```

부르는 두 곳 다 그 둘만 넘긴다 — `edgeLinks.ts:221`(자식→부모 줄) · `link.ts:536`(원료·완제품).
그런데 한 면이 실제로 세울 수 있는 벨트 줄 수는 **그 면의 `reach` 종류 수**이고(보통 2 —
`laneDepthsOf`, `linkPlanner.ts:171`), 붓기가 그것을 모르므로 **레인보다 많은 줄이 날 수 있다.**

```
붓기      "벨트 용량과 좌석이 허락하니 4줄"
배정      tryLinkFace: 레인 2개 — 3번째 줄부터 자리 없음 → undefined
결과      모듈이 통째로 다이렉트로 물러나거나(supply.mode="direct"), 그 줄이 unroutedLines 로 사라진다
사유      lanes-exceed-capacity  (clusterPortPlanner.ts:345)
```

**§14 가 세운 모델이 정확히 그 되먹임이다** — 자원은 레인이 아니라 `레인 × 행`이고
(TR1: *"`g_max` 는 처리량이 준 **상한**이고 실제 `g` 는 **자리**가 정한다"*), 자리가 모자라면
사다리를 내려간다(§9-마). **코드에는 그 사다리가 없다.** 있는 것은 *"못 앉으면 통째로 후퇴"*
하나뿐이다.

### 0.2 관문 — 무엇이 열리면 끝인가

| # | 관문 | 어떻게 재나 |
|---|---|---|
| **가** | `lanes-exceed-capacity` 로 **모듈 전체가** 다이렉트로 물러나는 일이 없다 | [[배선-형태]] **Step 5**(모듈 단위 tap/direct 후퇴 제거)가 떨어져 나간다 — 지금 그 사유 하나가 후퇴를 붙잡고 있다 |
| **나** | 자리가 모자라면 **그 줄만** 내려간다 | `flg.report()` 형태 줄: **붓기불가 0 · 과적재 0** |
| **다** | 내려간 결과가 게임에서 돈다 | `flg.check()` — R-연속 · R-도달 위반 0 |
| **라** | 왜 내려갔는지가 남는다 (R4) | 사유가 *"자리 없음"* 이 아니라 **수**로 나온다: 필요 레인 n · 있는 레인 m |

**"산출물이 안 바뀐다"는 관문이 아니다**(폴더 CLAUDE.md 함정 2) — 기준선이 미완성이라
아무것도 증명하지 않는다.

# 이월 — 지난 실패(옛 §10)

## 10. 이번에 실패한 이유 — 2026-08-13 롤백

**한 문장:** **모델을 안 만들고 기존 트렁크의 기하를 옮겨 심었다.**

*"기존 코드의 **의도만** 파악하라"* 는 지시를 받고 "의도 셋"을 적었는데
(면당 깊이로 갈림 · 상한은 reach 종류 수 · 끝을 어긋냄), **그 셋은 의도가 아니라 탭의
구현 방식**이었다 — §5 의 "직선에서만 나오는 제약" 바로 그것이다. 그걸 `LinkLane` 으로
옮겨 심고 "의도만 취했다"고 이름 붙였다.

| 롤백한 것 | 왜 |
|---|---|
| `mergeBaseline`(연속 구간 접기) | "연속"은 직선 전제 |
| `LinkLane`(깊이 슬롯) | 탭의 깊이 레인 복제 |
| `spans`·`crossedGaps`·`gapPorts` 장부 | 면×깊이 축 — 경로 모델엔 없는 축 |
| `supplyMode` + `supplyCompare` | 모델 없이 만든 스위치와 계측 |
| `machineExt`·`portFace`·`FaceRefusal` | 위와 얽혀 있음. 새 모델에서 다시 판단 |

**남긴 것:** 사실 정정(`CLAUDE.md` 사유 타입 · 용어사전 낟알 · `code-folders` 축 판정 ·
`module-planning` §5)과 작업 방법(`tempPlanDocs/CLAUDE.md`). 모델과 무관하게 참인 것들이다.

**되찾는 법:** 롤백 직전 상태가 scratchpad 의 `rollback-backup/`(패치 + 새 파일 4개)에 있다.

### 다음이 같은 데를 안 밟게

1. **기존 구현의 "어떻게"를 의도로 착각하지 않는다.** 의도는 *"무엇을 이루려 했나"* 이고,
   깊이·레인·stagger 는 *"직선으로 하기로 했을 때 따라온 것"* 이다.
2. **모델 없이 검증을 늘리지 않는다.** 잴 것이 남의 모델뿐이면 계측이 아무 말도 안 한다.
3. **"산출물이 안 바뀐다"를 합격선으로 쓰지 않는다.** 기준선이 미완성이면 아무것도 증명하지 않는다.

| **D10** | 경로는 **레인 예약**(§14·**§9.7**) — 레인 = 자유 타일 한 줄, 장부 = 레인마다 점유 구간. 탐색이 아니라 **배분**이다. `containerRouting` 은 **지하 규칙 제공자**로만 쓴다(경로 탐색기로 쓰지 않는다) |
| **TR1** | **`g_max = min(k, N)` 는 처리량이 준 *상한*이고, 실제 `g` 는 *자리*가 정한다**(2026-08-16 정정).<br>예전엔 *"항상 최대로 묶는다"* 라는 **값**으로 적었는데, 그러면 §9-마의 사다리가 지워진다. `g` 를 낮추는 것이 곧 **레인을 아끼는 것**이다 — 관통은 레인을 통째로 먹고 구간은 행만 먹는다. 그래서 *"포트를 아낀다"* 와 *"레인을 아낀다"* 는 **같은 축의 반대 방향**이고, 어디에 설지는 자리가 답한다.<br>`g_max` → 관통 · 낮추면 구간 · `g=1` 다이렉트 · 그래도 모자라면 gap · 그래도면 정직한 실패.<br>**탐색이 아니다** — 그 면의 관통 후보 수와 레인 수를 세면 한 번에 나온다. 쪼갬은 앞에서부터 `g` 대씩, 나머지는 뒤(4대·k=3 → **3+1**) |
| **TR2** | **깊이 배정은 "그 깊이의 인서터가 이 줄을 처리할 수 있나"로만 정한다**(2026-08-14 사용자). `a(j,d) = ⌈per_j / tp(d)⌉` 이고 `Σ a ≤ h` 인 조합만 후보다. **후보 중에는 우선순위가 없다** — 어느 줄이 깊고 얕은지는 중요하지 않다.<br>*옛 TR2("구간 적은 줄이 얕게")는 **폐기**. 진출 수단을 지상 전달 타일 하나로 가정해서 생긴 회피책이었고, 수단이 여럿이면 사라진다* |
| **TR3** | **같은 면의 품목들은 머신 안 행 offset 을 하나씩 나눠 갖고, 얕은 레인일수록 흐름 반대쪽 끝으로 밀린다**(= stagger). **모듈을 안 키우고 머신 안 여유 행 `h − a` 가 흡수한다** |
| **TR4** | **총 레인 = `2R`(깊이 축) + `G`(gap 행 축).** 긴 팔이 없으면(`R=1`) gap 을 열어 산다 — gap 가로 벨트 하나가 위·아래 **정확히 2대**를 먹인다. `ROW_GAP = 3` 이 그 폭(좌석/벨트/좌석) |
| **TR5** | **포트의 *선호* 면은 밖(부모/자식 방향)이 준다**(2026-08-14 사용자). 트렁크가 면을 **만들지는** 못하지만, 좌석 예산이 모자라면 **반대 면으로 분산한다**(TR8). 면은 강제가 아니라 선호다 |
| **TR6** | **진출 가로 구간은 포트 인서터가 흡수한다**(§14-7 배치2). 레인 `d` 는 `d+1..maxLane` 에 **한 칸씩**만 필요하고 가장 깊은 레인은 **0칸**. 포트 = `maxLane+1`(인서터) `+2`(상자).<br>**포트 인서터가 긴 팔로 레인을 건너뛰는 기하는 금지다**(2026-08-14 사용자). 얕은 레인은 반드시 **지상 전달 타일**로 나오고, 그 타일이 막히면 TR7 로 푼다 |
| **TR7** | **진출이 막히면 (가) 먼저 잠수시키고, 못 하면 (나) 끊는다**(2026-08-14 사용자: *"사용 가능한 지하 배타권 1회는 반드시 사용해야 한다"*).<br>**(가) 잠수** — 막고 있는 깊은 레인이 그 행에서 지하로 간다. 대가는 **몸통 칸의 탭 하나뿐**이고 입·출구 칸은 그대로 탭한다(`entity-roles.md` §C). 모듈 크기 0 · 포트 0.<br>**(나) 끊기** — 그 트렁크를 두 구간으로. 구멍이 생긴다. 포트 +1 · 모듈 크기 0.<br>**깊이 순서를 바꿔 피하지 않는다** — 그 축은 TR2 가 처리 가능성으로만 정한다 |
| **TR8** | **좌석 예산은 면이 아니라 모듈 전체다** — 밀착 기둥에서 머신 하나당 `2h`(W면 `h` + E면 `h`). 선호 면이 차면 **반대 면으로 분산한다**(2026-08-14 사용자).<br>**그 `2h` 마저 넘치면 gap 을 열어 N/S 면을 쓴다**(2026-08-15 사용자) — 예산이 `2h` → **`2h + 2w`** 로 는다. 이것이 *"한 머신에 여러 벨트로 입력"* 의 실체다: 한 머신이 **W·E·N·S 네 방향**에서 받는다. 대가는 모듈 높이(§14-5) |
| **TR13** | **홀수 대면 마지막 gap 은 한쪽만 쓴다**(2026-08-15 사용자). 가로 벨트 하나가 1대만 먹이고 높이가 `+g` 늘어난다. 짝을 다시 짜지 않는다 |
| **TR14** | **포트 방향은 언제나 부모/자식 방향이다** — 가로 벨트도 같다(2026-08-15 사용자). 상대가 **외부 상자**면 **전체 블루프린트 기준 가까운 면**을 바라본다. TR5 를 가로 레인까지 넓힌 것 |
| **TR11** | **gap 은 자리마다 다르고, 머신 *2대마다 하나*면 충분하다**(2026-08-15 사용자). 가로 벨트 하나가 위·아래 두 대를 먹이므로 `N` 대에 `⌈N/2⌉` 개면 된다 — 전부 여는 게 아니다. `layoutCluster(rowGap: number \| number[])` 가 **이미 배열을 받는다**(`clusterLayout.ts:51`: *"gap 은 자리마다 다를 수 있다"*).<br>4대·`h=3`: 전부 열면 21행, **2대마다 열면 18행**, 밀착이면 12행 |
| **TR12** | **가로 레인에 어느 품목을 올리나는 처리량만 본다**(2026-08-15 사용자). *"벨트 운반량과 머신 필요량, 이 둘을 감당하기만 하면 누가 오든 상관없다."* TR2 와 같은 정신 — **후보 중에는 우선순위가 없다** |
| **TR9** | **팔 처리량은 스칼라가 아니라 `깊이 → 처리량` 함수다** — `tp(d)` = `reach = d−1` 인 인서터의 **실측 처리량**(게임데이터). 세는 쪽과 놓는 쪽이 **같은 함수**를 쓴다. **어느 깊이가 빠른지 가정하지 않는다**(2026-08-14 사용자). 긴팔을 쓰는 레인의 처리량은 **긴팔의 처리량을 따른다** |
| **TR10** | **애매하면 머신이 100% 도는 쪽이다**(2026-08-14 사용자). 인프라(인서터·벨트)가 모자라면 **머신을 늘린다.** 자리나 포트를 아끼려고 머신을 굶기지 않는다. 두 배정이 둘 다 성립하면 그때 포트 수(§0 목표)가 가른다 |
| **D13** | **지하는 건너지는 쪽(세로 트렁크)이 들어간다**(§14-6). `entrance-straight` 때문에 건너는 쪽(가로 구간)은 코너에서 점프를 시작할 수 없다 |

# 이월 — R·D 읽는 법(옛 §0.1)

## 0.1 이 문서의 R·D 는 **분기문이 아니다** — 읽기 전에

> **여기 적힌 것을 하드코딩하면 매우 잘못된 설계다**(2026-08-15 사용자).
> **목적은 하나 — 모든 머신이 100% 가동한다.** 형태는 전부 그 목적을 이루려다 유도된 것이다.

```
목적    머신 m 의 줄 j 가 per_j 를 받는다/내보낸다.  전부, 항상
물리    팔은 좌석 타일에 앉는다.  reach 는 **고정 거리**라 집는 칸이 하나로 정해진다.
        팔 하나의 처리량은 **게임데이터가 준다**(가정하지 않는다)
자원    타일.  겹칠 수 없다
────────────────────────────────────────────────────────────────
유도    나머지 **전부**
```

| 형태 이름 | 실체 |
|---|---|
| 트렁크 · 부분 병합 · 다이렉트 | **벨트 구간 길이의 별명.** 배분기는 이 이름을 몰라야 한다 |
| **깊이(`d2`·`d3`)** | **축이 아니다 — 결과다**(§16). 축은 `(인서터, 그 팔이 집는 타일)` 쌍이다 |
| gap · N/S 면 | **좌석 타일이 모자랄 때 타일을 만드는 유일한 수단** |
| 모듈 크기 | 쓴 타일의 외접 사각형 |
| 팔 개수 `a` | `per ÷ (그 좌석에 실제로 앉는 팔의 처리량)` |

**구현이 답해야 하는 것은 하나다:**

```
"이 타일 배치에서 모든 머신이 100% 도는가.  아니면 타일을 어디서 더 만드나."
```

> `if (트렁크) … else if (fan-out) …` 같은 분기가 생기면 그 순간 이 모델을 배신한 것이다.
> **§13 의 TR1~TR13 은 규칙이 아니라 그 유도의 결과로 관측된 성질**이고,
> §14 의 여섯 단계는 분기 트리가 아니라 **유도 순서**다.
> 2026-08-13 롤백의 ★("구현의 *어떻게* 를 의도로 착각하지 않는다")를 **내 문서에도 적용한다.**
