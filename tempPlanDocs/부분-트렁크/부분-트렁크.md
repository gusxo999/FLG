# 부분 트렁크 — **계산을 계획으로 올린다**

> 상태·읽을 것·범위는 같은 폴더의 `CLAUDE.md`.
> **모델은 여기 없다** — `docs/auto-layout/module/trunk-assignment.md` 에 있다.

## §0 한 문장

> 자리를 정하는 일 중 **계산으로 풀리는 것**이 지금 *"앉혀 보고 안 되면 다시"* 로 일어난다.
> 그것을 **계획**으로 올리고, 남은 층은 **기록**과 **덧셈**만 하게 한다.

## §1 세 층 — **계획 · 배치 · 방출**

이름과 경계는 **코드의 사실**이라 `docs/` 에 있다 —
`docs/auto-layout/module/module-planning.md` **§3**(세 층 · 어느 필드를 어느 층이 정하나).

## §2 지금 어긋난 자리 — **계획이 할 일이 배치에서 일어난다**

```
계획이 정해야 할 것    배치가 실제로 하는 일
─────────────────────────────────────────────────────────────
g                     붓기가 확정하고, 배치는 못 바꾼다        ← **이 계획의 몫**
```

**`g` 는 계산으로 풀린다.** 팔 수가 `g` 와 무관하므로(머신은 `g` 가 얼마든 자기 몫을 다
받는다) 수요·처리량·레인만 세면 답이 나온다. 행도 좌표도 안 본다.

> **2026-09-03 정정 — 여기 `face`·`laneDepth` 가 함께 적혀 있었다.** *"셋 다 계산으로
> 풀린다"* 고 했는데 **틀렸다**: 인용한 식(`Σ⌈per ÷ tp⌉ ≤ h`)은 **좌석만** 말하고, 어느
> 레인이 **어느 행 구간에서** 비었는지는 안 알려 준다. 면·레인은 **행이 있어야** 답이
> 나오므로 배정의 몫이다(`계획-배정-개념정리` **C1**). 그 오해 위에 ⑤-3 이 얹혀 있었고,
> 함께 지웠다 — 이 계획의 한 문장은 처음부터 **`g` 하나**였다(폴더 `CLAUDE.md`).

> **2026-09-02 — 아래 절은 첫 줄(`g`)에 한해 역사다.** 인용된 코드
> (`planClusterPorts` · `supply.mode` · `bundle: supply.mode !== "tap"`)는 **지금 없다** —
> ⑤-1·⑤-2 와 지도 A 삭제가 지웠고, `g` 는 `planBundles` 가 줄마다 낸다.
> **`face`·`laneDepth` 두 줄은 그대로 유효하다**: 진단이 `overflow` 문자열에서
> `LaneShortage` 로 이름만 바뀌었을 뿐, *앉혀 보고 무르는* 구조는 `tryLinkFace` 에 남아 있다.

### 그리고 그 계산은 **이미 코드에 있다**

`planClusterPorts` 가 바로 그것이다 — 면×레인 슬롯을 만들고, 줄마다 팔을 세어 넣고,
자리가 없으면 **어느 줄이 넘쳤는지 이름까지** 안다:

```ts
if (rowsLeftOf(pool[k].side) < arms) continue;     // 좌석이 모자란 슬롯은 건너뛴다
overflow ??= `${line.role}:${line.name}`;          // **어느 줄이 넘쳤는지 안다**
```

**그런데 그 산출을 버린다.** `PlannedLine[]` 은 아무도 안 읽고, 남는 것은 모듈 하나의
낱말(`tap`/`direct`) 하나다.

> **그래서 ⑤는 "판정을 없애는 것"이 아니다.** 계산은 옳고 **산출의 낟알이 틀렸다** —
> 줄마다 나와야 할 답이 모듈 하나로 접혀 있다.

### 그래서 이것이 **부분 트렁크와 무슨 상관인가**

> **한 줄이 gap 을 필요로 하면, 그 모듈의 *모든* 줄이 부분 트렁크를 못 쓴다.**

```ts
// planModulePorts — 지금 코드
bundle: supply.mode !== "tap" ? 1 : undefined
//      ^^^^^^^^^^^^^^^^^^^^^^^^^^^  direct 면 **모든 줄이 g = 1**
```

`direct` 가 되는 조건은 **한 줄이라도 못 앉으면**이고, 그러면 `bundle: 1` 이 유도값을
**덮어쓴다.** 즉 **③(부분 트렁크)은 넣었지만 실제로 도는 것은 `tap` 인 모듈뿐이다.**

```
모듈에 줄 넷, 머신 6대.  그중 **철판 하나**가 좌석에 안 들어간다

지금        모듈 전체 direct  →  **네 줄 모두 g = 1**  →  포트 4 × 6 = **24개**
원하는 것   철판만 g = 1(gap 으로), 나머지 셋은 g = 유도값(예: 3)
            →  포트 6 + 2 + 2 + 2 = **12개**
```

**한 줄의 사정이 나머지 셋의 형태를 망친다.** 그리고 그 한 줄이 누구인지 계산은 **이미
알고 있다** — 이름까지:

```
계산이 아는 것   "**입력:철판**이 넘쳤다"        overflow ??= `${role}:${name}`
코드가 쓰는 것   "이 모듈은 direct 다"           ← 이름이 접혀서 사라진다
```

**그 이름 하나면 *"철판만 `g=1`, 나머지는 유도값"* 이 된다.**

> 앞서 *"⑤는 ③의 전제가 아니었다"* 고 적은 것은 **절반만 맞았다** — ③을 **넣는** 데는
> 전제가 아니었지만, ③이 **실제로 도는** 데는 전제다.

### 2026-09-01 — ④(`lanes-exceed-capacity`) 를 먼저 지우려다 **순서가 뒤집혔다**

조사가 낸 삭제 순서의 1번(*④ 는 낡은 상한이다*)을 **실제로 해 보고 되돌렸다.**
먼저 J1 을 코드로 확인했다 — `laneClear` 는 **그 깊이의 칸만** 본다(면당 줄 수를 세는
가드는 없다). 그래서 *"행이 안 겹치면 나눠 쓴다"* 는 참이다.

그런데 게이트를 지우자 **15개가 깨졌다**(기준선 2 → 17). 깨진 것은 임의가 아니라
아래 *"깨진 13개"* 의 갈래 A·B·C·D 그대로였고, 가장 눈에 띄는 것은 갈래 A 다:

```
battery(2) · reach{1} · 아이템 3줄        기대 unroutedLines = 0
실제   copper-plate 가 **못 앉았다**
```

**이유 — 관통이 레인을 독점한다.** 예전엔 게이트가 모듈을 통째로 `direct` 로 떨어뜨려
세 줄이 전부 `g=1` 이 됐고, `g=1` 줄은 머신마다 **한 행씩**만 먹어 셋이 W 의 한
레인을 나눠 썼다. 게이트를 줄마다로 풀자 넘치지 않은 두 줄이 `g = N` 을 되찾았고,
관통 그룹은 `beltRowSpan` 이 `[최소행, 최대행]` 하나라 **사이 행까지 통으로** 먹는다
→ 레인 독점 → 셋째 줄은 gap 으로도 못 간다(`machinesOn !== 1`).

> **모델이 낡았던 것이 확인됐다.** `trunk-assignment.md` §4 가 *"`g` 는 상한에 안
> 들어간다 — 약분된다"* 라고 적고 있었다. 약분은 *한 구간이 `g×h` 행을 먹는다* 를
> 전제로 하는데, 실제로 먹는 것은 **팔이 앉은 행**이다. 상한을 고쳤다 →
> `docs/auto-layout/module/trunk-assignment.md` **§4.1**(2026-09-01 정정).

**그래서 삭제 순서가 바뀐다:**

```
조사가 적은 순서   ④ 지우기  →  ① 좌석 판정 옮기기  →  ② 이름표  →  ③ + 삭제
실제 순서        ①이 먼저다.  ④ 는 그 다음이다
```

이유는 하나다 — ④ 를 지우면 *"이 줄은 `g=1`"* 을 정하는 사람이 없어지는데,
**그 판단은 레인 예산을 봐야 하고 레인 예산은 면을 알아야 한다.** 면을 정하는 것이
바로 ⑤-2 다. 즉 ④ 삭제는 ⑤-2 의 **앞**이 아니라 **뒤**다.

### 그래서 ⑤-2 가 먼저 답해야 할 것 — **맞바꿈이 거기 있다**

같은 품목 수를 두 가지로 담을 수 있고, 모델은 둘 중 하나를 고를 근거가 없다:

```
품목 3 · R = 1 · N = 2

(가) 전부 g = 1     레인 하나를 셋이 나눠 쓴다     포트 6 · gap 안 벌림   ← 오늘
(나) 둘은 g = 2    레인 둘 독점, 셋째는 gap 으로    포트 4 · gap 이 벌어짐
```

**이것이 바로 2026-08-30 에 범위 밖으로 둔 그 손잡이다** — *"`g` 를 늘릴지 모듈을
키울지는 사용자가 고른다"*. 그래서 ⑤-2 는 손잡이를 만드는 일이 아니라
**기본값을 문서에 박는 일**이다. 기울기는 (가) — 오늘의 동작이고, 사용자가
*"머신 100% 가동이 최우선"* 이라 했는데 (나)는 자리가 모자랄 때 **굶는 줄을 만들기
쉽다**. 다만 이건 **정해야 하는 것**이지 모델이 유도해 내는 것이 아니다.

### 2026-09-01 — ⑤-2 **레인 예산이 `g` 를 정한다**

`planBundles`(`planner/module/laneBudget.ts`)가 붓기 **앞에서** 줄마다 `g` 를 낸다.
모델은 `trunk-assignment.md` §4.2. 옛 경로(`supply.mode` / `supply.overflowed` 로 내리기)는
지웠다 — 그쪽은 **레인을 안 셌다.**

**세 번 틀리고 세 번 좁혔다.** 셋 다 실측이 가르쳤고, 셋 다 규칙을 *느슨하게* 만든 게
아니라 **낟알을 바꿨다**:

```
① 면마다 세다 → 모듈 전체로     electric-motor 4줄이 E 두 레인만 보고 둘을 내렸다.
                                실제로는 W 의 남은 레인으로 넘어가 넷 다 관통이 선다
② 유체 면을 빼다 → 넣는다        plastic-bar 3줄을 W 로 몰아 둘이 헛되이 내려갔다.
                                넘침 단계가 유체 면을 되찾아 오므로 그 레인은 실재한다
③ 예약을 그 면만 → 전역          일곱 줄 스펙에서 포트 하나가 사라졌다. `g=1` 줄은
                                좌석이 넘치면 **어느 면으로든** 밀리는데, 밀려간 면의
                                레인을 관통이 먹고 있으면 갈 곳을 잃는다
```

**검증: 타입 0 · 54파일 654테스트, 기존 실패 2건뿐(회귀 0).** 새 테스트 7개가 규칙을
잠근다(`laneBudget.test.ts`) — `R=1` 의 경계(kr-sand 꼴 둘 다 관통 · 셋이면 전부 다이렉트),
`R=2` 넷이 전부 관통, **부분 트렁크 생존**(처리량이 한 줄을 `g=1` 로 만들어도 나머지는 관통),
내리는 순서, 링크가 먹은 레인 빼기, 레인 0인 면은 예약도 안 함.

> **덤 — `InsertingDecisionResult.overflowed` 를 이제 아무도 안 읽는다.**
> ⑤-1 이 편 그 산출을 레인 예산이 대신했다. ④ 를 지울 때 함께 사라진다.

### 2026-09-02 — ④ 게이트 삭제 + **죽은 코드 76줄**

`planClusterPorts` 의 앞선 `slotsNeeded > W+E` 게이트를 지웠다. 2026-09-01 에 같은 일을
먼저 시도했을 땐 15개가 깨졌는데, 이번엔 **한 개**가 깨졌고 그건 게이트 자체를 잠근
테스트였다. 차이는 하나다 — **그 사이에 `g` 의 주인이 바뀌었다**(⑤-2).

진단은 `takeSeat` 이 사유를 값으로 들어 지킨다:

```
"lane"  슬롯이 아예 없다          →  lanes-exceed-capacity + reach 목록 + 넘친 줄 이름
"seat"  슬롯은 있는데 팔이 안 든다  →  seats-exceed-capacity + 넘친 줄 이름
```

그리고 **`splitIntervals`(옛 `c = 2` 부분 트렁크 시도)를 함께 지웠다** — 조사가 짚은 대로
죽은 코드였다(`planModulePorts` 가 `rest.lines` 를 `[]` 로 버린다). 그것만 만들던
`PlannedLine.machineRange`·`exitEnd` 와 `EPS_K` 도 따라 사라졌다. **76줄 삭제.**

노출 끝면(N/S)이 셈에 들어온 것이 유일한 동작 변화다 — 배정 쪽이 원료 입력에게 이미
주는 완화라, 빼 두면 **두 지도가 다른 수를 센다.** 그 테스트를 새 사실로 다시 썼다.

검증: 타입 0 · 54파일 655테스트 — 기존 실패 2건뿐, 회귀 0.

### 2026-09-02 — **지도 A 를 지웠다**

사용자가 모순을 짚었다 — *"진단 기능만 남았다면 다음 흐름을 결정할 순 없어야 한다."*
층을 갈라 보니 **둘 다 참**이었다:

```
배치 흐름    지도 A 에 분기가 0 이다      (방출 통합 2026-08-16 · g 는 레인 예산 2026-09-01)
사용자 흐름  지도 A 의 **문장**이 다음에 갈 위저드 단계를 정했다   ← 모순은 여기
```

그래서 처방을 **사실 옆으로** 옮겼다(`dc57c4f`) — 사다리 기록이 있으면 'inserter',
부을 수 없었으면 `unpourableFix`, 수량을 모르면 **비운다**. `why.includes(...)` 세 개가
사라졌고, 그러자 `supply` 를 읽는 비테스트 코드가 **0** 이 됐다.

그리고 지웠다(`22bf95e`) — `clusterPortPlanner.ts` **978줄 → 238줄**, 테스트 848줄.
남은 것은 낱말(`IoLine`·`PlannedLine`·`SupplyCapacity`)과 산술(`requiredInserterCount`·

## 왜 픽스처가 `direct` 를 만들었나 — 여기 있다

```ts
inserters: [{ entityName: "inserter", reach: 1, throughput: 0 }],
//                                                ^^^^^^^^^^^^^ **0**
belts: [{ entityName: "transport-belt", throughput: 15 }],
```

**팔 처리량이 `0`** 이라 `insertingPlanner` 가 팔 수를 못 세고 `direct` 로 떨어진다.
즉 이 픽스처는 *"레인이 모자란 상황"* 을 **팔 처리량을 지워서** 만들었다.
`g` 유도(`⌊벨트 ÷ per⌋`)는 그 결핍을 안 본다 — 벨트만 본다. **그래서 갈라졌다.**

## 결론 — **13개를 관문으로 쓰지 않는다**

```
A  → 새 테스트 1개:  레인이 모자란 스펙에서도 `unroutedLines === 0`
B  → 새 테스트 1개:  머신마다 모든 줄에 팔이 붙는다
C  → 새 테스트 2개:  좌석이 **차면** gap 으로 · **안 차면** 안 벌어진다   ← **⑤-b 의 관문**
D  → 픽스처만 고친다. 의도는 안 건드린다
```

**⑤-b 의 관문은 C 의 둘이다.** 나머지는 의도를 옮기거나 픽스처를 고치는 일이다.

## 이 설계가 **안 건드리는 것**


> **“실측으로 굳었다” 란** — 그 규칙의 근거가 **기전이 아니라 관측**이라는 뜻이다.
> 주석이 날짜와 증상을 적고 있다:
>
> ```
> 2026-08-05  이 순서를 븠뜨렸더니 x 입력이 W 로 밀렸고 **납품 1건이 실패**했다
> 2026-07-12  kr-components 가 W 로 밀려 모듈 위를 가로지르는 벌트가 생겼고,
>             그것이 W 포트 둘의 N 탈출로를 막아 **반출 skip 3건**이 났다
> ```
>
> 즉 *"왜 그 순서여야 하는가"* 를 코드로 **재유도할 수 없고**, 실물을 돌려 실패를 본
> 기록만 있다. 그래서 안 건드리는 것이고 — **이건 소극적인 이유이지 좋은 이유가 아니다.**
> 바꾸려면 다시 재야 한다.

```
· ②의 처리 순서(자식-공급 먼저, 원료 나중)      실측으로 굳었다
· ④의 면 순서(반대 면 → 노출 끝면 → gap)        실측으로 굳었다
· 링크 줄의 경로                                이미 seatLinkEdge 가 같은 일을 한다
· gap 의 `machinesOn !== 1`                     그 능력은 별개 단계다(⑤ 이후)
```

### 다음이 같은 데를 안 밟게

1. **기존 구현의 "어떻게"를 의도로 착각하지 않는다.** 의도는 *"무엇을 이루려 했나"* 이고,
   깊이·레인·stagger 는 *"직선으로 하기로 했을 때 따라온 것"* 이다.
2. **모델 없이 검증을 늘리지 않는다.** 잴 것이 남의 모델뿐이면 계측이 아무 말도 안 한다.
3. **"산출물이 안 바뀐다"를 합격선으로 쓰지 않는다.** 기준선이 미완성이면 아무것도 증명하지 않는다.

| **TR1** | **`g_max = min(k, N)` 는 처리량이 준 *상한*이고, 실제 `g` 는 *자리*가 정한다**(2026-08-16 정정).<br>예전엔 *"항상 최대로 묶는다"* 라는 **값**으로 적었는데, 그러면 §9-마의 사다리가 지워진다. `g` 를 낮추는 것이 곧 **레인을 아끼는 것**이다 — 관통은 레인을 통째로 먹고 구간은 행만 먹는다. 그래서 *"포트를 아낀다"* 와 *"레인을 아낀다"* 는 **같은 축의 반대 방향**이고, 어디에 설지는 자리가 답한다.<br>`g_max` → 관통 · 낮추면 구간 · `g=1` 다이렉트 · 그래도 모자라면 gap · 그래도면 정직한 실패.<br>**탐색이 아니다** — 그 면의 관통 후보 수와 레인 수를 세면 한 번에 나온다. 쪼갬은 앞에서부터 `g` 대씩, 나머지는 뒤(4대·k=3 → **3+1**) |

| **TR3** | **같은 면의 품목들은 머신 안 행 offset 을 하나씩 나눠 갖고, 얕은 레인일수록 흐름 반대쪽 끝으로 밀린다**(= stagger). **모듈을 안 키우고 머신 안 여유 행 `h − a` 가 흡수한다** |

| **TR5** | **포트의 *선호* 면은 밖(부모/자식 방향)이 준다**(2026-08-14 사용자). 트렁크가 면을 **만들지는** 못하지만, 좌석 예산이 모자라면 **반대 면으로 분산한다**(TR8). 면은 강제가 아니라 선호다 |

# 이월 — R·D 읽는 법(옛 §0.1)

## 0.1 이 문서의 R·D 는 **분기문이 아니다** — 읽기 전에

> **여기 적힌 것을 하드코딩하면 매우 잘못된 설계다**(2026-08-15 사용자).
> **목적은 하나 — 모든 머신이 100% 가동한다.** 형태는 전부 그 목적을 이루려다 유도된 것이다.

```
목적    머신 m 의 줄 j 가 per_j 를 받는다/내보낸다.  전부, 항상
물리    팔은 좌석 타일에 앉는다.  reach 는 **고정 거리**라 집는 칸이 하나로 정해진다.
        팔 하나의 처리량은 **게임데이터가 준다**(가정하지 않는다)
자원    타일.  겹칠 수 없다
────────────────────────────────────────────────────────────────
유도    나머지 **전부**
```

| 형태 이름 | 실체 |
|---|---|
| 트렁크 · 부분 병합 · 다이렉트 | **벨트 구간 길이의 별명.** 배분기는 이 이름을 몰라야 한다 |
| **깊이(`d2`·`d3`)** | **축이 아니다 — 결과다**(§16). 축은 `(인서터, 그 팔이 집는 타일)` 쌍이다 |
| gap · N/S 면 | **좌석 타일이 모자랄 때 타일을 만드는 유일한 수단** |
| 모듈 크기 | 쓴 타일의 외접 사각형 |
| 팔 개수 `a` | `per ÷ (그 좌석에 실제로 앉는 팔의 처리량)` |

**구현이 답해야 하는 것은 하나다:**

```
"이 타일 배치에서 모든 머신이 100% 도는가.  아니면 타일을 어디서 더 만드나."
```

> `if (트렁크) … else if (fan-out) …` 같은 분기가 생기면 그 순간 이 모델을 배신한 것이다.
> **§13 의 TR1~TR13 은 규칙이 아니라 그 유도의 결과로 관측된 성질**이고,
> §14 의 여섯 단계는 분기 트리가 아니라 **유도 순서**다.
> 2026-08-13 롤백의 ★("구현의 *어떻게* 를 의도로 착각하지 않는다")를 **내 문서에도 적용한다.**
