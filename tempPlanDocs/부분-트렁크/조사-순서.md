# 조사 · 순서 — 먼저 온 그룹은 어디를 먹나

> **사실 문서** — 계획이 아니라 조사 결과다. 계획은 `간선-배정.md` — Step 6(순서 규칙)의 근거가 여기 있다.

## §1 조사 — 먼저 온 그룹과 늦게 온 그룹은 **어디를 먹나**

배정은 `groups.forEach` 다. 먼저 온 그룹이 `commitLinkFace` 로 칸에 도장을 찍고, 늦게 온
그룹은 **남은 자리**를 본다. 자리마다 규칙이 다르다:

| 자원 | 규칙 | **먼저** | **늦게** |
|---|---|---|---|
| **레인**(`laneDepth`) | 후보를 팔 적은 순 → **얕은 순** | **`d2`**(짧은 팔) | `d2` 가 자기 구간에서 막혔으면 **`d3`**(긴 팔) |
| **좌석**(`slotIndex`) | `freeSeatRows(...).slice(0, k)` — **빈 칸을 앞에서부터** | 머신 면의 **위쪽** 칸 | **아래쪽** 칸 |
| **기둥 끝**(`portEnd`) | `["N","S"].find(안 찼음)` | **N** | S → 셋째는 **옆**으로 |
| **면**(`face`) | 선호 면이 차면 넘침 | 선호 면(W/E) | **gap**(N/S) → 그다음 **실패** |

> **레인은 "찼다/비었다"가 아니라 "내 행 구간이 겹치나"다.** 행이 안 겹치는 두 그룹은
> 같은 `d2` 를 **나눠 쓴다**(벨트가 자기 좌석 구간만 덮고 끝에서 꺾으므로). 그래서 짧은
> 줄 여럿은 `d2` 에 나란히 앉을 수 있다.

### 그림 — 지금 일어나는 일

```
             d1(좌석)   d2        d3
머신 0..29  │ ● ● ●  │ ▓▓▓▓▓  │        │   ① 짧은 줄 A 가 먼저 앉는다
            │        │   ◄    │        │      그 포트가 d3 에 **못**을 박는다
머신 30..59 │ ● ● ●  │ ▓▓▓▓▓  │        │   ② 짧은 줄 B
            │        │   ◄    │        │
머신 60..89 │ ● ● ●  │ ▓▓▓▓▓  │        │   ③ 짧은 줄 C
            │        │   ◄    │        │
                        ↑         ↑
                 d2 가 통째로   d3 는 못 셋에
                 먹혔다        찍혀 있다
            → 관통 줄 D(머신 0..89 연속 필요)가 **갈 곳이 없다**
```

**실측(`electronic-circuit`)이 정확히 이 모양이었다** — `copper-cable` 토막 4개가 `d2` 를
`[0,87] [90,177] [180,267] [270,297]` 로 먹고 `d3` 의 행 `0·90·180·270` 에 못을 박았다.
`stone-tablet`(머신 90대 관통)이 나중에 와서 `d2` 는 통째로 막히고 `d3` 는 행 **90·180**
두 칸에 막혔다 — **268행짜리 레인이 두 칸 때문에 못 쓰였다.**

### 늦게 오면 **비싸진다** — 대가가 셋이다

```
① 깊은 레인 = 긴 팔 = 처리량 ↓   (실측: reach-1 10/s → reach-2 3.6/s)
                    → 같은 양을 나르려면 **팔이 더 많이** 필요
                    → **좌석을 더 먹는다** (좌석은 유일하게 못 늘리는 자원)
② 못이 는다        — 얕은 레인 줄의 포트가 깊은 레인의 못이다. 줄이 조각날수록 못이 는다
③ 넘침 → gap      — 모듈이 **세로로 벌어진다**(gapRowsFromPlans)
```

**그래서 순서가 공짜가 아니다.** 늦게 오는 것은 그냥 "나중"이 아니라 **더 비싼 자리**다.

## §2 그래서 무엇을 얻나 — 순서를 정하는 이유

**자유도가 낮은 줄을 먼저 앉히면 못이 애초에 안 생긴다.**

| 줄의 성질 | 자유도 | 늦게 오면 |
|---|---|---|
| **관통**(머신 전부, 연속 구간 필요) | **가장 낮다** — 조각난 레인에 **못 앉는다** | 갈 곳이 없다 → 사다리 → 되먹임 |
| **구간**(머신 몇 대) | 높다 — 조각 **사이**에 앉을 수 있다 | 대개 앉는다 |
| **팔이 많은 줄** | 낮다 — 좌석을 많이 먹는다 | 깊은 레인 → 팔이 더 늘어남(악순환) |

이건 짐싸기의 오래된 규칙(**큰 것부터**)과 같다. 그리고 **결정 1(되먹임 제거)의 실질적
경로**다 — 못이 없으면 사다리가 필요 없고, 사다리가 없으면 되먹임 ②가 없다.

# 조사 · ⑤ 모듈 단위 tap/direct 모드 (2026-08-30)

## `supply.mode` 는 무엇인가

`insertingPlanner` 가 모듈 하나마다 내는 **한 값**이다:

```ts
type InsertingDecisionResult =
  | { mode: "tap";    plan: { ok: true; lines: PlannedLine[] } }
  | { mode: "direct"; reason: string }
```

## 언제 `direct` 가 되나 — **넷, 그리고 전부 "하나라도 안 되면"**

```
① complex: fluid-handled-by-generateModule   유체 줄이 있는데 fluidTrunk 가 없다
② complex: no-inserter                        팔을 모른다
③ complex: seats-exceed-capacity (역할:품목)   **줄 하나**가 두 면 어디에도 못 앉았다
④ belt: demand>beltCap (품목)                  **줄 하나**의 수요가 벨트 한 줄을 넘는다
```

**③과 ④는 실패한 줄의 이름을 사유에 싣는다** — 즉 **어느 줄이 문제인지 알면서도** 모듈 전체를
떨어뜨린다.

```ts
// ③ — 첫 실패 하나가 overflow 에 남고
overflow ??= `${line.role}:${line.name}`;
if (overflow) return { ok: false, complex: true, reason: `seats-exceed-capacity (${overflow})` };

// ④ — 첫 실패에서 즉시 반환
if (rate > capacity.beltCapacity) return direct(`belt: demand>beltCap (${planned.line.name})`);
```

> **한 줄이 안 되면 그 모듈의 모든 줄이 다이렉트가 된다.** 그것이 ⑤가 말하는 문제다.

## 그런데 — **기하를 바꾸는 소비처가 하나뿐이다**

`supply.mode` 를 읽는 곳을 전수했다:

| 읽는 곳 | 무엇에 쓰나 | |
|---|---|---|
| `planModulePorts.ts` `perMachine: supply.mode !== "tap"` | **`g` 를 `1` 로 할지 `N` 으로 할지** | ← **유일한 기하 소비처** |
| `clusterModule.ts` (`:303 → :336 · :407`) | `GeneratedModule.supply` 로 **그대로 내보낸다** | 진단 |
| `moduleWizard.ts` | `unrouted-lines` 이슈 문장의 사유 | 진단 |
| `moduleTransform.ts` (`:168 · :285`) | 모듈을 옮길 때 필드 보존 | 통과 |

**즉 모드가 기하에 남기는 것은 `perMachine` 하나뿐이다.** 코드 주석도 그렇게 적었다:

> *"모드가 남기는 것은 **쪼개기 여부** 하나뿐이다: 탭이면 묶은 그룹(벨트 하나가 전 머신),
> 다이렉트면 머신마다 하나. 그 둘은 `g = N` 과 `g = 1` 이라는 **같은 축의 두 끝**이다."*

## `perMachine` 이 실제로 하는 일 — **붓기의 낟알**

```ts
const batches: number[][] = opts?.perMachine
  ? Array.from({ length: n }, (_, i) => [i])       // 머신마다 따로 붓는다 → g = 1
  : [Array.from({ length: n }, (_, i) => i)];      // 한꺼번에 붓는다     → g = 상한
for (const batch of batches) made.push(...pour(batch));
```

**`g` 를 정하는 것이 아니라 "몇 명씩 묶어서 붓느냐"를 정한다.** 그리고 붓기(`createLinks`)는
받은 묶음 안에서 **언제나 최대로** 채운다. 그래서:

```
batch = [전 머신]        →  createLinks 가 벨트·좌석 상한까지 채운다  →  g = min(k, N)
batch = [0],[1],…,[n-1]  →  머신마다 따로라 섞일 수가 없다            →  g = 1
```

**`1 < g < N` 을 내려면 `batches` 를 `g` 명씩 끊으면 된다.** 지금은 그 두 극단만 만든다.

## 그래서 ⑤의 실제 크기

```
바꿀 것   ① insertingPlanner 가 **모듈 판정**을 그만두고 **줄마다** 판정한다
          ② planModulePorts 가 `perMachine`(모듈 하나의 불리언) 대신
             **줄마다의 낟알**을 넘긴다
          ③ externalLineGroups 의 `batches` 가 그 낟알을 받는다

안 바뀔 것 방출기 · 배정기 · 좌석표 — **아이템 줄은 이미 갈래가 하나다**
           (`clusterModule` *"아이템 줄 방출 — 갈래가 없다"*)
```

**그리고 ③이 곧 ③(부분 트렁크)이다** — `batches` 가 낟알을 받게 되면 `g` 명씩 끊는 것이
같은 자리에서 된다. ⑤와 ③은 **같은 함수의 앞뒤**다.

## 걸림돌 — 하나 있다

`insertingPlanner` 의 `tap` 산출은 **`PlannedLine[]` 한 벌**이고, 그것이 트렁크 기하
(`buildTrunkContext` · `emitTrunkPipe`)의 입력이다. 줄마다 모드를 갈면 **한 모듈 안에
탭 줄과 다이렉트 줄이 섞이고**, `plan.rest.lines` 가 그 둘을 함께 담아야 한다.

```
지금   supply.mode === "tap"  →  plan.rest.lines = 탭 줄 전부
                                 아니면          →  rest.lines = []  (전부 링크 경로로)
바꾼 뒤 rest.lines 에 **탭인 줄만** 담기고, 나머지는 링크 경로로 간다
```

**이것이 ⑤의 진짜 일이다.** 나머지(②③)는 인자를 넓히는 것이다.

> 유체 줄은 영향이 없다 — 언제나 `pipePlanned` 로 따로 가고 인서터를 안 쓴다.
