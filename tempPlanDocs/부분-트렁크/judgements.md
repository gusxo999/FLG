> 이고, 이 문서는 그 모델이 **아직 답하지 못하는 자리**다.
>

## J1 — `L_f = |ℛ|` 을 일반 `ℛ` 에 대해 증명하지 않았다

**무엇이 미결인가.** §1 은 면당 동시 벨트 레인 수를 `R = |ℛ|` 로 놓는다.
`R = 1, 2, 3` 은 `(s, r)` 짝을 **손으로 열거**해 확인했지만 임의 `ℛ` 에 대한 증명이 없다.
느슨한 상한(`k ≤ 2R − 1`)만 나와 있어 `R=2` 에서 3 — 열거로 얻은 2 보다 헐겁다.

**착수 조건 — 입력의 성질**

```
서로 다른 reach 가 4종 이상인 인서터 집합이 입력으로 들어올 수 있게 되면 착수.
그전까지는 **열거표가 곧 증명**이다(1·2·3 을 다 셌다).
```

**코드 역참조 — 아직 안 달았다.** 달 자리는 `module/clusterLayout.ts:90`(`columnTapCapacity`).
부모 폴더 정책상 **코드 변경 0** 을 지키느라 보류했고, 착수하는 단계에서 단다.

> **부수 발견 (미결이 아니라 사실):** `columnTapCapacity` 의 **수는 맞고 주석의 이유는 좁다.**
> 주석은 *"좌석은 d1"* 을 전제하지만 `(s=2, r=2) → belt d4` 배열도 성립한다.
> 같은 `R` 을 **다른 깊이 집합**으로 살 수 있고, **유체 파이프가 `d2` 를 먹은 면**에서만
> 차이가 드러난다.

## J4 — 격자로 가는 경계 — **이 계획의 범위 밖** (2026-08-15 사용자)

`R = 1` 이거나 품목이 아주 많아 gap 을 여러 개 열어야 할 때, 기둥을 유지할지 격자로 갈지가
갈린다. **이 계획에서는 결정하지 않는다.** 기둥 + gap 두 축으로 감당되는 데까지 간다.

**착수 조건**

```
이 계획이 끝난 뒤, 기둥 + gap 으로 100% 가동을 못 만드는 입력이 나오면 착수.
그때 새 계획으로 옮긴다.
```

**전제:** 기둥 + gap 의 한계가 `레인 2R + Σ가로줄` · `좌석 2h + 2w` 라는 것. §5·§11.

## J8 — 유체 레시피 UI 비활성화 — **이 브랜치 밖** (2026-08-17 사용자)

**결정:** 지하 파이프를 안 고르면 유체 처리 레시피를 **선택하지 못하게 막는다**(UI 비활성화).
그러면 `no-underground` 는 도달 불가능해지고, 케이스 B 가 사라진 근거가 완성된다.

**미룬다.** UI 는 다른 계층이고 지금 하면 범위가 두 배가 된다.

```
planner 는 그 게이트를 **전제로 삼지 않는다** — `no-underground` 거절 사유를 코드에 남겼다.
UI 가 새는 날 조용히 깨지는 것보다 정직한 거절이 낫다.
```

착수 조건: 트렁크 벨트 경로 모델이 끝나고 초록이 된 뒤.

## J11 — 같은 품목의 **외부 접점을 하나로** (삭제된 두 계획의 목적)

**목적만 살아남았다.** `공급원-모듈화`(더미 모듈 승격 + 트리→DAG)와 `공급-버스`(테두리에서
합치기)가 같은 목적을 다른 수단으로 풀려 했고, 2026-08-18 에 **둘 다 삭제**됐다.

```
문제   n0 이 iron-plate 필요 → 외부 상자 A       사용자가 **두 곳에** 철판을 넣는다
       n1 도 iron-plate 필요 → 외부 상자 B
목적   같은 품목은 **한 곳에서** 받는다 — 사용자가 체감하는 문제다
```

**수단 둘이 다 기각된 이유**

| 수단 | 기각 사유 |
|---|---|
| 더미 모듈 승격 | **외부 접점을 하나도 안 줄인다**(2026-08-18 확인). 상자가 모듈이 될 뿐 개수가 그대로다 |
| 트리 → DAG | `layoutY`(tidy-tree)가 트리를 전제한다. layered graph drawing 은 다른 종류의 문제 — 목적에 비해 너무 크다 |
| 테두리에서 합치기 | 상자는 이미 테두리에 있다. 부족한 것은 위치가 아니라 **개수**이고, 합치려면 결국 1:N 이 필요하다 |

**착수 조건 — 입력의 성질**

```
한 트리에서 **같은 품목의 외부 상자가 2개 이상** 나오는 경우가 실제로 흔한가.
concrete 트리(raw 5)에서는 전부 다른 품목이라 이 문제가 안 났다.
겹치는 트리가 나오면 그때 수단을 다시 고른다 — 지금 고르면 근거가 없다.
```

**전제:** 면까지 인도(§19.4 새)가 끝나면 외부 상자가 표면에 서므로, 합치기의 **기하 조건이
쉬워진다.** 그 뒤에 재는 것이 싸다.

## J12 — 지하벨트를 모듈 안쪽 트렁크 계획이 부르는 자리 (`1-지하벨트` 에서 옮김)

**조사는 끝났다. 만들 것이 거의 없다.**

```
간섭:  같은 blockGroup ∧ 같은 axis ∧ 같은 line  →  구간이 strict disjoint
       그 외(축 다름 · line 다름 · 티어 다름)   →  전부 무해
방향:  점프는 지상 도착 방향과 같은 방향만 (입구 칸에서 꺾을 수 없다)
탭:    **지하 구간 위에서는 인서터가 못 먹인다** — 그래서 탭 구간은 반드시 지상
blockGroup 은 벨트 프로토타입 자체다 — 티어를 여럿 고르면 지하 자유도가 그만큼 는다
```

간섭 규칙·자료형·입구 방향 제약·방출이 **전부 구현돼 있다**
(`planner/containerRouting.ts` 의 `isJumpAllowed`·`entrance-straight`·`startJump`/`endJump`).
**없는 것은 "모듈 안쪽 트렁크 계획이 그것을 부를 자리" 하나다.**

> 선례: `docs/auto-layout/channel/fluid-underground-crossing.md` §1 —
> *"페어링 모델 설계가 아니라 **있는 규칙을 장부에서도 부르기**"*.

**착수 조건:** 면까지 인도(§19.4 새)에서 **관통 레인을 가로질러야 하는 경우**가 실제로 나오면.
그때 지상 빈 행이 없으면 지하가 유일한 답이고, 부를 자리가 거기다.
지금 부르면 쓸 데가 없다 — 관통은 기둥 끝으로 나가므로(2026-08-17) 대개 안 마주친다.

## J13 — 링크가 자리를 잃었을 때 **무엇을 내주나** (2026-09-02)

**무엇이 미결인가.** 링크 줄에 `g` 를 **받을 자리**는 생겼다(`edgeLinkGroups(…, bundle?)` ·
[EdgeBundle], `planner/link/edgeLinks.ts`). 그런데 **아무도 그 값을 주지 않는다.** 줄 사람
(레인 예산 [planBundles])을 붙이려면 아래 셋 중 하나를 먼저 골라야 한다.

**먼저 확정된 기전 하나 — 부분 트렁크는 레인을 안 돌려준다.**

```
g > 1   덮는 행 = [첫 머신 첫 행 … 끝 머신 끝 행]   →  토막이 몇이든 그 레인은 그 줄 것
g = 1   덮는 행 = 그 머신의 자기 좌석 행뿐          →  여러 품목이 한 레인을 나눠 쓴다
```

`laneBudget.ts` 의 부등식이 이미 그 말이다 — `(g>1 줄 수) + (g=1 이 있으면 면 수) ≤ Σ_f R_f`.
**그러므로 `1 < g < N` 은 레인 압력에 대한 답이 아니다.** 부분 트렁크가 푸는 것은 **양**
(벨트 처리량·좌석)이고, 자리를 되찾는 것은 `g = 1` 뿐이다.

**증상** (2026-09-02 브라우저 실측, `advanced-circuit`):

```
E 면 링크 입력 3줄 (copper-cable · kr-electronic-components · electronic-circuit)
면당 레인 R = |reach 종류| = 2      ← 로드된 게임데이터에 reach 3 이 없다(인서터 7종 전수)
링크는 반대 면으로 못 가고 · gap 은 g=1 만 받는다   →  한 줄이 반드시 못 앉는다
처리량·머신 수와 무관하다(10/s 든 1/s 든 같다) — **구조적**이다
```

**길 셋**

| | 무엇을 내주나 | 값 | 위험 |
|---|---|---|---|
| **(가) 넘치는 링크를 `g = 1` 로** | 그 줄의 포트가 머신 수만큼 | 밸브가 이미 있다(`{side, g: 1}`) | 포트·납품 경로 폭증 → 채널 폭. 대조 실측: 외부 줄이 그렇게 떨어진 배치가 **포트 273 · 벨트 이용률 26%** |
| **(나) 링크 입력에 반대 면(W)을 연다** | 없음 — 레인이 2 → 4 | 가장 싸다 | 오늘 금지 사유가 *"벨트가 채널 반대쪽에서 출발해 되돌아올 길이 없다"*(`planModulePorts`). 납품 경로 기하가 성립하는지 **미확인** |
| **(다) 오늘처럼 정직하게 실패** | 배치 자체 | 0 | 트리 안에서 만드는 재료가 3종 이상인 레시피가 `R = 2` 에서 **전부** 못 돈다 |

**따라오는 둘째 물음 — 예산을 링크에 대해선 면마다 셀 것인가.**
`planBundles` 는 모듈 전체(`Σ_f R_f`)로 센다. 근거는 *"선호 면이 차면 반대 면으로 넘어가기
때문"*(2026-09-01 electric-motor 실측). **그 전제가 링크에는 거짓이다** — 링크는 못 넘어간다.
(나)를 고르면 참이 되고, (가)를 고르면 **링크만 면 단위로** 세야 한다.

**착수 조건 — 입력의 성질**

```
한 모듈의 링크 입력 줄 수 > R    (= 트리 안에서 만드는 재료가 R 종을 넘는 레시피)
```

**채울 자리는 정해져 있다** — `modulePacking` 의 간선 루프. 자식·부모의 좌석표를 **둘 다**
보는 유일한 자리다(`seatLinkEdge` 를 부르는 그 줄).

| **Q16. 좌석 예산은 면 단위인가 모듈 단위인가** | **모듈 단위 `2h`**(2026-08-14 사용자). *"다른 면도 좌석 예산에 포함시켜야 한다."* 면은 **선호이지 강제가 아니다**(TR5). **2026-08-13 에 이미 한 번 틀렸던 것을 반복했다** |
