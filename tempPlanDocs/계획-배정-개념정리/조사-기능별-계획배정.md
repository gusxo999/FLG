# 조사 — 기능마다 **계획과 배정이 어디서 갈리나**

> **왜 이 조사인가:** 이 폴더의 §1·§2 와 `judgements.md` 의 C1·C2 는 **한 경로**(모듈 공급 줄)만
> 보고 세운 것이다. 한 표본에서 뽑은 것은 개념이 아니라 **그 경로의 서술**이다.
> 나머지 기능 여섯을 같은 렌즈로 읽는다.

> **근거:** 각 파일의 **머리말 주석**(이 저장소에서 설계 의도의 단일 출처) +
> `docs/auto-layout/common/layout-models.md` §2 · `docs/auto-layout/module/trunk-assignment.md`.

---

## §1 읽는 렌즈 — 셋

```
① 무엇을 세나        수로 풀리는 것.  순서에 안 기댄다
② 무엇을 적나        자리를 못박는 것.  순서에 기댄다
③ 순환을 어떻게 끊었나  세는 값이 적는 결과에 달렸을 때 무엇을 했나
```

**③이 이 조사의 목적이다.** ①②의 경계는 기능마다 달라도 되지만, ③은 **처방**이라 옮겨 쓸 수 있다.

## §2 전수표

| 기능 | **센다**(계획) | **적는다**(배정) | 낟알이 멈추는 곳 | **순환 처방** |
|---|---|---|---|---|
| 채널 폭 `channelPlanner` | 트랙 수 = 겹침 없는 구간 채색 | — (안 적는다) | **폭까지.** 트랙 index 는 라우터 | **넉넉히 세고 안 적는다** |
| 채널 기하 `channelGeometryPlanner` | `trackCount` — **배정의 결과로** | 납품·반출이 각각 어느 트랙·행 | 행·트랙 전부 | **적고 나서 센다**(폭 역전) |
| 행 채널 `rowChannelPlanner` | 트랙 수 + 폭 (순수 함수) | — (호출자가) | **폭까지** | **축을 가르거나 두 패스** |
| 반출 레인 `perimeterTrackPlanner` | 세로 점유 구간 → 폭 | 진출 변(N/S) · host | **폭까지.** 트랙 index 는 라우터 | 순환 없음 — 폭을 남과 합쳐 센다 |
| 흐름 `allocateFlows` | 흐름 rate (자식→부모) | — | **rate 까지.** 줄 수·팔 수 안 정함 | 순환 없음 — 팔은 **반대로 유도** |
| 트리 배치 `modulePacking` | 열(depth) · 행(tidy-tree) | 모듈 좌표 | 좌표 전부 | 채널 폭을 **먼저** 받아 끊는다 |
| **모듈 안쪽** `planModulePorts` | `g`·`c`·팔 수·좌석 예산 | 면 · 레인 · 좌석 칸 · 포트 칸 | 좌표 직전까지 | **없다 — 세고, 적어 보고, 실패하면 다시 센다** |

## §3 처방 넷 — **무슨 상황이고, 왜 그렇게 끊었나**

각 처방을 *상황 → 고리 → 끊은 법 → 치른 값* 넷으로 적는다.

---

### 처방 1 — **넉넉히 세고 안 적는다** (`channelPlanner` · `perimeterTrackPlanner`)

**상황.** 모듈 두 열 사이에 세로 통로(채널)가 있다. 그 통로를 가로질러야 하는 벨트가 여럿이다.
**통로가 몇 칸 넓어야 하나?**

```
[모듈 A] │ ? ? ? │ [모듈 B]
         └─통로─┘
   지나야 하는 벨트 5줄 — 그런데 서로 세로 구간이 안 겹치면 같은 줄을 써도 된다
```

**고리처럼 보이는 것.** 폭을 알려면 몇 줄이 필요한지 알아야 하고, 몇 줄인지 알려면
누가 어느 줄로 갈지 정해야 할 것 같다.

**끊은 법 — 고리가 애초에 없었다.** **트랙은 서로 바꿔 놔도 결과가 같다.**
그러니 *"누가 몇 번 트랙"* 은 안 정하고 ***"몇 개 필요한가"*** 만 센다
(겹치지 않는 구간끼리 같은 트랙 = 구간 그래프 채색, **최소값이 정확히 나온다**).

```
계획   트랙 5개 필요하다.  누가 어느 트랙인지는 **안 정한다**
방출   라우터가 아무 빈 트랙이나 고른다 — **항상 있다**
```

> *"트랙 폭이 항상 충분하므로 **BFS 가 실패하지 않는다**"* — 그래서 **되돌아올 일이 없다.**

**치른 값 — 없다.** 최소 채색이라 낭비도 없다.
**다만 성립 조건이 있다:** ***자원이 교환가능해야 한다.*** 이게 §3.5 의 첫 물음이다.

---

### 처방 2 — **적고 나서 센다** (폭 역전, `channelGeometryPlanner`)

**상황.** 같은 통로를 **두 종류** 경로가 지난다.

```
납품 경로   자식 출력(E벽) → 부모 입력(W벽).      모양 = **계단꼴**
반출 경로   갇힌 상자 → 열린 N/S 변.              모양 = **한꺾임꼴** — 통로에 **절단선**을 긋는다
```

**왜 처방 1 이 안 되나 — 트랙이 더는 교환가능하지 않다.**
반출이 그은 절단선의 **반대편**이면 납품의 지상 경로가 **기하적으로 존재하지 않는다.**
어느 트랙이냐가 *가능/불가능*을 가르므로, 개수만 세는 것으로는 답이 안 나온다.

**고리처럼 보이는 것.** 폭을 정해야 트랙이 생기고, 트랙을 정해야 몇 개인지(=폭) 안다.

**끊은 법 — *"폭이 먼저"* 라는 가정을 버린다.**

```
배정을 **먼저** 끝낸다 (누가 어느 트랙·어느 행)
그다음 `trackCount` 를 **읽는다** — 폭은 배정의 **산물**이다
```

**치른 값 — 없다.** 고리가 아니라 **가짜 의존**이었다. 화살 방향만 바로잡은 것이다.

> **저장소가 가장 잘 푼 자리다.** 여기엔 고칠 것이 없다.

---

### 처방 3 — **축을 가르거나 두 패스** (`rowChannelPlanner`)

**상황.** 같은 깊이에서 세로로 이웃한 두 모듈 **사이의 가로 띠**(행 채널). 여기도 경로가 지난다.

**왜 어려운가 — 여기는 고리가 *진짜로* 닫힌다.**

```
띠가 높아진다  →  아래 모듈이 밀린다  →  모듈의 절대 y 가 바뀐다
              →  포트의 절대 y 가 바뀐다  →  **어느 띠를 지나는지가 바뀐다**
              →  띠 수요가 바뀐다  →  띠가 높아진다        ← 처음으로 돌아왔다
```

**세로 채널은 왜 안 걸리나 — 축이 다르다.**

```
세로 채널의 폭은 **x** 를 밀고, 경로 수요는 **y** 로 정해진다  →  고리가 **안 닫힌다**
행 채널의 높이는 **y** 를 밀고, 경로 수요도 **y** 로 정해진다  →  **닫힌다**
```

그래서 세로 채널의 처방은 ***"축을 가른다"*** 다 — `y` 는 상수 간격(`STACK_GAP = 3`)으로
**먼저 못박고**, `x` 만 수요에서 유도한다. 고리의 한 변을 **상수로 죽여** 없앤 것이다.

**행 채널은 같은 축이라 그 수가 안 통한다.** 적어 둔 처방은 **두 패스** —
임시 간격으로 배치 → 통과 경로 계산 → 폭 확정 → 재배치.

**치른 값 — 두 가지, 둘 다 크다.**

```
① 축 가르기의 값   `STACK_GAP = 3` 은 **수요를 안 본다**.  필요보다 넓거나 **좁다**
                   layout-models.md §2⑤ 가 이미 적어 뒀다 — *"폭이 우연히 생기고 아무도 예약하지 않는다"*
② 두 패스의 값     **아직 안 치렀다 — 구현이 없다**
```

> **2026-09-01 확인: 행 채널의 두 패스는 없다.** `modulePacking` 이 `band.wantHeight` 를
> 채우지만 소비처는 **`moduleWizard.ts:571` 하나 — 화면에 띄우는 것뿐**이다. 배치는 안 바뀐다.
> 즉 오늘의 실제 동작은 *"상수로 살고, 모자란 양은 **표시만** 한다"* 이다.
> 이건 순환 해법이 아니라 **미완성 경계를 드러내는 습관**이다.

---

### 처방 X — **세고 → 적어 보고 → 실패하면 다시 센다** (모듈 안쪽)

**상황.** 벨트 한 줄이 머신 `g` 대를 맡는다.

```
g 를 크게    줄이 줄어 좌석이 남는다.  대신 **관통**이라 끝까지 자리가 이어져야 한다
g = 1        줄과 포트가 늘어난다.      대신 gap(N/S)을 쓸 수 있다
```

**고리.** `g` 를 정해야 부을 수 있고 → 부어 봐야 자리가 되는지 알고 → 안 되면 `g` 를 낮춘다.

**왜 처방 1 이 안 되나 — 좌석은 교환가능하지 않다.**

```
좌석마다 **reach 가 다르다**       어느 칸이냐가 팔 종류를 바꾼다
좌석마다 **행 위치가 다르다**       그 줄의 포트가 **다음 레인을 막는다**(= 못)
```

*"몇 칸 필요"* 만으로는 답이 안 나온다. 그래서 채널처럼 *"세고 안 적기"* 를 할 수 없다.

**그러면 남는 것은 2·3 인데 — 모델은 이미 2 를 골랐다.**

> **TR1**(`docs/auto-layout/module/trunk-assignment.md`):
> *"`g_max` 는 처리량이 준 **상한**이고 실제 `g` 는 **자리**가 정한다"*

**그런데 코드가 안 따른다.** `externalLineGroups` 의 `bundle` 은 붓기 **인자**라
상한이 아니라 **확정값**으로 들어간다 → 자리가 안 맞으면 붓기를 **다시 부르는 수밖에 없다.**

**치른 값.** `부분-트렁크` ⑤ 에서 **네 번 되돌렸다.**

## §3.5 판정 축 — **처방은 세 물음으로 갈린다**

```
물음 1   이 자원은 **교환가능한가**  (어느 것을 줘도 결과가 같나)
         예   → **처방 1**.  수만 센다.  배정이 실패할 수 없다
         아니오 ↓

물음 2   수가 자리에서 **유도되나**  (자리를 정하면 수가 따라 나오나)
         예   → **처방 2**.  배정을 먼저.  수는 결과로 읽는다
         아니오 ↓

물음 3   자리가 **수요 자체를 바꾸나**  (고리가 닫히나)
         예   → **진짜 고리**.  축을 가르거나 두 패스.  **값을 치른다**
         아니오 → 고리가 아니다.  **순서를 잘못 잡은 것뿐**
```

**전수에 대입하면:**

| 기능 | 물음 1 | 물음 2 | 물음 3 | 처방 |
|---|---|---|---|---|
| 채널 폭 | **예**(트랙은 다 같다) | — | — | 1 |
| 반출 레인 | **예** | — | — | 1 |
| 흐름 `allocateFlows` | — | — | **아니오**(자리를 안 본다) | 고리 없음 |
| 채널 기하 | 아니오(절단선) | **예**(폭은 배정의 산물) | — | 2 |
| 행 채널 | 아니오 | 아니오 | **예**(높이가 위치를 민다) | 3 |
| **모듈 안쪽** | 아니오(reach·못) | **예**(TR1) | 아니오 | **2 여야 한다** |

> **모듈은 물음 2 에서 이미 "예" 다.** 물음 3 까지 안 간다 —
> `per`(머신 하나의 수요)는 `g` 와 무관하므로(`armsFromCarries`) **자리가 수요를 안 바꾼다.**
> 그러니 모듈은 **값을 치를 필요가 없다.** 처방 2 면 된다.

## §4 그래서 — **정상인 것과 아닌 것**

```
처방 2   **정상이다.**  고리가 아니라 가짜 의존이었고, 화살만 바로잡았다.  고칠 것 없다
처방 1   **조건부로 정상이다.**  자원이 교환가능할 때만 옳다.  채널은 옳고, 모듈에는 못 쓴다
처방 3   **정상이 아니다.**  자유도를 상수로 죽였고(축 가르기), 두 패스는 **아직 없다**
처방 X   **처방이 아니다.**  고리를 안 끊은 상태 그대로다
```

> **정정(2026-09-01).** 앞서 *"모듈이 처방 1 을 못 쓰는 것은 **넘길 라우터가 없어서**"* 라고
> 적은 것은 **표면적 이유**였다. 진짜 이유는 ***자원이 교환가능하지 않아서*** 다 —
> 좌석은 reach 와 행 위치가 저마다 다르다. 라우터를 붙여도 안 된다.
