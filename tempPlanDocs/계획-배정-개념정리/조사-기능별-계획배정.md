# 조사 — 기능마다 **계획과 배정이 어디서 갈리나**

> **왜 이 조사인가:** 이 폴더의 §1·§2 와 `judgements.md` 의 C1·C2 는 **한 경로**(모듈 공급 줄)만
> 보고 세운 것이다. 한 표본에서 뽑은 것은 개념이 아니라 **그 경로의 서술**이다.
> 나머지 기능 여섯을 같은 렌즈로 읽는다.

> **근거:** 각 파일의 **머리말 주석**(이 저장소에서 설계 의도의 단일 출처) +
> `docs/auto-layout/common/layout-models.md` §2 · `docs/auto-layout/module/trunk-assignment.md`.

---

## §1 읽는 렌즈 — 셋

```
① 무엇을 세나        수로 풀리는 것.  순서에 안 기댄다
② 무엇을 적나        자리를 못박는 것.  순서에 기댄다
③ 순환을 어떻게 끊었나  세는 값이 적는 결과에 달렸을 때 무엇을 했나
```

**③이 이 조사의 목적이다.** ①②의 경계는 기능마다 달라도 되지만, ③은 **처방**이라 옮겨 쓸 수 있다.

## §2 전수표

| 기능 | **센다**(계획) | **적는다**(배정) | 낟알이 멈추는 곳 | **순환 처방** |
|---|---|---|---|---|
| 채널 폭 `channelPlanner` | 트랙 수 = 겹침 없는 구간 채색 | — (안 적는다) | **폭까지.** 트랙 index 는 라우터 | **넉넉히 세고 안 적는다** |
| 채널 기하 `channelGeometryPlanner` | `trackCount` — **배정의 결과로** | 납품·반출이 각각 어느 트랙·행 | 행·트랙 전부 | **적고 나서 센다**(폭 역전) |
| 행 채널 `rowChannelPlanner` | 트랙 수 + 폭 (순수 함수) | — (호출자가) | **폭까지** | **축을 가르거나 두 패스** |
| 반출 레인 `perimeterLanePlanner` | 세로 점유 구간 → 폭 | 진출 변(N/S) · host | **폭까지.** 트랙 index 는 라우터 | 순환 없음 — 폭을 남과 합쳐 센다 |
| 흐름 `allocateFlows` | 흐름 rate (자식→부모) | — | **rate 까지.** 줄 수·팔 수 안 정함 | 순환 없음 — 팔은 **반대로 유도** |
| 트리 배치 `modulePacking` | 열(depth) · 행(tidy-tree) | 모듈 좌표 | 좌표 전부 | 채널 폭을 **먼저** 받아 끊는다 |
| **모듈 안쪽** `planModulePorts` | `g`·`c`·팔 수·좌석 예산 | 면 · 레인 · 좌석 칸 · 포트 칸 | 좌표 직전까지 | **없다 — 세고, 적어 보고, 실패하면 다시 센다** |

## §3 처방은 **이미 셋이 있다**

### 처방 1 — **넉넉히 세고 안 적는다** (`channelPlanner`)

> *"본 모듈은 **폭/트랙 산정만** 한다. 실제 셀 깔기는 검증된 기존 라우터가 담당한다 —
> **트랙 폭이 항상 충분하므로 BFS 가 실패하지 않는다**."*

**계획이 방출의 성공을 보장한다.** 계획은 *상한*만 내고 자리는 안 정한다. 그러면 배정이
실패할 수 없고, 실패하지 않으므로 **되돌아올 일이 없다.**

`perimeterLanePlanner` 가 같은 것을 명시적으로 적는다 — *"(A) **폭만 예약** — 트랙 index 는
못박지 않음 … 실제 몇 번째 트랙에 깔릴지는 검증된 라우터가 정한다(**납품 경로와 동일 관행**)."*

> **관행이라고 부를 만큼 반복됐다.** 그런데 모듈 안쪽만 이 관행 밖에 있다.

### 처방 2 — **적고 나서 센다** (`channelGeometryPlanner`, "폭 역전")

> *"**폭 역전**: 트랙·행 배정을 **먼저 끝내고** `trackCount` 는 **그 결과에서 나온다**."*

수가 자리를 정하는 게 아니라 **자리가 수를 낸다.** 순환의 한쪽 화살을 뒤집어 없앤 것이다.

### 처방 3 — **축을 가르거나, 두 패스** (`rowChannelPlanner`)

> *"**순환**: `topY → absPortY → 띠를 지나는 경로 → 띠 폭 → topY`.
> 세로 채널은 이 순환을 **축을 갈라서** 피한다 — `y` 는 상수 간격으로 먼저 정하고 `x` 만
> 수요에서 유도한다. 행 채널은 **같은 축**이라 그 수가 안 통한다 …
> 그래서 **두 패스**(임시 간격으로 배치 → 통과 경로 계산 → 폭 확정 → 재배치)로 순환을 끊는다."*

**우리가 "되먹임" 이라 부른 것을 이 파일은 "순환" 이라 부르고, 처방 둘을 이미 적어 놨다.**

## §4 그리고 **모듈만 넷째를 쓴다**

```
세고  →  적어 보고  →  실패하면 **다시 센다**
```

이게 `부분-트렁크` ⑤ 에서 네 번 되돌린 것의 정체다. 넷째는 처방이 아니라 **순환을 안 끊은 상태**다.

**왜 모듈만 그런가 — 낟알이 끝까지 간다.** 위 여섯은 전부 *"폭까지"* 나 *"rate 까지"* 에서
멈추고 마지막 칸은 라우터에게 넘긴다. 모듈 안쪽에는 **넘길 라우터가 없다** — 좌석 칸·포트 칸은
계획이 직접 못박는다. 그래서 처방 1(안 적는다)을 그대로는 못 쓴다.

### 남는 것은 처방 2·3 이고, **모델은 이미 2를 골라 놨다**

`docs/auto-layout/module/trunk-assignment.md` TR1:

```
g_j = min(k_j, N)   묶음 크기 — 처리량이 준 **상한**       ← TR1
```

> **`g_max` 는 상한이고 실제 `g` 는 자리가 정한다** — 정확히 처방 2(폭 역전)다.

**그런데 코드는 `g` 를 붓기 인자로 못박는다**(`externalLineGroups` 의 `bundle`). 상한이 아니라
**확정값**으로 들어가므로, 자리가 안 맞으면 붓기를 다시 부를 수밖에 없다 → 넷째.

> **모델과 코드의 어긋남이지 미지의 문제가 아니다.** `trunk-assignment.md` 본문도 이미
> *"채널 장부가 이미 이 모양이다 … 새 알고리즘이 아니라 **있는 뼈대를 축만 바꿔 두 번째로 쓰는 것**"*
> 이라고 적어 뒀다.

## §5 이 조사가 개념정리에 되돌리는 것

| 되돌리는 것 | 어디로 |
|---|---|
| **경계는 기능마다 다르고, 그게 정상이다** — 낟알을 어디서 멈추나가 설계 선택 | §1 의 *"계산/배정"* 이분법을 **낟알 축**으로 바꾼다 |
| **순환 처방은 셋이고 저장소에 이미 있다** | 새 §. C1·C2 는 그 앞에 서는 전제가 된다 |
| **모듈은 처방을 안 고른 상태** — 결함이 아니라 **미완성** | `부분-트렁크` ⑤ 의 진짜 서술 |
| **모델(TR1)은 이미 처방 2 를 골랐다** — 코드가 안 따를 뿐 | J2(순서)의 답이 여기서 갈린다 |
| **`지도 A` 삭제는 개념이 아니라 변경**이다 | `부분-트렁크` 로 돌려보낸다 |
