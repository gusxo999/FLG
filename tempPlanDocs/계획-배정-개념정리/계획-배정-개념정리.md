# 계획과 배정 — **낟알을 어디서 멈추나**

> 상태·읽을 것·범위는 같은 폴더의 `CLAUDE.md`. 전수 조사는 `조사-기능별-계획배정.md`.
> 아직 안 고른 갈림은 `judgements.md`.

## §0 한 문장

> 자동 배치의 기능마다 *"무엇을 **수로 세고**, 무엇을 **자리로 적나**"* 의 경계가 다르다.
> **그 자체는 정상이다** — 낟알을 어디서 멈출지가 설계 선택이기 때문이다.
> 문제는 **순환**(세는 값이 적는 결과에 달림)을 끊는 방식이 기능마다 흩어져 있고,
> **모듈 안쪽만 아직 아무 처방도 안 골랐다**는 것이다.

> **2026-09-01 범위 재설정.** 처음 이 문서는 모듈 경로 하나만 보고
> *"지도가 둘이다"* 로 시작했다. 그 사례는 §3 에 그대로 남는다 — 다만 **개념은 §2.5 가 낸다.**

## §1 낱말 — 무엇이 계산이고 무엇이 배정인가

```
계산   자리를 **수로 푸는 일**
       입력: 레시피 · 머신 · 인서터 · 벨트 (전부 **주어진 것**)
       출력: "이 줄은 몇 개로 · 어느 면에 · 어느 레인에 · 팔 몇 개"
       성질: **순서에 안 기댄다.**  같은 입력이면 같은 답

배정   그 답을 **표에 적는 일**
       입력: 계산의 답 + 지금까지 적힌 표
       출력: "이 머신의 몇 번째 칸" · "이 gap 은 몇 줄"
       성질: **순서에 기댄다.**  먼저 온 줄이 앞 칸을 갖는다
```

**한 줄 판정:** *계획은 **세고**, 배정은 **적는다**.*

> **다만 이 이분법만으로는 경계가 안 정해진다.** 일곱 기능 전수를 보면 갈리는 것은
> *"세느냐 적느냐"* 가 아니라 **어디까지 적고 멈추느냐**다 — `조사-기능별-계획배정.md` §2.
> 채널은 **폭까지** 적고 트랙 index 는 라우터에게 넘긴다. 채널 기하는 **행·트랙 전부** 적는다.
> 흐름은 **rate 까지**만 적고 줄 수도 팔 수도 안 정한다. 셋 다 옳다.

## §2 무엇이 수로 풀리고, 무엇이 **행**을 요구하나

이 갈림이 경계를 정한다.

| 물음 | 수만으로 되나 | 왜 |
|---|---|---|
| 이 줄을 몇 개로 나누나 (`g` · `c`) | ✅ | `⌊벨트 ÷ per⌋` |
| 머신 하나가 이 줄에 팔 몇 개 | ✅ | `⌈per ÷ tp(reach)⌉` — **`g` 와 무관** |
| 이 면의 좌석이 충분한가 | ✅ | `Σ_j 팔_j ≤ h` — 행 **위치**는 안 봐도 된다 |
| 관통인가 구간인가 | ✅ | `g = N` 인가 |
| **두 줄이 같은 레인을 나눠 쓸 수 있나** | ❌ | **행 구간이 겹치나**를 봐야 한다 |
| **이 줄의 포트가 남의 레인을 막나** | ❌ | 포트가 `(어느 행, 어느 깊이)` 에 서는지 알아야 한다 |
| 어느 칸에 앉나 (순번) | ❌ | 앞선 줄이 무엇을 먹었나 |

> **행이 필요한 셋은 순서가 정해져야 답이 나온다.** 그리고 순서가 정해지면 **결정적**이다 —
> 즉 *"순서를 누가 정하나"* 가 이 문서의 진짜 물음이다.

## §2.5 순환을 끊는 처방 — **저장소에 이미 셋 있다**

전수는 `조사-기능별-계획배정.md` §3. 요약만 여기 둔다.

```
처방 1  넉넉히 세고 안 적는다      계획이 **상한**만 내고 자리는 안 정한다
        (channelPlanner · perimeterLanePlanner)
        → 폭이 항상 충분하므로 **배정이 실패할 수 없다** → 되돌아올 일이 없다

처방 2  적고 나서 센다 (폭 역전)   자리를 먼저 못박고 **수는 결과로** 낸다
        (channelGeometryPlanner)
        → 순환의 한쪽 화살을 뒤집어 없앤다

처방 3  축을 가르거나 두 패스      두 변수를 다른 축에 놓거나,
        (rowChannelPlanner)        임시값으로 한 바퀴 돌고 확정한다
```

**그리고 넷째가 있다 — 처방이 아니다.**

```
처방 X  세고 → 적어 보고 → 실패하면 **다시 센다**     ← 모듈 안쪽이 지금 이것
```

> **모듈이 처방 1 을 못 쓰는 이유는 낟알이다.** 위 여섯은 마지막 칸을 라우터에게 넘기지만,
> 모듈 안쪽에는 **넘길 라우터가 없다**(좌석 칸·포트 칸은 계획이 직접 못박는다).
> 그래서 남는 것은 **처방 2·3** 이고, 모델은 **이미 2 를 골라 놨다** — TR1 의
> *"`g_max` 는 상한이고 실제 `g` 는 **자리**가 정한다"*.
> 코드가 `g` 를 붓기 **인자로 못박아** 안 따를 뿐이다.

## §3 사례 — **모듈 안쪽은 지도가 둘이고, 하나가 버려진다**

### 지도 A — 선반 (`planClusterPorts`)

```ts
const slotsOf = (side) => laneSlots(inserters);   // reach 종류마다 슬롯 하나 → 면당 R개
const [slot] = pool.splice(best, 1);              // 줄 하나가 슬롯 하나를 **소비한다**
rowsLeft.set(slot.side, rowsLeftOf(slot.side) - bestArms);
```

```
면마다   슬롯 R개(= reach 종류 수)  +  좌석 행 h개
줄 하나 = 슬롯 1개 + 팔 몇 개
**머신 축이 없다.** 모든 머신이 같다고 본다
```

### 지도 B — 격자 (`FaceTable`)

```
(행 × 깊이).  행 = 머신마다 h칸씩 이어 붙인 것
줄 하나 = 좌석 몇 칸 + 벨트 구간 + **포트 2칸**
레인은 **행이 안 겹치면 공유**한다
```

### 두 지도의 어긋남 — 셋

```
① 지도 A 가 **실제보다 적게** 센다 — 줄 수
   "면당 R줄" 은 벨트가 기둥 전체를 달리던 시절의 상한이다.
   지금은 자기 구간만 덮고 꺾으므로 행이 안 겹치면 여러 줄이 같은 깊이에 앉는다
   → **될 것을 안 된다고 한다**

② 지도 A 가 **실제보다 헐겁게** 센다 — 포트 칸
   줄마다 인서터+상자 2칸을 더 먹고 그게 다음 깊이를 막는다(= **못**). A 는 안 센다
   → **안 될 것을 된다고 한다**

③ 지도 A 에 **머신 축이 없다**
   구간 줄이면 어떤 머신은 꽉 차고 어떤 머신은 빈다. A 는 평균으로 본다
   → **평균은 되는데 개별이 안 된다**
```

### 그래서 벌어지는 일

```
지도 A 의 답(어느 줄이 · 어느 면에 · 어느 레인에)  →  **아무도 안 읽는다**(PlannedLine[])
지도 B 가 처음부터 다시 앉혀 본다                   →  후보를 정렬해 시도한다
A 에 남는 것은 "이 모듈 되나/안 되나" **불리언 하나**
```

**그리고 그 불리언이 그 모듈 전 줄의 `g` 를 정한다** — 한 줄이 안 되면 전부 `g=1` 이 된다
(`tempPlanDocs/부분-트렁크/` §2).

## §4 미래 구조 — **지도를 하나로**

```
계획   지도 B(격자) 하나로 **순서까지** 정한다
       → 줄의 순서 · 면 · 레인 · 좌석 칸 · 포트 칸 · gap 폭
       → 못 넣는 줄이 있으면 **그 줄의 이름과 사유**를 수로 낸다
방출   좌표를 더한다
```

**지도 A 를 버린다.** 지도 A 가 하던 유일한 참값(좌석 예산 `Σ팔 ≤ h`)은 지도 B 가
**더 정확한 낟알로**(머신마다) 이미 센다.

### 그러면 "배정" 은 무엇이 되나

**사라지는 것이 아니라 계획 *안*으로 들어간다.** §2 의 표가 그 이유다 — 레인 공유·포트 칸·
순번은 **행이 있어야** 답이 나오고, 행은 순서가 정해져야 나온다. 순서를 계획이 정하면
그 뒤는 전부 결정적이므로, **한 층 안에서 세고 적는 것이 맞다.**

```
지금    계산(버려짐)  →  배정(다시 함)  →  방출
미래    계획(세고 적는다)              →  방출
```

**두 번 세지 않는다**(R3)는 것이 이 통합의 근거다.
