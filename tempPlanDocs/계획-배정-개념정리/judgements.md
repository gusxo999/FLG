## 확정된 판단 (근거와 함께)

### C1 — 계산과 배정을 가르는 축은 **"행이 필요한가"** 다

```
수로 풀린다     g · c · 팔 수 · 좌석 예산(Σ팔 ≤ h) · 관통 여부
행이 필요하다   레인 공유(구간 겹침) · 포트 칸 · 순번
```

**근거:** 레인은 *"행 구간이 안 겹치면 공유"* 이고(`tryLinkFace`), 포트는 `(topT, d+1)`
`(topT, d+2)` 라는 **행·깊이 좌표**를 먹는다. 둘 다 행 없이는 답이 안 나온다.

**따름:** *"계산이 다 풀고 배정은 적기만 한다"* 는 **순서가 정해진 뒤에만** 참이다.
순서 전에는 계산이 레인·포트를 못 판정한다.

### C2 — 그래서 배정은 **없앨 수 없고, 계획 안으로 들어간다**

행이 필요한 셋은 순서가 정해지면 **결정적**이다. 그러니 순서를 계획이 정하면 계획이
그 셋까지 풀 수 있고, 그때 배정은 **같은 층의 장부**가 된다 — 별도 단계가 아니다.

**따름:** 층은 **둘**이다 — `계획(세고 적는다)` · `방출(좌표를 더한다)`.
*"계산 → 배정 → 방출"* 이라는 3단은 **현재 코드의 사고(事故)**이지 설계가 아니다.

### C3 — 지도 A(선반)의 좌석 판정은 **중복이고 덜 정확하다**

```
지도 A   면 단위 `rowsLeft`         모든 머신이 같다고 본다
지도 B   머신 단위 `seatsTaken(mi)`  구간 줄에서 갈린다
```

**근거:** 같은 사실을 두 곳이 세고(R3), **덜 정확한 쪽이 먼저 이긴다**(A 가 `direct` 를
내면 B 는 볼 기회도 없다).

## 아직 안 골랐다

### J1 — 지도 A 의 **"면당 R줄"** 상한이 정말 낡았나

```
그렇다면   지우면 될 배치가 늘어난다
아니라면   레인을 공유할 수 없는 경우가 남아 있다는 뜻이고, 그 조건을 적어야 한다
```

**착수 조건(트리거):** 지도 A 를 손대기 전. **확인 방법은 코드로 된다** —
`tryLinkFace` 가 같은 `laneDepth` 에 두 그룹을 앉히는 경로가 실제로 있는지
(`laneClear` 가 겹침만 보는지, 아니면 다른 가드가 더 있는지)를 읽는다.

**전제(2026-09-01):** 벨트가 자기 좌석 구간만 덮고 끝에서 꺾는다
(`LinkFacePlan.laneDepth` 머리말). 이 전제가 깨지면 J1 의 답이 뒤집힌다.

### J2 — **순서를 무엇이 정하나**

C2 가 *"순서를 계획이 정하면"* 을 전제로 선다. 그런데 그 순서를 무엇이 정할지는 안 골랐다.

```
(가) 지금 그대로 — 붓기가 낸 배열 순서(= 레시피 재료 순서)
(나) 자유도가 낮은 것 먼저 — 관통 줄이 먼저(도피처가 없다)
(다) 수요가 큰 것 먼저 — 팔을 많이 먹는 줄이 좋은 자리를
```

**(나)는 이미 한 번 확정됐다**(`부분-트렁크` §3 — *제약이 가장 센 것 먼저*, 스도쿠 원칙).
다만 그것이 **나머지 줄**(원료·완제품)에도 적용되는지는 안 정했다.

**착수 조건:** 지도 통합을 시작할 때. 순서 없이는 행이 안 정해지므로 **미룰 수 없다.**

**전제:** gap 은 `g = 1` 만 받는다(`machinesOn !== 1`). 이 제약이 풀리면 *"도피처가 없다"*
가 약해져 (나)의 근거가 흔들린다 — 다만 그 제약 해제는 **격자 클러스터의 몫**으로
범위 밖이다(2026-08-30 확정).

### J3 — 지도 A 를 지울 때 **진단 문자열**을 어디서 만드나

`unrouted-lines` 이슈가 `supply.reason` 을 싣는다. 지우면 그 줄이 *"사유 없음"* 이 된다.

```
(가) 지도 B 의 이름표를 넓힌다 — `laneShortages` 의 키를 `id ?? "역할:품목"` 으로
     → 링크에만 있던 이름표(`좌석부족`·`좌석막힘`…)가 나머지 줄에도 붙는다
(나) 지도 A 를 진단 전용으로 남긴다
     → **두 번 세게 된다**(R3). 권하지 않는다
```

**기울기는 (가)** 지만, 이름표가 `supply.reason` 만큼 구체적인지는 안 봤다
(`reason` 은 *"belt: demand>beltCap (철판)"* 처럼 **수와 이름**을 담는다).

**착수 조건:** 할 일 3(산출을 줄마다) 을 시작할 때.

### J4 — 통합 뒤 **계획이 실패를 어떻게 내나**

지금은 두 층이 각자 실패를 낸다 — 지도 A 는 `complex/direct`, 지도 B 는 `unroutedLines`.
합치면 하나여야 하는데, **무엇을 담아야 사다리가 읽을 수 있나**가 안 정해졌다.

```
지금 아는 것   사유는 **수**여야 한다(R4) — `(면, 레인, 막힌 행[])`
               이름표는 교착의 종류를 든다(`span-blocked` 등)
안 정한 것     그 둘이 한 자료인가, 두 자료인가
```

**착수 조건:** 할 일 3.
