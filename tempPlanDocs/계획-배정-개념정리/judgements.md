### C1 — 계산과 배정을 가르는 축은 **"행이 필요한가"** 다

```
수로 풀린다     g · c · 팔 수 · 좌석 예산(Σ팔 ≤ h) · 관통 여부
행이 필요하다   레인 공유(구간 겹침) · 포트 칸 · 순번
```

**근거:** 레인은 *"행 구간이 안 겹치면 공유"* 이고(`tryLinkFace`), 포트는 `(topT, d+1)`
`(topT, d+2)` 라는 **행·깊이 좌표**를 먹는다. 둘 다 행 없이는 답이 안 나온다.

**따름:** *"계산이 다 풀고 배정은 적기만 한다"* 는 **순서가 정해진 뒤에만** 참이다.
순서 전에는 계산이 레인·포트를 못 판정한다.

### C2 — 그래서 배정은 **없앨 수 없고, 계획 안으로 들어간다**

행이 필요한 셋은 순서가 정해지면 **결정적**이다. 그러니 순서를 계획이 정하면 계획이
그 셋까지 풀 수 있고, 그때 배정은 **같은 층의 장부**가 된다 — 별도 단계가 아니다.

**따름:** 층은 **둘**이다 — `계획(세고 적는다)` · `방출(좌표를 더한다)`.
*"계산 → 배정 → 방출"* 이라는 3단은 **현재 코드의 사고(事故)**이지 설계가 아니다.

### C3 — 지도 A(선반)의 좌석 판정은 **중복이고 덜 정확하다**

```
지도 A   면 단위 `rowsLeft`         모든 머신이 같다고 본다
지도 B   머신 단위 `seatsTaken(mi)`  구간 줄에서 갈린다
```

**근거:** 같은 사실을 두 곳이 세고(R3), **덜 정확한 쪽이 먼저 이긴다**(A 가 `direct` 를
내면 B 는 볼 기회도 없다).

### C4 — 경계는 기능마다 다르고, **그게 정상이다**

```
채널 폭      **폭까지** 적는다.  트랙 index 는 라우터        (처방 1)
채널 기하    **행·트랙 전부** 적는다.  폭은 결과            (처방 2)
행 채널      **폭까지**.  위치는 두 패스로                 (처방 3)
흐름         **rate 까지**.  줄 수도 팔 수도 안 정한다      (순환 없음)
모듈 안쪽    **좌표 직전까지** 전부.  넘길 라우터가 없다    (**처방 없음**)
```

**근거:** 일곱 기능 머리말 전수(`조사-기능별-계획배정.md` §2). 낟알을 어디서 멈출지는
**설계 선택**이고, 그 선택을 정하는 것은 *"뒤에 실패할 수 있는 단계가 있나"* 다 —
없으면(라우터가 항상 성공) 일찍 멈춰도 되고, 있으면 끝까지 적어야 한다.

**따름:** *"계획은 세고 배정은 적는다"* 는 **경계를 안 정한다.** 정하는 물음은
***"이 낟알까지 적으면 뒤가 실패할 수 없나"*** 다.

### C5 — 모듈이 고를 수 있는 처방은 **2·3 뿐이고, 모델은 이미 2 를 골랐다**

**근거 — 판정 축 세 물음**(`조사-기능별-계획배정.md` §3.5):

```
물음 1  자원이 교환가능한가   **아니오** — 좌석은 reach 가 다르고 행 위치가 다르다(못)
물음 2  수가 자리에서 유도되나 **예**   — TR1 이 이미 그렇게 적었다
물음 3  자리가 수요를 바꾸나   **아니오** — `per` 는 `g` 와 무관하다(`armsFromCarries`)
```

물음 2 에서 멈추므로 **처방 2 이고, 값을 치를 필요가 없다**(물음 3 까지 안 간다).
`trunk-assignment.md` **TR1**: *"`g_max` 는 처리량이 준 **상한**이고 실제 `g` 는 **자리**가 정한다"*.

> **정정.** 앞서 *"넘길 라우터가 없어서 처방 1 을 못 쓴다"* 고 적은 것은 표면적 이유였다.
> 진짜 이유는 **자원이 교환가능하지 않아서**다 — 라우터를 붙여도 안 된다.

**따름:** `부분-트렁크` ⑤ 가 네 번 실패한 것은 **미지의 문제가 아니라 모델·코드 어긋남**이다.
코드가 `g` 를 붓기 **인자**(`bundle`)로 못박아 상한이 확정값이 됐다.

## 아직 안 골랐다

### J1 — 지도 A 의 **"면당 R줄"** 상한이 정말 낡았나

> **2026-09-01 답했다 — 반만 낡았다.** `depthClear` 는 그 깊이의 칸만 보므로 면당 줄 수를
> 세는 가드는 **없다**(J1 의 확인 방법 그대로 읽었다). 하지만 나눠 쓸 수 있는 것은
> `g=1` 줄뿐이다 — `beltRowSpan` 이 `[최소행, 최대행]` 하나라 머신을 걸치는 그룹은
> **사이 행까지 통으로** 먹는다. 그래서 옳은 상한은
> `(g>1 줄 수) + (g=1 줄 있으면 1) ≤ R_f` 이고, **`g` 가 상한에 들어간다.**
> 모델을 고쳤다 → `docs/auto-layout/module/trunk-assignment.md` §4.1.
> 실측 기록은 `tempPlanDocs/부분-트렁크/부분-트렁크.md` §3(2026-09-01).


```
그렇다면   지우면 될 배치가 늘어난다
아니라면   레인을 공유할 수 없는 경우가 남아 있다는 뜻이고, 그 조건을 적어야 한다
```

**착수 조건 (트리거) · 종류: 해금형** — 지도 A 를 손대기 전. **확인 방법은 코드로 된다** —
`tryLinkFace` 가 같은 `clusterBeltDepth` 에 두 그룹을 앉히는 경로가 실제로 있는지
(`depthClear` 가 겹침만 보는지, 아니면 다른 가드가 더 있는지)를 읽는다.

**전제(2026-09-01):** 벨트가 자기 좌석 구간만 덮고 끝에서 꺾는다
(`LinkFacePlan.clusterBeltDepth` 머리말). 이 전제가 깨지면 J1 의 답이 뒤집힌다.

### J2 — **순서를 무엇이 정하나**

C2 가 *"순서를 계획이 정하면"* 을 전제로 선다. 그런데 그 순서를 무엇이 정할지는 안 골랐다.

```
(가) 지금 그대로 — 붓기가 낸 배열 순서(= 레시피 재료 순서)
(나) 자유도가 낮은 것 먼저 — 관통 줄이 먼저(도피처가 없다)
(다) 수요가 큰 것 먼저 — 팔을 많이 먹는 줄이 좋은 자리를
```

**(나)는 이미 한 번 확정됐다**(`부분-트렁크` §3 — *제약이 가장 센 것 먼저*, 스도쿠 원칙).
다만 그것이 **나머지 줄**(원료·완제품)에도 적용되는지는 안 정했다.

**2026-09-01 — C5 가 후보를 좁힌다.** 처방 2(적고 나서 센다)를 쓰면 순서를 정하는 것은
`g` 가 아니라 **자리**이므로, (가)의 *"붓기가 낸 배열 순서"* 는 후보에서 빠진다.
남는 것은 (나)·(다) 이고, 둘 다 **자리를 먼저 보는** 순서다.

**착수 조건 (트리거) · 종류: 해금형** — 지도 통합을 시작할 때. 순서 없이는 행이 안 정해지므로 **미룰 수 없다.**

**전제:** gap 은 `g = 1` 만 받는다(`machinesOn !== 1`). 이 제약이 풀리면 *"도피처가 없다"*
가 약해져 (나)의 근거가 흔들린다 — 다만 그 제약 해제는 **격자 클러스터의 몫**으로
범위 밖이다(2026-08-30 확정).

### J3 — 지도 A 를 지울 때 **진단 문자열**을 어디서 만드나

`unrouted-lines` 이슈가 `supply.reason` 을 싣는다. 지우면 그 줄이 *"사유 없음"* 이 된다.

```
(가) 지도 B 의 이름표를 넓힌다 — `depthShortages` 의 키를 `id ?? "역할:품목"` 으로
     → 링크에만 있던 이름표(`좌석부족`·`좌석막힘`…)가 나머지 줄에도 붙는다
(나) 지도 A 를 진단 전용으로 남긴다
     → **두 번 세게 된다**(R3). 권하지 않는다
```

**기울기는 (가)** 지만, 이름표가 `supply.reason` 만큼 구체적인지는 안 봤다
(`reason` 은 *"belt: demand>beltCap (철판)"* 처럼 **수와 이름**을 담는다).

**착수 조건 (트리거) · 종류: 해금형** — 할 일 3(산출을 줄마다) 을 시작할 때.
