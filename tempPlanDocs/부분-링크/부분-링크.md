# 부분 링크 — **간선의 묶음을 양끝에서 정한다**

> 상태·읽을 것·범위는 같은 폴더의 `CLAUDE.md`.
> 아직 안 고른 갈림은 `judgements.md` (**J14** — 기준을 모른다).

## §0 푸는 문제

> 나머지 줄(원료·완제품)의 `g` 는 **깊이 예산**이 정한다. 링크(간선)는 **밸브만 뚫려 있고
> 주는 사람이 없어** 언제나 관통이다. 그래서 자리가 모자라면 **한 줄이 통째로 못 앉는다.**

실측이 그것을 구조적 결함으로 짚었다 (2026-09-02, `advanced-circuit`):

```
E 면 링크 입력 3줄 (copper-cable · kr-electronic-components · electronic-circuit)
면당 깊이 R = |reach 종류| = 2      ← 로드된 게임데이터에 reach 3 이 없다
링크는 반대 면으로 못 가고 · gap 은 `g = 1` 만 받는다   →  한 줄이 **반드시** 못 앉는다
처리량·머신 수와 무관하다(10/s 든 1/s 든 같다)
```

> **넘침의 축은 "간선의 `g`" 가 아니라 "한 모듈 한 면의 줄 수"다** (2026-09-04 확인).
> 위 세 줄은 **서로 다른 세 간선**의 입력이고, 셋이 **부모의 E 면 하나**를 다툰다.
> 오늘은 `g` 를 주는 사람이 없어 셋 다 관통이므로 `g_from`·`g_to` 같은 값은 **아직 존재하지도
> 않는다** — 세는 것은 `g` 가 아니라 **줄 개수**다.
>
> **자식 쪽도 막힐 수 있다** — 한 자식이 부모 여럿을 먹이면 그만큼의 간선이 자식 W 면에 함께
> 앉는다. 이 실측에서 막힌 쪽이 받는 쪽이었을 뿐, 어느 쪽이 더 자주 막히는지는 **안 세어
> 봤다**(→ **J14**).

### 안 푸는 것

```
나머지 줄의 `g`      끝났다(`planBundles`)
면·깊이를 누가 정하나  `자리-배정` 의 몫 — 이 계획은 `g` 만 낸다
게임의 좌/우 레인     `벨트-레인` 의 몫
격자 클러스터        **`g>1` gap 형태만** 범위 밖이다 — `g=1` gap 은 이미 살아 있다(§3 사실 ③)
```

### 끝나면 열리는 문

```
· 링크가 자리를 잃었을 때 **통째로 실패하지 않는다** — 내줄 것이 생긴다
· `자리-배정` 의 사다리 2단이 후보 하나를 얻는다(*그 줄을 관통으로 밀어 포트를 기둥 끝으로*)
· 깊이 예산이 **모듈의 모든 줄**을 보게 된다 — 지금은 링크를 `taken` 으로만 센다
· **손잡이의 값을 아는 상태가 된다** — `trunk-assignment.md` §4.3 의 축(①공짜만 / ②gap N칸 /
  ③포트 최소)이 오늘은 기본값만 있고 **눈금이 없다**. Step 1 이 그 눈금을 낸다
```

## §2 어긋난 자리 — **깊이 예산이 링크를 반쪽만 본다**

```ts
// depthBudget.planBundles — 오늘
taken: (face) => { /* 링크가 이미 먹은 깊이를 뺀다 */ }
```

링크는 **이미 앉은 사실**(`taken`)로만 들어온다. 그래서 예산은 *"링크가 넷을 먹었으니
나머지 줄은 이만큼"* 을 셀 뿐, **링크 자신의 `g` 를 낮춰 자리를 만들 생각을 못 한다.**

## §4 할 일 — **기준은 유도한다. 관측하지 않는다**

### Step 1 — **부등식을 링크에 옮겨 적는다** ✅ 완료 (2026-09-04)

**기준은 이미 있었다.** `depthBudget` 의 부등식이 그것이고, **링크에 적용을 안 했을 뿐**이다.
눈금 넷이 그 부등식의 네 형태다 — `linkDepthNeed` (`module/arith/depth.ts`):

```
"free"           오늘 그대로 앉는다        면마다 L_f ≤ R_f
"opposite-face"  반대 면을 열어야 앉는다    ΣL ≤ ΣR       — 관통을 **유지한 채** 옮긴다
"direct"         g=1 로 내려야 앉는다      면마다 R_f ≥ 1 — 여기서부터 포트를 낸다
"depth-starved"  깊이가 아예 없다          줄 있는 면의 R_f = 0
```

> **"사다리 1단·2단" 이라고 안 부른다** (2026-09-04 정정). 그 낱말은 이미 **링크 토막내기**
> 사다리의 것이다(`LadderRung` — 구간막힘 1단 · 포트막힘 2단, `자리-배정` 이 지금 2단 작업 중).
> 처음 이 계획서가 "사다리 0~3단" 으로 적었는데 **충돌이라 눈금 이름으로 바꿨다.**

```
L_f  그 면이 받는 **링크 입력 줄 수** = 트리 안에서 만드는 재료 종류 수 (= 자식 수)
R_f  그 면의 깊이 수 = |reach 종류|
```

**둘 다 배치보다 먼저 아는 입력이다** — 그래서 이 기준은 **유도**되지 관측되지 않는다.

**검산:** `advanced-circuit` E 면 `L = 3 · R = 2` → 0단 위반. **실측한 실패와 일치한다.**
2단 부등식은 `module/arith/depth.ts` 에 **이미 그 문장 그대로** 있다 — 링크를 `taken` 으로만 보는
것이 유일한 차이다(§2).

> **오늘 배치의 분포로 기준을 세우지 않는다.** `격자-클러스터/CLAUDE.md` 가 **오늘
> (2026-09-04) 같은 함정을 밟고 철회**했다 — *"새 기능의 근거를 옛 산출물에서 찾으려 했다.
> 오늘 트리는 오늘 모델이 받아들인 것이라, 그 기능이 필요한 입력은 거기 **있을 수가 없다**."*
> 여기서는 더 직접적이다: **넘치는 모듈은 실패해서 산출물에 아예 없다.**
> 실측은 **유도한 기준이 그 실패를 재현하는지** 보는 회귀로만 쓴다.

```
전제  L_f 와 R_f 가 배정 **이전**에 결정된다. 확인: `L` 은 링크 줄의 품목 종류 수,
      `R` 은 `clusterBeltDepthsOf` — 둘 다 좌석표를 안 본다              ✅ 확인됨
불변  판정이 `advanced-circuit` 을 **`"free"` 가 아니라고** 해야 한다. 기전: `L=3 · R=2` 는
      입력만으로 나오는 값이고 `LinkDepthInput` 에 rate·count 가 **아예 없어** 다른 답을
      낼 재료가 없다                                                    ✅ 테스트로 잠김
관문  *"면이 얼마나 넉넉해야 하고 아이템이 몇 종부터 막히나"* 가 **부등식으로** 답해진다
      → **`R = 2` 인 오늘 게임데이터에서 재료 3종부터**                    ✅ 열렸다
```

#### 착수해서 알게 된 것 셋

**① `"direct"` 까지 내려가면 깊이는 더 이상 한계가 아니다.** `g=1` 줄들은 면당 공용 깊이
**하나**를 함께 쓰므로 줄이 몇이든 담긴다(`L: 99 · R: 1` 도 `"direct"` 다). 그래서
**`"depth-starved"` 는 깊이가 0 인 면에서만 나고, 진짜 벽은 좌석**(`Σ_j a_j(m) ≤ h`)이다 —
그건 `tryLinkFace` 의 몫이라 이 판정이 안 본다.

**② 눈금의 순서가 유도됐다.** `"opposite-face"` 가 `"direct"` 보다 싼 것은 취향이 아니라
**관통을 유지하느냐**다 — 반대 면은 줄을 관통인 채로 옮겨 토막 수 `c` 가 안 늘고, `c` 가 곧
포트 수다. `"direct"` 는 `c = N` 이라 양끝 모두 머신 수만큼 낸다. **Step 2 에서 A/B 로 정하려
했던 순서의 절반이 여기서 나왔다.**

**③ 깊이 0 은 그 면의 사실이지 판정이 아니다.** 첫 테스트가 *"줄 있는 면의 R=0 이면
depth-starved"* 로 적혔다가 틀렸다 — 반대 면에 자리가 있으면 `"opposite-face"` 다.
**판정은 모듈 전체를 보고서야 선다.** (틀린 쪽이 테스트였다.)

### Step 2 — **반대 면이 납품 경로를 깨뜨리나** ✅ 잰 만큼은 끝 (2026-09-04)

### Step 2 — 옛 서술 (참고)

> **물음이 좁아졌다.** 원래는 *"1단과 2단 중 무엇이 싼가"* 였는데, **비용 순서는 Step 1 에서
> 유도됐다**(알게 된 것 ②). 남은 것은 **값이 아니라 성립 여부**다 — 반대 면에 앉은 링크
> 입력이 실제로 납품 경로를 얻나. `planModulePorts` 가 자기 줄로 그 길을 이미 쓰지만
> 2026-08-05 에 **납품 1건이 실패**한 기록이 있다.

**분포는 이미 한 번 봤다** (2026-09-04 실측 — `judgements.md` J14):

```
advanced-circuit    앉는다 4 · 넘침 1 (반대면 1 · **다이렉트 0**)
                    n0-advanced-circuit → opposite-face (W 0/2 · E 3/2)
```

**반대 면이 두 칸 통째로 비어 있는데 링크가 못 간다.** 그래서 이 표본에서 (나)는
`spillPair` 의 **상수 하나**이고, (가)는 **한 번도 필요하지 않았다.**

그러니 Step 2 에 남은 물음은 하나다 — **반대 면에 앉히면 납품이 깨지나.**
켜 보고 `납품` 줄(`계획대로 / 탐색폴백 / 실패`)을 대조한다. 표본이 하나이므로 다른 트리도
같이 본다(다이렉트가 필요한 트리가 있으면 J14 가 (ㄴ)/(ㄷ) 로 옮겨간다).

### Step 3 — **다이렉트도 붙여 두 성공끼리 비교** ✅ 잰 만큼은 끝 (2026-09-04)

> **비교가 성립하지 않았다 — 다이렉트가 성공을 못 만들기 때문이다.** 그것이 답이다.
>
> ```
> 반대면만    ✅ errors 0 · 셀 1984 · 납품 실패 0     면깊이 배정  96 · fan-out 6
> 다이렉트만  ❌ errors 1 · n2 [input:kr-silicon]     면깊이 배정 137 · fan-out 10
> 둘 다       ❌ errors 2
> ```
>
> **실패가 링크 입력에서 원료 입력으로 옮겨 갔다** — 포트를 낸 대가로 면 자리를 먹어
> *나머지 줄*이 못 앉는다. 계획이 예측한 그 대가가 수로 나왔다(배정 96 → 137, **+43%**).
>
> 그래서 J14 의 미확정 둘(`dijkstra 7/16` · `check 8건`)은 **여전히 미확정**이다 —
> 비교 대상이 안 생겼다. 다른 자가 필요하다.

### Step 4 — 사다리로 만든다 (방향)

오늘 두 플래그는 각자 **무조건** 적용한다. 사다리는 *"반대 면으로 해 보고, 그래도 못 앉는
줄만 내린다"* 이고 — 그건 배정 결과를 보고 되먹임해야 하므로 **`seatLinkEdge` 안**이다.
실측이 그 순서를 지지한다(반대면 단독이 유일한 성공).

### 옛 Step 3 — 눈금을 실제로 붙인다 (참고)

`"opposite-face"` 는 `spillPair` 의 `OUT`/`IN` 에 반대 면을 넣는 일이다(§3 사실 ②가
그 선례). `"direct"` 는
`edgeLinkGroups` 에 `{side, g: 1}` 을 주는 일이다 — **밸브는 이미 있다.**

### Step 4 — 깊이 예산이 링크까지 본다 (방향)

고른 답을 `planBundles` 가 내게 한다. 그러면 링크와 나머지 줄이 **같은 예산**을 나눠 쓴다 —
오늘처럼 링크가 먼저 다 먹고 나머지가 남은 것을 받는 구조가 아니게 된다.

> **순서 주의.** 이 단계는 `modulePacking` 의 간선 루프에서만 가능하다(자식·부모 좌석표를
> 둘 다 보는 유일한 자리). 그런데 `planBundles` 는 모듈 **하나**의 함수다 — 이 어긋남을
> 착수 전에 다시 확인한다. 그리고 링크는 면을 못 넘으므로 **면별로** 세야 한다(→ **J14**).
