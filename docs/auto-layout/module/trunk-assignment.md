# 부록 A — 무대와 낱말 (계획서 §1~§8 이관)

## A1. 무대 — 격자 위의 네 가지

| 것 | 차지 | 규칙 |
|---|---|---|
| **머신** | `W×H` | 자기 타일 밖으로 아무것도 안 한다. 아이템은 **인서터를 통해서만** 드나든다 |
| **인서터** | 타일 **1** | 한쪽에서 집어 반대쪽에 놓는다. `reach r` = `r` 칸 건너 |
| **벨트** | 타일 1 | **방향이 하나**. 아이템이 그 방향으로 흐른다 |
| **포트** | 타일 1 | 모듈 경계. 밖과 주고받는 유일한 창구 |

머신 면에서 바깥으로 센 거리 `d`:

```
d0   머신 자신의 가장자리
d1   머신에 붙은 첫 칸        ← 인서터 좌석
d2   reach 1 이 닿는 곳
d3   reach 2(긴팔)가 닿는 곳
```

**물리 하나:** 좌석 `d` 의 인서터는 `d + r` 을 집는다. 그래서 **벨트가 깊을수록 긴 팔이
필요**하고, 팔 종류가 유한하므로 **한 면에 겹쳐 놓을 수 있는 벨트 줄 수도 유한**하다.

## A2. 다이렉트 / 트렁크 — 정확히 무엇인가

### 다이렉트 — 머신 하나, 품목 하나

```
        ┌───────┐
   ▣ ←i │  M1   │    ▣ 포트  i 인서터(d1)  ║ 벨트(d2)
   ║    │       │
   ║ ←i │       │
        └───────┘
```

벨트가 **머신 하나만** 상대하므로 남의 행을 안 지난다 → **다른 품목이 같은 깊이를 행으로
나눠 쓸 수 있다.** 대가는 포트가 `머신 수 × 품목 수`.

### 트렁크 — 여러 머신의 인서터가 같은 벨트를 쓴다

```
        ┌───────┐
   ▣ ←i │  M1   │     인서터 넷이 벨트 하나를 공유
   ║ ←i │       │     → 포트 1개 (다이렉트였다면 3개)
   ║    └───────┘
   ║    ┌───────┐
   ║ ←i │  M2   │
   ║    └───────┘
   ║    ┌───────┐
   ╚ ←i │  M3   │
        └───────┘
```

> **"합친다"의 정확한 뜻:** 다이렉트 벨트 `N` 개(각자 포트 하나)를 **벨트 하나 + 포트 하나**로
> 바꾼다. **인서터 개수는 그대로다** — 머신이 필요로 하는 처리량은 안 변하니까.
> 병합은 처리량을 바꾸는 게 아니라 **배선을 바꾸는 것**이다.

## A3. 합치기가 성립할 조건 — 여섯

| # | 조건 | 어긋나면 |
|---|---|---|
| **①** | **같은 품목** | 두 품목이 한 벨트에 섞인다 |
| **②** | **같은 방향** — 전부 공급이거나 전부 수거 | 벨트 방향이 하나뿐이라 불가 |
| **③** | **부하 ≤ 벨트 용량** | 포화 → 뒤쪽 머신이 굶는다 |
| **④** | **도달가능** — 머신마다, 그 머신에 닿으면서 벨트에도 닿는 **좌석 타일**이 존재 | 그 머신은 이 트렁크에서 못 먹는다 |
| **⑤** | **연속** — 포트에서 모든 집는 지점까지 끊김 없이 | 구멍 너머는 아이템이 안 간다. **겹침도 미배치도 아니라 아무도 못 잡는다** |
| **⑥** | **비충돌** — 벨트·좌석·포트가 머신·남의 벨트·남의 좌석·파이프와 안 겹친다 | 배치 실패 |

**④가 기하의 전부다.** 형식으로:

> 머신 `M`, 벨트 `B` 에 대해 타일 `s` 가 존재해 — `s` 는 `M` 에 인접하고,
> `B` 의 어떤 타일 `b` 에 대해 `dist(s, b) = r` 인 인서터가 있다.

## A4. 맞바꿈 — **문제의 심장**

| | 다이렉트 | 트렁크 |
|---|---|---|
| **포트 수** | 머신 × 품목 | **품목당 1** ← 얻는 것 |
| 벨트가 지나는 타일 | 머신 하나 주변 | **여러 머신을 잇는 길 전체** ← 치르는 것 |
| 같은 깊이를 남과 나눠 쓰기 | **된다**(행 구간 서로소) | **안 된다**(길을 통째로 차지) |

> 트렁크는 포트를 줄이는 대신 **자리를 더 먹는다.** 그리고 **얼마나 더 먹느냐가 길의
> 모양에 달려 있다.** 이 한 줄이 §5~§7 전부의 근원이다.

## A5. 직선은 **특수해**다

지금 트렁크는 한 면을 따라 달리는 직선이다. **그 형태에서만** 나오는 제약이 셋:

```
직선이면 →  ① 머신들이 그 선 위에 나란히 있어야 한다      → 기둥 형태 강제
            ② 그 면의 그 깊이를 선 길이만큼 통째로 먹는다  → 다른 품목이 그 면을 못 씀
            ③ 겹쳐 놓으려면 더 깊이 → 더 긴 팔 → 팔 종류 수가 상한
```

**셋 다 "직선"에서 나온 것이지 "트렁크"에서 나온 것이 아니다.**

> **2026-08-13 실패의 정체가 이것이다** — 이 셋을 트렁크의 성질로 착각하고
> 새 코드에 그대로 옮겨 심었다(§10).

## A6. 그래서 모델의 핵심 객체는 **경로**다

```
   ┌────┐
   │ M1 │──┐          · 머신이 나란할 필요가 없다
   └────┘  │          · 지나가는 타일만 먹는다
   ┌────┐  ├──▶ ▣     · 두 트렁크가 안 만나면 깊이를 다툴 일이 없다
   │ M2 │──┤
   └────┘  │
      ┌────┴─┐
      │  M3  │
      └──────┘
```

> **기둥에서는 이 경로가 구간 하나로 퇴화한다** — 자유도가 (레인, 구간 양끝) 셋뿐이다.
> 일반형이 필요해지는 것은 격자(J4)부터다. 무엇을 어떻게 고르는지는 **§9.7**.

> **트렁크 = (경로 `P`, 좌석 집합 `S`, 끝점)**
> `P` = 연결된 벨트 타일 열 · `S` = {(머신, 좌석)} 로 각 좌석이 자기 머신과 `P` 에 동시에 닿음
> **직선 트렁크는 `P` 가 직선인 특수해다.**

"면"과 "깊이"는 모델의 **축이 아니다.** 직선일 때 나오는 **좌표의 별명**일 뿐이다.

### 경로는 **두 종류의 조각**으로 갈린다

머신 하나가 팔 `k` 개를 쓰면 좌석도 `k` 개고, 좌석마다 닿는 벨트 타일이 있어야 한다.
**머신의 탭 자리는 점이 아니라 길이 `k` 의 지상 주행이다.**

```
▣ ──연결──▶ ═══ ──연결──▶ ═══ ──연결──▶ ═══
             M1탭          M2탭          M3탭
   ↑ 탐색한다   ↑ 구성한다(계산)
```

| 조각 | 누가 정하나 | 성질 |
|---|---|---|
| **탭 주행** | **구성**한다 — 좌석 수·면에서 바로 나온다 | **정의상 지상**. 여기가 일하는 자리다 |
| **연결 구간** | **열거**한다 — 후보가 손으로 셀 만큼이다(§14-2) | 여기서만 꺾이고, 여기서만 지하로 간다 |

> **이 갈래의 기하가 §14 에서 확정됐다**(2026-08-14): 탭 주행은 **세로만**,
> 연결은 **가로만**, 그리고 가로 행의 개수가 코너 후보의 개수다.

이 갈래가 하나를 공짜로 준다: **연결 구간이 지하로 가도 탭에 지장이 없다**
(지하 위에서는 인서터가 못 먹인다 — judgements J12).

## A7. 좌표 문제 — 고리를 어디서 끊나

```
경로를 짜려면   →  머신이 어디 있는지 알아야 한다
머신을 놓으려면 →  벨트·좌석이 자리를 얼마나 먹는지 알아야 한다
```

지금 코드는 **직선이라서** 고리를 끊는다 — 직선이 먹는 폭은 좌표 없이 계산된다
(`gap 폭 = 깊이 수`). **경로가 되면 그 계산이 불가능하다.**

**그래서 반대쪽에서 끊는다: 머신을 먼저 놓고, 그 위에서 경로를 예약한다.**

이것은 예약 철학에 **어긋나지 않는다.** 철학은 *"좌표를 모르라"* 가 아니라
*"큰 그림을 보는 **주체 하나**가 자리를 먼저 잡고, 방출은 탐색 없이 놓기만 한다"* 이다.
그리고 **이 저장소에 이미 그 패턴이 있다** — `channelGeometryPlanner`·`deliveryRoute` 는
모듈이 놓인 뒤 좌표 위에서 경로를 **예약**하고 `emitPath` 는 덧셈만 한다.

> **진짜 남는 문제는 하나:** 경로를 짜다 자리가 없으면 무엇을 되돌리나(§9-마).
> 지금은 gap 폭이 그 되먹임을 암묵적으로 한다. 경로 모델은 그걸 **명시해야** 한다.

## A8. 끝점은 두 종류다 — 포트 | 머신집합

| | 트렁크의 양 끝 |
|---|---|
| **외부 줄**(원료·완제품) | 한쪽 **머신들**, 다른 쪽 **포트**(모듈 경계) |
| **내부 링크**(자식→부모) | **양쪽 다 머신들** — 이상적으로 포트가 **없다**(자식이 벨트에 놓고 부모가 그 벨트에서 집는다) |

외부만 보고 설계하면 타입에 *"끝은 포트"* 가 박히고, 내부 링크를 넣을 때 **핵심 타입을
고쳐야 한다.** 그리고 내부 링크는 **모듈 둘이 합의**해야 해서 `module/`(형제를 모른다)의
경계를 넘는다.

> **결정:** 끝점을 처음부터 **`포트 | 머신집합`** 둘 다 받게 정의하되,
> **구현은 외부 줄부터.** 타입이 열려 있으면 확장이 안 깨진다.

# 본문 — 배정 모델

## 1. 자원 — 면 하나가 가진 것

```
        d1        d2 .. d(1+R)         d(2+R)      d(3+R)
      좌석 열       벨트 레인          포트 인서터    포트 상자
      행으로 나눔    깊이 축. R = |reach 종류|
```

**레인에는 두 축이 있다.** 이것이 §5 의 전부다.

```
깊이 축   면당 R 개.   한 레인이 최대 N 대를 먹인다        ← 긴 팔이 있어야 쌓인다
행   축   연 gap 마다 가로 한 줄. 한 줄이 **정확히 2대**   ← 긴 팔 없이도 쌓인다
```

**인서터 물리** — 좌석 `s`, reach `r`, 벨트 `b = s + r`, 그리고 `s ≤ r`.
`ℛ={1,2}` 에서 동시 성립 조합은 `{(1,1),(1,2)}`(belts d2·d3) 또는 `{(1,2),(2,2)}`(belts d3·d4).
**개수는 `R` 로 유일하고 깊이 배열은 유일하지 않다**(유체가 d2 를 먹은 면에서 차이가 산다).

## 2. 수요 — 수 넷이면 끝이고 분기문이 없다

```
k_j = ⌊벨트처리량 / per_j⌋     한 벨트가 맡을 수 있는 머신 수
g_j = min(k_j, N)              묶음 크기 — 처리량이 준 **상한**       ← TR1
c_j = ⌈N / g_j⌉                구간 수(상한일 때)
a_j(m)                          머신 m 에서 이 줄이 쓰는 팔 수
```

`c=1` 관통 · `c=N` 다이렉트 · 그 사이가 부분 병합 — **한 공식의 구간이지 다른 형태가 아니다.**

#### 실제로 어디서 자르나 — **못을 피해서** (2026-08-26 정정)

옛 서술은 *"앞에서부터 `g` 대씩, 나머지는 뒤"* 라는 **균등 분할**이었다. 폐기한다 —
자리가 요구하는 자름과 균등 분할이 **우연히만** 일치한다.

```
못(nail) = 얕은 레인 줄의 **포트 인서터**가 다음 레인에 서는 칸
           포트는 자기 구간의 진출 행에 `d+1`·`d+2` 로 서므로, 레인 `d` 에 앉으려는 줄에게
           **레인 d−1 에 앉은 줄들의 진출 행**이 전부 못이다
```

**자름은 못이 정한다** — 못이 `n` 개면 토막이 `n+1` 개다:

```
막힌 행 [90, 180]  →  [1,88] · [91,178] · [181,268]        토막 3, 포트 3
```

> **2026-08-26 실측이 이 정정을 요구했다.** `electronic-circuit`(머신 100대)에서
> `copper-cable` 이 네 토막으로 잘리며 `d3` 에 못을 박았고(행 `0·90·180·270`),
> `stone-tablet`(관통 90대 한 줄)이 `d2`·`d3` 을 다 못 써서 **트리가 거절됐다.**
> 이번엔 노란 줄이 머신 30·60 에서 잘려 균등 분할과 우연히 같았지만, 40/40/20 로
> 잘렸다면 못이 `120·240` 에 서고 균등 분할은 **빗나간다.**

**균등은 못이 없을 때의 특수해다** — 못이 0개면 `c_j` 대로 앞에서부터 `g` 대씩 자른다.

### 4.1 레인을 먹는 것은 구간이 아니라 **팔이 앉은 행**이다 (2026-09-01 정정)

위 약분은 *한 구간이 `g×h` 행을 먹는다* 를 전제로 했다. 그게 틀렸다 —
벨트가 덮는 행은 **그 줄의 팔이 앉은 행**이지 머신 면 전체가 아니다
(`linkPlanner.beltRowSpan`: 머신마다 `freeSeatRows(mi).slice(0, k)` 의 처음·끝).

```
g = 1   구간 하나 = 머신 한 대의 `a_j(m)` 행       → 여러 품목이 한 레인을 **나눠 쓴다**
g > 1   구간 하나 = 첫 머신 첫 행 … 끝 머신 끝 행   → **사이 행까지 통으로** 먹어 레인을 독점한다
```

`beltRowSpan` 은 `[최소행, 최대행]` **하나**를 낸다 — 구멍이 없다. 그래서 머신을
걸치는 순간 그 사이의 남의 자리까지 문닫는다([laneClear] 가 칸으로 막는다).

**그래서 상한 ① 이 다시 서진다:**

```
면 f:   (g > 1 인 품목 수)  +  (g = 1 인 품목이 있으면 1)   ≤  R_f
```

즉 **`g` 가 상한에 들어간다.** `g = 1` 줄들은 레인 하나를 함께 쓰고(좌석이
허락하는 만큼), `g > 1` 줄은 하나씩 레인을 다 가진다.

> **이것이 TR1 의 *"실제 `g` 는 자리가 정한다"* 에 붙는 이빨이다.**
> 처리량이 `g_max` 를 주고, **레인 예산이 거기서 더 깎는다.**

**그리고 여기서 맞바꿈이 나온다** — 같은 품목 수를 두 가지로 담을 수 있다:

```
품목 3 · R = 1 (긴팔 없음) · N = 2

(가) 전부 g = 1    레인 하나를 셋이 나눠 쓴다      포트 6개 · gap 안 벌림  ← **오늘의 동작**
(나) 둘은 g = 2   레인 둘을 독점, 셋째는 gap 으로   포트 4개 · gap 이 벌어진다
```

**어느 쪽도 틀리지 않다** — 포트를 줄일지 모듈을 작게 할지의 문제다. 그래서 이것은
모델이 혼자 정할 수 없고 **사용자 손잡이**다 — 축과 선택지는 §4.3, 기본값은
**공짜일 때만 관통**이다(2026-09-01 사용자).

### 4.2 **"공짜"** 의 정확한 뜻 (2026-09-01 사용자 확정)

> **공짜 = 그 관통을 줘도 *다른 줄이 밀리지 않는다*.**
> 즉 **모듈이 안 커진다** — gap 이 안 벌어지고, 어느 줄도 자리를 잃지 않는다.

관통은 레인을 하나 독점하므로(§4.1), 공짜인지 아닌지는 **레인이 남나**로 판정된다:

```
모듈 전체:   (g>1 줄 수)  +  (g=1 줄이 있으면 **면 수**)   ≤   Σ_f R_f
                             └ 그 줄들은 면마다 공용 레인 하나씩을 쓴다
```

**둘째 항은 g=1 줄이 하나라도 있을 때만 붙는다.** 그래서 줄이 전부 관통이면 상한은
그냥 `줄 수 ≤ Σ R_f` 이고, **한 줄이라도 내려가는 순간 예산이 면 수만큼 줄어든다** —
그 연쇄가 이 규칙의 핵심이다(§4.2.1 의 `R=1` 이 그 결과다).

> **면마다 따로 세지 않는다** — §4 의 좌석 예산과 같은 이유다. 선호 면이 차면 반대 면으로
> 넘어가므로(`spillLinkFacesToGap`), 면마다 세면 **넘어갈 수 있는 자리를 없다고 센다.**
> (2026-09-01 실측: `electric-motor` 4줄이 E 의 두 레인만 보고 둘을 내렸다 — 실제로는
> W 의 남은 레인으로 넘어가 넷 다 관통이 선다.)

> **유체 면도 레인으로 센다.** 선호 단계는 유체 면을 비켜 가지만 넘침 단계가 되찾아 온다
> (§10 — 파이프가 지하로 벨트를 넘어 좌석 줄이 산다). 유체 면이 좁다는 사실은 이미 `R_f`
> 안에 있다(지하파이프 사거리가 그 면의 레인을 깎는다) — **두 번 깎지 않는다.**
> (2026-09-01 실측: `plastic-bar` 3줄을 W 한 면으로 몰아 둘이 헛되이 `g=1` 로 떨어졌다.)

#### 정하는 절차 — **한 방향으로만 흐른다**(되먹임 없음)

```
1  줄마다 g_max 를 낸다        ⌊벨트 처리량 ÷ per⌋ 와 N 중 작은 것            ← TR1
2  남은 레인을 센다            Σ_f R_f  −  링크가 이미 독점한 레인
3  위 부등식을 확인한다
4  넘치면 **우선순위가 낮은 줄부터** g = 1 로 내린다
   (출력 → 자식-공급 입력 → 원료 입력 순이고, 뒤에서부터 내린다)
5  다시 3 으로. 예산이 단조 감소하므로 **반드시 끝난다**
```

#### 이 판정에 **행(좌표)이 필요한가 — 아니다**

들어가는 값이 전부 **주어진 수**다:

```
R_f       인서터 reach 종류 수(유체 면이면 지하파이프 사거리로 깎임)   ← 스펙
a_j(m)    ⌈per_j ÷ tp(reach)⌉                                     ← 수요 + 스펙
h_f       머신 면 칸 − 유체 상자 행                                 ← 스펙
우선순위   역할이 정한다(출력 → 자식-공급 → 원료)                     ← 정책
```

**면조차 안 물어도 된다** — 예산이 모듈 전체라 *"어느 면에 앉나"* 는 배정의 몫으로 남는다.

**좌석만 맞으면 레인은 저절로 맞는다** — `g=1` 줄의 벨트 조각은 자기 팔이 앉은 행만
덮으므로, 좌석이 서로 다른 행에 배정된 이상 **겹칠 수가 없다.** 그래서 `Σ_j a_j(m) ≤ h_f`
하나로 충분하고 *"몇 번째 행"* 은 안 물어도 된다.

> **다만 이 판정은 보수적이다.** 관통 줄이 마지막 머신의 좌석을 다 안 쓰면 그 **꼬리 행**은
> 비는데, 이 부등식은 그걸 안 센다 — *"앉을 수 있는데 못 앉는다고 한다"* 가 남는다.
> 행을 봐야 알 수 있는 이득이고, **행을 안 보기로 한 대가**다. 기본값이 보수적인 것은
> 옳다(모듈이 커지는 쪽으로 틀리지 않는다).

#### 전제 — **벨트가 지상으로만 간다** (2026-09-01 사용자)

이 부등식은 *"관통 벨트가 첫 팔에서 끝 팔까지 **지면을 계속 덮는다**"* 를 전제한다.
그래서 사이 행이 통째로 죽고, 레인 하나가 줄 하나에 묶인다.

**지하 벨트가 생기면 그 전제가 깨지고 공짜의 범위가 넓어진다.** 관통 줄이 팔 없는
구간을 **잠수해서** 지나가면 그 행의 지면이 살아나므로, 같은 레인에 다른 줄이 들어올
수 있다 — 즉 `R_f` 는 그대로인데 **한 레인이 담을 수 있는 줄이 는다.**

```
지금(지상만)   관통 1줄  =  레인 1개              사이 행까지 죽는다
지하 생기면    관통 여럿  =  레인 1개도 가능       팔 행만 살아 있으면 된다
               (대신 지상 복귀 칸 · 사거리 · 두 벨트가 안 만날 것을 세야 한다)
```

**이건 아직 없는 능력이다** — §7 의 TR7 (나) *잠수* 가 코드에 없다(§0 표).
그러니 §4.2 의 부등식은 **"지하가 없는 동안의" 공짜 기준**으로 읽어야 하고,
잠수가 들어오면 **다시 세야 한다**(느슨해지는 방향이라 오늘의 배치는 안 깨진다).

#### 4.2.1 `R = 1` 일 때 — **관통은 품목 둘까지**

긴팔이 없으면 `R_f = 1` 이라 부등식이 아주 좁아진다:

```
Σ R_f = 2 (W1 + E1)     ·     g=1 줄이 생기면 예약이 2 → 예산 0
```

**그래서 `R=1` 에서 관통이 서는 것은 품목이 정확히 둘일 때뿐이다** — 즉
**입력 1 + 출력 1**(예: `kr-sand` = stone → kr-sand). 그때만 `2 ≤ 2` 로 딱 맞고,
아무도 `g=1` 이 아니라 예약이 안 켜진다.

품목이 셋이면 **전부 다이렉트**가 된다 — 하나를 내리는 순간 예약 2가 켜져 예산이 0이 되고,
나머지도 따라 내려간다:

```
출력 1 + 입력 2 · R=1
  관통 3  >  레인 2                    → 원료 입력 하나를 내린다
  관통 2  >  2 − 2 = 0                 → 나머지도 따라 내려간다
  ⟹ **셋 다 다이렉트.**  레인 하나를 셋이 나눠 쓴다(오늘의 동작 그대로)
```

> **이 연쇄가 보수성의 값이다.** 출력 하나만 관통시키고 입력 둘을 다이렉트로 두면 포트가
> 둘 줄지만, 그 둘이 좌석 넘침으로 반대 면에 밀렸을 때 **관통이 먹은 레인 때문에 갈 곳을
> 잃는다**(2026-09-01 실측: 일곱 줄 스펙에서 포트 하나가 사라졌다). 공짜의 정의가
> *"아무도 안 밀린다"* 인 이상, 밀릴 **가능성**이 있으면 안 사는 것이 맞다.

### 4.3 손잡이 — **자리를 얼마나 내주고 포트를 살 것인가**

§4.1 의 (가)·(나)는 대립하는 두 정책이 아니라 **한 축의 두 지점**이다:

```
        관통을 덜 산다 ←────────────────────────────→ 관통을 더 산다
        포트 많다 · 모듈 작다              포트 적다 · 모듈 크다

  ①  공짜만            남는 레인에만 관통.  **모듈이 절대 안 커진다**      ← 기본값
  ②  gap N칸까지       gap 을 N칸 벌리는 데까지 관통을 산다
  ③  포트 최소         필요한 만큼 벌린다.  관통을 최대로
```

**기본값은 ① 이다**(2026-09-01 사용자). 근거는 최적화 우선순위다 — *"머신 100% 가동이
최우선"* 인데, ②·③ 은 자리가 모자랄 때 **못 앉는 줄**(= 굶는 머신)을 만들 수 있다.
①은 정의상 그럴 수 없다: 공짜가 아니면 안 사기 때문이다.

```
① 이 보장하는 것   관통을 켠다고 **모듈이 커지지도, 줄이 밀리지도 않는다**
                   ⟹ 언제 켜도 손해가 없다 → 손잡이 없이 항상 켜도 되는 유일한 지점
②③ 이 파는 것     포트 수(= 밖과의 접점 · 인서터 · 상자)
②③ 이 치르는 것   모듈 높이(gap) — 그리고 그 높이는 **클러스터 전체로 번진다**
```

> **왜 ②·③ 을 지금 안 만드나.** 손잡이의 값이 gap 폭이고, gap 을 벌리는 트렁크 형태는
> 기둥이 아니라 **격자**가 된다 — 그건 격자 클러스터의 몫이다(2026-08-30 범위 밖 확정).
> 그때 이 축이 **그대로** 손잡이가 된다: ①은 `gap 예산 = 0`, ③은 `gap 예산 = ∞`.

**넘으면 행 축으로 간다** — gap 을 연다(§5). *어느 품목을 내리나*는 미결(judgements **J2**).

## 5. 두 축 — 긴팔이 없으면 gap 으로 산다

`ℛ={1}` 이면 `R=1` → 면당 레인 1 → **관통(`g>1`) 품목은** W+E 로 2개가 한계다.

> **그런데 품목 3개가 밀착 기둥에 선다** — 예전엔 여기가 *"불가능"* 이라 적혀 있었고,
> 그것이 §4 의 약분 오류와 같은 뿌리다. 셋 다 `g=1` 이면 머신마다 한 행씩만 먹어
> **한 레인을 나눠 쓴다**(§4.1). 실제로 코드가 그렇게 놓는다 —
> `clusterModule.test.ts` *"아이템 3줄이 유체 면을 비켜 W 3칸에 앉는다"*(battery, `ℛ={1}`).
> gap 이 필요해지는 것은 **좌석이 챙을 때**이지 레인이 모자랄 때가 아니다.


## 6. 지하 — 건너지는 쪽이 들어간다

`y=t` 행에서 얕은 레인 A 가 깊은 레인 B 를 건너려 할 때, **A 는 점프를 시작할 수 없다**:

```

```

A 는 코너에 **남쪽으로** 도착하므로 남쪽으로만 점프할 수 있다. **B 가 잠수해야 한다:**

```
 y=t-1   ⊐   ║      ⊐ B 지하 입구 (남쪽 도착 → 남쪽 점프 ✓)
 y=t    ══╝  ·      ← A 가 지상으로 지나간다.  B 의 corridor 는 axis='v'
 y=t+1   ⊏   ║      ⊏ B 지하 출구
         B   A
```

**대가:** B 는 행 `t` 에서 탭을 못 한다(몸통이 땅속). 그 행에 B 의 좌석이 없어야 한다.
**언제 쓰나는 미결** — J3(모든 줄이 관통이면 구멍이 없다).

## 10. 지하는 **아끼는 자원이 아니다** (2026-08-14 정정)

§16 는 지하를 *"`(축, 티어)` 배타권이라는 한정 자원"* 이라 적었다. **모듈 안쪽에서는 그렇지 않다.**

```
containerRouting.isJumpAllowed
   같은 blockGroup ∧ 같은 axis ∧ 같은 line  →  range 가 strict disjoint 여야 한다
   line 이 다르면  →  **검사 자체를 건너뛴다**
```

레인 하나(`axis='v'`, `line=x`)는 **그 트렁크가 이미 독점**하고 있다. 그러니 같은 line 위의
corridor 들은 서로만 안 겹치면 되고, 그건 자기 구간을 자기가 쪼개는 것이라 **다툴 상대가 없다.**

> **§16 의 "한정 자원"은 채널 층(모듈 사이)에서 여러 경로가 같은 line 을 다툴 때의 이야기다.**
> 모듈 안쪽 트렁크에는 적용되지 않는다.

**인접한 두 행을 건너야 하면 하나로 합친다.** 계단(§3 ③)에서 얕은 레인 둘이 `t`, `t+1` 에서
같은 깊은 레인을 건너야 할 때, corridor `[t−1, t+1]` 과 `[t, t+2]` 는 겹쳐 둘 다는 못 판다.
대신 **`[t−1, t+2]` 하나**로 판다 — 몸통이 `t`·`t+1` 둘이 되고 그 두 행의 탭만 잃는다.
필요 점프 길이 3 은 바닐라 `transport-belt`(`max_underground_distance = 4`) 안이다.

**(나) 끊기로 떨어지는 경우 — 규칙으로**

```
① 그 벨트에 지하 변종이 없다              maxJumpDistance = 0
② 필요한 점프 길이 > max_underground_distance   (합쳐야 할 인접 행이 너무 많다)
③ 잠수 구간의 몸통 칸이 그 트렁크의 탭 행이다   탭을 잃으면 그 머신이 굶는다
```

## 11. 좌석 예산이 넘치면 — **gap 을 열어 N/S 면을 쓴다** (TR8)

밀착 기둥(`gap = 0`)에서 머신 한 대가 가진 좌석은 **W면 `h` + E면 `h` = `2h`** 뿐이다.
N/S 면은 **옆 머신의 몸통**이라 못 쓴다.

```
 y=88   ███████  ┐
 y=89   ███████  │ ← 이 경계가 M0 의 S면인데 바로 M1 이라 좌석이 없다
 y=90   ███████  ┘
```

**gap 을 열면 그 경계가 살아난다.**

```
gap = 3   (좌석 / 벨트 / 좌석)
 y=88   ███ M0 ███
 y=89    ·  [i]  ·      ← M0 의 S면 좌석.  남쪽(y=90)에서 집어 M0 에 넣는다
 y=90   ══ ══ ══ ══     ← 가로 벨트 **하나가 위·아래 두 대를 먹인다**
 y=91    ·  [i]  ·      ← M1 의 N면 좌석.  북쪽(y=90)에서 집어 M1 에 넣는다
 y=92   ███ M1 ███
```

```
좌석 예산    2h  →  2h + 2w      (w = 머신 폭.  3×3 이면 6 → 12)
```

**gap 은 전부 열지 않는다 — 머신 2대마다 하나면 충분하다**(TR11). 가로 벨트 하나가 위·아래
두 대를 먹이기 때문이다.

```
M0 ┐
   ├ gap  ← 가로 벨트가 M0(S) 과 M1(N) 을 먹인다
M1 ┘
M2 ┐      ← M1·M2 는 **밀착**.  여기 gap 을 열면 아무도 안 쓴다
   ├ gap  ← M2(S) · M3(N)
M3 ┘

4대 · h=3 · gap=3    전부 열면 21행 · **2대마다 열면 18행** · 밀착이면 12행
N 대에 필요한 gap 수 = ⌈N/2⌉
```

`layoutCluster` 가 **이미 `rowGap: number | number[]` 를 받는다**(`clusterLayout.ts:51`) —
*"gap 은 자리마다 다를 수 있다. 그 gap 을 지나는 가로 벨트 수에서 유도되기 때문이다."*
**새 자료구조가 필요 없다.**

#### gap 폭은 가로 벨트 줄 수에서 유도된다 (2026-08-15 사용자 확인)

gap `g` 행: 맨 위가 위 머신의 S면 좌석, 맨 아래가 아래 머신의 N면 좌석, 가운데가 벨트.
좌석 `r` 은 `r + reach` 를, 좌석 `r+g−1` 은 `r+g−1−reach` 를 집는다. `ℛ = {1,2}` 로 세면:

```
g = 3   벨트 1줄  {r+1}                위 reach1 · 아래 reach1     → **양쪽 공유**
g = 4   벨트 2줄  {r+1, r+2}           위 reach1·2 · 아래 reach2·1 → **둘 다 양쪽 공유**
g = 5   벨트 3줄  {r+1, r+2, r+3}      가운데만 공유, 바깥 둘은 한쪽 전용
g = 6   벨트 4줄  {r+1..r+4}           **공유 0** — 가로 벨트의 이점(2대 동시)이 사라진다
```

> **`ℛ = {1,2}` 에서 "위·아래를 동시에 먹이는" 가로 레인은 최대 2줄이고 그때 `g = 4` 다.**
> 이게 면당 `R` 의 가로판이다 — 세로는 면당 `R` 줄, 가로는 gap 당 `R` 줄.
> `g` 를 더 벌리면 줄은 늘지만 **한쪽 전용**이 되어 좌석 예산이 안 는다.

**몇 줄이 지나가야 하는가는 요구에서 나온다** — 그 gap 이 맡은 두 대에게 N/S 로 공급해야 할
품목 수. 세로 레인 배정에서 밀려난 품목 수가 곧 그 수다.

> **이것이 *"한 자식 머신이 한 부모 머신에 여러 벨트로 전달하는 형태"* 의 실체다**(2026-08-15 사용자).
> 한 머신이 **W·E·N·S 네 방향**에서 벨트를 받는다.

**그리고 gap 행은 세로 트렁크가 공짜로 잠수하는 자리다.** 가로 벨트가 세로 레인을 건너야
하는데, 그 행에는 **어차피 탭이 없다**(머신이 없으니까) — TR7 (가)의 대가가 0 이 된다.

**gap 은 두 가지 부족을 동시에 푼다:**

```
레인이 모자라다 (품목 수 > R)      →  가로 레인이 생긴다        (TR4)
좌석이 모자라다 (Σa > 2h)          →  N/S 좌석이 생긴다         (TR8)
```

#### 폐기 — *"fan-out = 같은 레인을 행으로 나눠 쓴다"*

2026-08-14 에 내가 적었던 해석이고 **기하가 성립하지 않는다**:

```
레인 x=159 에 구리(offset 0)와 나무(offset 2)를 올리면
   구리 M0 = 86,  나무 M0 = 88,  구리 M1 = 89
                              88 과 89 가 **붙어 있다** → 두 벨트가 이어져 아이템이 섞인다
offset 0/1 로 해도 86-87 이 붙는다
```

**밀착 기둥에서 `h = 3` 이면 한 레인에 두 품목을 못 올린다.** 그러니 그 해석으로는 팔이 줄지
않는다. 실제 답은 위의 **gap** 이다.

## 12. 축의 정정 — **깊이는 결과이지 입력이 아니다** (2026-08-15 사용자)

> *"깊이에 대해서 저는 잘 모릅니다. 제가 아는 건 사용자가 선택한 인서터들 중 reach-1·reach-2 가
> 존재한다는 것이고, 그것들을 **정확하게 작동시키려면** 벨트를 깊이-2·깊이-3 에 두어야 한다는
> 사실뿐입니다. … 여러 머신의 **규칙성을 파악하기만 한다면** 깊이 개념을 몰라도 괜찮습니다.
> **인서터를 제대로 배치할 수만 있으면 됩니다.**"*

### 16.1 무엇이 축인가

```
축이 아니다   깊이 d2 · d3        ← 기둥에서 규칙성이 만들어 낸 **이름**
축이다        (인서터 i, 그 팔이 집는 타일)   ← 물리.  reach 는 고정 거리다
```

```
줄 j 를 인서터 i 로 먹인다  →  팔 개수  a(j,i) = ⌈ per_j / tp_i ⌉
팔 i 하나를 앉히려면        →  타일 둘.  **좌석**(머신에 인접) + **벨트**(좌석에서 reach_i 칸)
```

**"깊이"는 그 벨트 타일이 머신 면에서 몇 칸인지의 별명**일 뿐이다. `reach 1` 을 고르면 벨트가
`d2` 에, `reach 2` 를 고르면 `d3` 에 가는 것이지, **`d3` 를 고르고 나서 긴팔이 딸려 오는 게 아니다.**

### 16.2 그래서 순서가 뒤집힌다

```
지금 코드   팔 개수를 센다(reach 1 고정) → 앉힌다 → **깊이/reach 를 재배정**한다
            (옛 clusterPortPlanner.ts:402-427 — 수요 내림차순 ↔ throughput 내림차순 zip. 2026-09-02 삭제)
            ③이 ① 뒤에 있어 ①이 쓴 수가 무효가 된다

새 순서    **줄마다 인서터를 고른다** → 팔 개수가 그 인서터에서 나온다 → 타일을 예약한다
```

### 16.3 규칙성은 **결과**다

같은 레시피의 머신 `N` 대는 같은 줄 집합을 가지므로 **같은 인서터 배정이 반복**된다.
그래서 좌석이 같은 열에 늘어서고, 벨트가 같은 열에서 길어진다.

> **트렁크는 그 규칙성을 한 줄로 이어 붙인 것**이고, 이 문서 의 "깊이 레인"은 그 규칙성의 이름이다.
> **격자로 가면 규칙성의 모양이 바뀌지만 축은 안 바뀐다** — 여전히 `(인서터, 집는 타일)` 이다.
> 그래서 §12 은 이 문서를 폐기하지 않는다. 이 문서 는 **기둥에서의 §12** 이다.

### 16.4 이 문서를 읽을 때

```
이 문서 의 "깊이 d"      →  "reach = d−1 인 인서터를 골랐을 때 벨트가 놓이는 칸"
이 문서 의 "면당 R 레인"  →  "한 면에 동시에 세울 수 있는 서로 다른 (인서터, 벨트타일) 쌍의 수"
이 문서 의 tp(d)         →  tp_i  (그냥 그 인서터의 처리량)
```

**수는 전부 같다.** 바뀌는 것은 **무엇이 원인이고 무엇이 결과인지**뿐이고, 그것이
§18(하드코딩 금지)을 지키는 데 결정적이다 — 깊이를 입력으로 두면 `if (depth === 3)` 이 생긴다.

## 13. 권한 — 트렁크가 **포트 위치와 모듈 크기를 정한다**

```
트렁크 계획이 정한다        받는다
  · 경로                    · 머신 좌표(다이렉트 기준 배치)
  · 좌석                    · 레시피 줄 · 팔 수
  · 포트 위치
  · 모듈 크기  ← 경로의 부산물
```

**모듈 크기가 경로의 부산물**인 것은 오늘 `gap 폭 = 배정의 부산물` 과 같은 구조다
(`layoutCluster(rowGaps)`). 새 패턴이 아니라 있는 패턴을 한 겹 넓히는 것이다.
모듈이 커져도 **다른 모듈은 평행이동만 한다** — 그 외 영향은 없어야 한다.

그래서 §7 의 고리가 풀린다:

```
다이렉트 기준 머신 배치 → 트렁크 경로 예약 → 모듈 크기 확정 → 모듈 배치
```

#### ④ 채택안 — 조각 셋

**㉠ 후보(도형)** — 하나 = `(레인 d, 팔 수 a(d), 구간 [lo,hi], 진출 깊이, 포트 끝 | 옆)`.
채널의 `staircaseShape`·`elbowShape` 에 대응하는 **`combShape` 하나**면 된다.

> **구간은 입력이 아니라 후보의 결과다.** 레인이 인서터를 정하고(§12), 인서터가 팔 수를
> 정하고(`a = ⌈per / tp⌉`), 팔 수가 좌석 행을 먹고, 그 행들이 구간이 된다.
> `beltRowSpan`(`linkPlanner.ts:189`)이 **이미 그렇게 센다**(`used` 를 읽어 시작 행을 안다).
>
> **여기가 채널과 다른 유일한 점이다.** 채널은 출발·도착 행이 포트에 고정돼 구간이
> 상수인데, 트렁크는 **색(레인)을 고르면 구간이 바뀐다.** 그래서 순수 left-edge 를
> 그대로 못 쓴다 — 구간이 색에 의존하는 채색이다. **이것이 ㉢ 이 3단인 이유다.**

**㉡ 충돌 술어** — 셀 서로소 + 흐름 인접. **행이 인접하는 것은 허용**된다:
끝 칸이 포트 쪽으로 꺾여 이웃 벨트로 안 흐른다(`emitOutputLinks` ①, `emitModule.ts:236` 주석).
그래서 술어가 strict 하고, `assignTracksLeftEdge` 의 `end < iv.lo`(`channelPlanner.ts:43·57`)와
**정확히 같다.** 오늘 `tryLinkFace:335` 의 겹침 판정도 이미 그것이다 — **자를 새로 만들 필요가 없다.**

**㉢ 배정 3단** — 전부 결정적:

```
1  정렬 first-fit         구간 lo 오름차순.  assignTracksLeftEdge 그대로
2  반복 심화 백트래킹       레인 수를 1부터 올린다.  예산 소진 시 3 으로
3  탐욕 폴백 + 사다리       실패 비용 순으로 자리를 먼저 준다(⑤)
```

**채널 장부가 이미 이 모양이다**(`channelGeometryPlanner.ts:529–575`, `SEARCH_BUDGET`:`184`).
새 알고리즘이 아니라 **있는 뼈대를 축만 바꿔 두 번째로 쓰는 것**이고, 그 선례가
`rowChannelPlanner` 다 — 같은 `assignTracksLeftEdge` 를 가로축으로 읽었을 뿐이다.

#### ⑤ 자리가 없을 때 — 사다리는 **후보를 늘린다** (옛 계획서의 §9-마 구체화)

```
0  g_max 로 붓는다 (오늘)        후보 = 레인 R 개              대가 ―
1  g 를 낮춰 구간으로            후보 = 레인 R x 나눔 c        대가 포트 +1
2  gap 을 연다 (가로 레인)        후보 += 가로 G 줄             대가 모듈 높이 +
3  g = 1 다이렉트                극한                         대가 포트 = 머신 수
4  정직한 실패                   ―                            unroutedLines + **수**
```

**되돌리는 게 아니라 넓히는 것**이 요점이다 — 백트래킹의 되돌림은 **같은 후보 집합 안**에서
일어나고 사다리는 **집합 자체를 키운다.** 그래서 둘이 안 싸우고, 순서도 자명하다(㉢ 이 먼저).

> **되먹임 자리는 한 곳이다** — `LinkLimits`(`link.ts:138`)에 상한 ③(레인)을 더한다.
> 사다리 1 은 새 배정기가 아니라 **붓기가 자리를 보게 하는 것**이다(§18).

##### 사다리가 받는 것 — **부족 사유는 `(레인, 막힌 행)` 이다** (2026-08-26 확정)

수량(*"레인이 하나 모자라다"*)으로는 **어디서 자를지 못 정한다.** 사다리 1 이 필요로 하는
것은 자름의 **경계**이고, 그건 못의 행 번호다(§2):

```
사유 = { 면, 레인 깊이, 막힌 행[] }        →  토막 = 막힌 행으로 자른 구간들
```

**어느 면의 사유를 쓰나 — 선호 면.** `tryLinkFace` 는 면마다 불리고 면마다 사유가 난다.
사다리는 **그 줄이 원래 앉고 싶던 면**(출력=W · 입력=E)의 못으로 자른다 — 다른 면으로 밀려나는
것은 이미 넘침 단계가 시도했고 실패한 뒤이기 때문이다.

**못은 연쇄하지만 유한하다.** 레인 `d` 에 앉은 줄의 포트는 `d+1` 에 못을 박으므로 한 단계씩
깊어지고, 레인이 `R` 개면 **`R−1` 단계에서 멈춘다** — 가장 깊은 레인의 포트가 박는 못은
레인이 아닌 칸에 서서 아무와도 안 다툰다. 그래서 *"쪼갰더니 또 막힌다"* 가 무한히 돌지 않는다.

#### ⑥ 오늘 코드와의 거리 (2026-08-26 갱신 — **좌석표 계획이 실행됐다**)

**좌석표 배정** 계획이 Step 0~3 을 실행하고 폐기됐다(커밋 `f6f5d29`~`b71c87d`). 그 결과로 **㉠(후보)과
㉡(충돌 술어)이 섰다** — 남은 것은 ㉢(배정 3단)과 ⑤(사다리)뿐이고, 그게 이 계획의 몫이다.

| 조각 | 있나 | 자리 |
|---|---|---|
| **면 좌석표** — 칸 = `(행, 깊이)`. 옛 장부 셋이 여기로 접혔다 | ✅ **신규** | `planner/module/faceTable.ts` · 설계는 [[module-planning]] §4.5 |
| 레인 장부 · 좌석 장부 · 구간 계산 | ✅ | 표를 읽는 질문이 됐다 — `laneClear` · `seatsTaken` · `beltRowSpan` |
| 끝(N/S) 장부 | ✅ | `ends` — **표 밖에 남는 유일한 것**(기둥 끝은 면의 칸이 아니다) |

> **남은 실패 하나가 이 계획의 입구다.** `electronic-circuit` 의 `input:stone-tablet` 은
> 여전히 `unrouted` 다 — 이제는 **배정이 자리 없음을 정직하게 판정해서**이고, 그 줄에 자리를

## 16. 비용은 **전부 소프트**다 — 하드 금지를 두지 않는다

| 인자 | 성질 | 실패를 만드나 |
|---|---|---|
| `blocked` · `bounds` | 하드 | **만든다** |
| 타일 수 · `turnPenalty` · 점프 비용 | 소프트 | 안 만든다 |

**비용 때문에 트렁크가 연결이 안 되면 안 된다**(2026-08-13 사용자). 그래서
*"모듈 밖으로 나가는 것"* 은 `bounds` 가 아니라 **가산점**으로 넣는다.

```
bounds  = 탐색이 끝나게 하는 상한   ← 설계 의도가 아니다. 넉넉히
가산점   = 안쪽을 선호한다          ← 설계 의도
```

**`jumpCostModel` 은 `'length'` 로 고정한다**(막혔을 때만 지하). `'flat'` 은 막히지 않아도
지하로 가는데, 지하는 `(축, 티어)` 배타권이라는 **한정 자원**이라 공짜로 쓰면 나중 트렁크가
건널 자리를 잃는다.

## 17. 손잡이는 **하나**다 — 여유 마진

*"모듈 크기"* 와 *"트렁크 연결 수준"* 은 같은 손잡이의 양면이다:

```
마진 크게 → 경로가 멀리 돈다 → 많이 묶인다 → 모듈이 크다
마진 작게 → 경로가 못 돈다   → 쪼개진다    → 모듈이 작다
```

마진이 모자라 경로가 없으면 §마(쪼개기)로 떨어지고 극한이 다이렉트다.
**손잡이 하나가 라와 마를 동시에 구현한다.** (D4·D5 — 모듈마다, 파라미터까지)

## 18. 최적화는 나중이다

*"우선 구현되는 게 중요하다"*(2026-08-13 사용자). `turnPenalty`·모듈 밖 가산은
**켤 자리만 만들어 두고 값은 나중에** 정한다 — 교차가 실제로 관측되면 그때 켠다(D3).

## 19. 기존 코드와의 상호작용 — **새로 만들 접점이 0 이다**

모듈 크기는 **이미 셀의 부산물**이다:

```ts
// moduleTransform.moduleExtent — 머신 ∪ **모든 셀**의 외접 사각형
for (const m of mod.machines) mk(...);
for (const c of mod.cells)    mk(c.x, c.y);   // ← 벨트 한 칸만 밖으로 나가도 반영된다
```

`linkPlanner` 주석이 이미 그렇게 적고 있다 — *"자리는 그냥 **바깥으로 자란다**: 모듈이
차지하는 범위는 `moduleExtent`(머신 ∪ 모든 셀)라 배치가 이 셀들을 이미 셈에 넣는다."*

**소비처 넷은 전부 `moduleExtent` 하나만 본다** — 모듈 내부를 아무도 안 들여다본다:

| 소비처 | 무엇에 | 모듈이 커지면 |
|---|---|---|
| `modulePacking` tidy-tree(`heightOf`) | 세로 배치 | **평행이동만** |
| `modulePacking` `colWidth[depth]` | 열 폭 = 그 열 모듈들의 **최대 w** | 그 열이 넓어진다 |
| `modulePacking` `absPortY` | 포트 절대 y = `anchor.y + topY − ext.y` | **포트 위치가 자동으로 따라온다** |
| `modulePerimeterPass` | 반출 시작점 | 자동 |

**포트 위치도 이미 모듈이 정한다** — `ModulePort.anchor` 는 방출기가 만들고
(`makeLinkPortChest`) 바깥은 **읽기만** 한다. *"트렁크가 포트 위치를 정한다"* 는
새 권한이 아니라 **이미 있는 권한**이다.

> **딱 하나 값을 무는 곳:** `colWidth` 는 **열 단위 최대치**라, 한 모듈이 커지면 같은
> depth 의 **열 전체**가 넓어진다. 트렁크 하나의 욕심이 이웃 모듈들의 배치까지 벌린다 —
> 그게 §9.3 손잡이가 실제로 무는 비용이다.
