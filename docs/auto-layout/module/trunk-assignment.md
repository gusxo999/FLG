## 1. 자원 — 면 하나가 가진 것

```
        d1        d2 .. d(1+R)         d(2+R)      d(3+R)
      좌석 열       벨트 깊이          포트 인서터    포트 상자
      행으로 나눔    깊이 축. R = |reach 종류|
```

**깊이에는 두 축이 있다.** 이것이 §5 의 전부다.

```
깊이 축   면당 R 개.   한 깊이가 최대 N 대를 먹인다        ← 긴 팔이 있어야 쌓인다
행   축   연 gap 마다 가로 한 줄. 한 줄이 **정확히 2대**   ← 긴 팔 없이도 쌓인다
```

**인서터 물리** — 좌석 `s`, reach `r`, 벨트 `b = s + r`, 그리고 `s ≤ r`.
`ℛ={1,2}` 에서 동시 성립 조합은 `{(1,1),(1,2)}`(belts d2·d3) 또는 `{(1,2),(2,2)}`(belts d3·d4).
**개수는 `R` 로 유일하고 깊이 배열은 유일하지 않다**(유체가 d2 를 먹은 면에서 차이가 산다).

## 2. 수요 — 수 넷이면 끝이고 분기문이 없다

```
k_j = ⌊벨트처리량 / per_j⌋     한 벨트가 맡을 수 있는 머신 수
g_j = min(k_j, N)              묶음 크기 — 처리량이 준 **상한**       ← TR1
c_j = ⌈N / g_j⌉                구간 수(상한일 때)
a_j(m)                          머신 m 에서 이 줄이 쓰는 팔 수
```

`c=1` 관통 · `c=N` 다이렉트 · 그 사이가 부분 병합 — **한 공식의 구간이지 다른 형태가 아니다.**

#### 실제로 어디서 자르나 — **못을 피해서** (2026-08-26 정정)

옛 서술은 *"앞에서부터 `g` 대씩, 나머지는 뒤"* 라는 **균등 분할**이었다. 폐기한다 —
자리가 요구하는 자름과 균등 분할이 **우연히만** 일치한다.

```
못(nail) = 얕은 줄의 **포트 인서터**가 다음 깊이에 서는 칸
           포트는 자기 구간의 진출 행에 `d+1`·`d+2` 로 서므로, 깊이 `d` 에 앉으려는 줄에게
           **깊이 d−1 에 앉은 줄들의 진출 행**이 전부 못이다
```

**자름은 못이 정한다** — 못이 `n` 개면 토막이 `n+1` 개다:

```
막힌 행 [90, 180]  →  [1,88] · [91,178] · [181,268]        토막 3, 포트 3
```

> **2026-08-26 실측이 이 정정을 요구했다.** `electronic-circuit`(머신 100대)에서
> `copper-cable` 이 네 토막으로 잘리며 `d3` 에 못을 박았고(행 `0·90·180·270`),
> `stone-tablet`(관통 90대 한 줄)이 `d2`·`d3` 을 다 못 써서 **트리가 거절됐다.**
> 이번엔 노란 줄이 머신 30·60 에서 잘려 균등 분할과 우연히 같았지만, 40/40/20 로
> 잘렸다면 못이 `120·240` 에 서고 균등 분할은 **빗나간다.**

**균등은 못이 없을 때의 특수해다** — 못이 0개면 `c_j` 대로 앞에서부터 `g` 대씩 자른다.

## 3. 배정 여섯 단계 — 전부 결정적, 탐색 0

```
① 면       밖(부모/자식 방향)이 준다. 트렁크는 못 고른다              ← TR5
② 깊이     a(j,d) = ⌈per_j / tp(d)⌉ 로 후보를 거르고, 통과한 것 중 아무거나  ← TR2
③ offset   ②의 순서대로 머신 안 행을 하나씩. 얕을수록 흐름 반대쪽 끝   ← TR3
④ 구간     좌석 행에서 유도:  [min seat row .. max seat row]
⑤ 진출     구간 끝 행에서 d+1 .. maxLane 을 **한 칸씩**
⑥ 포트     maxLane+1 = 인서터,  maxLane+2 = 상자
```

**②(TR2)의 근거 — 처리 가능성뿐이다:**

```
깊이가 팔 종류를 정하고(`emitModule.seatInserterName`), 팔 종류가 처리량을 정한다.
        d2 = reach 1 = 가장 빠른 팔        d3 = reach 2 = 그보다 느린 팔
        실측 모드팩에서 fast 10/s vs long-handed 1.2/s — **8배**(moduleWizard:278)

a(j, d) = ⌈ per_j / tp(d) ⌉        그 깊이의 팔로 머신 하나를 먹이는 데 필요한 팔 수
후보     = Σ_j a(j, d_j) ≤ h 인 (줄 → 깊이) 조합
```

> **후보 중에는 우선순위가 없다.** 어느 줄이 얕고 깊은지는 **중요하지 않다**(2026-08-14 사용자).
> 옛 규칙(*"구간 적은 줄이 얕게"*)은 폐기 — [[trunk-blocked]] §3 참조.

**⑤가 요구하는 것 — 진출 조건:**

> 깊이 `d` 의 구간이 진출하는 행에서, `d+1 .. maxLane` 이 **그 행에 비어 있어야** 한다.

`c` 개로 쪼개진 깊이는 구멍이 `c+1` 개(사이 + 양끝)라 대개 저절로 맞는다.
**막히면 수단은 둘뿐이다(TR7)** — [[trunk-blocked]] §3 이 실물로 보인다.

## 4. 상한

```
면 f 에 배정된 품목:   개수 ≤ R_f        (깊이 깊이 수 — ①)
                       Σ_j a(j, d_j) ≤ h  (그 면의 좌석 행 — ③)

모듈 전체 좌석 예산 = 2h   (W면 h + E면 h).  **면은 선호이지 강제가 아니다**(TR5·TR8)
```

> **면마다 따로 세지 않는다.** 선호 면이 차면 반대 면으로 분산한다.
> (2026-08-13 에 같은 실수를 한 적이 있다 — *"입력은 E를 선호하니 E에만 앉는다"* 로 세다가
> 4줄 레시피에서 포트가 8개가 됐다. 예산을 모듈 전체로 바꾸니 4개가 됐다.)

> ~~**`g`·`k` 는 상한에 안 들어간다.** 깊이의 행 예산 `N×h` 를 구간 `g×h` 로 나누면~~
> ~~깊이당 `N/g` 구간이고, 품목 하나의 요구도 `N/g` 라 **`g` 가 약분된다.**~~
> **2026-09-01 정정 — 약분이 안 된다.** 아래 §4.1.

### 4.1 깊이를 먹는 것은 구간이 아니라 **팔이 앉은 행**이다 (2026-09-01 정정)

위 약분은 *한 구간이 `g×h` 행을 먹는다* 를 전제로 했다. 그게 틀렸다 —
벨트가 덮는 행은 **그 줄의 팔이 앉은 행**이지 머신 면 전체가 아니다
(`module/ledger/seat.beltRowSpan`: 머신마다 `freeSeatRows(mi).slice(0, k)` 의 처음·끝).

```
g = 1   구간 하나 = 머신 한 대의 `a_j(m)` 행       → 여러 품목이 한 깊이를 **나눠 쓴다**
g > 1   구간 하나 = 첫 머신 첫 행 … 끝 머신 끝 행   → **사이 행까지 통으로** 먹어 깊이를 독점한다
```

`beltRowSpan` 은 `[최소행, 최대행]` **하나**를 낸다 — 구멍이 없다. 그래서 머신을
걸치는 순간 그 사이의 남의 자리까지 문닫는다([depthClear] 가 칸으로 막는다).

**그래서 상한 ① 이 다시 서진다:**

```
면 f:   (g > 1 인 품목 수)  +  (g = 1 인 품목이 있으면 1)   ≤  R_f
```

즉 **`g` 가 상한에 들어간다.** `g = 1` 줄들은 깊이 하나를 함께 쓰고(좌석이
허락하는 만큼), `g > 1` 줄은 하나씩 깊이를 다 가진다.

> **이것이 TR1 의 *"실제 `g` 는 자리가 정한다"* 에 붙는 이빨이다.**
> 처리량이 `g_max` 를 주고, **깊이 예산이 거기서 더 깎는다.**

**그리고 여기서 맞바꿈이 나온다** — 같은 품목 수를 두 가지로 담을 수 있다:

```
품목 3 · R = 1 (긴팔 없음) · N = 2

(가) 전부 g = 1    깊이 하나를 셋이 나눠 쓴다      포트 6개 · gap 안 벌림  ← **오늘의 동작**
(나) 둘은 g = 2   깊이 둘을 독점, 셋째는 gap 으로   포트 4개 · gap 이 벌어진다
```

**어느 쪽도 틀리지 않다** — 포트를 줄일지 모듈을 작게 할지의 문제다. 그래서 이것은
모델이 혼자 정할 수 없고 **사용자 손잡이**다 — 축과 선택지는 §4.3, 기본값은
**공짜일 때만 관통**이다(2026-09-01 사용자).

### 4.2 **"공짜"** 의 정확한 뜻 (2026-09-01 사용자 확정)

> **공짜 = 그 관통을 줘도 *다른 줄이 밀리지 않는다*.**
> 즉 **모듈이 안 커진다** — gap 이 안 벌어지고, 어느 줄도 자리를 잃지 않는다.

관통은 깊이를 하나 독점하므로(§4.1), 공짜인지 아닌지는 **깊이가 남나**로 판정된다:

```
모듈 전체:   (g>1 줄 수)  +  (g=1 줄이 있으면 **면 수**)   ≤   Σ_f R_f
                             └ 그 줄들은 면마다 공용 깊이 하나씩을 쓴다
```

**둘째 항은 g=1 줄이 하나라도 있을 때만 붙는다.** 그래서 줄이 전부 관통이면 상한은
그냥 `줄 수 ≤ Σ R_f` 이고, **한 줄이라도 내려가는 순간 예산이 면 수만큼 줄어든다** —
그 연쇄가 이 규칙의 핵심이다(§4.2.1 의 `R=1` 이 그 결과다).

> **면마다 따로 세지 않는다** — §4 의 좌석 예산과 같은 이유다. 선호 면이 차면 반대 면으로
> 넘어가므로(`spillLinkFacesToGap`), 면마다 세면 **넘어갈 수 있는 자리를 없다고 센다.**
> (2026-09-01 실측: `electric-motor` 4줄이 E 의 두 깊이만 보고 둘을 내렸다 — 실제로는
> W 의 남은 깊이로 넘어가 넷 다 관통이 선다.)

> **유체 면도 깊이로 센다.** 선호 단계는 유체 면을 비켜 가지만 넘침 단계가 되찾아 온다
> ([[trunk-blocked]] §4 — 파이프가 지하로 벨트를 넘어 좌석 줄이 산다). 유체 면이 좁다는 사실은 이미 `R_f`
> 안에 있다(지하파이프 사거리가 그 면의 깊이를 깎는다) — **두 번 깎지 않는다.**
> (2026-09-01 실측: `plastic-bar` 3줄을 W 한 면으로 몰아 둘이 헛되이 `g=1` 로 떨어졌다.)

#### 정하는 절차 — **한 방향으로만 흐른다**(되먹임 없음)

```
1  줄마다 g_max 를 낸다        ⌊벨트 처리량 ÷ per⌋ 와 N 중 작은 것            ← TR1
2  남은 깊이를 센다            Σ_f R_f  −  링크가 이미 독점한 깊이
3  위 부등식을 확인한다
4  넘치면 **우선순위가 낮은 줄부터** g = 1 로 내린다
   (출력 → 자식-공급 입력 → 원료 입력 순이고, 뒤에서부터 내린다)
5  다시 3 으로. 예산이 단조 감소하므로 **반드시 끝난다**
```

#### 이 판정에 **행(좌표)이 필요한가 — 아니다**

들어가는 값이 전부 **주어진 수**다:

```
R_f       인서터 reach 종류 수(유체 면이면 지하파이프 사거리로 깎임)   ← 스펙
a_j(m)    ⌈per_j ÷ tp(reach)⌉                                     ← 수요 + 스펙
h_f       머신 면 칸 − 유체 상자 행                                 ← 스펙
우선순위   역할이 정한다(출력 → 자식-공급 → 원료)                     ← 정책
```

**면조차 안 물어도 된다** — 예산이 모듈 전체라 *"어느 면에 앉나"* 는 배정의 몫으로 남는다.

**좌석만 맞으면 깊이는 저절로 맞는다** — `g=1` 줄의 벨트 조각은 자기 팔이 앉은 행만
덮으므로, 좌석이 서로 다른 행에 배정된 이상 **겹칠 수가 없다.** 그래서 `Σ_j a_j(m) ≤ h_f`
하나로 충분하고 *"몇 번째 행"* 은 안 물어도 된다.

> **다만 이 판정은 보수적이다.** 관통 줄이 마지막 머신의 좌석을 다 안 쓰면 그 **꼬리 행**은
> 비는데, 이 부등식은 그걸 안 센다 — *"앉을 수 있는데 못 앉는다고 한다"* 가 남는다.
> 행을 봐야 알 수 있는 이득이고, **행을 안 보기로 한 대가**다. 기본값이 보수적인 것은
> 옳다(모듈이 커지는 쪽으로 틀리지 않는다).

> **그럼 행을 보려면 무엇이 더 있어야 하나 — [[face-occupancy]].** 이 절이 *"행을 안 본다"*
> 를 **선택**으로 정한 자리이고, 그 문서가 그 선택의 축(낟알)과 다른 칸에 무엇이 있는지를 든다.
> 요지: 행 구간의 산술은 **이미 있다**(좌석이 접두합이다). 모자란 것은 넣을 **면과 깊이**이고,
> 그 둘은 *"자리가 남았나"* 를 알아야 정해진다 — **고리를 어디서 끊느냐**의 문제다.

#### 전제 — **벨트가 지상으로만 간다** (2026-09-01 사용자)

이 부등식은 *"관통 벨트가 첫 팔에서 끝 팔까지 **지면을 계속 덮는다**"* 를 전제한다.
그래서 사이 행이 통째로 죽고, 깊이 하나가 줄 하나에 묶인다.

**지하 벨트가 생기면 그 전제가 깨지고 공짜의 범위가 넓어진다.** 관통 줄이 팔 없는
구간을 **잠수해서** 지나가면 그 행의 지면이 살아나므로, 같은 깊이에 다른 줄이 들어올
수 있다 — 즉 `R_f` 는 그대로인데 **한 깊이가 담을 수 있는 줄이 는다.**

```
지금(지상만)   관통 1줄  =  깊이 1개              사이 행까지 죽는다
지하 생기면    관통 여럿  =  깊이 1개도 가능       팔 행만 살아 있으면 된다
               (대신 지상 복귀 칸 · 사거리 · 두 벨트가 안 만날 것을 세야 한다)
```

**이건 아직 없는 능력이다** — [[trunk-blocked]] §3 의 TR7 (나) *잠수* 가 코드에 없다(§0 표).
그러니 §4.2 의 부등식은 **"지하가 없는 동안의" 공짜 기준**으로 읽어야 하고,
잠수가 들어오면 **다시 세야 한다**(느슨해지는 방향이라 오늘의 배치는 안 깨진다).

#### 4.2.1 `R = 1` 일 때 — **관통은 품목 둘까지**

긴팔이 없으면 `R_f = 1` 이라 부등식이 아주 좁아진다:

```
Σ R_f = 2 (W1 + E1)     ·     g=1 줄이 생기면 예약이 2 → 예산 0
```

**그래서 `R=1` 에서 관통이 서는 것은 품목이 정확히 둘일 때뿐이다** — 즉
**입력 1 + 출력 1**(예: `kr-sand` = stone → kr-sand). 그때만 `2 ≤ 2` 로 딱 맞고,
아무도 `g=1` 이 아니라 예약이 안 켜진다.

품목이 셋이면 **전부 다이렉트**가 된다 — 하나를 내리는 순간 예약 2가 켜져 예산이 0이 되고,
나머지도 따라 내려간다:

```
출력 1 + 입력 2 · R=1
  관통 3  >  깊이 2                    → 원료 입력 하나를 내린다
  관통 2  >  2 − 2 = 0                 → 나머지도 따라 내려간다
  ⟹ **셋 다 다이렉트.**  깊이 하나를 셋이 나눠 쓴다(오늘의 동작 그대로)
```

> **이 연쇄가 보수성의 값이다.** 출력 하나만 관통시키고 입력 둘을 다이렉트로 두면 포트가
> 둘 줄지만, 그 둘이 좌석 넘침으로 반대 면에 밀렸을 때 **관통이 먹은 깊이 때문에 갈 곳을
> 잃는다**(2026-09-01 실측: 일곱 줄 스펙에서 포트 하나가 사라졌다). 공짜의 정의가
> *"아무도 안 밀린다"* 인 이상, 밀릴 **가능성**이 있으면 안 사는 것이 맞다.

### 4.3 손잡이 — **자리를 얼마나 내주고 포트를 살 것인가**

§4.1 의 (가)·(나)는 대립하는 두 정책이 아니라 **한 축의 두 지점**이다:

```
        관통을 덜 산다 ←────────────────────────────→ 관통을 더 산다
        포트 많다 · 모듈 작다              포트 적다 · 모듈 크다

  ①  공짜만            남는 깊이에만 관통.  **모듈이 절대 안 커진다**      ← 기본값
  ②  gap N칸까지       gap 을 N칸 벌리는 데까지 관통을 산다
  ③  포트 최소         필요한 만큼 벌린다.  관통을 최대로
```

**기본값은 ① 이다**(2026-09-01 사용자). 근거는 최적화 우선순위다 — *"머신 100% 가동이
최우선"* 인데, ②·③ 은 자리가 모자랄 때 **못 앉는 줄**(= 굶는 머신)을 만들 수 있다.
①은 정의상 그럴 수 없다: 공짜가 아니면 안 사기 때문이다.

```
① 이 보장하는 것   관통을 켠다고 **모듈이 커지지도, 줄이 밀리지도 않는다**
                   ⟹ 언제 켜도 손해가 없다 → 손잡이 없이 항상 켜도 되는 유일한 지점
②③ 이 파는 것     포트 수(= 밖과의 접점 · 인서터 · 상자)
②③ 이 치르는 것   모듈 높이(gap) — 그리고 그 높이는 **클러스터 전체로 번진다**
```

> **왜 ②·③ 을 지금 안 만드나.** 손잡이의 값이 gap 폭이고, gap 을 벌리는 트렁크 형태는
> 기둥이 아니라 **격자**가 된다 — 그건 격자 클러스터의 몫이다(2026-08-30 범위 밖 확정).
> 그때 이 축이 **그대로** 손잡이가 된다: ①은 `gap 예산 = 0`, ③은 `gap 예산 = ∞`.

**넘으면 행 축으로 간다** — gap 을 연다(§5). *어느 품목을 내리나*는 미결(judgements **J2**).

## 5. 두 축 — 긴팔이 없으면 gap 으로 산다

`ℛ={1}` 이면 `R=1` → 면당 깊이 1 → **관통(`g>1`) 품목은** W+E 로 2개가 한계다.

> **그런데 품목 3개가 밀착 기둥에 선다** — 예전엔 여기가 *"불가능"* 이라 적혀 있었고,
> 그것이 §4 의 약분 오류와 같은 뿌리다. 셋 다 `g=1` 이면 머신마다 한 행씩만 먹어
> **한 깊이를 나눠 쓴다**(§4.1). 실제로 코드가 그렇게 놓는다 —
> `clusterModule.test.ts` *"아이템 3줄이 유체 면을 비켜 W 3칸에 앉는다"*(battery, `ℛ={1}`).
> gap 이 필요해지는 것은 **좌석이 챙을 때**이지 깊이가 모자랄 때가 아니다.

```
 y=88  ███ M0 ███
 y=89   i   i   i   i     ← reach 1.  픽업 y=90, 드롭 y=88 (M0)
 y=90  ══ ══ ══ ══ ══     ← 가로 트렁크. 팔 개수는 길이만큼 무제한
 y=91   i   i   i   i     ← 픽업 y=90, 드롭 y=92 (M1)
 y=92  ███ M1 ███
```

**가로 벨트 하나가 위·아래 두 머신을 먹인다.** `clusterLayout.ts:17` 의 `ROW_GAP = 3` 이
정확히 이 폭(좌석/벨트/좌석)이다.

```
총 깊이 = 2R  +  G          긴팔 있음 → 깊이에 쌓는다 → 모듈이 옆으로
          ↑깊이  ↑행         긴팔 없음 → gap 에 쌓는다  → 모듈이 아래로
```

4대·`R=1`·gap 3개 → 깊이 `2+3=5`. 대가는 높이 12행 → 21행(**+75%**).

> **그래서 §1 의 *"탭 주행은 세로뿐"* 은 `gap = 0` 전제였다.** gap 이 열리면 무너진다.

## 12. 축의 정정 — **깊이는 결과이지 입력이 아니다** (2026-08-15 사용자)

> *"깊이에 대해서 저는 잘 모릅니다. 제가 아는 건 사용자가 선택한 인서터들 중 reach-1·reach-2 가
> 존재한다는 것이고, 그것들을 **정확하게 작동시키려면** 벨트를 깊이-2·깊이-3 에 두어야 한다는
> 사실뿐입니다. … 여러 머신의 **규칙성을 파악하기만 한다면** 깊이 개념을 몰라도 괜찮습니다.
> **인서터를 제대로 배치할 수만 있으면 됩니다.**"*

### 12.1 무엇이 축인가

```
축이 아니다   깊이 d2 · d3        ← 기둥에서 규칙성이 만들어 낸 **이름**
축이다        (인서터 i, 그 팔이 집는 타일)   ← 물리.  reach 는 고정 거리다
```

```
줄 j 를 인서터 i 로 먹인다  →  팔 개수  a(j,i) = ⌈ per_j / tp_i ⌉
팔 i 하나를 앉히려면        →  타일 둘.  **좌석**(머신에 인접) + **벨트**(좌석에서 reach_i 칸)
```

**"깊이"는 그 벨트 타일이 머신 면에서 몇 칸인지의 별명**일 뿐이다. `reach 1` 을 고르면 벨트가
`d2` 에, `reach 2` 를 고르면 `d3` 에 가는 것이지, **`d3` 를 고르고 나서 긴팔이 딸려 오는 게 아니다.**

### 12.2 그래서 순서가 뒤집힌다

```
지금 코드   팔 개수를 센다(reach 1 고정) → 앉힌다 → **깊이/reach 를 재배정**한다
            (옛 clusterPortPlanner.ts:402-427 — 수요 내림차순 ↔ throughput 내림차순 zip. 2026-09-02 삭제)
            ③이 ① 뒤에 있어 ①이 쓴 수가 무효가 된다

새 순서    **줄마다 인서터를 고른다** → 팔 개수가 그 인서터에서 나온다 → 타일을 예약한다
```

### 12.3 규칙성은 **결과**다

같은 레시피의 머신 `N` 대는 같은 줄 집합을 가지므로 **같은 인서터 배정이 반복**된다.
그래서 좌석이 같은 열에 늘어서고, 벨트가 같은 열에서 길어진다.

> **트렁크는 그 규칙성을 한 줄로 이어 붙인 것**이고, 이 문서 의 "깊이 깊이"은 그 규칙성의 이름이다.
> **격자로 가면 규칙성의 모양이 바뀌지만 축은 안 바뀐다** — 여전히 `(인서터, 집는 타일)` 이다.
> 그래서 **이 절**(§12)은 이 문서를 폐기하지 않는다. 이 문서는 **기둥에서의 §12** 이다.

### 12.4 이 문서를 읽을 때

```
이 문서 의 "깊이 d"      →  "reach = d−1 인 인서터를 골랐을 때 벨트가 놓이는 칸"
이 문서 의 "면당 R 깊이"  →  "한 면에 동시에 세울 수 있는 서로 다른 (인서터, 벨트타일) 쌍의 수"
이 문서 의 tp(d)         →  tp_i  (그냥 그 인서터의 처리량)
```

**수는 전부 같다.** 바뀌는 것은 **무엇이 원인이고 무엇이 결과인지**뿐이고, 그것이
§18(하드코딩 금지)을 지키는 데 결정적이다 — 깊이를 입력으로 두면 `if (depth === 3)` 이 생긴다.

## 13. 권한 — 트렁크가 **포트 위치와 모듈 크기를 정한다**

```
트렁크 계획이 정한다        받는다
  · 경로                    · 머신 좌표(다이렉트 기준 배치)
  · 좌석                    · 레시피 줄 · 팔 수
  · 포트 위치
  · 모듈 크기  ← 경로의 부산물
```

**모듈 크기가 경로의 부산물**인 것은 오늘 `gap 폭 = 배정의 부산물` 과 같은 구조다
(`layoutCluster(rowGaps)`). 새 패턴이 아니라 있는 패턴을 한 겹 넓히는 것이다.
모듈이 커져도 **다른 모듈은 평행이동만 한다** — 그 외 영향은 없어야 한다.

그래서 [[trunk-concepts]] A7 의 고리가 풀린다:

```
다이렉트 기준 머신 배치 → 트렁크 경로 예약 → 모듈 크기 확정 → 모듈 배치
```

## 15. 경로를 어떻게 찾나 — **탐색이 아니라 배분이다** (2026-08-24 재작성)

옛 계획서의 §9-나 는 *"구간 사슬 — `containerRouting` 재사용"* 이라 적혀 있었다. **폐기한다.** 셋이다:

```
① 문서 안에서 모순이었다   D10(2026-08-16)이 이미 반대로 정했는데 옛 계획서의 §9 표가 안 고쳐졌다
② 사실이 아니었다          모듈 안쪽은 containerRouting 을 **한 번도 안 부른다**
                           (호출자는 납품 사다리(link/policy) 하나뿐 — 옛 파사드는 2026-09-16 삭제)
                           → "재사용"이 아니라 **없는 의존을 새로 만드는** 제안이었다
③ 예약 철학에 어긋난다     아래 ②
```

#### ① 질문이 둘로 갈린다 — 하나는 이미 답이 있다

```
㉠ 이 줄의 벨트 칸이 어디인가        ← **답이 있다.** 탐색 0
㉡ N 개의 줄이 한 면에서 동시에 서나  ← 아무도 안 답한다.  **여기가 문제다**
```

㉠ 은 싣는 쪽 틀과 길(`module/shape/body` 의 `linkFrameOf` · `outputRouteOf`)이 **다섯 수**에서 덧셈으로 만든다:

| 수 | 누가 정하나 | 자리 |
|---|---|---|
| 면 | 밖(부모/자식 방향) — TR5 | `plan.face` |
| **깊이** | **배정** | `plan.clusterBeltDepth` |
| 구간 `[loT..hiT]` | 좌석 행에서 유도 | `LinkFrame.rows` |
| 진출 깊이 | 배정 | `plan.exitDepth` |
| **포트 끝** | **배정** | `plan.portEnd` |

그래서 [[trunk-concepts]] A6 이 "경로"라 부른 것은 **기둥에서 구간 하나로 퇴화한다.** 채널 문서(§3)의 표를
그대로 옮기면:

| 경로 | 밖이 고정한 것 | 계획이 고르는 것 | 결과 모양 |
|---|---|---|---|
| 납품(채널) | 출발 행 · 도착 행 | 트랙 1개 | 계단꼴 |
| **트렁크(면)** | 면 · 좌석 행 · 흐름 방향 | **깊이 1개 + 구간 양끝** | **갈퀴꼴** — 세로 주행 1 + 탭 `k` 개 |
| 진출(가로) | 진출 행 · 목표 열 | 없다 — `d+1..maxLane` 에 한 칸씩(TR6) | 직선 |

> *"트랙 번호 하나만 정하면 경로 전체가 확정된다"* 와 **같은 구조다**
> (`channel-geometry-reservation` §3). 그 관점의 값은 빠르다는 게 아니라
> **충돌이 미리 보인다**는 것이다 — 벨트를 한 칸도 깔기 전에 숫자 비교로 끝난다.

#### ② 그래서 다익스트라가 답이 아니다 — 이유 넷

| # | 이유 | 근거 |
|---|---|---|
| **1** | **질문이 다르다.** 다익스트라는 *"이 두 점의 최단"* 을 답하고 우리는 *"N 개가 동시에 서나"* 를 묻는다. 줄마다 순차로 부르면 **순서 의존**이라 먼저 깐 것이 요지를 먹는다 | 그 버그가 2026-07 외부상자 갇힘이고 **채널 예약이 그것 때문에 태어났다**(같은 문서 §1·§7-B: *"라우터 강화는 실패를 늦출 뿐 보장이 없다"*) |

> 셀장부 계획의 공통 제약 "가" 와 같은 방향이다 — *"장부는 라우터 안으로 안 들어간다.
> 계획·판정은 장부, 탐색은 라우터."* 트렁크 배정은 **장부 쪽**이다.

#### ④ 채택안 — 조각 셋

**㉠ 후보(도형)** — 하나 = `(깊이 d, 팔 수 a(d), 구간 [lo,hi], 진출 깊이, 포트 끝 | 옆)`.
채널의 `staircaseShape`·`elbowShape` 에 대응하는 **`combShape` 하나**면 된다.

> **구간은 입력이 아니라 후보의 결과다.** 깊이가 인서터를 정하고(§12), 인서터가 팔 수를
> 정하고(`a = ⌈per / tp⌉`), 팔 수가 좌석 행을 먹고, 그 행들이 구간이 된다.
> `beltRowSpan`(`module/ledger/seat.ts`)이 **이미 그렇게 센다**(`used` 를 읽어 시작 행을 안다).
>
> **여기가 채널과 다른 유일한 점이다.** 채널은 출발·도착 행이 포트에 고정돼 구간이
> 상수인데, 트렁크는 **색(깊이)을 고르면 구간이 바뀐다.** 그래서 순수 left-edge 를
> 그대로 못 쓴다 — 구간이 색에 의존하는 채색이다. **이것이 ㉢ 이 3단인 이유다.**

**㉡ 충돌 술어** — 셀 서로소 + 흐름 인접. **행이 인접하는 것은 허용**된다:
끝 칸이 포트 쪽으로 꺾여 이웃 벨트로 안 흐른다(`module/shape/body.outputRouteOf` 의 끝 칸 주석).
그래서 술어가 strict 하고, `assignTracksLeftEdge` 의 `end < iv.lo`(`channelPlanner.ts:43·57`)와
**정확히 같다.** 오늘 `tryLinkFace:335` 의 겹침 판정도 이미 그것이다 — **자를 새로 만들 필요가 없다.**

**㉢ 배정 3단** — 전부 결정적:

```
1  정렬 first-fit         구간 lo 오름차순.  assignTracksLeftEdge 그대로
2  반복 심화 백트래킹       깊이 수를 1부터 올린다.  예산 소진 시 3 으로
3  탐욕 폴백 + 사다리       실패 비용 순으로 자리를 먼저 준다(⑤)
```

**채널 장부가 이미 이 모양이다**(`channelGeometryPlanner.assignSurface` · `SEARCH_BUDGET`).
새 알고리즘이 아니라 **있는 뼈대를 축만 바꿔 두 번째로 쓰는 것**이고, 그 선례가
`rowChannelPlanner` 다 — 같은 `assignTracksLeftEdge` 를 가로축으로 읽었을 뿐이다.

#### ⑤ 자리가 없을 때 — 사다리는 **후보를 늘린다** (옛 계획서의 §9-마 구체화)

```
0  g_max 로 붓는다 (오늘)        후보 = 깊이 R 개              대가 ―
1  g 를 낮춰 구간으로            후보 = 깊이 R x 나눔 c        대가 포트 +1
2  gap 을 연다 (가로 깊이)        후보 += 가로 G 줄             대가 모듈 높이 +
3  g = 1 다이렉트                극한                         대가 포트 = 머신 수
4  정직한 실패                   ―                            unroutedLines + **수**
```

**되돌리는 게 아니라 넓히는 것**이 요점이다 — 백트래킹의 되돌림은 **같은 후보 집합 안**에서
일어나고 사다리는 **집합 자체를 키운다.** 그래서 둘이 안 싸우고, 순서도 자명하다(㉢ 이 먼저).

> **되먹임 자리는 한 곳이다** — `LinkLimits`(`link.ts:138`)에 상한 ③(깊이)을 더한다.
> 사다리 1 은 새 배정기가 아니라 **붓기가 자리를 보게 하는 것**이다(§18).

##### 사다리가 받는 것 — **부족 사유는 `(깊이, 막힌 행)` 이다** (2026-08-26 확정)

수량(*"깊이가 하나 모자라다"*)으로는 **어디서 자를지 못 정한다.** 사다리 1 이 필요로 하는
것은 자름의 **경계**이고, 그건 못의 행 번호다(§2):

```
사유 = { 면, 깊이, 막힌 행[] }        →  토막 = 막힌 행으로 자른 구간들
```

**어느 면의 사유를 쓰나 — 선호 면.** `tryLinkFace` 는 면마다 불리고 면마다 사유가 난다.
사다리는 **그 줄이 원래 앉고 싶던 면**(출력=W · 입력=E)의 못으로 자른다 — 다른 면으로 밀려나는
것은 이미 넘침 단계가 시도했고 실패한 뒤이기 때문이다.

**못은 연쇄하지만 유한하다.** 깊이 `d` 에 앉은 줄의 포트는 `d+1` 에 못을 박으므로 한 단계씩
깊어지고, 깊이가 `R` 개면 **`R−1` 단계에서 멈춘다** — 가장 깊은 줄의 포트가 박는 못은
깊이가 아닌 칸에 서서 아무와도 안 다툰다. 그래서 *"쪼갰더니 또 막힌다"* 가 무한히 돌지 않는다.

#### ⑥ 오늘 코드와의 거리 (2026-08-26 갱신 — **좌석표 계획이 실행됐다**)

**좌석표 배정** 계획이 Step 0~3 을 실행하고 폐기됐다(커밋 `f6f5d29`~`b71c87d`). 그 결과로 **㉠(후보)과
㉡(충돌 술어)이 섰다** — 남은 것은 ㉢(배정 3단)과 ⑤(사다리)뿐이고, 그게 이 계획의 몫이다.

## 16. 비용은 **전부 소프트**다 — 하드 금지를 두지 않는다

| 인자 | 성질 | 실패를 만드나 |
|---|---|---|
| `blocked` · `bounds` | 하드 | **만든다** |
| 타일 수 · `turnPenalty` · 점프 비용 | 소프트 | 안 만든다 |

**비용 때문에 트렁크가 연결이 안 되면 안 된다**(2026-08-13 사용자). 그래서
*"모듈 밖으로 나가는 것"* 은 `bounds` 가 아니라 **가산점**으로 넣는다.

```
bounds  = 탐색이 끝나게 하는 상한   ← 설계 의도가 아니다. 넉넉히
가산점   = 안쪽을 선호한다          ← 설계 의도
```

**`jumpCostModel` 은 `'length'` 로 고정한다**(막혔을 때만 지하). `'flat'` 은 막히지 않아도
지하로 가는데, 지하는 `(축, 티어)` 배타권이라는 **한정 자원**이라 공짜로 쓰면 나중 트렁크가
건널 자리를 잃는다.

## 17. 손잡이는 **하나**다 — 여유 마진

*"모듈 크기"* 와 *"트렁크 연결 수준"* 은 같은 손잡이의 양면이다:

```
마진 크게 → 경로가 멀리 돈다 → 많이 묶인다 → 모듈이 크다
마진 작게 → 경로가 못 돈다   → 쪼개진다    → 모듈이 작다
```

마진이 모자라 경로가 없으면 §마(쪼개기)로 떨어지고 극한이 다이렉트다.
**손잡이 하나가 라와 마를 동시에 구현한다.** (D4·D5 — 모듈마다, 파라미터까지)

## 18. 최적화는 나중이다

*"우선 구현되는 게 중요하다"*(2026-08-13 사용자). `turnPenalty`·모듈 밖 가산은
**켤 자리만 만들어 두고 값은 나중에** 정한다 — 교차가 실제로 관측되면 그때 켠다(D3).

## 19. 기존 코드와의 상호작용 — **새로 만들 접점이 0 이다**

모듈 크기는 **이미 셀의 부산물**이다:

```ts
// moduleTransform.moduleExtent — 머신 ∪ **모든 셀**의 외접 사각형
for (const m of mod.machines) mk(...);
for (const c of mod.cells)    mk(c.x, c.y);   // ← 벨트 한 칸만 밖으로 나가도 반영된다
```

`module/ledger/seat.fitOnGap` 주석이 이미 그렇게 적고 있다 — *"자리는 그냥 **바깥으로 자란다**: 모듈이
차지하는 범위는 `moduleExtent`(머신 ∪ 모든 셀)라 배치가 이 셀들을 이미 셈에 넣는다."*

**소비처 넷은 전부 `moduleExtent` 하나만 본다** — 모듈 내부를 아무도 안 들여다본다:

| 소비처 | 무엇에 | 모듈이 커지면 |
|---|---|---|
| `modulePacking` tidy-tree(`heightOf`) | 세로 배치 | **평행이동만** |
| `modulePacking` `colWidth[depth]` | 열 폭 = 그 열 모듈들의 **최대 w** | 그 열이 넓어진다 |
| `modulePacking` `absPortY` | 포트 절대 y = `anchor.y + topY − ext.y` | **포트 위치가 자동으로 따라온다** |
| `modulePerimeterPass` | 반출 시작점 | 자동 |

**포트 위치도 이미 모듈이 정한다** — `ModulePort.anchor` 는 방출기가 만들고
(`makeLinkPortChest`) 바깥은 **읽기만** 한다. *"트렁크가 포트 위치를 정한다"* 는
새 권한이 아니라 **이미 있는 권한**이다.

> **딱 하나 값을 무는 곳:** `colWidth` 는 **열 단위 최대치**라, 한 모듈이 커지면 같은
> depth 의 **열 전체**가 넓어진다. 트렁크 하나의 욕심이 이웃 모듈들의 배치까지 벌린다 —
> 그게 §9.3 손잡이가 실제로 무는 비용이다.

# 부록 B — 기각과 정정

**여기 있는 것은 *"무엇을 하나"* 가 아니라 *"왜 다른 걸 안 했나"* 다.** 떼어 내지 않고 이
문서에 업혀 둔 이유는 **앵커가 없기 때문**이다 — *"옛 TR2 를 왜 버렸나"* 는 §3 옆에 있어야
읽히고, 혼자 떼면 아무도 안 여는 문서가 된다([docs/CLAUDE.md](../../CLAUDE.md)).

**절 번호는 옛 자리 그대로다**(§9 · §14) — 자리만 옮겼다.

## 9. 폐기된 것 — 옛 TR2 (2026-08-14)

```
옛 TR2:  구간이 적은 줄일수록 얕은 줄, 많은 줄일수록 깊은 줄
```

**근거였던 것:** 얕은 줄의 진출은 깊은 줄에 **지상 전달 타일**이 필요하니, 구간 많은 줄을
깊게 두면 구멍이 남아돈다.

**폐기 이유 셋**

```
① 진출 수단을 하나(지상 전달 타일)로 가정했다.  TR7 이 둘을 주면 회피가 필요 없다
② c 가 같으면 완전 대칭이다 — 배치2 에서 나무↔구리를 offset 까지 바꾸면 타일 하나까지 같다
③ 처리량 논리와 정면 충돌한다:
     c 작다 ⟺ k 크다 ⟺ per 작다  →  옛 TR2 는 **수요가 작은 줄에 가장 빠른 팔**을 준다
     그런데 a = ⌈per/tp⌉ 라 빠른 팔은 **수요가 큰 줄**에 필요하다
```

**그리고 이 폐기가 순환을 끊는다.** 옛 TR2 는 `c` 를 깊이 배정의 입력으로 썼는데,
`c` 는 `그릇 = ⌊벨트/tp(d)⌋` 를 거쳐 깊이에 의존한다 — `c → 깊이 → tp → 그릇 → c`.
새 TR2 는 `c` 를 안 보므로 고리가 없다:

```
① 면  →  ② 깊이(a 로 후보 거르기)  →  a·그릇·g·c 를 한 번 계산  →  ③④⑤⑥
```

## 14. 전용 탐색기(B)를 왜 안 쓰나 (옛 제목: *"왜 (A′)인가"*)

> **정정(2026-08-24): (A′)도 폐기됐다 — 채택안은 §15 의 (C) 구간 배정이다.**
> 아래 표는 **(B)를 기각한 근거로 유효**하고 §15 ③ 이 그대로 인용한다. 다만 (A′)가
> *"1·2·3 을 탐색 밖으로 뺀다"* 고 적은 그 논리를 **끝까지 밀면 탐색이 아예 사라진다** —
> 남는 자유도가 셋(깊이·구간 양끝)뿐이라 열거가 탐색보다 싸다. (A′)는 그 절반에서 멈춘 안이었다.

트렁크가 납품 경로와 다른 점 다섯:

| # | 트렁크 고유 | `containerRouting` 이 표현하나 |
|---|---|---|
| 1 | **N개 머신 곁을 지난다**(경유지) | ❌ 시작·끝 집합만 |
| 2 | **탭 주행이 지상 연속 `k`칸** | ❌ *"여기서 k칸 곧게"* 를 못 시킨다 |
| 3 | **자기 교차 금지**(벨트 한 줄) | ❌ 한 번 호출에선 자동, 여러 번이면 수동 |
| 4 | 흐름 방향 일관 | ✅ 경로가 곧 방향 |
| 5 | 지하 · corridor · 입구 방향 | ✅ 전부 있다 |

**(A′)는 1·2·3 을 탐색 밖으로 뺀다:**

```
1 경유지   →  구간으로 쪼갠다 (순서를 밖에서 정한다)
2 탭 주행  →  탐색 안 하고 **구성**한다 (좌석 수에서 바로 나온다)
3 자기교차 →  이전 구간 셀을 다음 구간의 `blocked` 에 넣는다
```

**(B)는 셋을 탐색 안으로 넣는다** — 상태에 *"몇 번째 머신을 지났나"* 를 더한 경유지
Dijkstra. 순서까지 탐색이 골라 **전역 최적**이 되지만, 상태 공간이 머신 수만큼 곱해지고
**지하·방향·corridor 를 다시 구현**해야 한다(R3 위반).

**(A′)가 지는 경우:** 구간1 이 최단으로 갔더니 구간2 가 크게 돌아야 하는 배치.
(B)라면 구간1 을 조금 돌려 전체를 줄인다. **기둥에서는 순서가 위→아래 하나뿐이라 이 손해가
거의 없고**, 격자(judgements J4 — 범위 밖)에서 커진다.
