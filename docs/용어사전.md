# 용어 사전 (Glossary)

이 vault(`docs/`)에 등장하는 모든 도메인 용어의 단일 정의 출처다. 각 문서 본문에서 용어가 **처음 나올 때** 이 사전의 해당 항목으로 링크된다(`[[용어사전#<용어>|<용어>]]`).

> **사용법(Obsidian):** 용어를 클릭하면 이 문서의 해당 소제목으로 점프한다. 각 항목 끝의 `→` 는 그 용어를 자세히 다루는 원본 문서 링크다.
> **문서와 코드가 어긋나면 코드가 현재 사실**이다(CLAUDE.md 규칙). 이 사전도 시점 기록이다.
> 진입점 지도는 [[README]] 참조.
>
> 🔧 **디버그 플래그·콘솔 로그를 찾는다면 [[변수명사전]] 으로.** 이 사전은 **도메인 용어**(사람이
> 대화할 때 쓰는 말)를 담고, 저쪽은 **코드에만 사는 스위치와 진단 출력**(켜고 끄거나 콘솔에서 읽는 것)을
> 담는다. 예: "[[용어사전#ClusterBelt / ClusterBelts|ClusterBelt]] 가 뭔가" 는 여기, "모듈 경로가 왜 폴백했나" 는 저기.

## A. 배치 핵심 모델 (컨테이너)

### 컨테이너
머신·무한상자·무한파이프 세 종류의 게임 엔티티를 하나로 묶은 **추상 단위**. 배치와 라우팅은 이 추상 위에서 동작한다. 어떤 배치 전략에서도 변하지 않는 불변 기반. → [[auto-layout-wizard.placement-search#2-컨테이너]]

### 머신 (machine)
레시피를 처리하는 [[용어사전#컨테이너|컨테이너]]. `assembling-machine`·`furnace`·`rocket-silo` 등. 직접 운반 능력이 없어 [[용어사전#투입기 (inserter)|투입기]]·[[용어사전#벨트 (belt)|벨트]]·[[용어사전#파이프 (pipe)|파이프]]가 붙어야 입출력된다. → [[auto-layout-wizard.entity-roles#a-변환기-조립기계-그룹]]

### 무한상자 (infinity chest)
외부 item 입출력을 담당하는 1×1 컨테이너(`infinity-chest`). 라인 경계에서 아이템을 무한 공급/흡수한다. → [[auto-layout-wizard.placement-search#2-컨테이너]]

### 무한파이프 (infinity pipe)
외부 fluid 입출력을 담당하는 1×1 컨테이너(`infinity-pipe`). 유체 버전의 무한상자. → [[auto-layout-wizard.placement-search#2-컨테이너]]

### 포트 (port)
컨테이너가 외부와 통하는 셀. `port.kind ∈ {item, fluid:<fluid-name>}` 이며 라우팅은 **같은 kind 의 두 포트 사이만** 짝지을 수 있다. → [[auto-layout-wizard.placement-search#22-ports]]

### item port
[[용어사전#footprint|footprint]] 둘레 셀 전체(`2(w+h)`개)가 후보인 아이템 포트. 머신·무한상자가 노출. → [[auto-layout-wizard.placement-search#22-ports]]

### fluid port
`fluid_boxes[].connections[].positions` 가 정하는 **고정 셀**에서만 나오는 유체 포트. 보통 1~2개라 item 보다 제약이 크다. → [[auto-layout-wizard.entity-roles#d-액체-운반-파이프]]

### footprint
컨테이너가 차지하는 타일 영역. `Entity.tile_width × tile_height`. 머신마다 다르다(조립기 3×3, 보일러 3×2, 로켓사일로 9×9). → [[auto-layout-wizard.entity-roles#a-변환기-조립기계-그룹]]

### 클러스터 (cluster)
**같은 레시피 노드의 N대 동일 머신** 묶음. 트렁크 병합·채널 라우팅·그룹화의 기본 단위. → [[auto-layout-wizard.placement-search#71-클러스터-한-노드-n대]]

**형태는 두 가지다** — [[용어사전#ColumnCluster|ColumnCluster]](세로 한 줄)와 [[용어사전#GridCluster|GridCluster]](붙이지 않음). 코드는 아직 ColumnCluster 만 낸다(`clusterLayout.layoutCluster` 의 `dx` 가 상수 0). **클러스터는 규칙을 강요하는 개념이 아니다**(2026-07-19 사용자 정정) — 링크는 머신↔머신이라 클러스터를 안 본다. → [[auto-layout-wizard.machine-link]]

### ColumnCluster
**클러스터를 한 열에 세로로 쌓은 형태**(2026-07-22 사용자 명명. 그 전 이름 = [[용어사전#기둥 (column)|기둥]]). `origin.y = baseTop + i*(h + gap)`, `origin.x` 는 전부 같다.

**왜 붙이나 — 인접은 원인이 아니라 대가다.** 붙여야 하는 이유는 딱 하나, **벨트 한 줄이 부모 머신 여럿을 관통해 나눠 먹이기로 했을 때**뿐이다. 그렇게 합치면 채널 트랙 하나를 아끼지만, 그 값으로 머신들의 인접을 내주고, 인접을 내주면 벨트가 면과 **평행**으로만 흐를 수 있어 한 면의 벨트 줄 수가 **인서터 reach 종류 수**(보통 2, [[용어사전#ClusterBeltDepth|ClusterBeltDepth]])로 묶인다.

**단 그 상한 자체가 가정 위에 있다**(2026-07-22): "팔이 **모든** 벨트를 직접 집는다"고 볼 때만 참이다. 팔이 집어야 하는 건 첫 줄 하나뿐이고 그 뒤로는 **벨트가 벨트를 먹이므로**, 벨트끼리 잇는 걸 허용하면 상한이 사라진다. → [[auto-layout-wizard.cluster-redesign]]

### GridCluster
**머신을 세로 한 줄에 가두지 않고 면이 트이도록 늘어놓은 클러스터 형태**(2026-07-22 사용자 명명). 목적지마다 벨트를 따로 내면(= 병합 안 함) 벨트가 머신 **한 대**만 상대하므로 이웃 머신을 지날 일이 없고, 그러면 붙여 놓을 이유 자체가 사라진다 — 그래서 **병합을 안 하면 GridCluster 가 기본**이다.

면이 트여 있으므로 벨트를 면과 **수직으로** 뽑을 수 있다([[용어사전#ParallelBelt|ParallelBelt]]) → 한 면의 줄 수가 인서터 reach 에 안 묶이고 좌석 열 수만큼 난다. **미구현**(2026-07-22 재설계 대상). → [[auto-layout-wizard.cluster-redesign]]

### 기둥 (column)
[[용어사전#ColumnCluster|ColumnCluster]] 의 옛 이름(2026-07-22 개명 — 형태가 둘이 되면서 `GridCluster` 와 짝이 맞는 이름이 필요해졌다). 코드·옛 문서에 `column`/`기둥` 으로 남아 있다.

클러스터를 한 열에 세로로 쌓은 형태(`origin.y = baseTop + i*(h + ROW_GAP)`). 안쪽 머신은 N/S 면을 이웃에 뺏기고 W·E 면만 남는 [[용어사전#포트 기하|포트 기하]] 한계가 있다. → [[auto-layout-wizard.known-limits#1-클러스터-형태가-세로-기둥column-고정]]

**"N/S 를 이웃에 뺏김"이 정의의 일부다** — 그래서 gap 을 열어 N/S 면을 되찾으면 **더 이상 기둥이 아니다**(2026-07-17 확인). [[용어사전#간단한 레시피|간단한 레시피]]가 "기둥으로 표현 가능"으로 정의돼 있으므로, **gap 이 필요한 레시피는 정의상 간단하지 않다.** 코드도 같은 말을 한다: `clusterLayout.pickClusterShape` 는 수요 > 기둥 용량이면 `overflow=true`(*"본래 2D 형태가 필요, 현재 미구현"*)를 내고, `clusterModule.MODULE_ROW_GAP=0` 주석은 *"복잡 레시피(2D)가 도입되면 그 경로가 자기 gap 을 따로 정한다"* 고 적고 있다. **gap 은 기둥에 달린 손잡이가 아니라 다른 형태의 속성이다.** → [[용어사전#allocateMachineLinks|allocateMachineLinks]]

### 지배축 (dominant axis)
클러스터에서 머신 중심 분포가 가장 넓은 축. 기둥이면 세로축. 방문 순서·그룹 정렬·[[용어사전#트렁크 시드|트렁크 시드]]가 이 축을 따른다. → [[auto-layout-wizard.placement-search#71-클러스터-한-노드-n대]]

### 포트 기하
기둥 배치에서 안쪽 머신이 N/S 면을 이웃에게 빼앗겨 W·E 면만 노출되는 제약. 포트 수요가 많은 레시피가 한 열에 다 안 들어가는 원인. → [[auto-layout-wizard.known-limits#1-클러스터-형태가-세로-기둥column-고정]]

## B. 영역·좌표

### 내부 영역 (internal area)
머신 + 내부 라우팅(벨트·파이프·투입기)이 사는 영역. 좌표 기준점은 머신 footprint 의 bbox. → [[auto-layout-wizard.placement-search#3-영역--내부-영역--perimeter-ring-외부]]

### 외부 영역 (external area)
무한상자·무한파이프가 사는 영역. 별도 좌표계가 아니라 **internal bbox 의 [[용어사전#perimeter ring|perimeter ring]] 위**에 산다. → [[auto-layout-wizard.placement-search#3-영역--내부-영역--perimeter-ring-외부]]

### perimeter ring
내부 영역(머신+라우팅) bbox 를 둘러싼 한 겹의 둘레. 외부 컨테이너는 이 링 위에만 배치되고, 사용자 드래그도 이 셀로만 제한된다. → [[auto-layout-wizard.placement-search#3-영역--내부-영역--perimeter-ring-외부]]

### bbox
bounding box. 한 묶음의 셀을 감싸는 최소 직사각형. `|W−H|` 가 작을수록(정사각형에 가까울수록) 좋은 후보([[용어사전#O1|O1]]). → [[auto-layout-wizard.placement-search#o1--내부-영역-bbox-가-정사각형에-가까울수록-우선]]

### graceful degradation
외부 컨테이너 배치·라우팅이 실패해도 전체를 중단하지 않고 부분 결과로 우아하게 물러나는 처리. → [[auto-layout-wizard.placement-search#3-영역--내부-영역--perimeter-ring-외부]]

### 외부 상자 집결 (externalGatherPass)
**같은 품목**을 공급/흡수하는 외부상자들을 한 곳에 인접 이송해 품목당 외부 물류 접점을 하나로 모으는 **맨 마지막 후처리 패스**. 흐름 합류([[용어사전#트렁크 병합|트렁크 병합]])가 아니라 위치만 모은다 — 각 상자의 belt 는 따로 유지. 그룹 단위 폴백. 크로스-변 집결(P3)은 보류라 **같은 변에 앉은 상자끼리만** 모을 수 있다 — 상자 seat 의 변 선택이 집결 가능성을 결정. (전용 문서 없음, 코드: `externalGatherPass.ts`)

## C. 라우팅·경로 탐색

### 라우팅 (routing)
두 컨테이너의 (producer port, consumer port) 사이를 잇는 [[용어사전#운반체|운반체]] 체인. **라우팅 1개 = 컨테이너 1개** 원칙. 처리량을 못 채우면 컨테이너 수를 늘려 분할한다. → [[auto-layout-wizard.placement-search#4-라우팅-형식]]

### 운반체
아이템/유체를 실제로 나르는 엔티티. item 체인 = `투입기—벨트(+지하벨트)—투입기`, fluid 체인 = `파이프(+지하파이프)`. → [[auto-layout-wizard.placement-search#4-라우팅-형식]]

### 벨트 (belt)
고체 아이템 운반체(`transport-belt`, 1×1). 한 방향으로 좌/우 두 [[용어사전#레인 (lane)|레인]]을 흘린다. → [[auto-layout-wizard.entity-roles#c-고체-운반-벨트]]

### 지하벨트 (underground-belt)
입구·출구 페어로 이루어진 벨트(1×1 두 개). 사이 칸은 다른 엔티티가 통과 가능. 지하 점프는 **같은 prototype 끼리만** 서로 차단한다([[용어사전#blockGroup|blockGroup]]). → [[auto-layout-wizard.placement-search#41-지하-변형-underground-belt--pipe-to-ground]]

### 투입기 (inserter)
머신과 운반체 사이를 잇는 [[용어사전#핸드오프|핸드오프]] 엔티티(1×1). `direction` 이 "픽업→드랍" 을 가리키며 양옆 두 셀에 닿는다. 처리량 = `rotation_speed × stack_size`. → [[auto-layout-wizard.entity-roles#b-핸드오프-투입기--로더]]

### 파이프 (pipe)
유체 운반체(1×1). 인접한 fluid_box 와 **자동으로** 연결되며 direction 의미가 없다(0 고정). → [[auto-layout-wizard.entity-roles#d-액체-운반-파이프]]

### 지하파이프 (pipe-to-ground)
유체용 지하 점프 페어(1×1 두 개). 같은 직선 위 다른 페어를 **무조건** 차단한다(단일 `blockGroup = "pipe-to-ground"`). → [[auto-layout-wizard.placement-search#41-지하-변형-underground-belt--pipe-to-ground]]

### 지하 변형
지상 경로를 비우려고 [[용어사전#지하벨트 (underground-belt)|지하벨트]]/[[용어사전#지하파이프 (pipe-to-ground)|지하파이프]] 점프 페어를 쓰는 것. Dijkstra 에서 점프 edge(cost 2)로 표현된다([[용어사전#O2|O2]]). → [[auto-layout-wizard.placement-search#41-지하-변형-underground-belt--pipe-to-ground]]

### blockGroup
지하 운반체가 같은 직선 위에서 서로 차단되는 그룹 키. `pipe-to-ground` 는 prototype 무관 단일 그룹, `underground-belt` 는 `blockGroup = entityName`(같은 티어끼리만). → [[auto-layout-wizard.placement-search#41-지하-변형-underground-belt--pipe-to-ground]]

### 흐름-인접 (flow adjacency)
두 벨트가 타일을 공유하지 않아도, **한 벨트의 지표 출력이 옆 타일 벨트로 떨어지면** 물리적으로 이어지는 연결(직진 투입 / [[용어사전#side-load|side-load]]). 서로 다른 라우팅에서는 항상 의도치 않은 오염이다. → [[auto-layout-wizard.entity-roles#c-고체-운반-벨트]]

### side-load
벨트 옆면으로 아이템이 합류하는 것. 흐름-인접의 한 형태. → [[auto-layout-wizard.entity-roles#c-고체-운반-벨트]]

### collectBeltFlow
이미 배치된 벨트의 타일 + 지표 출력 칸을 수집해, 새 라우팅이 흐름-인접으로 오염되지 않게 막는 함수. `dijkstraWithJumps` 의 lazy-constraint 가드(`beltFlowConflictCell`)와 함께 동작. → [[auto-layout-wizard.entity-roles#c-고체-운반-벨트]]

### PipeFlow / collectPipeFlow
[[용어사전#collectBeltFlow|collectBeltFlow]] 의 **유체판**. 이미 놓인 남의 파이프·유체 상자를 훑어서, 새 파이프를 놓으면 **남의 관망과 합쳐져 버리는 칸**을 모아 둔 것. 벨트와 결정적으로 다른 점 둘:

1. **파이프에는 흐름 방향이 없다.** 벨트는 "내가 남에게 붓느냐 / 남이 나에게 붓느냐"가 갈려 검사가 두 갈래지만(그래서 `tiles` 와 `sinkTargets` 가 따로 있다), 파이프는 **닿기만 하면 무조건 합쳐진다**. 그래서 검사가 한 갈래다.
2. **같은 유체끼리는 합쳐져도 된다.** 파이프 처리량을 무한으로 보기 때문에, 같은 유체 두 줄이 한 관망이 돼도 잃는 게 없다. 그래서 막아야 할 칸이 **유체마다 다르다** — 물 파이프에겐 금지 칸인 자리가 석유 가스 파이프에겐 아무렇지 않을 수 있다.

그래서 `collectPipeFlow` 는 **"지금 깔려는 유체 이름"을 받아서**, 그 유체에게 금지된 칸만 모은 지도를 돌려준다(칸마다 유체 이름을 매달아 두는 대신 유체별로 지도를 하나씩 만든다 — 유체 종류가 몇 개 안 되므로 이쪽이 단순하다). 담는 것:

- **`blockedTilesHard`** — **무조건** 못 놓는 칸. ① 다른 유체 파이프 셀과 그 **사방 네 칸**(파이프는 방향이 없어 닿기만 하면 이어진다), ② 머신 **출력** 유체 상자의 연결 칸 — 같은 유체라도 막는다. 스치면 그 머신의 생산물이 내 관망으로 **조용히 새어나가기** 때문이다.
- **`blockedTilesSoft`** — 못 놓지만 **규칙을 풀 수 있는** 칸. 이 유체를 **안 받는** 머신 **입력** 유체 상자의 연결 칸. 머신이 스스로 필터링해 필요한 유체만 받으므로 엄밀히는 안 막아도 안전하다 — 막는 편이 더 좋은 배치일 뿐이라, 자리가 열악하면 해제한다(**해제 기준 미정**. 코드에선 `pipeFlowConflict(…, soft: false)` 한 줄).
- **`joinableTile`** — 남의 파이프가 **깔려 있는** 칸과 그 유체 이름. 막으려는 게 아니라 그 반대다: **같은 유체라면 이미 깔린 관을 타고 가도 된다.** (아직 **미구현** — 모듈 간 유체 공급 공유를 할 때 쓸 자리. 가드 자체는 위 두 맵으로 완결된다.)

`Hard`/`Soft` 는 규칙의 **강도**를 뜻한다(출처가 아니라).

**어디서 걸리나(2026-07-14 구현):** 새 모듈 경로에만 건다. ① [트렁크 기둥](auto-layout-wizard.trunk-pipe.md) — 배치 직후 검사, 걸리면 트리 전체가 옛 경로로 폴백(거절은 항상 안전하다). ② 유체 반출(`modulePerimeterPass`) — 파이프를 깔기 **전에** 검사, 걸리면 그 상자만 건너뛰어 로컬 ring 에 남긴다(회귀 0). 옛 경로는 [[용어사전#Deprecated Dijkstra Guard|일부러 무방비]]다. → [[auto-layout-wizard.trunk-pipe]]

### Deprecated Dijkstra Guard
**코드와 문서에 같이 박아 둔 표식 단어.** 뜻: "이 자리는 파이프를 까는데 [[용어사전#PipeFlow / collectPipeFlow|합류 가드]]를 안 거친다 — 폐기 예정인 옛 경로(Dijkstra)라서 **일부러** 안 걸었다."

유체 배치에서 원인 모를 오염(다른 유체가 섞임)이나 유실(생산물이 남의 관망으로 샘)이 보이면 이 단어로 grep 하면 무방비인 자리가 전부 나온다. → [[auto-layout-wizard.known-limits#12-deprecated-dijkstra-guard--옛-경로의-파이프는-합류-가드를-안-거친다]]

### occupancy
셀이 이미 점유돼 통과 불가한지의 지도. 현재 1차 단순화로 **모든 placed 셀을 통과 불가**로 본다(belt/pipe [[용어사전#mixing|mixing]] 미구현). → [[auto-layout-wizard.known-limits#5-라우팅-occupancy-가-모든-셀-통과-불가-beltpipe-mixing-미구현]]

### mixing
한 운반 셀에 서로 다른 내용물이 섞이는 것. **금지**: 벨트 2-레인 혼류·다른 fluid 파이프 공유. C3(액체 mixing 방지)가 이를 강제. → [[auto-layout-wizard.placement-search#c3--액체-mixing-방지]]

### fallback (라우팅)
한 라우팅이 실패하면 모든 포트 페어를 맨해튼 거리 오름차순으로 재시도하는 폴백(`routeWithFallback`). S-LAYER 는 채널 보장으로 실패가 사실상 안 난다. → [[auto-layout-wizard.placement-search#74-fallback]]

### 멀티소스/싱크 라우팅
Dijkstra 를 멀티소스·멀티싱크로 돌려 **포트 선정을 라우팅 출력으로 역전**시키는 것. 후보 포트를 미리 정하지 않고 경로가 고르게 한다. → [[auto-layout-wizard.priority-ordering#2-우선순위-등록부-모든-결정점]]

## D. 트렁크 병합

### 트렁크 벨트 (trunk belt)
같은 품목을 쓰는 N대 머신을 **공유 belt 1줄 + 머신별 탭 인서터 + 종단**으로 묶은 N:1 병합 구조. → [[auto-layout-wizard.placement-search#72-트렁크-벨트-n1-병합]]

### 탭 (tap)
트렁크 belt 에서 개별 머신으로 갈라지는 인서터 접점. `탭 = (포트 p, 면 f, reach r)` → `tapCell = p + f×r`. → [[auto-layout-wizard.placement-search#72-트렁크-벨트-n1-병합]]

### 트렁크 병합
클러스터/외부 상자의 여러 흐름을 트렁크 벨트로 합치는 패스. 내부(클러스터→부모)는 `clusterTrunkMerge`, 외부(상자↔머신)는 `externalMergePass` 가 담당. → [[auto-layout-wizard.placement-search#72-트렁크-벨트-n1-병합]]

### 트렁크 시드
트렁크 경로를 그리디로 키울 때의 시작점 후보(centroid 근접 + 끝-축 평행). seed 점수 `[untapped, 횡축 span, 길이]` 최소를 채택. → [[auto-layout-wizard.priority-ordering#2-우선순위-등록부-모든-결정점]]

### supply / collect
트렁크의 두 방향. `supply` = 상자→머신, `collect` = 머신→상자. 서로 흐름·픽업이 반전된 거울 관계. → [[auto-layout-wizard.placement-search#72-트렁크-벨트-n1-병합]]

### 탭 인서팅 (Tap Inserting)
[[용어사전#트렁크 벨트 (trunk belt)|트렁크 벨트]]가 쓰는 공급 방식 — [[용어사전#ClusterBelt / ClusterBelts|ClusterBelt]] 한 줄이 면을 세로로 흐르고, 머신들이 [[용어사전#탭 (tap)|탭]] 인서터로 그 줄을 나눠 집는다. 한 면의 용량 = 그 면에 세울 수 있는 ClusterBelt 수 = **인서터 reach 값의 종류 수**(reach 1 → [[용어사전#ClusterBeltDepth|ClusterBeltDepth]] 2, reach 2 → 3, …). 코드: `clusterPortPlanner.laneSlots` (미지정 `slotsPerFace` = 이 모델, 하위호환 기본값). ↔ [[용어사전#다이렉트 인서팅 (Direct Inserting)|다이렉트 인서팅]]

(2026-07-15 재설계 완료: `laneSlots` 가 reach 목록에서 벨트 줄을 유도하고, 유체 면도 [[용어사전#isJumpableToClusterPipe|점프 가능]]하면 좌석이 산다 — 하드코딩·과잉 선점 둘 다 제거됐다.)

### 다이렉트 인서팅 (Direct Inserting)
1:1 파이프라인이 쓰는 공급 방식 — belt 가 아예 없다. 머신 둘레(rim) 각 칸마다 `[상자][인서터]` 쌍을 독립적으로 세워 상자↔머신을 인서터로 직결한다. 한 면의 용량 = **그 면의 둘레 칸 수**(W/E 면=머신 높이, N/S 면=머신 폭) — 머신이 몇 대든 개수만큼 자란다. [[용어사전#탭 인서팅 (Tap Inserting)|탭 인서팅]](면당 최대 2줄)과 혼동하면 세 번째 입력 이상이 자리가 남는데도 다른 면으로 넘친다(kr-glass 갇힘의 원인). 코드: `clusterPortPlanner.PortPlannerInput.slotsPerFace`. ↔ [[용어사전#탭 인서팅 (Tap Inserting)|탭 인서팅]]

### 트렁크 파이프 (trunk pipe)
파이프 **한 줄**이 [[용어사전#기둥 (column)|기둥]]을 따라 달리며 머신들의 유체 입구를 죽 이어서 공급하는 형태(2026-07-13, 사용자 명명 — [[용어사전#탭 인서팅 (Tap Inserting)|탭 인서팅]]/[[용어사전#다이렉트 인서팅 (Direct Inserting)|다이렉트 인서팅]]과 나란한 유체판). **인서터가 없다** — 파이프가 머신 유체 입구 칸에 **직접 닿아야** 하므로 depth 는 늘 1이고, 칸은 프로토타입의 `fluid_boxes` 가 정한다(둘레 아무 칸이나 못 쓴다). 벨트와 달리 **합류가 공짜**라 "합치는 기술"이 아니라 그냥 자연스러운 모양이다. 기둥에서 유체 입구를 노출시키려고 **머신을 90° 회전**한다. → [[auto-layout-wizard.trunk-pipe]]

### 케이스 B (파이프 넘김 레인)
[[용어사전#트렁크 파이프 (trunk pipe)|트렁크 파이프]]가 좌석 줄([[용어사전#ClusterBeltDepth|ClusterBeltDepth]] 1)을 **통째로** 먹은 면에 아이템 벨트를 놓는 방법 — 긴팔 인서터가 **2** 에 앉아 파이프를 넘어 **4** 에서 집고 머신 가장자리에 떨군다. 일반 인서터는 1 에 앉아야 하는데 그 자리가 파이프라 **쓸 수 없다** → 그 면의 [[용어사전#ClusterBelt / ClusterBelts|ClusterBelt]] 는 **하나뿐**(긴팔 전용)이다.

**2026-07-14: 이건 과잉 선점이었다.** 파이프가 좌석 줄을 통째로 먹을 이유가 없다 — 유체 상자의 연결 칸 하나만 먹고 [[용어사전#pipeJumpToClusterPipe|pipeJumpToClusterPipe]] 로 바깥([[용어사전#ClusterPipe|ClusterPipe]])에 나가면 나머지 좌석이 산다. **2026-07-15 구현 완료:** 케이스 B 는 [[용어사전#isJumpableToClusterPipe|isJumpableToClusterPipe]] 가 거짓일 때(지하파이프 미보유·점프 거리 부족·좌석 부족)의 **폴백**으로 남았다. → [[auto-layout-wizard.trunk-pipe#4-depth-규약--파이프가-1칸을-먹으면-아이템이-밀린다]]

### ClusterBelt / ClusterBelts
**머신 면에서 바깥으로 일정 거리에 떨어져 기둥을 따라 세로로 달리는 벨트 한 줄**(2026-07-14, 사용자 명명). [[용어사전#탭 인서팅 (Tap Inserting)|탭 인서팅]]에서 머신들이 [[용어사전#탭 (tap)|탭]] 인서터로 집어 가는 그 줄이다. 여러 줄이면 `ClusterBelts`.

전에 "레인" 이라고 부르던 것 — **개명했다.** 게임의 "레인"은 **한 벨트가 가진 좌/우 두 줄**([[용어사전#레인 (lane)|레인]])이라는 전혀 다른 뜻이고, [[용어사전#MixedItemBelt|MixedItemBelt]] 를 만들기 시작하면 "depth 3 레인의 벨트의 오른쪽 레인" 같은 말이 나와 반드시 깨진다.

### ParallelBelt
**여러 벨트가 서로 나란히(parallel) 밖으로 향하는 것**(2026-07-22 사용자 명명, 2026-07-23 정의 확정). 벨트마다 **자기 줄과 자기 포트**를 갖고, **서로 합류하지 않는다.**

> **합류하지 않는 것이 이 개념의 전부다.** 포화된 벨트 둘을 합치면 뒤엣것이 막혀 예상대로 안 돈다 — 그래서 줄 수를 늘릴 때는 **반드시** 끝까지 따로 내보낸다.

**한 면에 벨트를 여러 줄 놓는 방법은 이것 하나다.** 예전엔 벨트를 바깥으로 한 칸씩 밀어 쌓고 [[용어사전#ClusterBeltDepth|ClusterBeltDepth]] 를 긴팔이 집게 했는데, 긴팔이 느리면(실측 모드팩 1.2/s 대 10/s) 줄을 늘려도 처리량이 안 는다 → [[auto-layout-wizard.cluster-redesign]].

#### 면이 트였나에 따라 모양이 둘 — **둘 다 ParallelBelt 다**

| | 면이 트임 (W/E, 클러스터 양 끝) | 면이 막힘 (머신 사이) |
|---|---|---|
| 그 면의 좌석 **줄** 수 | 여럿 (세로 면이라 행이 여러 개) | **하나** (가로 면이라 행이 하나) |
| 벨트가 갈리는 축 | **행** — 벨트마다 자기 팔 | **깊이** — 첫 줄이 다음 줄에 부어 준다 |
| 나가는 방향 | 면과 **수직**으로 곧장 | 수직은 이웃 머신에 막힘 → **옆으로 돌아** 나감 |
| 벨트 깊이 | 전부 d2 | d2, d3, … |

**막힌 면의 깊이는 ClusterBeltDepth 가 아니다.** 팔은 여전히 d2 만 집고, 더 깊은 줄은 **벨트가 벨트에 붓는다**([[용어사전#ClusterBelt / ClusterBelts|ClusterBelt]] 의 depth 는 팔이 집어야 해서 reach 에 묶이지만, 이쪽은 안 묶인다). 그래서 줄 수가 팔 길이와 무관하다.

**구현됨** — [emitOutputLinks / emitInputLinks](../frontend/src/utils/autoLayout/module/clusterModule.ts). 합류하지 않는다는 것은 흐름 방향을 한 칸씩 따라가는 검사(`beltLeaks`)로 확인한다 — 좌표 겹침 검사로는 못 잡는다(겹치지도 않고 품목도 같다).

**아직 안 깔린 곳:** 외부 줄(바깥에서 오는 원료·밖으로 나가는 완제품)은 여전히 옛 방식이다 → [[auto-layout-wizard.cluster-redesign]] "열어 둔 것".

### ClusterBeltDepth
**ClusterBelt 가 머신 면에서 바깥으로 몇 칸 떨어져 있나**(2026-07-14, 사용자 명명). 그냥 `depth` 라고 쓰면 안 되는 이유: 코드의 `depth` 는 이미 **레시피 트리의 깊이**(= 채널 열 번호)를 뜻한다.

- `0` = 머신 자신의 가장자리(인서터가 떨구는 목적지).
- `1` = **좌석 줄** — 인서터가 앉는 칸. 일반이든 긴팔이든 좌석은 여기다. [[용어사전#머신 유체 상자 (machine fluid box)|머신 유체 상자]]의 연결 칸도 여기라, 파이프는 이 줄에서 **상자 칸 하나만** 먹는다(줄 전체가 아니다).
- `2 … (1 + 최대 reach)` = ClusterBelt 가 설 수 있는 칸. **상한이 인서터의 최대 reach 다** — 벨트를 더 바깥에 둬 봐야 인서터가 못 닿는다. 그래서 ClusterBelt 의 개수는 하드코딩이 아니라 **게임데이터의 인서터 reach 값 집합**에서 나와야 한다.

### requiredInserterCount
**머신 한 대의 한 줄(품목 하나)을 먹이는 데 필요한 인서터 팔의 개수**(2026-07-16, 사용자 명명).

```
requiredInserterCount = ceil(머신 한 대의 초당 수요 ÷ 인서터 하나의 초당 처리량)
```

**공급 방식과 무관한 물리량이다.** 인서터 하나가 나르는 양은 그 팔이 벨트에서 집든 상자에서 집든 같다. 그래서 이 수는 [[용어사전#탭 인서팅 (Tap Inserting)|탭]]이냐 [[용어사전#다이렉트 인서팅 (Direct Inserting)|다이렉트]]냐를 **고르기 전에** 이미 정해져 있다 — 레시피·머신 속도·인서터 프로토타입이 전부 밖에서 오는 값이라 협상 대상이 아니다. 모드는 **이 팔들을 어떻게 앉히느냐**의 문제일 뿐이다:

- **탭** — 팔들이 같은 [[용어사전#ClusterBelt / ClusterBelts|ClusterBelt]] 한 줄에서 집는다(= [[용어사전#Parallel Inserting|Parallel Inserting]]).
- **다이렉트** — 팔들이 각자 자기 상자에서 집는다. 상자 한 칸의 이웃은 4칸뿐이고 인서터는 **상자와 머신 양쪽에 닿아야** 하므로, 팔이 늘면 상자도 늘어야 한다.

수량을 모르면(범위 산출물인데 게임데이터에 `amount_min`/`amount_max` 가 없는 등) **`undefined`** 다 — 숫자를 지어내지 않는다. 소비처가 "판정 보류"(1로 봄)를 고른다. → [[project_silent_nan_and_recursion]]

**팔은 면을 넘나든다**(2026-07-17). 한 줄의 팔이 면 하나의 좌석 행보다 많으면 배정을 하나 더 만들어 **다른 면에 나눠 앉는다**(각 배정이 자기 벨트·자기 포트). 7×7 머신이면 W 에 7개 + E 에 3개 하는 식이라, 한 줄이 쓸 수 있는 상한은 면당 7행이 아니라 **W/E 합쳐 14행**이다.

이때 배분기는 **자원 두 가지를 따로 센다** — 하나로 뭉뚱그리면 안 된다:

| 세는 것 | 한 면에 몇 개 | 왜 |
|---|---|---|
| **벨트 슬롯** | 인서터 reach 종류 수 (보통 2) | 벨트는 [[용어사전#ClusterBeltDepth|ClusterBeltDepth]] 마다 한 줄 |
| **좌석 행** | 머신 높이 (7×7 이면 7) | 팔은 좌석 칸마다 하나 |

**배정 하나가 벨트 슬롯 1개를 먹으면서 팔은 여러 개 앉힌다** — 그래서 두 수는 서로 유도되지 않는다. 좌석을 안 세면 슬롯이 남았다고 팔 10개를 7행짜리 면에 몰아넣고, 그 사실은 **배정이 끝난 뒤에야** 드러나 되돌릴 수 없다(2026-07-17 이전 동작). 코드: `PortPlannerInput.slotsPerFace`(벨트) vs `seatRowsPerFace`(좌석).

**그래도 천장은 있다 — 단, [[용어사전#기둥 (column)|기둥]]일 때만.** 기둥에서 머신 둘레는 유한하다(7×7 이면 W/E 합쳐 14행 — 중간 머신의 N/S 면은 옆 머신 몸통이라 못 쓴다). 필요한 팔이 그걸 넘으면 **기둥으로는 배치가 존재하지 않는다** → 굶주림 보상이 머신을 더 놓아 총량을 맞추고 콘솔에 `인프라 부족` 경고를 낸다. gap 을 열어 N/S 를 되찾으면 천장이 올라가지만 **그 순간 기둥이 아니다**(기둥의 정의가 "N/S 를 이웃에 뺏김"이다) → [[용어사전#allocateMachineLinks|allocateMachineLinks]].

> **반올림 방향이 역할마다 달라야 한다** — 지금 이 함수는 **입력·출력 둘 다 `ceil`** 이다. 입력은 그게 맞지만(모자라면 부모가 굶는다), **출력은 `floor` 여야 한다**(넘치면 없는 걸 나른다고 주장한다). 현재 데이터에선 벨트 하나에 인서터가 넉넉히 들어가 안 드러난다. → [[용어사전#allocateMachineLinks|allocateMachineLinks]] 규칙 6

### Parallel Inserting
**한 머신·한 품목에 인서터를 둘 이상 붙여 처리량을 늘리는 것**(2026-07-14, 사용자 명명). 인서터 하나의 처리량은 유한하므로, 머신 한 대의 수요가 인서터 하나를 넘으면 좌석을 하나 더 써서 같은 ClusterBelt 를 두 번 집는다. **몇 개 붙일지가 곧 [[용어사전#requiredInserterCount|requiredInserterCount]] 다** — 탭 모드에서 그 팔들을 벨트 한 줄에 앉히는 방식이 Parallel Inserting 이다.

> **주의 — "좌석은 보통 남는다"는 틀렸다.** 예전 이 항목은 "자리는 있다(ClusterBelt 수 < 좌석 칸 수)" 라고 적혀 있었는데, **실측이 반증했다**(2026-07-16): `kr-glass` ← `kr-sand` 를 kr-advanced-furnace(속도 8)로 돌리면 머신 한 대가 kr-sand 를 초당 8개 먹어 팔이 **24개** 필요했다 — 좌석은 W/E 합쳐 14행뿐이라(팔이 면을 넘나들어도) 좌석 예산에서 걸려 다이렉트로 떨어졌다. 인서터 처리량 범위가 넓으면(모드 인서터·긴팔) 좌석은 **얼마든지 모자랄 수 있다.** 이 가정에 기대는 코드를 새로 쓰지 말 것.

↔ [[용어사전#탭 (tap)|탭]](인서터 하나)

### MixedItemBelt
**한 벨트 줄에 두 품목을 좌/우 [[용어사전#레인 (lane)|레인]]에 나눠 싣는 것**(2026-07-14, 사용자 명명). 벨트 한 줄의 아이템 용량이 2배가 된다.

**입력과 출력이 비대칭이다:**
- **입력** — 필터 인서터가 자기 품목만 골라 집으므로 한 벨트에 두 품목이 실려도 된다. **가능.**
- **출력** — 인서터는 **항상 먼 레인**에 떨군다. 같은 면의 두 인서터가 같은 벨트에 떨구면 둘 다 먼 레인으로 가서 섞인다. 사이드로드 없이는 **불가능.**

### ClusterPipe
**ClusterBelts 바깥에 세로로 서서 머신들의 유체 상자를 잇는 파이프 줄**(2026-07-14, 사용자 명명). [[용어사전#트렁크 파이프 (trunk pipe)|트렁크 파이프]]의 **자리를 옮긴 형태**다.

옛 트렁크 파이프는 ClusterBeltDepth 1(좌석 줄)에 기둥째 서서 그 면의 좌석을 통째로 잡아먹었다. 그럴 필요가 없다 — 파이프는 [[용어사전#머신 유체 상자 (machine fluid box)|유체 상자]]의 **연결 칸 하나**에만 닿으면 되고, 거기서 [[용어사전#pipeJumpToClusterPipe|pipeJumpToClusterPipe]] 로 ClusterBelts 를 **넘어** 바깥에서 합류하면 된다. 그래서 좌석 줄에서 파이프가 먹는 칸은 **머신당 1칸**뿐이고 나머지 좌석은 산다.

파이프는 인서터가 없어서 **reach 제약이 없다** — 유일하게 ClusterBelts 바깥으로 나갈 수 있는 운반체다.

### pipeJumpToClusterPipe
**머신 유체 상자에서 지하파이프로 ClusterBelts 를 넘어 [[용어사전#ClusterPipe|ClusterPipe]] 로 나가는 한 번의 점프**(2026-07-14, 사용자 명명. 2026-07-15 구현 완료 — `clusterModule.emitTapInserting`). 머신마다 하나씩 생긴다. 지하파이프 **입구가 곧 유체 상자 접점**이다(입구 자체가 유체 연결점이므로 상자 칸에 바로 놓는다).

점프 한 번의 두 끝(둘 다 지하파이프 엔티티, 2026-07-15 사용자 명명):
- **fluidboxPipeCell** — 유체 상자 칸([[용어사전#ClusterBeltDepth|ClusterBeltDepth]] 1)에 앉는 끝. 표면 연결이 머신 유체 상자를 향한다. 상자 칸의 위치는 `fluidTrunk.fluidboxOffset`(머신 footprint 내 면 위 행/열, `chooseMachineDirection` 이 고른 slot 에서 나옴)이 알려준다.
- **ClusterPipeTapCell** — 벨트들을 넘어 착지하는 끝. **ClusterPipe 줄보다 1칸 안쪽**에 앉는다 — 지하파이프는 **지하 방향으로만 합류**하고 옆(수직 방향)으론 못 이어서, 줄 위에 앉히면 ClusterPipe 의 세로 연속이 끊긴다. 표면 연결이 바깥(ClusterPipe)을 향해 직교 인접으로 합류한다.

그래서 배치 순서는: `머신 | d1 fluidboxPipeCell | d2.. 벨트(지하 통과) | ClusterPipeTapCell | ClusterPipe`. ClusterPipe 깊이 = 그 면 벨트 최대 깊이 + 2.

각 점프는 **자기 머신의 행**에서 가로로 일어나므로 머신끼리 corridor 가 안 부딪힌다(같은 열을 공유하는 건 바깥의 ClusterPipe 뿐). 점프 불가 시 폴백 = [[용어사전#케이스 B (파이프 넘김 레인)|케이스 B]] 복귀(연속적 저하, 2026-07-15 확정). **최적화 보류(사용자: 최종적으로는 똑똑하게):** 벨트를 지하벨트로 접으면 탭·ClusterPipe 를 더 안쪽으로 당길 수 있다.

### isJumpableToClusterPipe
**"이 면에서 파이프가 좌석을 비우고 밖으로 점프할 수 있는가"** 불리언(2026-07-15, 사용자 명명). `generateModule` 이 계산해 planner 에 넘기고, planner 는 이걸로 [[용어사전#트렁크 파이프 (trunk pipe)|파이프 면]]의 슬롯 모양만 가른다(참=일반 면과 같은 벨트, 거짓=[[용어사전#케이스 B (파이프 넘김 레인)|케이스 B]]) — planner 는 지하파이프 역학을 모른다.

셋 다 성립해야 참: ① 상자 칸 위치(`fluidboxOffset`)와 지하파이프를 안다 ② 점프 거리가 최악 폭(최대 reach + 1)을 감당한다 ③ 좌석 줄에서 상자 행 1개를 빼고도 벨트 좌석이 남는다(벨트 수 ≤ 면 좌석 − 1). 코드: `clusterModule.generateModule` / `clusterPortPlanner.PortPlannerInput.isJumpableToClusterPipe`.

### determineBeltCount
**이 초당 수요를 나르려면 벨트를 어떤 걸 몇 줄 깔아야 하나**(2026-07-12 사용자 명명, 2026-07-16 규칙 확정·구현). 코드: `beltThroughput.determineBeltCount`.

규칙(2026-07-16, 사용자 지정):
1. **가장 빠른 벨트부터** 채워 수요를 감당한다.
2. 딱 안 나눠떨어지고 남는 만큼은 **그 나머지를 감당할 수 있는 가장 싼(느린) 벨트**로 덮는다. 나머지 벨트는 **넉넉해도 된다**.
3. **부모가 굶으면 절대 안 된다** — 합계는 언제나 수요 이상. 모자라느니 한 티어 위를 쓴다.

수요는 **부모 수요 기준**이다 — 자식이 정수 대수 탓에 과잉 생산해도 남는 건 신경 쓰지 않는다(벨트가 차면 자식이 알아서 쉰다). 수요를 모르면 **빈 배열**(없는 숫자로 벨트를 깔지 않는다).

**왜 중요한가 — 이게 모듈 경계를 안정시킨다.** 줄 수를 **수요에서** 유도하므로 자식과 부모가 **같은 수요를 같은 규칙으로 보면 같은 줄 수**를 낸다. 포트 개수를 [[용어사전#requiredInserterCount|팔 개수]]에서 유도하면 양쪽 머신이 달라 어긋난다(2026-07-16 실측: 자식 출력 26포트 vs 부모 입력 14포트 → 12개가 갈 곳을 잃고 raw sink 가 됐다). **경계는 벨트가 정하고, 팔은 모듈 내부 사정이다.**

> **두 축은 다르다**(2026-07-16 분리):
> - **인서터 처리량** → [[용어사전#requiredInserterCount|requiredInserterCount]]. 팔을 늘려 푼다. **모드와 무관**하다.
> - **벨트 처리량** → 이 함수. 팔을 늘려도 안 풀리고(벨트가 못 나른다), 공유 벨트가 없는 다이렉트엔 **이 축 자체가 없다**.

> **범위 정정 (2026-07-17).** 위의 "경계는 벨트가 정한다"는 **[[용어사전#기둥 (column)|기둥]]이라서** 성립한다 — 벨트 한 줄이 머신 전부를 훑어 포트가 머신 수와 무관하기 때문이다. **기둥이 아니게 되면(gap 을 열어 N/S 를 쓰면) 그 근거가 사라진다.** 그때는 포트가 머신 수를 따라가는 게 정상이고, 짝짓기가 index zip 이 아니라 **흐름**이 된다 → [[용어사전#allocateMachineLinks|allocateMachineLinks]].

### MachineLink
**자식 머신 하나에서 부모 머신 하나로 가는, 인서터 n개가 채우는 벨트 하나**(2026-07-17 사장님 명명). 코드: **미구현**(설계 확정, [[용어사전#allocateMachineLinks|allocateMachineLinks]] 가 낼 예정).

그림으로 먼저:

```
   [자식 머신]                          [부모 머신]
       │ 인서터 3개가 이 벨트에 내린다
       ├──▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓──────────────┤ 인서터가 여기서 집어 넣는다
       │   └─ MachineLink 하나 = 벨트 하나
```

들고 있는 것: 어느 자식 머신(`fromMachine`) · 어느 부모 머신(`toMachine`) · 무슨 품목(`item`) · **인서터 몇 개**(`inserterCount`) · 어떤 벨트(`beltEntityName`). **실제 운반량은 안 들고 다닌다** — `인서터 개수 × 인서터 처리량` 으로 언제든 유도된다.

**왜 인서터 개수가 알맹이인가:** 인서터는 벨트가 얼마나 필요한지와 **무관하게 무조건 내린다.** 그래서 "이 벨트에 6.5개를 흘린다" 같은 건 없다 — **인서터 하나(예: 6개/초)가 최소 단위**고, 그 아래로는 못 쪼갠다. 벨트에 몇 개를 실을지가 아니라 **인서터를 몇 개 붙일지**가 우리가 정하는 전부다.

**홉(hop)과 다른 층이다.** 홉은 **모듈 포트 ↔ 모듈 포트**(`planner/modulePacking.HopSpec`)고, MachineLink 는 **머신 ↔ 머신**이다. 포트 개수·[[용어사전#기둥 (column)|기둥]]의 gap 폭·짝짓기가 전부 MachineLink 목록**에서 유도된다** — 반대가 아니다.

### allocateMachineLinks
**자식 머신들의 산출을 부모 머신들에게 어떻게 나눠 주나**(2026-07-17 사장님 명명·규칙 확정). [[용어사전#MachineLink|MachineLink]] 목록을 내는 순수 함수. 코드: `module/allocateMachineLinks.ts`(2026-07-18 구현, 아직 소비처 없음 — 순수 함수+테스트). 아래 예시가 그대로 테스트다.

> **드러난 설계 사실 — 꼬리 부모는 살짝 굶는다.** 앞 부모들을 규칙 5(올림)로 넉넉하게 채우면 예산이 앞으로 쏠려, 마지막 부모가 인서터 단위 경계에서 미세하게 모자랄 수 있다(아래 예시의 부모3 = 60 < 60.5). 자식 꼬리를 버리는 규칙 6과 대칭이다. 실무에선 `childCount` 가 `ceil` 로 과공급되게 잡혀(→ [[용어사전#requiredInserterCount|requiredInserterCount]] / assignThroughputCounts) 대개 다음 자식이 메운다.

`clusterPortPlanner.allocateArms` 와 형제다 — **유한한 예산을 두고 순서대로 탐욕적으로 나눠 주는** 함수. 다른 점은 예산이 좌석 행이 아니라 **머신 하나가 감당할 수 있는 인서터 총 개수**라는 것.

**규칙 (2026-07-17 사장님 지정):**

1. **순서** — 자식·부모 둘 다 **위에서 아래로**(배치 순서). 벨트는 물건이라 순서가 어긋나면 서로 교차한다.
2. **단위** — 인서터 하나. 그 아래로 못 쪼갠다.
3. **그릇** — 벨트 하나에 붙일 수 있는 인서터는 `floor(벨트 처리량 ÷ 인서터 처리량)` 개까지. (벨트 20 · 인서터 6 이면 **3개 = 18**. 남는 2는 벨트의 자투리.)
4. **모으기** — 그 인서터들의 출력은 **포트로 나가기 전에 이미 합류**해 있어야 한다(트렁크 벨트 또는 side-load 합류).
5. **채우기** — 부모는 필요량 **이상**으로 채운다. 딱 안 맞으면 인서터를 하나 더 붙여 **넉넉하게** 준다. ([[용어사전#determineBeltCount|determineBeltCount]] 의 "부모가 굶으면 절대 안 된다"와 같은 원칙.)
6. **한도** — 자식 머신에 붙는 인서터 총합 × 처리량이 **그 머신의 생산량을 넘으면 안 된다.** 넘으면 **없는 걸 나른다고 주장**하게 되고, 그 순간 "부모가 굶지 않는다"를 **국소적으로 증명할 수 없게 된다**(인서터들이 서로 경쟁하고 누가 얼마를 가져갈지는 우리가 못 정한다). 그래서 한도에 못 미치는 **자투리(인서터 한 개 몫 미만)는 버린다** — 그만큼 머신이 덜 돈다.
7. **포트** — 벨트 하나 = 포트 하나. **자식 포트 개수 ≠ 부모 포트 개수가 정상이다.** 자식의 벨트 6개가 부모 A에 4개, 부모 B에 2개로 **갈라져 나간다** — index 로 짝짓는 게 아니라 **흐름**이다.

**예시** (사장님 예시, 2026-07-17). 자식 생산 100 · 부모 필요 60.5 · 벨트 20 · 인서터 6:

```
벨트 하나에 인서터 3개까지 → 벨트 하나 = 18

자식 1 (생산 100)
  → 부모 1:  18, 18, 18  (인서터 9개 = 54)
             12          (인서터 2개 — 남은 6.5 를 넉넉하게)
             ────────────────────── 인서터 11개 = 66 ≥ 60.5 ✓   잔량 34
  → 부모 2:  18          (인서터 3개)                            잔량 16
             12          (인서터 2개 — 3개 붙이면 17×6=102 > 100 이라 못 붙인다)
             ──────────────────────
  자식 1 총 인서터 16개 × 6 = 96.   100 − 96 = 4 는 버린다 → 자식 1 은 96% 로 돈다.

자식 2 (생산 100, 부모 2 는 30.5 더 필요)
  → 부모 2:  18, 18      (인서터 6개 = 36)  부모 2 총계 66 ≥ 60.5 ✓
  → 부모 3:  18, 18, 18, 6 (인서터 10개 = 60 — 한도 16개에서 멈춘다)
  자식 2 총 인서터 16개 = 96
```

**두 손가락이 각자 자기 줄을 훑는 물 붓기다** — 자식이 인서터 한도를 다 쓰면 다음 자식으로, 부모가 다 차면 다음 부모로.

> **순환은 안 생긴다.** 물 붓기가 자식 머신을 **인서터 한도까지 다 쓰고** 다음으로 넘어가므로, **모든 자식 머신이 `floor(생산량 ÷ 인서터 처리량)` 에서 똑같이 멈춘다**(꼬리 머신 하나만 예외). 그래서 실효 산출은 **머신 수와 무관**하고, `①팔 → ②실효 산출 → ③머신 수` 가 한 방향으로 흐르는 성질이 유지된다. → [[용어사전#requiredInserterCount|requiredInserterCount]]

> **입력과 출력은 반올림 방향이 반대다.** 입력은 `ceil`(모자라면 부모가 굶는다 → 넉넉히), 출력은 `floor`(넘치면 없는 걸 나른다고 주장한다 → 모자라게). 지금 `requiredInserterCount` 는 **둘 다 `ceil`** 이라 출력 쪽이 과다 주장한다. 현재 데이터에선 벨트 하나에 인서터가 넉넉히 들어가(fast 30 ÷ long-handed 1.2 = 25개) 벨트가 안 쪼개지므로 드러나지 않지만, **벨트가 빠듯해지면 터진다.**

## E. 배치 전략 레이어

### 배치 전략 레이어
컨테이너 모델·정합성 조건은 불변으로 두고, **머신 좌표를 어떻게 정하고 무엇을 반환하는지**만 교체 가능한 전략으로 분리한 설계. → [[auto-layout-wizard.placement-search#55-배치-전략-레이어-pluggable]]

### S-LAYER
현재 유일하게 구현된 전략. 레시피 트리를 [[용어사전#레이어 (layer)|레이어]](열)로 깔고 레이어 사이에 [[용어사전#채널 (channel)|채널]]을 예약해, **백트래킹 없이 결정적으로 후보 1개**를 만든다. 계층화 DAG 레이아웃 + 채널 라우팅([[용어사전#Sugiyama 프레임워크|Sugiyama]]). → [[auto-layout-wizard.placement-search#7-알고리즘-흐름--현재-전략-s-layer]]

### S-EXH
(폐기·롤백) 하향식 완전탐색 전략. 형제 순서 `n!` × 방향 2 를 완전 열거하고 [[용어사전#FailureLeaf|FailureLeaf]] 백트래킹했다. 코드에 없음. → [[auto-layout-wizard.placement-search#55-배치-전략-레이어-pluggable]]

### S-DP
(미구현 설계 후보) 상향식 모듈 합성 전략. 부분트리를 불투명 [[용어사전#모듈 (S-DP)|모듈]]로 동결하고 post-order 로 [[용어사전#shape curve|shape curve]]를 합성해 Pareto-최적 소수 후보를 낸다. → [[auto-layout-wizard.placement-search#7b-미구현-설계-후보-s-dp--상향식-모듈-합성]]

### S-MEMO
(미구현 설계 후보) S-EXH + 부분트리 메모이제이션. 완전성은 유지하되 재계산만 줄인 변형. → [[auto-layout-wizard.placement-search#55-배치-전략-레이어-pluggable]]

### 모듈 (S-DP)
S-DP 에서 부분트리(레시피 노드 + 자손)를 불투명하게 동결한 배치 단위. 단일 배치가 아니라 [[용어사전#shape curve|shape curve]]를 들고 다닌다. (게임 모듈/beacon 과 무관) → [[auto-layout-wizard.placement-search#7b-미구현-설계-후보-s-dp--상향식-모듈-합성]]

### shape curve
S-DP 모듈이 갖는 비지배 형상 집합 `{(W, H, attachFace, connectorPort)}`. 목적함수 `|W−H|` 가 분리 불가능하므로 부모가 자기에 맞는 형상을 고를 수 있게 한다. → [[auto-layout-wizard.placement-search#7b-미구현-설계-후보-s-dp--상향식-모듈-합성]]

### 백트래킹
막힌 배치에서 이전 선택으로 되돌아가 다른 조합을 시도하는 것. S-EXH 의 핵심 비용. S-LAYER 는 채널 예약으로 이를 제거한다. → [[auto-layout-wizard.s-layer-channel-reservation#3-채널이-푸는-문제-현재-설계와의-대비]]

### FailureLeaf
S-EXH 에서 배치·라우팅 실패를 표시하던 후보 트리 노드. 현재는 머신 매칭 실패 전용으로만 남음. → [[auto-layout-wizard.s-layer-channel-reservation#10-현재-코드-매핑]]

### CandidateLeaf / CandidateTree
후보를 담는 자료구조. S-LAYER 는 성공 후보 1개를 `CandidateLeaf` 로 래핑해 `CandidateTree` 에 담는다(S-EXH UI 와 호환). 라우팅 실패가 있으면 leaf 라벨에 `⚠` 표기. → [[auto-layout-wizard.placement-search#75-종결]]

## F. 채널 라우팅 (Sugiyama / VLSI)

### 레이어 (layer)
루트(최종 제품)로부터 같은 거리에 있는 머신들의 묶음. 한 열(column)에 세로로 쌓인다. → [[auto-layout-wizard.s-layer-channel-reservation#1-용어-정의]]

### 채널 (channel)
인접한 두 레이어 **사이**의, 머신이 없는 예약된 빈 세로 띠(gutter). 레이어 경계를 가로지르는 모든 연결은 이 안에서만 달린다 → 라우팅이 실패할 수 없다. **세로축으로 뻗으므로** 명확히 구분할 땐 "레이어 채널", 직교 짝은 [[용어사전#행 채널 (row channel)|행 채널]]. → [[auto-layout-wizard.s-layer-channel-reservation#0-한-줄-요약]]

### 행 채널 (row channel)
한 레이어(열) 안에서 **세로로 쌓인 두 모듈 사이**의 빈 **가로 띠**(gutter). [[용어사전#채널 (channel)|채널]]을 90° 돌린 직교 짝 — 채널이 세로축으로 뻗어 좌우 레이어를 가르면, 행 채널은 가로축으로 뻗어 상하 모듈 행을 가른다. 모듈 간 홉 벨트와 외부상자 exit 레인이 이 띠를 지난다(홉이 이 띠를 가로막으면 상자가 [[용어사전#perimeter ring|perimeter]]로 못 빠져나가는 skip 의 무대). [[용어사전#ROW_GAP|ROW_GAP]](기둥 **내** 머신 세로 간격)과는 다르다 — 행 채널은 모듈 **사이** 가로 간격. → (전용 문서 없음; 3.txt 예시의 corridor 경로가 이 띠)

### 트랙 (track)
채널 안에서 연결 1개가 세로로 달리는 1셀 폭의 세로선. 채널 = 트랙 여러 개의 묶음. 트랙 수 = 동시 연결 수. → [[auto-layout-wizard.s-layer-channel-reservation#1-용어-정의]]

### 크로싱 셀 (crossing cell)
연결이 레이어 경계를 가로질러 채널로 진입/진출하는 가로 구간. → [[auto-layout-wizard.s-layer-channel-reservation#1-용어-정의]]

### 납품 경로 (deliveryRoute)
자식 머신의 출력 상자에서 [[용어사전#채널 (channel)|채널]]을 건너 부모 머신의 입력 상자로 물건을 올려보내는 벨트 경로. 양끝 행은 포트가 고정하고 [[용어사전#트랙 (track)|트랙]] 하나만 자유 → 모양은 항상 계단꼴(staircase, 가로–세로–가로 직선 3개). 현 코드명 hop(`moduleHop.ts`), 개명 예정. → [[auto-layout-wizard.channel-geometry-reservation#2-용어--채널을-지나는-두-종류의-경로]]

### 반출 경로 (exportRoute)
배치 안쪽에 갇힌 외부 상자를 채널을 따라 열린 변(N/S)으로 빼내 [[용어사전#perimeter ring|perimeter ring]]에 앉히는 벨트 경로. 벽의 한 점 → 열린 변이므로 모양은 한꺾임꼴(elbow, 직선 2개). 현 코드명 lane(`perimeterLanePlanner.ts`), 개명 예정 — 벨트의 좌/우 [[용어사전#레인 (lane)|레인]]과 무관. → [[auto-layout-wizard.channel-geometry-reservation#2-용어--채널을-지나는-두-종류의-경로]]

### 절단선 (cut)
[[용어사전#반출 경로 (exportRoute)|반출 경로]]가 채널 위에 만드는 분리선. "벽의 한 점 → 열린 변" + "지상 벨트는 교차 불가" 가 합쳐져 채널을 안쪽/바깥쪽 두 구역으로 가른다. 그래프 이론의 절단(모든 경로가 반드시 건너야 하는 선)과 동형. → [[auto-layout-wizard.channel-geometry-reservation#4-같은-쪽-판정--반출-경로는-채널에-절단선을-긋는다]]

### 같은 쪽 판정 (sameSideOfCut)
[[용어사전#납품 경로 (deliveryRoute)|납품 경로]]의 두 끝이 [[용어사전#절단선 (cut)|절단선]]의 같은 쪽인지 비교하는 판정. 같은 쪽 → 지상 계단꼴 존재, 다른 쪽 → 지상 불가(해소 사다리: 반출 재배정 → 지하 횡단 → 폴백). 행·트랙 숫자 비교뿐이라 벨트를 깔기 전에 끝난다. → [[auto-layout-wizard.channel-geometry-reservation#42-판정]]

### 열 갈아타기 (columnSwitch)
세로 구간이 부분 겹침인 두 납품 경로의 모순("서로가 서로의 서쪽")을 풀기 위해, 한쪽이 상대 구간 밖의 행에서 한 번 꺾어 트랙을 바꾸는 것. 탐색이 아니라 좌표 배정. → [[auto-layout-wizard.channel-geometry-reservation#5-납품-경로끼리의-충돌--세-가지-경우와-열-갈아타기]]

### 지하 횡단 (undergroundCrossing)
같은 쪽 판정이 "다른 쪽"으로 나온 납품 경로가 절단선 밑을 [[용어사전#지하벨트 (underground-belt)|지하벨트]]로 통과하는 해소책. 역시 탐색 아닌 좌표 배정. → [[auto-layout-wizard.channel-geometry-reservation#44-case-b--다른-쪽-지상-불가-해소-사다리로]]

### 더미 노드 (dummy node)
두 레이어 이상을 건너뛰는 긴 간선이 중간 레이어를 통과할 때 차지하는 자리. 머신이 아니라 "지나가는 트랙". → [[auto-layout-wizard.s-layer-channel-reservation#6-긴-간선-더미-노드--채널을-통과하는-연결]]

### 채널 폭 (channel width)
`channelWidthFromTracks(trackCount, CHANNEL_MIN) = max(CHANNEL_MIN, trackCount + 2)`. 임의 상수가 아니라 경계를 가로지르는 동시 연결 수로 계산. → [[auto-layout-wizard.s-layer-channel-reservation#4-채널-폭w-계산--가장-중요한-디테일]]

### CHANNEL_MIN
채널 폭의 하한(=3). 아이템 체인 최소 가로 폭(투입기+벨트+투입기). → [[auto-layout-wizard.s-layer-channel-reservation#4-채널-폭w-계산--가장-중요한-디테일]]

### left-edge algorithm
구간(interval)을 시작점 순으로 정렬해 겹치지 않는 것끼리 같은 트랙에 모으는 그리디. 채널 폭을 최소화하는 VLSI channel routing 의 고전 기법. 코드에서는 `assignTracksLeftEdge`. → [[auto-layout-wizard.s-layer-channel-reservation#5-채널-안에서-트랙-배정-좌표-확정]]

### channel routing (VLSI)
VLSI 배선에서 두 소자 열 사이 빈 채널에만 배선을 몰아 라우팅 성공을 구조적으로 보장하는 기법. S-LAYER 채널 예약의 이론적 원형. → [[auto-layout-wizard.s-layer-channel-reservation#3-채널이-푸는-문제-현재-설계와의-대비]]

### Sugiyama 프레임워크
계층형 그래프 그리기의 표준 파이프라인(레이어 배정 → 레이어 내 정렬 → 좌표 확정 → 라우팅). S-LAYER 가 따르는 뼈대. → [[auto-layout-wizard.s-layer-channel-reservation]]

### tidy-tree
부모를 자식 중앙에 정렬하는 트리 레이아웃(Reingold–Tilford 풍). S-LAYER 4단계 `layout()` 이 세로 배치에 사용. → [[auto-layout-wizard.placement-search#7-알고리즘-흐름--현재-전략-s-layer]]

### Reingold–Tilford
겹침 없이 컴팩트하게 트리를 그리는 고전 알고리즘. tidy-tree 세로 배치의 원형. → [[auto-layout-wizard.placement-search#7-알고리즘-흐름--현재-전략-s-layer]]

### barycenter 정렬
레이어 내에서 이웃 레이어와의 무게중심에 맞춰 노드 세로 순서를 정해 교차를 줄이는 정렬. 트랙 배정과 맞물린다. → [[auto-layout-wizard.s-layer-channel-reservation#5-채널-안에서-트랙-배정-좌표-확정]]

### colWidth / colX
레이어(열)의 폭(깊이별 최대 머신 폭)과 그 x 시작 좌표. 레이어 폭 + 채널 폭을 왼쪽부터 누적해 확정. → [[auto-layout-wizard.s-layer-channel-reservation#9-의사코드]]

### ROW_GAP
기둥 내 머신 사이 세로 간격 상수(=3, 인서터+벨트+인서터 최악값). 포트와 무관하게 고정돼 면적 낭비를 만든다(개선 후보). → [[auto-layout-wizard.known-limits#2-클러스터-세로-간격-row_gap-이-포트와-무관하게-고정3]]

## G. 엔티티 4역할

### 엔티티 4역할
위저드가 다루는 엔티티를 작동 방식으로 나눈 4분류: [[용어사전#변환기|변환기]]·[[용어사전#핸드오프|핸드오프]]·[[용어사전#고체 운반|고체 운반]]·[[용어사전#액체 운반|액체 운반]]. 이 4가지에 없는 엔티티(heat-pipe·electric-pole·rail·beacon 등)는 자동완성 관심사 밖이다. → [[auto-layout-wizard.entity-roles]]

### 변환기
역할 A. 레시피를 처리하는 모든 머신(조립기·화로·채굴기·로켓사일로·연구실). 입력 재료를 받아 산출물을 만들지만 직접 운반 능력은 없다. → [[auto-layout-wizard.entity-roles#a-변환기-조립기계-그룹]]

### 핸드오프
역할 B. 머신과 운반체 사이를 잇는 다리(투입기/로더). `long-handed-inserter`·`fast-inserter`·`bulk-inserter`·`loader` 등. → [[auto-layout-wizard.entity-roles#b-핸드오프-투입기--로더]]

### 고체 운반
역할 C. item 을 흘려보내는 동맥(벨트·지하벨트·splitter). router 가 실제로 깔아내는 거의 유일한 운반체. → [[auto-layout-wizard.entity-roles#c-고체-운반-벨트]]

### 액체 운반
역할 D. fluid 를 나르는 파이프·지하파이프·pump. 현재 위저드는 fluid 를 **1:1 파이프**로만 라우팅한다(트렁크 병합 미지원). → [[auto-layout-wizard.entity-roles#d-액체-운반-파이프]]

### loader (로더)
머신/체스트 한 면에 붙으면 인서터 없이 자동 적재/배출하는 엔티티(인서터+짧은 벨트의 융합). 현재 자동완성 미사용. → [[auto-layout-wizard.entity-roles#b-핸드오프-투입기--로더]]

### splitter
두 입력 → 두 출력의 벨트 분배기(2×1). 분배/우선순위/필터 가능. 현재 자동 분기 미사용. → [[auto-layout-wizard.entity-roles#c-고체-운반-벨트]]

### 레인 (lane)
한 벨트가 가진 좌/우 두 줄. 게임상 한 벨트로 서로 다른 두 item 을 동시 운반 가능하지만, 현재 router 는 이를 활용하지 않는다(한 라우팅=한 belt 줄). 활용하는 형태의 이름이 [[용어사전#MixedItemBelt|MixedItemBelt]] 다(미구현).

**"레인"은 이 뜻뿐이다.** 머신 면 바깥 거리로 구분되는 **벨트 줄**은 [[용어사전#ClusterBelt / ClusterBelts|ClusterBelt]] 다 — 2026-07-14 이전 코드·문서가 그것도 "레인"이라 불러 뜻이 겹쳤다. → [[auto-layout-wizard.entity-roles#c-고체-운반-벨트]]

### pump (펌프)
유체 라인의 단방향 이송/차단 장치(1×2). 현재 자동 배치 미사용. → [[auto-layout-wizard.entity-roles#d-액체-운반-파이프]]

### EntityType
렌더용 엔티티 타입. 현재 모든 변환기는 `EntityType` 이 Assembler 로 단순 매핑된다(`machineEntityType`). → [[auto-layout-wizard.entity-roles#a-변환기-조립기계-그룹]]

## H. 위저드·수량 산정

### 위저드 (wizard)
사용자가 레시피와 사용할 엔티티 군을 단일 흐름으로 선택하면 머신 수를 산출하고 그리드에 배치하는 5단계 UI 복합 기능. → [[auto-layout-wizard]]

### 수량 모드 (countMode)
머신 수 산정 방식. `최소값`(기본) = 비-외부 노드마다 조립기 1대(처리량 균형 미보장), `사용자 지정`(perTarget) = 타깃 머신 수를 입력하고 하위는 비례 산정. → [[auto-layout-wizard#1단계--레시피--수량]]

### 레시피 트리 (recipe tree)
타깃 레시피 → 재료 → 그 재료의 첫 매칭 레시피 → … 를 BFS 로 펼친 트리. `expandRecipeTree` 가 만들며 품목을 중복 전개하는 **트리**(DAG 아님). → [[auto-layout-wizard#1단계--레시피--수량]]

### 외부 공급 (external ingredient)
레시피 트리에서 "이 라인에서 만들지 않음" 으로 토글한 노드. 그 노드와 후손은 라인 입력 벨트로만 수급된다. → [[auto-layout-wizard#1단계--레시피--수량]]

### 처리량 (throughput)
초당 처리량. 머신은 `crafting_speed × (1 / energy_required)`, 인서터는 `rotation_speed × stack_size`. → [[auto-layout-wizard.entity-roles#a-변환기-조립기계-그룹]]

### crafting_speed
머신의 제작 속도 계수. 처리량 산정의 핵심 입력. → [[auto-layout-wizard.known-limits#8-인서터-처리량모듈이-머신-수-산정에-미반영]]

### energy_required
레시피 1회 제작에 필요한 시간(초). `crafting_speed / energy_required` 가 머신별 수요를 결정. → [[auto-layout-wizard.placement-search#72-트렁크-벨트-n1-병합]]

### stack size
인서터가 한 번에 집는 최대 개수. stack size = 1 vs 12 는 처리량 12배 차이. `circuit_set_stack_size` 로 회로 제어. → [[auto-layout-wizard.control-behavior-scope#in-scope-]]

### inserter override
사용자가 인서터별 처리량/묶음 갯수를 직접 지정하는 것(`inserterOverrides`). 트렁크 용량 게이트에는 반영되지만 머신 수 산정에는 아직 미반영. → [[auto-layout-wizard.known-limits#8-인서터-처리량모듈이-머신-수-산정에-미반영]]

### 자동 체크 규칙 (tech group)
후반 투입기/벨트/지하파이프를 체크하면, 그것을 언록하는 기술의 [[용어사전#prerequisite 클로저|prerequisite closure]] 안에서 해금되는 하위 엔티티들도 함께 체크되는 규칙. → [[auto-layout-wizard#3단계--투입기-선택]]

### WizardInput
위저드의 입력 타입. targetRecipe·countMode·externalIngredients·selectedMachines·selectedInserters·selectedBelts·region 등. → [[auto-layout-wizard#입력--wizardinput]]

### BuildSpec
**우리에게 주어진 것 — "무엇으로 지을 수 있고, 그것이 얼마나 멀리·얼마나 빨리 할 수 있는가"**(2026-07-14, 사용자 명명).

두 출처가 합쳐진 한 덩어리다:
- 사용자가 위저드에서 **고른 엔티티들**의 이름 — 벨트·인서터·긴팔 인서터·파이프·지하벨트·지하파이프.
- 그 엔티티들의 **게임데이터 능력치** — 인서터의 [[용어사전#레인 (lane)|reach]](→ [[용어사전#ClusterBeltDepth|ClusterBeltDepth]] 를 유도한다), 인서터의 초당 [[용어사전#처리량 (throughput)|처리량]], 지하벨트·지하파이프의 최대 점프 거리.

성질 넷 — 이걸로 다른 것과 구분한다:
1. **주어진 것이지 우리가 돌리는 손잡이가 아니다.** 배치 중에 안 바뀐다(읽기 전용). ↔ `debugFlags`(우리가 켜고 끄는 토글) · OS 환경 변수(`process.env`) — 이름이 비슷해 보여도 전혀 다른 것이다.
2. **능력의 한계를 말한다.** 배치가 거절할 때 그 근거는 대개 여기서 나온다 — "지하 점프 거리가 0이다", "reach 1 인서터밖에 없다", "인서터 하나로 이 수요를 못 받는다".
3. **탐색과 무관하다.** 다익스트라든 예약(장부)이든 똑같이 이걸 본다.
4. **유일한 출처다.** 프로토타입 이름을 코드 곳곳에 하드코딩하지 않는다.

코드: 지금은 `routeFallback.ts` 의 `RouteOptions` / `buildRoutingOptions` 라는 **잘못된 이름**으로 그 파일에 얹혀 있다("라우팅 옵션"이 아니고, 그 파일의 나머지 절반은 폐기 대상 다익스트라 폴백이다). **별도 파일로 떼어내며 BuildSpec 으로 개명한다**(2026-07-14 결정).

## I. 정합성·우선순위·결정성

### 정합성 조건 (C1–C3)
어떤 배치 전략에서도 만족해야 하는 불변식. C1=충돌 없는 배치, C2=라우팅 가능, C3=액체 mixing 방지. → [[auto-layout-wizard.placement-search#6-조건-등록부]]

### C1
충돌 없는 배치. 모든 컨테이너 footprint·라우팅 점유 셀·인서터 셀이 한 셀도 겹치지 않는다. → [[auto-layout-wizard.placement-search#c1--충돌-없는-배치]]

### C2
라우팅 가능. 모든 (producer, consumer, content, kind) 페어에 라우팅이 존재. S-LAYER 는 채널 예약으로 구성에 의해 보장. → [[auto-layout-wizard.placement-search#c2--라우팅-가능]]

### C3
액체 mixing 방지. 한 fluid-route 셀은 단 하나의 fluid 만 운반. → [[auto-layout-wizard.placement-search#c3--액체-mixing-방지]]

### O1
정렬 기준. 내부 영역 bbox 가 정사각형에 가까울수록(`|W−H|` 작을수록) 우선. 현재 후보 1개라 선택엔 안 쓰이고 `squarenessPenalty` 로만 기록. → [[auto-layout-wizard.placement-search#o1--내부-영역-bbox-가-정사각형에-가까울수록-우선]]

### O2
정렬 기준. 지상 셀을 지하 변형으로 비울 수 있으면 우선. Dijkstra cost(지상 1 / 점프 2)가 자연히 구현. → [[auto-layout-wizard.placement-search#o2--지하-변형-우선]]

### squarenessPenalty
후보의 정사각형 이탈 정도(`|W−H|`) 메타데이터. 현재는 계산만 하고 후보 선택엔 미사용. → [[auto-layout-wizard.known-limits#9-후보-1개만-생성-탐색선택-없음]]

### fail-first
배치 우선순위 원리 — **제약 큰 연결을 먼저** 놓아 희소 자원을 선점시켜, 쉬운 연결이 어려운 연결을 굶기는 것을 막는다. CSP 의 [[용어사전#MRV|MRV]]·bin packing decreasing 계열. → [[auto-layout-wizard.priority-ordering#1-두-가지-지배-원리]]

### cost-first
라우팅 우선순위 원리 — 싼 경로 먼저(지상<지하, 가까운 포트<먼 포트, 곧은 spine<우회). → [[auto-layout-wizard.priority-ordering#1-두-가지-지배-원리]]

### MRV
Minimum Remaining Values. 남은 선택지(가용 셀)가 가장 적은 변수를 먼저 배정하는 CSP 휴리스틱. 배치 제약 측정의 진짜 척도지만 비싸서 정적 프록시로 근사. → [[auto-layout-wizard.priority-ordering#3-핵심-배치의-제약-측정-p1]]

### DSATUR
그래프 색칠에서 채도(포화도)가 높은 정점을 먼저 칠하는 휴리스틱. 동적 MRV 승급 시의 동형. → [[auto-layout-wizard.priority-ordering#3-핵심-배치의-제약-측정-p1]]

### tie-break
정렬에서 값이 같을 때의 결정적 순서 규칙(예: `machineId → chestId` 사전순). 결정성 보장에 필수. → [[auto-layout-wizard.priority-ordering#5-결정성-불변식]]

### 결정성 (determinism)
같은 입력에 항상 같은 결과. 난수 금지 + 안정 정렬 + 명시적 tie-break. 시각화 재생·회귀 테스트의 전제. → [[auto-layout-wizard.placement-search#8-결정성--종료--완전성]]

### 우선순위 등록부
배치·라우팅에 흩어진 순서 결정점(P1~P9)을 한곳에 모아 정합성 보장(C)인지 품질 최적화(Q)인지 분류한 표. → [[auto-layout-wizard.priority-ordering#2-우선순위-등록부-모든-결정점]]

## K. Factorio 데이터 시맨틱스

### FluidBox
머신의 유체 연결 프로토타입. `production_type`(게임플레이 층위)과 connection별 `flow_direction`(물리 층위) 두 방향 필드를 가진다. → [[fluid-box-semantics]]

### 머신 유체 상자 (machine fluid box)
머신이 유체를 **받거나 내보내는 입구**. 게임데이터의 [[용어사전#FluidBox|FluidBox]] 가 그 정의다. 아이템은 인서터가 팔을 뻗어 머신 둘레 **아무 칸**에서나 옮기지만, 유체는 팔이 없어서 **파이프가 이 상자에 직접 닿아야** 한다. 그래서 유체 줄이 **어느 면으로 들어가는지는 우리가 고르는 게 아니라 머신이 정한다** — 우리가 할 수 있는 건 머신을 돌리는 것뿐이다.

알아야 할 것 셋:

- **연결 칸** — 상자 하나가 파이프를 받는 칸은 머신 **바로 바깥 한 칸**이다. 그 한 칸이 아니면 파이프가 머신 벽을 스쳐도 아무 일도 안 일어난다. 그 칸이 **어느 면**에 있는지는 좌표로 못 뽑는다(상자가 **모서리 칸**이라 `|x| = |y|`) — `PipeConnection.direction` 이 답한다.
- **역할** — [[용어사전#production_type|production_type]] 이 입력 상자냐 출력 상자냐를 가른다. 남의 **출력** 상자에 파이프가 닿으면 그 머신의 생산물이 내 관망으로 **조용히 새어나간다**(→ [[용어사전#PipeFlow / collectPipeFlow|합류 가드]]의 hard 규칙).
- **받는 유체 이름은 집합이다** — 상자 하나가 유체 이름 하나에 대응하지 않는다. 레시피가 `fluidbox_index` 로 못박지 않으면 그 유체는 **그 역할의 상자 전부**에 들어갈 수 있다(화학 공장이 입력 상자 2개 중 아무 데나 받는 이유).

→ [[fluid-box-semantics]] · [[pipe-semantics]]

### production_type
FluidBox 가 **레시피에서** 갖는 용도: input/output/input-output/none. `input-output` 은 본래 보일러 가열 모드 전용. → [[fluid-box-semantics]]

### flow_direction
연결점에서 파이프로 **실제 유체가 흐를 수 있는 방향**: input/output/input-output. 앱은 이걸 우선 사용(`flow_direction ?? production_type`). → [[fluid-box-semantics]]

### MapPosition
Factorio 좌표 타입. **keyed(`{x,y}`)** 또는 **positional(`{[1],[2]}`)** 두 형태로 오며, JSON 왕복 중 `{}` 로 깨질 수 있어 3중 방어로 정규화한다. → [[map-position-parsing]]

### 3중 방어 (triple defense)
MapPosition 파싱을 Lua 정규화(`vec2`) → 파서 정규화(`normalizeVec2`) → 렌더링 가드(`isValidVec`) 세 경계에서 각각 재검증하는 전략. → [[map-position-parsing#3지점-방어-전략]]

### trust boundary
데이터가 신뢰 경계를 넘는 지점(Lua→JSON, JSON→메모리, 메모리→렌더링). 각 경계에서 재검증하는 게 3중 방어의 원칙. → [[map-position-parsing#설계-원칙]]

### Direction (내부)
앱 내부 방향 타입 `Direction = 0 | 4 | 8 | 12`(cardinal N/E/S/W). Factorio 2.0 `defines.direction` 인코딩과 의미 통일됨. → [[direction-encoding]]

### defines.direction
Factorio 2.0 의 16방향 인코딩(0..15, 22.5° 단위). 짝수 4·8·12 = cardinal, 2/6/10/14 = diagonal, 홀수 = sub-cardinal(곡선 레일용). → [[direction-encoding#2-우리-앱의-내부-모델]]

### cardinal
정방위 4방향(N/E/S/W = 0/4/8/12). 일반 엔티티는 이것만 쓴다. → [[direction-encoding]]

### sub-cardinal
22.5° 단위 세분 방향(1/3/5/7/9/11/13/15). 곡선 레일·half-diagonal-rail 표현용. 현재 앱은 미지원, import 시 가장 가까운 cardinal 로 round. → [[direction-encoding]]

### normalizeDir
import 시 방향을 정규화하는 함수. 1.x 블루프린트는 ×2 업그레이드 후 cardinal 로 round. → [[direction-encoding#3-boundary-변환-importexport]]

### 1.x → 2.0 ×2 매핑
Factorio 1.x 의 8방향(0..7)을 2.0 의 짝수 위치로 옮기는 단순 ×2 변환. 정보 손실 없음. → [[direction-encoding#1-factorio-의-direction-인코딩-변천]]

### surface_conditions
vanilla 가 우주/지상 표면 제약을 표현하는 필드. SE 모드는 대신 collision_mask 로 표현해 메커니즘이 모드마다 다르다 → 앱은 표면 자동 판단을 포기. → [[surface-restriction-limits]]

### collision_mask
엔티티가 충돌하는 타일 layer 집합. SE 는 `space_tile`/`ground_tile` layer 부정 매칭으로 표면 제약을 표현한다. → [[surface-restriction-limits]]

### crafting_categories
머신이 처리할 수 있는 레시피 카테고리 집합. 위저드 2단계 후보 산정(`getMachinesForCategory` 합집합)의 기준. → [[surface-restriction-limits]]

## N. 알고리즘·CS 일반

### Dijkstra
라우팅 경로 탐색 알고리즘. 지상 인접 edge(cost 1) + 지하 점프 페어 edge(cost 2). 상태 `(x, y, arr)` 가 지하 출구/입구 직진 제약을 강제(`dijkstraWithJumps`). → [[auto-layout-wizard.placement-search#41-지하-변형-underground-belt--pipe-to-ground]]

### BFS
너비 우선 탐색. 레시피 트리 펼침·prerequisite 클로저·(구) 라우팅 경로 발견에 사용. → [[tech-tree-resolution#prerequisite-클로저]]

### DAG
방향 비순환 그래프. 공유 자식(한 product 를 여러 부모가 요청)을 합류시키려면 트리 대신 DAG 가 필요하다(현재는 트리라 품목 중복 전개). → [[auto-layout-wizard.known-limits#10-다중-부모-공유-자식-미처리]]

### CSP
제약 충족 문제(Constraint Satisfaction Problem). 배치 우선순위(fail-first)가 CSP 의 MRV 휴리스틱과 대응. → [[auto-layout-wizard.priority-ordering#1-두-가지-지배-원리]]

### Pareto
여러 목적에서 어느 하나도 손해 없이 개선 불가한 비지배 해 집합. S-DP 가 shape curve 를 Pareto 필터로 추린다. → [[auto-layout-wizard.placement-search#7b-미구현-설계-후보-s-dp--상향식-모듈-합성]]

### 프록시 (proxy)
비싼 정확값(동적 MRV) 대신 좌표·종류 검사만으로 제약 크기를 어림잡는 싼 정적 근사. → [[auto-layout-wizard.priority-ordering#3-핵심-배치의-제약-측정-p1]]

### fuzz 테스트
무작위·대량 입력으로 불변식(결정성 등)을 흔들어 회귀를 잡는 테스트. 현재 부재(P3 백로그). → [[auto-layout-wizard.known-limits#11-결정성-fuzz-테스트-부재]]

### 파이프라인 계측기 (pipeline metrics)
같은 레시피 트리를 파이프라인에 통과시켜 **면적·[[용어사전#채널 폭 (channel width)|채널 폭]]·벨트 수·포트 수·실패 수**를 재는 도구(`pipelineMetrics.ts`). **판단하지 않고 재기만 한다** — 비용 숫자에 `expect` 를 걸지 않는다(트렁크가 바꾸라고 만드는 값이라 못 박으면 개선이 곧 실패가 된다). 못 박는 건 [[용어사전#결정성 (determinism)|결정성]]뿐. 공급 방식([[용어사전#탭 인서팅 (Tap Inserting)|탭]] ↔ [[용어사전#다이렉트 인서팅 (Direct Inserting)|다이렉트]])을 갈아타기 전에 **숫자로 이기는 걸 먼저 보려고** 만들었다(2026-07-10 대규모 리팩터가 근거 부재로 전량 롤백된 전례). → [[auto-layout-wizard.pipeline-metrics]]

### 기준선 (baseline)
갈아타기 전 현행 구현의 계측값을 박제해 둔 것. 새 구현은 **같은 트리·같은 자**로 재서 이 숫자를 이겨야 채택된다. 판정 기준은 면적이 아니라 **실패 0 + 채널 폭이 머신 수에 안 따라 커지는가**. → [[auto-layout-wizard.pipeline-metrics#4-함정--면적으로-판단하지-마라]]

렌더링 라이브러리. React 와 분리되어 그리드/와이어 layer 를 그린다. → [[blueprint-metadata-coverage#5-작업-원칙]]

### zustand
프론트엔드 상태 저장소. 게임 데이터·레이아웃을 store 로 관리하고 persist `migrate` 로 마이그레이션. → [[direction-encoding#4-localstorage-마이그레이션]]

### parametrized blueprint
Factorio 2.0 의 매개변수화 청사진. `parameter-0~9` placeholder 레시피/아이템으로 "어떤 아이템이 들어와도 동작" 하는 추상 템플릿. 현재 처리 보류. → [[parametrized-blueprints-deferred]]

### is_parameter
`LuaRecipePrototype.is_parameter` — parameter placeholder 를 식별하는 플래그. → [[parametrized-blueprints-deferred#정체]]

### icon mapping (보류)
엔티티 아이콘을 게임에서 추출하려던 시도. Factorio 런타임 API 가 아이콘 경로를 의도적으로 숨겨(저작권 보호) 두 접근 모두 폐기. 현재는 단색 사각형만. → [[icon-mapping]]

### ModData 브리지
아이콘 추출 2차 시도. 별도 mod 의 `mod-data` prototype 으로 data-단계→런타임 브리지를 만들려 했으나 **보안 정책 우회**로 롤백. → [[icon-mapping#시도-2-file-system-access-api--moddata-브리지-2026-04-26-롤백]]
