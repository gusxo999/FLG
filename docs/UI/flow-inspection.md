# 흐름 검사 화면 — 100% 가 아닌 머신은 빨간 테두리, 포트가 막힌 머신은 빗금

> **이 문서를 읽어야 하는 때**
> - `src/UI/components/flow/**` · `pixi/pixi-draw-flow.ts` · `store/flowStore.ts` 를 수정할 때
> - 벨트나 머신을 눌렀는데 흐름이 안 나온다고 느낄 때 → **§2.3**
> - 빗금 친 머신 · ✗ 표시된 상자가 무엇인지 → **§2.1**(까닭은 [[flow-model]] §2.6)
> - 흐름·가동률 표시를 다른 자리에 하나 더 만들자는 생각이 들 때 → **§1 을 먼저**

## 0. 한 줄 요약

그리드를 정상상태로 푼 결과([[flow-model]]) **하나**를 캔버스 테두리 · 캔버스 칩 · 정보 모달 · 연결선 모달 ·
모듈 패널 · 콘솔이 **같이** 읽는다. 흐름을 보여 주는 UI 는 전부 `components/flow/` 에 있다.

## 1. 한 범주로 모은 이유

흐름에 관한 표시가 세 군데에 흩어져 있었다 — 벨트 흐름 섹션(정보 모달 안), 레시피 섹션의 **초당 정격**,
그리고 계산 없이 그 둘을 떠받치던 옛 `analysis/beltFlow`(누를 때마다 그 칸의 상류만 따로 더했다).
정격과 실제가 다른 섹션에 있으면 *"이 머신은 정격대로 도나"* 를 사용자가 두 곳을 보고 맞춰야 한다.
지금은 **흐름 섹션이 정격 → 실제를 나란히** 보여 주고, 레시피 섹션은 레시피 사실만 남는다.

**입력을 모으는 곳도 하나다** — `flowStore.currentFlow()`. 그리드 · 게임데이터 · 인서터 보정(위저드 3단계)을
따로 모으는 자리가 여럿이면 한 곳이 보정을 빠뜨리는 순간 같은 그리드에 두 답이 나온다.

**그리드 정적 분석이다**(옛 문서의 결정 1 을 잇는다) — 자동 배치 결과만이 아니라 손으로 놓거나 고친
그리드도 푼다. 라우팅 세션에 기대는 안은 수동 배치를 못 덮어 기각됐었다.

## 2. 어디에 무엇이 나오나

### 2.1 캔버스

| 표시 | 뜻 |
|---|---|
| **빗금** 채움 + 더 굵은 테두리 + `⚠` | **포트 실패** — 밖과 못 잇는 상자에 매달렸다. 가동률이 100% 여도 실패다([[flow-model]] §2.6) |
| 그 상자에 흰 **✗** 상자 표시 | 그 머신을 실패로 만든 **갇힌 상자** — 어디를 고쳐야 하는지가 같은 화면에 있어야 한다 |
| 빨간 굵은 테두리 + 옅은 채움 + `73%` | **미달** — 100% 로 못 돈다. 숫자는 반올림해도 99 를 못 넘는다(99.6% 를 "100%" 빨간 테두리로 보이면 거짓이다) |
| 주황 **점선** 테두리 + `?` | **판정 불가** — 까닭은 모달에 |
| 없음 | 100% |

색만으로 가르지 않는다(모듈 테두리와 같은 까닭 — 색각 이상). 모듈 테두리는 앰버라 판정 불가는 **주황 점선**이고,
이것은 머신 footprint **안쪽**을 감싸 모듈 bbox 와 크기로도 갈린다. 모듈 테두리 **위에** 그린다 — 모듈 안의
어느 머신이 노는지가 이 그림의 물음이다. 게임데이터가 없으면 전부 판정 불가라 **안 그린다**.

**포트 실패는 미달과 같은 무게로, 그러나 갈라 보인다.** 둘 다 빨강 계열이라 멀리서 보면 똑같이 시끄럽지만
(사용자 요구 2026-09-28 — *"머신이 100% 가 안 도는 것과 비슷한 수준의 시인성"*), 가까이서는 **빗금과 ⚠** 로
갈린다 — 고칠 곳이 다르기 때문이다. 미달은 줄·팔의 저울 문제이고, 포트 실패는 **상자가 밖으로 못 나간 것**이다.
그래서 두 표시가 겹칠 일도 없다: 포트가 실패한 머신은 가동률 숫자 대신 `⚠` 를 단다(그 숫자가 갇힌 상자가
만들어 준 값이라 거짓이다).

**좌상단 칩** — *가동률 · N대 · ⚠ 포트 실패 · ✗ 미달 · ? 판정 불가* 와 **테두리 표시/숨김**
토글(`flowStore.showMachines`, persist · 기본 켜짐). 그리드에 머신이 없으면 칩도 없다.

### 2.2 정보 모달의 흐름 섹션 — [FlowSection](../../src/UI/components/flow/FlowSection.tsx)

- **머신** — 배지(포트 실패 / 100% / 미달 N% / 판정 불가) · 모자란 한 줄(*"ore — 벨트가 덜 준다"*) · 재료별
  **받을 수 있음 / 필요** · 산출별 **내보낼 수 있음 / 정격** · 정격 제작 수. 까닭은 넷이다 — 넣는/꺼내는 **팔** ·
  **벨트**(덜 준다 / 안 받아 간다 = 정체) · **관**(유체).
- **포트 실패**면 그 위에 빨간 판이 하나 더 붙는다 — 반출/공급 중 무엇이 막혔나 · **갇힌 상자의 좌표와 품목** ·
  *"가동률은 그 상자를 무한 공급/회수로 보고 낸 값"* 이라는 단서. 좌표를 적는 이유는 §2.1 의 ✗ 와 같다.
- **벨트** — 레인별 흐름/용량 · 포화 · 이 칸의 팔(넣는 레인 · **정체로 거절한 양**) · 한 레인 두 품목 경고.

### 2.3 누르는 길 — 연결선이 벨트 클릭을 가로챈다

캔버스 클릭 분기(`pixi-manager.handlePointerDown`)는 **연결선을 벨트 칸보다 먼저** 본다 — 실패 진단 선이 빈
그리드 위에 떠 있어 그 분기가 유일한 입구라서다. 그런데 성공 배치의 연결선은 **벨트 칸 위에** 그려진다(히트
반경 10px). 그래서 자동 배치의 벨트를 누르면 **언제나 연결선 모달**이 뜨고, 옛 흐름 모달은 거기서 한 번도
안 떴다(2026-09-22 발견).

순서를 뒤집으면 이번엔 연결선 모달이 거의 안 열린다. 그래서 **둘 다 살렸다** — 연결선을 누른 칸을 함께
넘기고(`layoutStore.selectedRoutingAt`), 연결선 모달이 그 칸의 흐름을 **같은 컴포넌트**(`BeltFlowAt`)로
보인다. 흐름 표시를 만드는 컴포넌트는 여전히 하나다.

| 무엇을 누르나 | 무엇이 뜨나 |
|---|---|
| 머신(빈손) | 정보 모달 — 흐름 섹션이 **인스턴스 id 로** origin 을 찾는다(빈손 단일 클릭은 칸 좌표를 안 싣는다) |
| 자동 배치 벨트(빈손) | 연결선 모달 + 그 칸의 흐름 |
| 연결선 없는 벨트(빈손 · 배치 모드) | 정보 모달 — 흐름 섹션이 누른 칸을 본다 |
| 모듈 이름표 | 모듈 패널 — *"가동률 4대 중 미달 2"* 한 줄 |

## 3. 함정

- **벨트 칸 클릭 = 셀 드래그 선택 시작 불가.** 빈손 모드에서 벨트류 칸을 누르면 흐름이 떠서, 벨트 칸에서
  **시작하는** 사각 선택은 막힌다(빈 칸에서 시작하면 벨트 위를 지나는 선택은 된다). 클릭 = 정보 요구가 우선이다.
- **팬·줌에 다시 풀지 않는다.** `renderGrid` 는 뷰포트가 바뀔 때마다 불리므로 결과는 그리드 참조로 메모한다
  (`currentFlow`). 그리드가 **바뀔 때마다 새 객체**라는 성질에 기댄다 — 되돌리기 이력도 같은 성질에 선다.
  그 이유를 적은 문장은 저장소에 없다.
- **콘솔의 `await import('/src/…')` 로 스토어를 읽지 않는다** — 다른 인스턴스가 올 수 있다([[ai-console]] §4).
  흐름은 `flg.flow` 로 읽는다.
